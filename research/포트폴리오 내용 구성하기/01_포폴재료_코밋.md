## 1. 재료 목록

### 1.1 컴포즈로 감당되지 않는 지점을 확인하고 배포 기반을 바꾸기

**상황**
여러 서버를 직접 운영해 오면서 Docker Compose의 한계가 쌓였다. TeenyFinny에서 Grafana·Loki·Prometheus로 여러 서버를 관측하고 Jenkins·SonarQube로 개발 흐름을 자동화한 경험, 개인 서버와 DailyBand 운영이 모두 여기 깔려 있다. 컨테이너가 떠 있는지는 볼 수 있지만 **비정상 동작에 대한 자동 재시작과 health check 기반 상태 확인이 어려웠고**, 블루-그린·카나리 같은 배포 전략과 무중단 배포를 적용하기 어려웠다. 컨테이너 단위로 자원을 세부 제한하는 것도, 설정이 늘어나면서 복잡해진 구성을 유지보수하는 것도 비효율적이었다. `[답변]`

**구현**
K3s 단일 노드 클러스터를 구성하고 애플리케이션·DB·캐시를 그 위로 옮겼다. `service`·`escrow`·`fe`를 각각 2 Pod로 띄우고, DB는 CloudNativePG 오퍼레이터로 `service-db`·`escrow-db` 클러스터를 각각 Primary 1 + Standby 2로, 캐시는 redis-operator로 Primary 1 + Replica 2 + Sentinel 3으로 구성했다. 오퍼레이터 → DB·Redis → 애플리케이션 순으로 적용 단계를 나눴다. CRD가 설치된 뒤에만 Cluster 리소스를 만들 수 있기 때문이다. `[실물]` `bd7bef5 feat: K3s 설정 추가`, `deploy/k3s/README.md`

**판단**
"쿠버네티스를 써보고 싶었다"가 아니라 **컴포즈에서 막힌 항목을 먼저 적고 그것들이 해결되는지로 판단했다.** `[답변]` 쓰임새에 따라 가용성 장치를 다르게 적용하기도 했다 — 검증용 프론트엔드에는 HPA·PDB를 두지 않았다. `[실물]` `deploy/k3s/README.md`

**검증**
다중 인스턴스 rolling update로 배포했다. `[답변]`

`[미확인]` 자동 재시작·health check가 장애 상황에서 어떻게 동작했는지 관측 기록은 따로 남기지 않았다. **다만 "확인하지 못했다"는 본인이 한 말이 아니므로 포트폴리오 본문에 쓰지 않는다.**

**한계**
- **단일 노드다.** 노드가 하나뿐이므로 노드 장애 대응은 구성하지 않았고 검증할 수도 없었다
- 컴포즈의 한계는 본인 체감이며 측정값이 아니다. **`배포 시간을 N% 줄였다` 같은 수치를 만들지 않는다**
- **`무중단 배포를 검증했다`고 쓰지 않는다.** rolling update를 썼다는 것까지만 사실이다. 반대로 **`확인하지 못했다`고 대신 적지도 않는다** — 본인이 하지 않았다고 말한 적 없는 일이다

**활용**
앞 프로젝트와 이 프로젝트를 잇는 `bridgeNote`의 근거. **도구를 바꾼 이유를 기능 목록이 아니라 막혔던 항목으로 말할 수 있다는 점**이 핵심이다.

### 1.2 다중화가 처리량을 높이는지 측정해 내 가설을 폐기하기

**상황**
같은 서버 안에서 애플리케이션을 여러 인스턴스로 나누면 처리량이 올라갈 것이라고 보았다. **초기 가설은 `K3s 2 Pod`가 `Docker 단일`보다 높은 처리량을 낸다는 것이었다.** `[실물]` 보고서 2장

**구현**
총 애플리케이션 자원을 `2 CPU / 3 GiB`로 고정하고 네 환경을 비교했다 — A(Docker 단일) · B(K3s 1 Pod) · C(K3s 2 Pod, 각 1 CPU/1536 MiB) · D(Docker 2개). 대상은 DB 조회 비중이 높은 API 3종(개발자 목록·상세·리뷰)이고 요청 비율은 50/30/20, 부하는 k6 `constant-arrival-rate`로 환경별 60초씩 넣었다. 통과 기준은 p95 500 ms · p99 1,000 ms · 무효 요청 1% 미만 · 목표 요청 시작률 99% 이상으로 **제품 SLO가 아니라 환경 비교용 기준**임을 보고서에 명시했다. `[실물]` `부하테스트쓰.md`

**판단**
**"어느 구성이 더 좋은가"가 아니라 "같은 총 자원에서 나누는 것이 이득인가"로 질문을 좁혔다.** B와 D를 함께 측정한 것도 차이가 K3s에서 오는지 인스턴스를 나눈 데서 오는지 구분하기 위해서였다. `[실물]` 보고서 2장

**검증**
**가설은 틀렸다.** `[실물]`

| 확인 항목 | 결과 |
| --- | --- |
| 119 RPS | 네 환경 모두 100% 처리. 처리량 차이 없음 |
| 119 RPS 자원 | 이중 구성이 앱 CPU를 20~30% 더 사용 (A 0.61 → C 0.80 core) |
| 179 RPS | C 실패 — R1 p95 1,161 ms, 두 Pod가 60초 중 약 24초 CPU throttling |
| 214 RPS | A 통과. A의 한계는 찾지 못함 |
| K3s 자체 | A와 B가 거의 동일 → **K3s가 느린 것이 아니었다** |
| 병목 | DB(4 CPU 중 1.9)와 부하 발생기(0.18 core) 모두 병목 아님 |

원인은 Pod별 1 CPU quota와 JVM을 두 개 띄우는 중복 비용(JIT·GC·내부 스레드·Spring 런타임·커넥션 풀·힙)이었다. 요청당 CPU가 A 0.0049~0.0054 s/req, C 0.0063~0.0068 s/req로 **C가 요청 하나에 25~35% 더 썼다.** `[실물]`

콜드 스타트도 함께 관측했다. 새로 띄우고 바로 부하를 넣으면 네 환경 모두 첫 30초에 timeout과 drop이 몰렸고, 120초 워밍업 뒤에도 CPU가 계속 떨어지고 있어 완전히 안정된 상태로 보기 어려웠다. `[실물]`

**한계**
보고서가 자기 한계를 직접 적고 있다. 이 문장들을 포트폴리오에서도 유지한다. `[실물]`

- **단일 VM·단일 노드다.** 여러 물리 서버에 Pod를 분산했을 때의 확장성과 장애 대응은 확인하지 못했다
- C의 179 RPS 실패는 **예비 단계에서 1회 측정**이고 JVM이 완전히 warm된 상태가 아니었다. CPU throttling 자체는 측정됐지만 "정확히 179 RPS에서 실패한다"고 단정할 수 없다
- 반복이 부족하다. 119 RPS에서 A 2회·B 2회·C 3회·D 2회로 **수 ms 수준의 지연 차이를 통계적으로 확정할 수 없다**
- 읽기 전용 warm-cache 워크로드다. 쓰기 부하·대용량 I/O·네트워크 지연은 포함하지 않았다

**활용**
**이 프로젝트에서 가장 강한 재료다.** 측정했다는 사실보다 **자기 가설이 틀린 것을 그대로 싣고 한계까지 적었다는 점**이 값이다. TeenyFinny의 "Active DB를 직접 끊어보고 확인했다"와 같은 결이되, 그때는 구성이 도는지를 본 것이고 이번에는 **가설을 세워 반증했다**는 점에서 한 단계 위다.

면접 반문 `그럼 단일 인스턴스를 썼어야 하는 것 아닌가요?` → 처리량만 보면 그렇지만 비용 제약으로 서버가 한 대뿐이라 **이 실험 자체가 수평 확장을 검증한 것이 아니다**라고 보고서에 적어둔 대로 답한다.

### 1.3 도구가 못 하는 일을 확인하고 라우팅 책임을 옮기기

**상황**
DB를 Primary–Standby로 이중화하면서 읽기를 Standby로 보내려 했다. 앞단에 Pgpool을 두는 구성을 먼저 그렸다. `[실물]` `코밋 인프라 구조도(설계).png`에 `코밋 DB Proxy -1/-2`와 `에스크로 DB Proxy -1/-2`가 그려져 있다

**구현**
조사 과정에서 **Pgpool에는 트랜잭션 성격별로 라우팅을 다르게 하는 기능이 없다**는 것을 알게 되어 Pgpool을 구성에서 빼고, Spring이 `readOnly` 트랜잭션을 Standby로 직접 보내도록 바꿨다. `[답변]` `[실물]` `b988cc0 feat: Pgpool을 제거하고 스프링에서 직접 읽기 작업 시 standby에 요청하도록 수정`

현재 구성은 애플리케이션이 CloudNativePG가 제공하는 `-rw`·`-ro` 서비스로 나눠 접속하고, 쓰기는 Primary로 `readOnly` 조회는 Standby로 간다. `[실물]` `deploy/k3s/README.md`

**판단**
**프록시 계층을 한 겹 더 두는 것보다, 트랜잭션의 성격을 이미 알고 있는 쪽이 라우팅을 맡는 편이 맞다고 보았다.** 도구에 구성을 맞추지 않고 도구를 뺐다. `[답변]`

**검증**
바꾼 뒤 **로그로 읽기가 실제 Standby로 가는지 확인했다.** `[답변]`

**한계**
- **로그 확인까지가 전부다.** 부하 상황에서 분배 비율이 어떻게 되는지, 복제 지연 중 읽기가 무엇을 보는지는 확인하지 않았다 `[미확인]`
- **복제 지연에 따른 읽기 정합성 문제를 다루지 않았다.** 쓰기 직후 조회를 Primary로 강제하는 처리가 있는지 확인 필요 `[미확인]`
- TeenyFinny의 ProxySQL·Orchestrator 구성과 **반대 방향의 선택**이다. 이전 선택이 틀렸다는 식으로 쓰지 않는다. 요구가 달랐다

**활용**
**설계 구조도와 최종 구조도 두 장이 before/after로 그대로 남아 있다.** 그림에서 DB Proxy가 사라진 것이 이 판단의 근거다. 포트폴리오에서 가장 보여주기 쉬운 재료.

면접 반문 `그럼 애플리케이션이 인프라 관심사를 떠안은 것 아닌가요?` → 트랜잭션 성격은 애플리케이션만 아는 정보라 그쪽이 판단하는 편이 자연스럽다고 답하되, **복제 지연 대응은 아직 다루지 않았음을 먼저 밝힌다.**

### 1.4 목서버를 명세의 결과가 아니라 원본으로 삼기

**상황**
프론트엔드와 백엔드가 병행 개발해야 했다. 보통은 API 명세를 먼저 쓰고 그 명세로 목서버를 만든다. `[답변]`

**구현**
**순서를 뒤집었다.** 목서버를 먼저 구현하고 거기서 나오는 OpenAPI와 docs를 API 명세로 썼다. 명세가 목서버의 산출물이 되므로 둘이 어긋날 자리가 없어진다. 그만큼 목서버를 디테일하게 만들어야 해서 **HTTP 상태 코드와 예외까지 목서버에 넣었다.** `[답변]` `[실물]` `a7b8570 feat: 목서버 프로젝트 생성, 뼈대 구축` → `feat: 목서버의 서비스/에스크로 영역을 분리` → `feat: 에스크로 목서버 디폴트 요청/응답/예외 작성` → `feat: 서비스 목서버 형식 추가`

**판단**
AI 에이전트를 쓰면 명세 작성과 목서버 구현을 한 번에 할 수 있겠다고 보고 순서를 바꿨다. `[답변]` 서비스 영역과 에스크로 영역을 처음부터 나눠 둔 것도 두 서버가 별개 계약을 갖기 때문이다. `[실물]`

**검증**
**나중에 실제 서버와 붙일 때 어긋난 곳이 없었다.** `[답변]`

**한계**
- **목서버의 뼈대와 규격은 본인이 잡았지만 개별 엔드포인트 구현은 팀이 함께했다.** 목서버 문서의 설명 문장(`default` 태그의 "규약의 기준 API", 카카오 로그인 계약의 예외 목록 등)은 깃상 **전지웅**이 `09-14 feat: 코밋 서비스 API 명세 작성 (영역 1~9)`에서 넣은 것이다 `[실물]`. **캡션이나 본문에서 그 문장을 본인이 썼다고 읽히게 쓰지 않는다.** `mock/` 커밋은 이해준 56 · 박연수 53 · 전지웅 32 · 본인 25다 `[실물]`. **"목서버를 만들었다"가 아니라 "목서버를 명세의 원본으로 삼는 구조를 잡았다"로 쓴다**
- `어긋난 곳이 없었다`는 본인 체감이며 통합 결함 수를 센 것이 아니다. **수치를 만들지 않는다**
- TeenyFinny의 Postman Mock Server와 같은 목적이지만 **방법이 다르다.** 그때는 명세 → 목, 이번은 목 → 명세다

**활용**
TeenyFinny 1.2 `계약을 먼저 정하고 구현하기`의 **후속편.** 같은 원칙을 한 번 더 적용하되 방법을 바꿨고 그 이유가 AI 도구의 변화라는 점이 서사가 된다.

### 1.5 AI가 만든 코드를 사람 눈보다 파이프라인이 먼저 보게 하기

**상황**
AI 에이전트로 코드를 생성하는 비중이 큰 팀이었다. **생성된 코드를 곧이곧대로 믿을 수 없다고 보았다.** `[답변]`

**구현**
GitLab CI에 `convention` 스테이지를 가장 앞에 두고 MR 파이프라인에서 브랜치 이름·병합 대상 브랜치·커밋 메시지를 정규식으로 검사하게 했다. 브랜치는 `S15P21A201-<이슈번호>/<파트>/<유형>/<설명>` 형식이고 파트는 `fe|be-api|be-escrow|ai|infra|common`, 유형은 `feature|fix|hotfix|docs`로 고정했다. 이후 스테이지는 build → test → sonar(정적 분석 + Quality Gate) → deploy 순이다. `[실물]` `46ebf94 feat(infra): 브랜치/커밋 컨벤션 확인 작업 추가`, `.gitlab-ci.yml` (본인 28/36 커밋)

**판단**
**사람이 리뷰에서 걸러야 할 것과 기계가 먼저 막아야 할 것을 나눴다.** 형식과 규칙 위반은 파이프라인이 막고, 사람은 그 뒤를 본다. `[답변]`

**검증**
정적 분석에서 **랜덤 함수 시드 문제를 찾아냈다. 다만 중요도가 작다고 판단해 고치지 않고 남겨뒀다.** `[답변]`

AI가 임의로 건드린 결과를 되돌린 흔적도 남아 있다 — `6fd2d87 fix: claude가 지멋대로 추가한 파이프라인 삭제--` `[실물]`

**한계**
- **어느 도구가 랜덤 시드 문제를 잡았는지 확인하지 못했다.** 연결된 SonarQube 인스턴스에는 `KomitSonarTest` 프로젝트 하나뿐이고 Security Hotspot이 0건이며, `09-22 fix: 테스트케이스가 확률적으로... 통과하던 문제 해결` 커밋은 `LoggingAspectTest`·`RealtimeIntegrationTest`의 타이밍 문제라 별개 건이다 `[미확인]`. **본문에서 도구 이름을 특정하지 않는다**
- **고치지 않은 것을 성과로 쓰지 않는다.** 찾았고 중요도를 판단해 남겼다까지가 사실이다
- 컨벤션 검사는 형식을 막을 뿐 **코드의 정확성을 검증하지 않는다.** `AI 코드를 검증했다`로 확대하지 않는다
- `docs/` 아래 컨벤션 문서 중 백엔드 컨벤션 본문은 팀원이 썼고 **본인은 전역 예외 처리 절을 추가했다** `[실물]`. 저장소 공통 에이전트 규칙 `AGENTS.md`는 팀원 작업이므로 본인 재료로 쓰지 않는다

**활용**
DailyBand의 `AI가 짠 코드도 검증했습니다`와 묶이는 축. 다만 **그때는 결과물을 검증했고 이번에는 검증 자체를 파이프라인에 올렸다**는 차이로 쓴다.

### 1.6 백엔드 준비 상태를 기준으로 기본 환경을 뒤집기

**상황**
개발 초기에는 **루트 주소의 화면이 목서버를 보고**, 실제 백엔드를 보는 화면이 확인용으로 따로 떠 있었다. 백엔드 기능이 붙으면서 이 기준이 더는 맞지 않았다. `[실물]` `deploy/k3s/README.md` 개편 전 서술

**구현**
루트가 실제 백엔드를 보고 목은 `/test`로 내려가도록 뒤집었다. 함께 한 일은 다음과 같다. `[실물]` `d4391838 fix: 배포 환경 대개편` → `35c515c9` → `3be04bbd fix: 배포 후 설정 안정화`

- API 주소와 카카오 Redirect URI를 **CI/CD 변수부터 ConfigMap까지 루트용과 `TEST_*`용으로 분리**해 한쪽 값을 바꿔도 다른 쪽이 바뀌지 않게 했다
- Next.js `basePath`가 빌드 시점 값이라 같은 이미지를 재사용할 수 없다는 제약을 확인하고 이미지를 따로 구웠다
- nginx 함정 두 가지를 README에 남겼다 — `proxy_pass` 끝에 `/`를 붙이면 접두사가 떨어져 호출이 루트 쪽으로 새고, `location = /test { return 301 /test/; }`를 두면 Next의 되돌림과 맞물려 `ERR_TOO_MANY_REDIRECTS`가 난다
- 목서버를 로컬 클러스터 구성에도 포함시켜 로컬과 운영의 차이를 줄였다
- "이미 돌고 있는 클러스터에 FE를 처음 추가할 때" 같은 **실패 사례와 복구 절차**를 README에 적었다

**판단**
**기준을 바꾼 것 자체보다, 두 환경이 섞이지 않도록 변수 계층까지 분리한 것이 핵심이다.** 주소 하나를 공유하면 로그인 콜백이 반대쪽으로 빠진다. `[실물]` README에 그 이유가 적혀 있다

**검증**
`[미확인]` 전환 후 두 경로가 각각 올바른 백엔드를 보는지 확인한 기록은 커밋 메시지(`fix: 배포 후 설정 안정화`) 외에 없다.

**한계**
- **이 작업은 "환경을 정리했다"이지 기능 개발이 아니다.** 분량을 키우지 않는다
- 삽질을 문서로 남긴 것이 재료지 **삽질 자체가 재료가 아니다**

**활용**
TeenyFinny 1.x의 `문서로 넘기기`와 같은 축. **막혔던 지점을 다음 사람이 다시 막히지 않게 적어둔 사례**로 쓴다.

### 1.7 재시도돼도 한 번만 반영되도록 멱등키를 재사용하기

**상황**
코밋 서비스 서버가 에스크로 서버로 계좌 발급과 1원 인증을 요청한다. **돈이 걸린 외부 호출이라 재시도되더라도 한 번만 반영돼야 했다.** `[답변]`

**구현**
회원마다 행을 하나 두고 **멱등키를 계속 재사용하도록 했다.** 그래서 가입을 중간에 그만둔 회원이 다시 들어와도 새 계좌를 발급하지 않고 같은 계좌를 이어받는다. 외부 호출이 실패하면 상태를 실패로 되돌리고 예외를 그대로 올린다. `[실물]` `service/.../domain/account/` — 이 디렉터리 커밋 4/4가 본인, `27a5b47 feat: 서비스 서버에 1원 인증, 계좌 등록 기능 구현`

주석에 규칙 번호(`R-ACC-13`)를 인용해 `docs/RULES.md`의 정책 값과 코드를 연결했다. `[실물]`

**판단**
**분산 환경에서 기능이 문제 없이 돌게 하는 일을 따로 떼어 다뤘다.** Redis를 중앙 토큰 저장소로 두고 refresh token과 캐시를 그쪽에 모은 것도 같은 맥락이다. `[답변]` `[실물]` `deploy/k3s/README.md`

**검증**
유닛 테스트로 동작을 고정했다. `[실물]` `MemberAccountProvisioningServiceTest`

- `reusesTheIssuedAccountWithoutCallingEscrowAgain` — 이미 발급됐으면 에스크로를 다시 부르지 않는다
- `issuesOnceAndKeepsWhatEscrowReturned` — 한 번만 발급하고 받은 값을 보관한다
- `marksTheProvisionFailedWhenEscrowRejects` — 에스크로가 거절하면 실패로 표시한다

운영 중 Race Condition은 발생하지 않았다. `[답변]`

**한계**
- **에스크로 서버 안쪽의 멱등 처리는 본인 작업이 아니다.** `escrow/` 커밋은 이해준 47건이 압도적이다 `[실물]`. **본인 몫은 에스크로를 호출하는 쪽이다**
- **E2E 테스트를 본인 성과로 쓰지 않는다.** `fe/e2e/` 커밋은 이해준 22 · 박연수 15 · 전지웅 8 · 본인 1이다 `[실물]`. "팀이 E2E로 확인했다"로 주어를 바꾸거나 유닛 테스트만 근거로 든다
- **`Race Condition이 없음을 검증했다`가 아니라 `발생하지 않았다`이다.** 동시 요청을 일부러 밀어 넣은 테스트는 account 도메인에 없다 `[실물]`
- 유닛 테스트는 멱등 **동작**을 고정할 뿐 동시성 자체를 시험하지 않는다

**활용**
TeenyFinny·DailyBand에 없던 **금융 도메인의 정확성 재료.** 기능을 만들었다가 아니라 **되돌릴 수 없는 호출을 어떻게 한 번으로 묶었는가**로 쓴다.

## 3. 금지 문장

- `에스크로 서버를 설계했다.` — 팀원 작업
- `E2E 테스트로 동시성 문제가 없음을 검증했다.` — `fe/e2e` 커밋 1/46
- `Race Condition이 없음을 검증했다.` — 발생하지 않았다는 관찰이지 검증이 아니다
- `쿠버네티스로 수평 확장과 고가용성을 검증했다.` — 단일 노드. 보고서가 직접 부정하고 있다
- `다중화로 처리량을 높였다.` — 측정 결과는 정반대다
- `K3s가 Docker보다 느리다.` — A와 B는 거의 동일했다. 차이는 자원 분할에서 왔다
- `무중단 배포를 검증했다.` — rolling 배포를 썼다까지만 사실
- `SonarQube가 랜덤 시드 문제를 잡았다.` — 어느 도구인지 미확인
- `읽기/쓰기 분리를 부하 테스트로 검증했다.` — 로그 확인까지가 전부
- `목서버를 만들었다.` — 뼈대·규격이 본인 몫. 엔드포인트는 팀
- `179 RPS에서 한계에 도달한다.` — 1회 측정이고 warm 상태가 아니었다
- `커밋 규칙 검사로 AI 코드 품질을 보장했다.` — 형식 검사다
- 기능 목록 나열 (계약·정산·채팅·파일 업로드 등)
