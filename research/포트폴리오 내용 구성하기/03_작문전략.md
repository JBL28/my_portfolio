# 포트폴리오 작문 전략

## 1. 판단 기준

모든 문장은 세 기준으로만 본다.

1. **회사가 나를 채용하고 싶게 만드는가**
2. **내가 전달하려는 개발자상이 선명해지는가**
3. **채용담당자가 짧게 읽어도 이해되는가**

기술적으로 흥미롭거나 고생한 경험이어도 위 기준에 기여하지 않으면 비중을 낮춘다.

---

## 2. 작성 순서

사이트는 Hero부터 읽히지만 글은 Detail부터 쓴다.

`Project Detail → 프로젝트 간 연결 → Home Projects → How I Work → Hero`

주장을 먼저 만들고 경험을 끼워 맞추지 않는다.
실제 경험을 작성한 뒤 위로 올라가며 압축한다.

---

## 3. 프로젝트별 역할

### TeenyFinny

**팀 개발에서 기준과 검증을 처음 적용한 프로젝트**

* API 계약 우선 개발
* 요구사항 기반 기술 선택
* DB 장애 주입
* 운영 환경의 문제 발견

### Home Server

**개발 기준을 실제 운영 환경까지 확장한 프로젝트**

* Public / Private 접근 경계
* Docker 실제 노출 확인
* 모니터링 기반 장애 추적
* 개인 운영 환경을 팀 프로젝트에 재사용

### DailyBand

**복잡한 시스템과 AI까지 같은 기준으로 통제한 대표 프로젝트**

* 컴포넌트 간 계약 복구
* BE / Storage / AI Worker 책임 분리
* 파일 무결성 검증
* 외부 AI Worker 실패 복구
* AI 코드 + Quality Gate
* 실시간 오디오 구조 판단

각 프로젝트의 역할을 강화하지 않는 경험은 우선순위를 낮춘다.

---

## 4. Detail 작성 방식

사례 하나는 기본적으로 다음 흐름으로 쓴다.

`상황 → 판단 → 행동 → 확인된 결과`

### 상황

왜 판단이 필요했는지만 짧게 설명한다.

### 판단

무엇을 기준으로 어떤 선택을 했는지가 핵심이다.

### 행동

직접 설계·구현·제안한 내용을 명확하게 쓴다.

### 결과

가능하면 다음 순서로 쓴다.

1. 프로젝트·사용자 결과
2. 팀 개발 방식의 변화
3. 시스템에서 확인한 결과
4. 구현 완료

한 사례는 **2~4문장**을 기본으로 한다.

---

## 5. 소제목

기술명이 아니라 **판단이나 결과**를 쓴다.

### X

* DB 이중화
* Presigned URL
* SonarQube
* AOO

### O

* 이중화를 구성하는 데서 끝내지 않고 직접 장애를 발생시켰습니다
* 백엔드를 우회해도 파일은 검증하도록 했습니다
* AI가 만든 코드에도 같은 품질 기준을 적용했습니다
* 제어할 수 있는 지연을 골라 기술을 변경했습니다

소제목만 훑어도 어떤 개발자인지 보여야 한다.

---

## 6. 작문 중 상담 트리거

작문 전에 모든 경험을 캐내려고 하지 않는다.

**쓰다가 더 강한 근거가 필요해지는 순간 바로 상담한다.**

### 트리거 1. 주장이 근거보다 강할 때

예:

> 팀의 개발 기준을 만들었습니다.

근거가 단순 문서 작성 정도라면 상담한다.

* 누가 문제를 발견했는가
* 내가 무엇을 제안했는가
* 실제 팀 개발 방식이 달라졌는가

---

### 트리거 2. 문장이 추상적일 때

다음 표현이 나오면 구체적인 사건을 찾는다.

* 협업 효율을 높였습니다
* 안정성을 개선했습니다
* 생산성을 높였습니다
* 운영 경험을 쌓았습니다

→ **정확히 무엇이 달라졌는가?**

---

### 트리거 3. 기술 사용 설명밖에 없을 때

예:

> Redis를 사용했습니다.

다음을 확인한다.

* 왜 필요했는가
* 기존 방식의 문제는 무엇이었는가
* 다른 선택지는 무엇이었는가
* 왜 이것을 선택했는가
* 결과를 실제로 확인했는가

판단이 없으면 기술 목록으로만 처리한다.

---

### 트리거 4. 내 기여가 불분명할 때

예:

> 팀에서 API 계약을 정리했습니다.

확인한다.

* 문제를 처음 발견한 사람
* 내가 제안한 내용
* 직접 설계·구현한 범위
* 팀과 합의한 부분
* 내 작업 이후 달라진 점

최종 글에서는 본인 기여와 팀 결과를 명확히 구분한다.

---

### 트리거 5. 결과가 구현 완료에서 끝날 때

예:

> Quality Gate를 구축했습니다.

확인한다.

* 실제 MR이 차단됐는가
* 문제를 배포 전에 발견했는가
* 반복 작업이 줄었는가
* 팀이 계속 사용했는가

---

### 트리거 6. 성장 연결이 추상적일 때

> 이전 프로젝트에서 배운 것을 적용했습니다.

라고 쓰지 않는다.

대신 확인한다.

* 이전 문제 때문에 처음부터 다르게 한 것은 무엇인가
* 판단 기준이 바뀐 것은 무엇인가
* 새로 추가한 검증 절차가 있는가
* 이전 환경이나 도구를 실제 재사용했는가

---

### 트리거 7. 더 강한 사건이 숨어 있을 때

다음 표현이 나오면 한 번 더 파고든다.

* 처음에는
* 원래는
* 문제가 생겨서
* 팀원과
* 실제로 돌려보니
* 예상과 달리
* 다시
* 직접 확인해보니

갈등·실패·판단 변경·검증 경험이 숨어 있을 가능성이 높다.

---

## 7. 상담 방식

상담 때문에 전체 작문을 멈추지 않는다.

해당 문단에 필요한 질문만 짧게 한다.

`작문 → 부족함 감지 → 질문 → 아이템 발굴 → 바로 작문 재개`

새 경험이 기존 사례보다 강하면 교체하거나 추가한다.
약하면 기존 흐름을 유지한다.

---

## 8. 프로젝트 간 성장

성장을 직접 선언하지 않는다.

**다음 프로젝트에서 실제 행동이 달라진 사실**로 보여준다.

예:

`TeenyFinny의 Public 운영 문제`
→ `Home Server에서 Public / Private 경계 분리`

`TeenyFinny의 API 계약 우선 개발`
→ `DailyBand에서 무너진 계약을 Mock Server 기반으로 복구`

`Home Server의 Runner / SonarQube 운영`
→ `DailyBand CI/CD와 Quality Gate에 실제 사용`

이 연결 자체가 성장 메시지다.

---

## 9. Home Project 카드

Detail 작성 후 압축한다.

카드에서는 이것만 보여준다.

* 무슨 프로젝트인가
* 내가 무엇을 맡았는가
* 가장 강한 판단 1~2개
* 확인된 결과 1개
* 핵심 기술
* Detail / GitHub / Architecture 등

**Home은 읽게 만들고, Detail은 믿게 만든다.**

상세 사례를 Home에 전부 넣지 않는다.

---

## 10. How I Work

필수 섹션이 아니다.

프로젝트 작성 후에도 공통 행동을 정리할 가치가 있을 때만 유지한다.

현재 후보:

* 기준
* 경계
* 검증

Projects를 다시 설명하는 수준이면 삭제한다.

---

## 11. Hero

가장 마지막에 쓴다.

Hero가 답할 질문은 하나다.

> **이 사람을 어떤 개발자로 기억해야 하는가?**

현재 중심 메시지:

> **팀이 함께 쓸 기준을 만드는 백엔드 개발자**

보조 문장은 실제 프로젝트에서 반복된 행동만 압축한다.

AI를 별도 정체성으로 과장하지 않는다.
DailyBand의 실제 사례로 보여준다.

---

## 12. AI 서술

AI를 썼다는 사실만으로 어필하지 않는다.

`AI 활용 → 결과 검토 → 실제 실행/테스트 → 품질 기준 → 운영`

흐름이 있을 때 사용한다.

목표는

> AI를 많이 쓰는 개발자

가 아니라

> **AI를 활용하면서도 결과를 검증하고 운영 가능한 시스템으로 만드는 백엔드 개발자**

라는 인상을 주는 것이다.

---

## 13. 증거

핵심 주장에는 가능하면 확인 가능한 증거를 붙인다.

* Architecture Diagram
* Sequence Diagram
* Pipeline 결과
* 테스트 결과
* GitHub
* Demo

스크린샷을 많이 넣는 것이 목적이 아니다.

**사례 하나당 가장 설득력 있는 증거 하나**면 충분하다.

---

## 14. 압축

초고 후 모든 문장에 묻는다.

> **이 문장을 지워도 채용담당자가 나에 대해 받는 인상이 같은가?**

같다면 줄이거나 합친다.

특히 줄일 것:

* 기술의 일반적인 장점 설명
* 기능 나열
* 같은 의미 반복
* 당연한 결론
* `성장했습니다`, `깨달았습니다` 같은 결산
* 면접에서 설명해도 되는 세부 구현

---

## 15. 분량 기준

### Home

30초 안에 다음이 보여야 한다.

`백엔드 개발자 → 대표 강점 → 대표 프로젝트 → 가장 강한 근거 → Detail`

### Detail

첫 화면에서 다음이 보여야 한다.

* 무슨 프로젝트인가
* 내가 무엇을 맡았는가
* 왜 이 프로젝트를 읽어야 하는가

사례 하나는 2~4문장.

프로젝트별 핵심 사례는 대략:

* TeenyFinny: 3~4개
* Home Server: 3~4개
* DailyBand: 5~6개 이하

단, 작문 중 더 강한 아이템이 발굴되면 교체할 수 있다.

# 최종 검수

모든 섹션에 세 질문만 한다.

1. **이 내용이 회사를 나를 채용하도록 설득하는가?**
2. **내가 전달하려는 메시지가 더 선명해지는가?**
3. **같은 설득력을 더 짧게 전달할 수 있는가?**

작문 중 답이 부족하다면 바로 삭제하지 않는다.

먼저:

> **여기에 아직 안 꺼낸 더 강한 경험이 있지 않은가?**

를 확인하고 상담한다.
