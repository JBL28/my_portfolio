# Project Detail — TeenyFinny

부모와 자녀가 함께 사용하는 청소년 용돈·투자 관리 서비스입니다. 처음 PL을 맡아 **API 계약과 공통 백엔드 구조, 인프라와 개발 흐름을 정리하는 역할**을 맡았습니다.

2025.10 \~ 2025.12 · 5인  
**본인 담당** · API 명세·공통 구조 · DB·AWS 인프라 · DevOps·기술 문서  
Spring Boot · MySQL · AWS · Nginx · Jenkins · SonarQube  
**Team Result. 최종 프로젝트 우수팀**

## 처음 맡은 PL에서 팀이 일할 방식을 먼저 정했습니다

PL을 맡은 뒤 역할부터 조사해 문서·산출물 관리와 기술 이슈 관리를 핵심으로 잡았습니다. API 명세와 이슈·PR 템플릿을 정하고 Notion 기술 문서를 관리했으며, 프론트엔드는 Postman Mock Server를 기준으로 백엔드와 병행 개발했습니다.

## 의견이 갈렸을 때 요구사항으로 판단 기준을 맞췄습니다

실시간 주식 시세에 WebSocket과 Polling 중 팀 의견이 갈렸습니다. 두 방식의 특징을 조사해 문서로 공유한 뒤 **초저지연·양방향 통신이 필요한가**를 서비스 요구사항과 대조했습니다. Polling을 제안했고, 팀이 이를 받아들였습니다.

## 이중화는 직접 끊어보고 확인했습니다

MySQL 이중화와 ProxySQL·Orchestrator 기반 Failover를 구성한 뒤 Active DB를 직접 중단했습니다. Failover 동안 **읽기는 유지됐고, 쓰기는 수 초 지연된 뒤 재개**됐습니다. 구성 완료를 무중단으로 표현하지 않고 읽기와 쓰기가 실제 장애에서 어떻게 달라지는지 구분해 확인했습니다.

## 운영의 아쉬움을 다음 환경에서 다시 설계했습니다

Grafana·Loki·Prometheus로 여러 서버를 관측하고 Jenkins·SonarQube로 개발 흐름을 자동화했지만, 운영 도구까지 Public 환경에 둔 점이 남았습니다. 프로젝트가 끝난 뒤 개인 서버를 구축해 **서비스 공개 필요 여부에 따라 접근 경계를 다시 설계**했습니다.

# Project Detail — Home Server

TeenyFinny에서 남은 Public 운영 문제를 다시 다루기 위해 미니 PC에 Linux 서버를 구축했습니다. **접근 경계부터 장애 진단, 자동화까지 직접 운영하고 그 환경을 다시 팀 프로젝트에 사용했습니다.**

2026.01 \~ 현재 · 개인 프로젝트  
**본인 담당** · 전체 설계·구축·운영  
Ubuntu · Docker · Nginx · Tailscale · Cloudflare Tunnel · Grafana

## 공개 필요 여부에 따라 접근 경로를 나눴습니다

처음에는 SSH와 비밀번호 관리자까지 포트포워딩으로 열어 두었습니다. 이후 **내부 서비스는 Tailscale, 공개 서비스는 Cloudflare Tunnel → Nginx**로 분리하고 기존 포트포워딩을 제거했습니다. 변경 뒤 공인 포트 차단, VPN 내부 접속, 외부 공개 서비스 응답을 각각 확인했습니다.

## 방화벽 설정보다 실제 노출 경로를 확인했습니다

Docker Published Port가 호스트 방화벽 정책과 별개로 노출될 수 있음을 확인했습니다. 외부 접근이 필요 없는 컨테이너는 Published Port를 없애고 Docker Network 내부에서만 통신한 뒤 Nginx를 거치게 했습니다. 설정값이 아니라 **실제로 외부에 열리는 경로**를 확인하며 경계를 다시 잡았습니다.

## 메트릭과 접속 경로를 대조해 장애를 좁혔습니다

VPN 경유 접속만 막혔을 때 메트릭과 서비스 상태로 서버 문제를 먼저 배제하고, 내부망과 VPN 경로의 차이에서 Tailscale node key 만료를 특정했습니다. 만료 기능을 끄는 대신 갱신을 자동화했고 이후 같은 장애는 재발하지 않았습니다. 이 과정에서 내부 상태가 정상이어도 **외부 접근 경로는 별도의 관측 대상**이라는 사각지대도 확인했습니다.

## 개인 서버를 팀의 품질 검증 환경으로 연결했습니다

GitLab Runner와 SonarQube를 직접 호스팅해 팀 프로젝트에 사용했습니다. Runner는 Private 환경에서 outbound로 작업을 가져오게 하고, 팀원이 열람해야 하는 SonarQube는 접근 권한을 둔 Public 접점으로 분리했습니다. 이 환경은 DailyBand의 **Build → Test → SonarQube → Quality Gate** 흐름으로 이어졌습니다.

# Project Detail — DailyBand

초보자가 온라인으로 합주하고 AI 피드백을 받을 수 있는 서비스입니다. **고스트 기능의 FE·BE·AI·MinIO 연결 API와 파일·Job 구조, API 계약 복구, CI/CD를 맡아 컴포넌트 사이의 계약과 실패 흐름을 정리했습니다.**

2026.07 \~ 2026.08 · 5주 · 6→5인 팀 프로젝트  
**본인 담당** · 고스트 기능 연결 API · `files`·Job · Redis 프로젝션·폴백 구조 · API 계약 복구 · CI/CD·Quality Gate · Nginx · 기술 조사  
Spring Boot · PostgreSQL · Redis · MinIO · FastAPI · Electron · C/C++ · GitLab CI/CD · SonarQube · AOO · JUCE  
**Team Result. 최종 발표에서 전체 기능 실시간 시연**

> 비공개 저장소입니다. 공개 가능한 범위에서 설계 판단과 검증 결과를 정리했습니다.

## 서로 달라진 계약을 실행 가능한 형태로 복구했습니다

공통 계약 없이 개발이 진행되면서 BE·Signaling·FE·AI의 엔드포인트와 데이터 형식이 달라졌습니다. AI Agent로 기존 BE를 역분석해 초안을 만들되 그대로 채택하지 않고 **다른 Agent의 검토 → 팀의 실제 구현 대조 → FastAPI Mock Server와 API Docs 확인**을 거쳤습니다. 복구와 재정렬에 1주가 들었지만 통합을 완료했고 이후 같은 유형의 계약 불일치는 재발하지 않았습니다.

## 반복되던 파일 메타데이터 책임을 한 곳으로 모았습니다

MP3·MIDI·MusicXML·JSON 등 파일마다 객체 키·크기·해시 같은 스토리지 정보가 반복되는 문제를 보고 공통 `files` 테이블을 제안했습니다. 팀의 회의적인 의견에는 실제 사례와 중복 컬럼을 근거로 설명했고, 최종 스키마에서는 **10개 테이블이 `files`를 참조**하도록 구성했습니다. MinIO 관련 변경도 도메인마다 흩어지지 않고 파일 책임 안에서 다룰 수 있었습니다.

## 백엔드를 우회해도 파일은 검증했습니다

원본 1개가 결과 MP3 5개로 늘어나는 흐름에서 BE가 모든 파일을 중계하지 않도록 FE와 AI가 Presigned URL로 MinIO에 직접 업로드하게 했습니다. BE는 URL 발급·완료 신호·Job 상태를 조정하고, 직접 업로드로 생긴 신뢰 공백은 **업로드 전 SHA-256·크기·Content-Type 선언 → 업로드 후 실제 객체 대조**로 보완했습니다.

## 트랜잭션 밖의 AI 실패를 별도 상태로 회수했습니다

DB에 Job을 기록하는 것과 외부 AI Worker에 작업을 보내는 것은 서로 다른 시스템입니다. DB가 rollback됐는데 Worker만 실행되는 상태를 피하려고 **Job commit → AFTER\_COMMIT 비동기 dispatch** 순서로 분리했습니다. 커밋 뒤 dispatch 실패는 rollback할 수 없으므로 15초 주기의 Reconciler가 PENDING Job을 다시 보내거나 timeout 처리하게 했습니다.

## AI가 만든 코드도 같은 검증 흐름을 통과시켰습니다

AI Agent로 여러 언어의 코드를 빠르게 작성하되 생성 결과를 신뢰의 근거로 삼지 않았습니다. `Build → Test → SonarQube → Quality Gate → Deploy` 파이프라인을 만들고 **Quality Gate를 MR 병합 조건**으로 연결했습니다. 실제로 기준을 통과하지 못한 MR이 차단됐고, SonarQube의 판정도 입력 경로와 수정 비용을 확인한 뒤 적용했습니다.

## 처음 다루는 네이티브 영역도 판단 근거부터 만들었습니다

저지연 합주를 위해 레이턴시를 **I/O · Network · Receive Buffer**로 나눠 조사하고 다이어그램으로 팀에 공유했습니다. 사용자 장비와 ISP 경로보다 팀이 직접 통제할 수 있는 수신 버퍼에 집중했고, WebRTC 대신 C++ 네이티브 애드온에서 AOO·JUCE로 오디오 입출력과 전송을 다루는 방향을 제안했습니다. **처음 다루는 C/C++·AOO·JUCE 영역에서 5주 안에 전환 방향을 구체화했고, 팀은 이를 네이티브 오디오 입출력·전송 기능으로 실제 서비스에 연결했습니다.**
