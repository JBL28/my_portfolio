## 1. 재료 목록

### 1.1 없던 계약을 실행 가능한 기준으로 복구하기

**상황**
C/C++ 네이티브 애드온의 구조를 예측하기 어려운 상태에서 공통 API 명세 없이 구현을 시작했다. 통합 단계에서 BE·시그널링·FE·AI 네 컴포넌트의 엔드포인트, 요청·응답 형식, 자료형, 예외 처리가 서로 달랐다.

**구현**
AI 에이전트로 기존 BE API를 역분석해 초안을 만들고, 다른 코딩 에이전트의 비관적 검토와 팀 전체의 구현·설계 대조를 거쳤다. 텍스트 명세를 정리한 뒤 FastAPI Mock Server를 만들고, 생성된 API Docs를 공통 명세로 사용했다. `[답변]`

**판단**
처음부터 이상적인 계약을 다시 설계할 수도 있었지만 이미 각 컴포넌트의 구현이 진행 중이었다. 존재하는 BE 구현을 기준점으로 삼아 불일치를 줄이고, 나머지 컴포넌트가 **실제로 호출해 볼 수 있는** 기준을 만드는 쪽을 택했다. AI가 만든 문서를 곧바로 계약으로 채택하지 않았다. 실제 구현을 아는 사람이 검수하고, 실행 가능한 Mock Server와 API Docs가 같은 계약을 표현하는지 다시 대조해야 팀 기준으로 쓸 수 있다고 보았다. `[답변]`

**검증**
계약 복구와 네 컴포넌트 재정렬에 **1주**가 걸렸고 팀 일정도 **1주** 지연됐다. 복구 후 실제 통합을 완료했고, 남은 프로젝트 기간에는 같은 유형의 계약 불일치가 재발하지 않았다. `[답변]`

**한계**
복구 비용 때문에 다음 주에 크런치가 생겼다. **이를 헌신의 성과로 미화하지 않는다.** 코드·명세·Mock Server는 비공개 저장소에 있어 외부 공개 불가. AI가 절감한 시간은 측정하지 않았다.

**활용**
**핵심 재료.** TeenyFinny에서 계약 우선 방식을 이미 성공시켰다는 사실과 짝을 이룬다. `처음 몰랐다가 배웠다`가 아니라 **`효과를 알던 원칙도 불확실성이 큰 환경에서는 지키기 어려웠고, 그 비용과 복구를 직접 겪었다`** 는 이야기다. AI 시대의 협업 문제 정의라는 점에서 외부 사례에서 관찰되지 않은 차별점이기도 하다.

### 1.2 원본 하나가 결과 다섯 개가 되는 파일 흐름 설계

**상황**
고스트 추출은 원본 음원 한 개를 AI가 분석해 다섯 개의 MP3로 분리한다. 처음에는 백엔드가 파일을 직접 중계하는 방식을 생각했다. 가장 직관적이었기 때문이다.

**구현**
FE가 원본 업로드 URL을 요청하면 BE가 Presigned URL을 발급하고, FE는 MinIO에 직접 업로드한 뒤 완료를 알린다. BE가 AI에 분석을 의뢰하고, AI도 BE가 발급한 결과용 Presigned URL로 다섯 MP3를 직접 업로드한 뒤 완료를 알린다. BE는 최종 고스트 음원 위치를 FE에 전달한다. **전체 흐름은 비동기다.** `[답변]` `[실물]` `domain/ghost/` 커밋 15건

전체 호출 흐름:
```
① FE 원본 음원 선택
② FE → BE  원본 업로드용 Presigned URL 요청
③ FE → MinIO  직접 업로드
④ FE → BE  업로드 완료 신호
⑤ BE → AI  악기 분리 분석 의뢰
⑥ AI → BE  결과 MP3 업로드용 Presigned URL 요청
⑦ BE → AI  Presigned URL 발급
⑧ AI → MinIO  분리된 MP3 직접 업로드
⑨ AI → BE  업로드 완료 신호
⑩ BE → FE  고스트 음원 URL 전달
⑪ FE 고스트 음원 재생
```

**판단**
두 가지 이유로 BE 중계를 버렸다.
1. **부하** — mp3 한 개가 최대 다섯 개로 늘어나므로, BE가 원본과 결과 파일을 모두 받아 다시 MinIO로 보내면 네트워크 트래픽과 메모리 부하가 한 서버에 집중된다. `FE → BE → Storage` 한 구간의 최적화가 아니라 파일 수가 늘어나는 전체 흐름을 본 판단이다.
2. **결과물 품질** — BE에서 음원 파일을 만들면 네트워크 상태에 따라 결과물 자체에 영향이 갈 수 있다고 보았다. 그래서 FE에서 녹음한 뒤 업로드하는 방식을 택했다.

BE를 파일 데이터 경로가 아니라 **Presigned URL 발급, 완료 신호 수신, 분석 요청, 결과 위치 전달을 담당하는 조정 경로**로 제한했다. FE든 AI든 구분 없이 `Presigned 요청 → 직접 업로드 → 완료 API → BE가 Job 완료 처리`라는 **동일한 계약**을 쓰게 했다. `[답변]`

**검증**
FE의 원본 선택부터 AI 분리, 결과 업로드, FE 재생까지 통합했고 최종 발표의 실시간 시연에 포함됐다. `[답변]`

**한계**
직접 업로드 전후의 트래픽·메모리·처리 시간을 비교 측정하지 않았으므로 **부하 감소율을 말할 수 없다.** 실제 근거는 예상되는 부하 구조와 이를 피하도록 구현한 아키텍처다.

**활용**
**본인이 짠 유일한 백엔드 기능이며, 하필 난이도가 높은 축이다.** 비동기 + 외부 스토리지 + 3자 연동은 평범한 CRUD보다 위다. `어떤 기능을 만들었나요?` 질문의 답은 항상 이것이다. 개수가 하나뿐이므로 어떤 각도로 찔러도 답이 나오도록 아래 1.3~1.6과 함께 준비한다.

### 1.3 파일 메타데이터를 공통 테이블로 분리하고 팀을 설득하기

**상황**
다뤄야 할 파일이 음원만이 아니었다. MIDI, MusicXML, 분석 결과 JSON, 믹스 결과 등 종류가 여럿이었고 각각 MinIO에 저장됐다.

**구현**
`files` 공통 테이블을 두고, 파일을 쓰는 도메인 테이블들이 이를 참조하게 설계했다. MinIO 관련 정보(객체 키·원본 파일명·컨텐츠 타입·크기·재생 길이·해시·검증 시각·상태·삭제 요청 시각)는 `files`에, 아티스트·BPM 같은 음악 자체 정보는 도메인 테이블에 두었다. `[실물]`

**판단**
스토리지 메타데이터와 도메인 정보는 관심사가 다르므로 분리해야 한다고 보았다. **팀원들이 처음 쓰는 방식이라 확신이 없어 회의적이었고**, 다른 ERD에서 `files` 패턴을 쓰는 실제 사례와 중복 컬럼이 많다는 점을 근거로 제시해 채택시켰다. `[답변]`

**검증**
최종 구현에서 **`files`는 10개 테이블에서 13개 외래키로 참조된다.** `[실물]` 마이그레이션 확인

효과도 관찰했다. MinIO 연동 작업에서 복잡도가 확실히 낮았다. 파일을 쓰는 테이블마다 연결을 따로 관리했다면 작은 수정에도 여러 테이블과 비즈니스 로직을 고쳐야 했지만, 책임을 나눴기 때문에 `files` 테이블과 관련 로직만 고치면 됐다. `[답변]`

**한계**
`파일 종류가 추가됐을 때 스키마 변경 없이 흡수됐다` 같은 **구체적 수정 사례를 아직 확보하지 못했다.** 면접에서 `예를 들면요?`가 나오면 답이 필요하다. `[미확인]`

**활용**
**DB 설계 재료 중 가장 강하다.** 문제(중복 컬럼) → 대안(테이블별 개별 관리) → 판단(관심사 분리) → **반대에 부딪힘** → 근거 제시(실사례·중복) → 채택 → 효과(변경 범위 축소)까지 전부 있다. 신입 포트폴리오에서 이 형태는 흔치 않다. 특히 마지막 `책임 분리 → 변경 국소화` 연결은 SOLID를 이름 대지 않고 설명한 셈이다.

### 1.4 백엔드를 우회시키면서 검증은 포기하지 않기

**상황**
Presigned URL로 클라이언트가 스토리지에 직접 업로드하면 **백엔드는 실제로 무엇이 올라갔는지 알 수 없다.** 클라이언트가 다른 파일을 올릴 수도, 파일이 손상될 수도 있다. BE를 데이터 경로에서 뺀 대가로 생기는 신뢰 공백이다.

**구현**
선언-검증 프로토콜을 두었다. `[실물]`
1. 업로드 전 클라이언트가 `expected_sha256`, `expected_size_bytes`, `expected_content_type`을 선언하고 `uploads` 테이블에 저장한다.
2. 업로드 후 실제 객체의 해시를 계산해 선언값과 대조한다.
3. 통과하면 `files.sha256`과 `files.verified_at`을 기록한다.

세션 녹음 원본(`session_sources`)도 같은 패턴을 쓴다. `object_key`·`sha256`·`size_bytes`를 갖고, DB 제약이 `status = COMPLETED`일 때 `file_id`·`size_bytes`·`sha256`·`completed_at`이 모두 존재해야 한다고 강제한다.

AI 워커가 완료 콜백을 보낼 때의 인증도 있다. `media_jobs`에 `callback_token_key_id`, `callback_token_hash`, `callback_token_expires_at`을 두고 **토큰을 평문이 아니라 해시로 저장하며 만료 시각을 둔다.**

**판단**
BE를 데이터 경로에서 빼는 선택의 대가를 인지하고, 그 공백을 무결성 검증과 콜백 인증으로 메웠다. `[답변]` 구조 설계는 본인, 세부 로직은 AI 생성 후 리뷰

**검증**
DB 스키마에 제약으로 존재하며 마이그레이션에서 확인된다. `[실물]`

**한계**
`Presigned URL을 최소 권한으로 안전하게 구성했다`고 쓰지 않는다. URL 자체의 유효 시간·객체 키 제한·HTTP 메서드 제한은 별도로 확인되지 않았다. 확인된 것은 **업로드 결과의 무결성 검증**과 **콜백 토큰 관리**다.

**활용**
**보안 칸을 채우는 재료.** `Presigned URL 쓰면 서버가 뭐가 올라왔는지 모르지 않나요?`라는 반문에 정확히 답할 수 있다. 신입이 이 공백을 인지하고 메운 사례는 드물다.

### 1.5 트랜잭션 경계 밖의 외부 시스템 다루기

**상황**
분석 Job을 DB에 기록하는 것과 AI 워커에 실제로 작업을 보내는 것은 서로 다른 시스템이다.

**구현**
세 단계로 구성했다. `[실물]`
```
① 트랜잭션 안     Job을 DB에 기록하고 커밋
② AFTER_COMMIT   @TransactionalEventListener(AFTER_COMMIT) + @Async 로 워커 디스패치
                  예외는 log.warn만 남기고 삼킴
③ Reconciler     @Scheduled 15초 주기
                  PENDING 재디스패치 · 타임아웃 실패 처리
```

**판단**
한 트랜잭션 안에서 외부 워커를 호출하면 **디스패치는 나갔는데 트랜잭션이 롤백되는** 경우가 생긴다. 그러면 DB에는 Job이 없는데 워커는 작업을 시작한 상태가 되고, 워커가 콜백을 보내도 받을 레코드가 없다. 커밋이 확정된 뒤에만 디스패치해 이 불일치를 막았다.

`@Async`를 쓴 이유는 디스패치가 HTTP 호출이라 느릴 수 있는데 커밋이 이미 끝났으므로 사용자 응답을 붙잡을 이유가 없기 때문이다. 예외를 삼킨 이유는 `AFTER_COMMIT` 시점에는 이미 커밋되어 롤백할 수단이 없기 때문이다.

**그 대가로 디스패치 실패 시 Job이 PENDING으로 남는 구멍이 생기므로 Reconciler로 메웠다.** `[답변]` 구조 설계는 본인

**검증**

실시간 합주에는 낮은 지연이 필요하지만 Wi-Fi 환경에서는 도착 간격이 흔들리며 소리가 끊길 수 있었다.

**구현**
동일 내부망의 두 피어에서 애플리케이션 송신·응답 시각 차이를 **10회 측정해 하드웨어 지연을 제외한 RTT 평균 약 10ms**를 확인했다. 실사용 중 Wi-Fi에서 음 끊김이 발생하자 지터 버퍼를 **20ms에서 40ms로** 늘렸다. `[답변]`

**판단**
지터 버퍼를 줄이면 지연은 작아지지만 늦게 도착한 패킷을 기다릴 여유가 줄고, 늘리면 끊김은 완화되지만 지연이 커진다. 완전한 최적값보다 당시 환경에서 끊김을 없애는 쪽을 택했다.

**검증**
버퍼를 늘린 뒤 관찰되던 음 끊김이 사라졌고 체감 지연은 약간 증가했다. 서로 다른 외부 환경에서 **최대 4명이 약 6시간** 밤샘 작업 대화 수단으로 서비스를 사용했다. `[답변]`

**한계**
- 약 10ms는 **동일 내부망 P2P 통신 RTT**이며 하드웨어와 오디오 입출력 지연을 포함하지 않는다
- **`40ms`는 경험적으로 선택한 값**이며 계산이나 체계적 탐색의 결과가 아니다
- 버퍼 변경 뒤 지연을 다시 수치로 측정하지 않았다
- 6시간 사용은 합주가 아니라 **작업 대화**였고, 실제 전송 경로가 직접 P2P였는지 릴레이였는지 런타임에서 확인할 수 없었다. 릴레이 폴백을 강제로 검증하지도 않았다
- Discord에 표시된 약 40ms는 **서버–클라이언트 경로**의 값이라 P2P 실측값과 토폴로지가 다르다. 대조군으로 쓰지 않는다
- 지터 버퍼 코드 수정의 직접 담당자가 본인인지 확인되지 않았다 `[미확인]`

**활용**
**무장애 장시간 성능 증명이 아니라 `실사용 중 문제 발견 → 버퍼 조정 → 안정성과 지연의 절충 확인` 사례로만 쓴다.** 조건을 붙인 수치는 조건 없는 수치보다 강하다.

### 1.12 설계와 다른 구현을 발견하고 되돌리기

**상황**
계약 복구 중 검수 과정에서 방 관리가 설계와 달리 WebSocket으로 구현된 것을 발견했다.

**구현**
시그널링의 실시간 책임과 방 정보의 JPA 소유권을 구분해, 기존 BE의 폴링 방식으로 고쳤다. `[답변]`

**판단**
실시간 신호 전달과 방 정보의 영속 상태는 다른 책임이라고 보았다. 방 정보는 DB가 소유하고, WebSocket은 시그널링에 쓰는 것이 맞다고 판정했다. `[답변]`

**검증**
수정 후 통합이 완료됐다. 폴링으로 인한 조회 부하는 Redis 프로젝션(1.6)으로 흡수했다. `[답변]`

**한계**
폴링 주기와 인원 증가 시의 DB 부하를 측정하지 않았다. `[미확인]`

**활용**
**팀이 이미 짜놓은 것을 근거를 들어 되돌린 사례.** 설계 주체가 누구냐가 아니라 판단이 누구 것이냐를 보여준다. TeenyFinny의 웹소켓·폴링 중재와 같은 형태가 반복된다는 점도 의미가 있다.

### 1.13 자기 산출물의 과잉 설계를 진단하기

**상황**
최종 스키마는 30개 테이블, 58개 외래키다. ERD가 복잡했다.

**구현**
전체 테이블 이름을 소스에서 검색해 실제 사용 여부를 확인했다. `[실물]`

**판단과 발견**

**① 사용되지 않는 테이블 1개.** `sessions_files`는 생성 마이그레이션과 pg_dump 산출물에만 등장하고 **Java 코드에는 엔티티도, 네이티브 SQL도, 테스트도 없다.** 이름도 실제 구조와 맞지 않는다. `files`와 무관하며 컬럼은 `upload_id` + `session_id`다. V1 주석이 이미 *실제 참조는 uploads (명칭 검토)* 라고 지적하고 있었다.

**② 구조적으로 불필요한 연결 테이블 4개.** 실제 카디널리티는 1:N인데 다대다 연결 테이블로 만들고 `UNIQUE` 제약으로 1:N을 강제한 경우다.

| 테이블 | 제약 | V1 주석 | 대체 가능 |
| --- | --- | --- | --- |
| `rooms_sessions` | `UNIQUE(session_id)` | `그려진 카디널리티: 세션은 한 방` | `sessions.room_id` |
| `upload_ghosts` | `UNIQUE(ghost_id)` | `그려진 카디널리티: 스템은 한 업로드` | `ghosts.upload_id` |
| `users_results` | `UNIQUE(result_id)` | `그려진 카디널리티: 결과당 소유자 1명` | `results.user_id` |
| `tracks_results` | `UNIQUE(result_id)` | `그려진 카디널리티: 결과는 한 트랙` | `results.track_id` |

주석의 **`그려진`** 이라는 표현이 원인을 보여준다. 팀이 합의한 ERD가 다대다로 그려져 있었고, ERD를 수정하는 대신 그린 대로 구현한 뒤 `UNIQUE`로 실제 카디널리티를 맞췄다. 이 선택은 코드에도 흔적을 남겼다. 세션은 방을 다대일로 참조하면서도 연결 테이블 때문에 `@ManyToOne` + `@JoinTable` 우회 매핑을 쓴다.

**③ 접근 방식이 두 갈래다.** JPA 엔티티가 있는 테이블은 22개, 나머지는 JdbcTemplate 네이티브 SQL로 접근한다. 쓰기 모델은 JPA, 조회·정리 경로는 raw SQL로 나뉘어 있다.

**검증**
30개 중 5개(약 17%)가 없어도 됐다. 넷을 FK 컬럼으로 접고 미사용 테이블을 제거하면 30개 → 25개, FK 58개 → 54개가 된다. `[실물]`

**한계**
JPA와 JdbcTemplate을 나눈 것이 의식적 결정이었는지 확인되지 않았다. `[미확인]` 확인 전에는 설계 의도로 주장하지 않는다.

**활용**
**`이 ERD를 다시 설계한다면 뭘 바꾸시겠어요?`의 답.** 거의 확정으로 나오는 질문이다. 준비된 대사:

> 실제로는 1:N인 관계 네 개를 다대다 연결 테이블로 만들고 UNIQUE 제약으로 카디널리티를 강제한 부분을 FK 컬럼으로 바꾸겠습니다. 팀이 합의한 ERD를 그대로 구현하느라 그렇게 됐는데, 결과적으로 테이블이 늘고 불필요한 조인이 생겼으며 JPA에서도 다대일 관계에 `@JoinTable`을 쓰는 우회가 나왔습니다. 그리고 만들어놓고 한 번도 쓰지 않은 테이블이 하나 있었습니다.

**자기 팀 산출물의 결함을 원인 → 결과 → 코드 영향까지 추적해 말할 수 있다는 것이 이 재료의 값어치다.**

### `files`를 참조하는 13개 외래키

| 소유 테이블 | 컬럼 | 의미 |
| --- | --- | --- |
| `ghosts` | `file_id` | 분리된 고스트 음원 |
| `uploads` | `source_file_id` | 업로드 원본 |
| `session_sources` | `file_id` | 참여자별 연주 원본 |

| `analysis_results` | `transcribed_midi_file_id` | 전사된 MIDI |
| `analysis_results` | `feedback_file_id` | LLM 피드백 JSON |

- MIDI 전사와 정확도 측정
- 룰 기반 음정·박자 채점과 LLM 피드백 생성 전체
- P2P·릴레이 구조 전체
- Three.js 게이미피케이션

### AI 채점 기능의 정확한 설명

```
연주 음원 → MIDI 전사 → 정답 MIDI와 음정·박자를 룰 기반 비교해 점수 계산
         → 음정·박자 결과와 점수를 LLM에 전달 → 설명형 피드백 생성
```

- **`LLM이 연주를 직접 채점했다`고 쓰지 않는다.** 점수는 룰 기반 비교로 계산된다
- 전사 정확도는 정답 MIDI와 대조해 측정했지만 본인은 AI 담당이 아니며 정확한 수치를 기억하지 못한다
- 사람이 실제 연주 소리를 듣고 음정·박자 결과, 점수, LLM 피드백이 맞는지 대조했다
- **샘플 수, 정확도, 검수 통과율을 만들지 않는다**

- `Presigned URL로 서버 부하를 특정 비율만큼 줄였다.` — 측정 없음
- `Presigned URL을 최소 권한으로 안전하게 구성했다.` — URL 자체의 권한 설정 미확인
- `Transactional Outbox 패턴을 구현했다.` — 아웃박스 테이블 없음
- `AI가 만든 결과의 정확성을 다른 AI가 보장했다.`
- `AI로 개발 기간을 특정 일수 또는 비율만큼 단축했다.`
- `800개 이상의 유지보수 이슈를 해결했다.` — 규칙 위반 수
- `중복도 57.1%를 개선했다.` — 실제 두 파일 각 8줄
- `반복 호출로 DoS가 가능하다.` — 백트래킹은 입력 길이에 의존
- 비공개 저장소의 코드·명세·캡처를 허가 없이 게시하는 것
