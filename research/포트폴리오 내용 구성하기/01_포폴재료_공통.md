# 포폴 재료 — 공통

## 0. 이 문서의 성격

세 프로젝트 파일(`포폴재료_티니피니` · `포폴재료_개인서버` · `포폴재료_데일밴드`)에 담기지 않는 재료를 모았다. 이력, 성장 흐름, 핵심 주장 후보, 문장 자산, 서술 기준이다.

### 학력 표기 정정 — 즉시 반영 대상

현재 Notion 표기는 `순천향대학교 컴퓨터공학과 중퇴`다. **실제 사건은 시험을 준비해 통과한 편입이다.**

`중퇴`는 사실이지만 이탈로 읽히고, `전북대 편입`은 같은 사실을 성취로 읽히게 한다. 과장이 아니라 정확한 표기다. 두 학교의 기간이 이어지는 것(2023.02 종료, 2023.03 시작)도 편입 사실과 일치한다.

### 정보처리기사의 정확한 위치

**계기와 시점** — 여러 멘토가 전공자라면 갖추는 것이 좋다고 조언해 준비했고, 데일밴드를 시작하기 직전에 취득했다. `[답변]`

**의미** — 자격증 공부가 이후 프로젝트에 도움을 준 것이 아니라, **이전 프로젝트에서 다룬 내용이 자격증 준비에 도움이 됐다.** 웹 개발 기본, 테스트 종류, 보안, 데이터베이스, 인프라까지 넓은 범위가 이전 경험과 겹쳤다. `[답변]`

특히 소프트웨어 설계 순서를 공부할 때 실제 프로젝트의 `기획 → 요구사항 정리 → 와이어프레임 → 기능 명세 → ERD → API 명세` 흐름을 떠올렸고, 순서를 암기하는 대신 **단계 순서가 달랐다면 어떤 문제가 생겼을지를 상상해봤다.** `[답변]`

**배치** — 자격증·이력 영역에 한 줄로 둔다. 본문에서 필요할 때만 `프로젝트에서 경험한 개념을 이론 체계와 다시 대조했다`는 보조 설명을 쓴다.

**금지** — `자격증을 취득해 프로젝트 역량을 갖췄다`는 인과는 쓰지 않는다. 여러 시험 영역이 익숙했다는 사실을 각 영역의 숙련도나 전문성으로 확대하지 않는다. 위 설계 순서를 모든 프로젝트의 유일한 정답으로 표현하지 않는다.

## 2. 성장 흐름 — 세 개의 닫힌 루프

문제 인식이 다음 판의 실제 행동으로 이어진 사례가 세 건이다. **서사를 만들기 위해 묶은 것이 아니라 각각 출처가 다르다.**

| 입력 | 행동 | 결과 | 근거 |
| --- | --- | --- | --- |
| GP 복무 중 이대로는 살아남기 어렵겠다는 판단 | 토익과 알고리즘 공부 | 편입 성공 → 학점 관리 → FIS 아카데미 → SSAFY | `[답변]` 편입·졸업은 이력으로 확인 가능 |
| 운영 도구가 퍼블릭 환경에 노출된 아쉬움 | 내부망 기반 개인 서버 구축 | 팀 프로젝트 CI/CD로 재투입 | `[실물]` Notion에 기록 |
| 문서만으로는 팀원이 숙지하기 어렵다는 회고 | Docker·SonarQube·CI/CD 설명회 개최 | 팀원 반응 확인 | `[답변]` Notion에 기록 없음 |

**입력의 종류가 자기 회고, 아쉬움, 외부 조언으로 서로 다르다는 점이 중요하다.** 한 가지 동기로 설명되지 않는다.

### 프로젝트 간 인과

```
TeenyFinny                개인 서버                  데일밴드
─────────────────────────────────────────────────────────────
계약 우선 성공        →                        →  계약 붕괴와 복구
운영 도구 퍼블릭 노출  →  접근 경로 분리          →  Private Runner·
  아쉬움                  (VPN / Tunnel)           Public SonarQube
문서만으로 부족       →                        →  설명회 개최
웹소켓·폴링 중재      →                        →  방 관리 폴링 회귀
JWT stateless 선택    →  이중화 이점 체감        →
```

**핵심은 `처음 몰랐다가 배웠다`가 아니다.** TeenyFinny에서 계약 우선 방식을 이미 성공시켰는데, 데일밴드에서는 처음 다루는 C/C++ 애드온의 구조를 예측할 수 없어 지키지 못했다. **효과를 이미 알던 원칙도 불확실성이 큰 환경에서는 지키기 어려웠고, 그 비용과 복구 과정을 직접 겪었다**는 이야기다.

C/C++ 기술 자체가 문제였다고 쓰지 않는다. **처음 다루는 애드온 구조의 불확실성**과 **합의된 연결 계약의 부재**를 구분한다.

## 3. 핵심 주장 후보

### 현재 Notion 상태

첫 콘텐츠 블록이 `직접 해보는 개발자` + 연락처다. **목표 직무도 직무 관련 구체 강점도 문자로 없다.**

### 후보 방향

> **팀이 함께 쓸 기준을 만드는 백엔드 개발자**

이 후보를 택하는 이유는 빈도가 아니라 근거다. **서로 다른 다섯 개의 행동이 같은 형태로 수렴하고 세 프로젝트에 걸쳐 반복된다.**

| 만든 기준 | 실물 |
| --- | --- |
| 코드 규약 | API 명세 규격에 맞춘 `BaseEntity` · `BaseException` · JWT 인증 세팅 |
| 협업 규약 | 이슈·PR 템플릿 정의, 기술 문서 관리 |
| 품질 기준 | SonarQube Quality Gate, 커버리지 컷 80%, Jacoco 연동, 실제 MR 차단 |
| 개발 환경 | 개인 서버에 GitLab Runner·SonarQube 호스팅 |
| 판단 근거 | 레이턴시 구간 분석 문서, 직접 그린 다이어그램, 설명회 |

**이점**
- 인프라 경험이 `백엔드인데 인프라도 한다`가 아니라 **같은 성향의 다른 표현**으로 읽힌다
- 인프라 지향과 백엔드 지원이라는 이중 지원 문제를 하나의 주장으로 처리한다
- 개인 서버 프로젝트가 취미가 아니라 주장의 일부가 된다

### 3회차 이후 함께 비교할 방향

데일밴드 저장소 확인으로 DB 설계·트랜잭션 경계·캐시 정합성·보안 재료가 확보되면서 **더 백엔드다운 방향이 가능해졌다.** 아래를 함께 놓고 비교한다.

- `계약과 검증으로 복잡한 통합을 수습하는 백엔드 개발자`
- `구현 사이의 책임과 경계를 명확히 하는 백엔드 개발자`
- `팀이 함께 쓸 기준을 만드는 백엔드 개발자` (현행 후보)

**최종 문장은 확정하지 않았다.**

### 앵커 단어 회수 계획

첫 블록에서 굵게 쓴 단어를 **동의어로 바꾸지 않고 문자 그대로** 아래 층에서 반복한다.

| 앵커 | Projects에서 | Detail에서 |
| --- | --- | --- |
| **기준** | 세 프로젝트에 각각 `만든 기준` 항목 | 코드 규약, 품질 기준, 접근 정책의 실물 |
| **경계** | BE·FE·AI·Storage 책임 분리 | 조정 경로 설계, 트랜잭션 경계, Public·Private 경로 |
| **검증** | 각 프로젝트의 `확인한 결과` | 장애 주입, MR 차단, 무결성 대조, 접근 경로 확인 |

## 4. 목표 직무와 포지셔닝

**본인 상태** `[답변]`
- 마음은 인프라와 DevOps다
- 신입 대상 인프라·운영 포지션이 적어 백엔드와 인프라 양쪽에 지원하고 있다
- 본인은 이를 약점으로 인식한다

**합의된 포지셔닝** — 포트폴리오는 하나로 유지하고 **`인프라를 아는 백엔드`** 방향으로 간다. 역방향은 신입 운영 포지션이 적어 지원 범위가 좁아진다.

이 방향은 발굴된 근거와 일치한다. **모든 인프라 작업의 목적이 인프라 자체가 아니라 개발과 서비스였다.**

| 한 일 | 목적 |
| --- | --- |
| SonarQube 게이트 | 팀이 애플리케이션 코드를 신뢰하기 위해 |
| 개인 서버 CI/CD 호스팅 | 팀원이 개발에 집중하기 위해 |
| Failover 장애 주입 | 쓰기 요청이 실패하는지 확인하기 위해 |
| 레이턴시 구간 분석 | 기능 구현 방향을 결정하기 위해 |

대규모 트래픽·SLO 중심의 SRE 지향이 아니라 **개발팀을 돕는 플랫폼 엔지니어링 성향의 백엔드**다.

**대가** — 백엔드로 지원하면 도메인 설계, API 설계, 쿼리, 테스트를 반드시 확인받는다. 데일밴드 저장소에서 상당 부분 확보됐으나 **TeenyFinny에는 기능 모듈 구현 경험이 없다는 사실은 변하지 않는다.**

**왜 인프라를 계속 맡았나** `[답변]`
처음에는 팀원들이 잘 모르는 분야라 꺼려해서 나선 것에 가까웠다. 이후 동기가 바뀌었다 — 재미가 있었고, 인프라 지식의 유무가 개발 실력에 큰 차이를 만든다는 것을 알게 됐으며, DevOps로 따라오는 팀 생산성 향상도 이유였다. 나중에는 **본인이 계속 맡는 것이 팀원의 학습 기회를 빼앗는다고 느껴 설명회를 열었다.**

동기의 변화를 정직하게 설명할 수 있다는 점, 자기 전문 영역의 독점을 팀의 손실로 인식했다는 점이 재료다.

## 5. 지식을 팀에 넘기는 방식

**설명회** `[답변]`
Docker, SonarQube, CI/CD 등 여러 주제로 설명회를 열고 문서로 정리했다. **구두와 종이로 진행했으며 자료는 남아 있지 않다.**

**처리 방침** — 검증 근거가 없으므로 **결과나 성과로 서술하지 않고 행동으로만 기록한다.** 같은 주장을 뒷받침할 확인 가능한 근거가 따로 있다.

| 근거 | 상태 |
| --- | --- |
| TeenyFinny 공유 문서 `Teenyfinny의 분산환경 세팅` | `[실물]` Notion 하위 페이지 |
| 데일밴드 `기술 조사 및 문서화`, `기술 조사 결과 문서화 및 팀 공유` | `[실물]` Notion 담당 업무 기재 |
| 레이턴시 구간 분석 문서와 직접 그린 다이어그램 2장 | `[실물]` 로컬 이미지 |

**`지식을 혼자 쌓지 않고 팀에 넘겼다`는 주장의 대표 근거는 남아 있는 문서로 세우고, 설명회는 그 문서를 보완한 행동으로 배치한다.**

## 6. About 초안

첫 주장을 준비하는 맥락으로만 사용한다. **두 문장 이내, 성적 언급 금지.**

> 전북대학교 컴퓨터공학과를 졸업했습니다. 군 복무 중 진로를 다시 정하고 편입을 준비해 학업을 이어갔고, 이후 우리 FIS 아카데미와 삼성 청년 SW·AI 아카데미를 거치며 금융 도메인과 팀 개발을 경험했습니다.
>
> 세 프로젝트에서 반복된 것은 같은 습관입니다. 아쉬웠던 점을 다음 프로젝트의 기준으로 만드는 것입니다. 운영 도구가 외부에 노출된 아쉬움은 내부망 개인 서버가 되었고, 문서만으로는 팀에 전달되지 않는다는 회고는 설명회가 되었습니다.

**서술 제한**
- 학력은 `중퇴`가 아니라 편입 사실로 쓴다
- 군 복무 서사는 한 절로 제한한다. 상세는 쓰지 않는다
- `되는대로 살았다` 같은 표현은 그대로 쓰지 않는다. 전환의 계기와 실제 행동(토익·알고리즘·편입 합격)만 남긴다
- 성적은 근거로 제시할 수 없고 불필요한 약점을 노출하므로 쓰지 않는다

## 7. 첫 콘텐츠 블록 잠정 문안

> # 이정복 · 백엔드 개발자
>
> 팀이 함께 쓸 **기준**과 연결 **경계**를 만드는 일을 해왔습니다.
> API 명세와 실행 가능한 Mock Server로 네 컴포넌트의 계약을 복구했고,
> 개인 서버의 Runner와 SonarQube로 팀의 품질 기준이 실제 개발 흐름에서 작동하게 했습니다.

**사용하지 않는 표현** — `직접 해보는 개발자`, `성장하는`, `도전하는`, `항상 새로운 것을 배우는`. 추상적 성향 선언은 목표 직무와 구체 강점을 대체하지 못한다.

**미확정** — `네 컴포넌트`가 첫 화면에서 과도하게 상세하면 Projects 문장으로 내린다. 실제 렌더를 보기 전에는 위치를 확정하지 않는다.

## 8. 바로 쓸 수 있는 문장

사실 범위 안에서 검증된 문장 후보다.

- `TeenyFinny에서는 API 명세와 Mock Server를 먼저 만들어 프론트엔드와 백엔드가 같은 계약 위에서 병행 작업하도록 했습니다.`
- `데일밴드에서는 선행 계약을 충분히 만들지 못했고, BE·시그널링·FE·AI의 형식 불일치를 복구하는 데 1주가 들었습니다.`
- `기존 BE를 역분석해 텍스트 계약을 복원하고, FastAPI Mock Server와 API Docs를 실행 가능한 공통 기준으로 만들었습니다.`
- `원본 음원 한 개가 결과 MP3 다섯 개로 분리되는 흐름에서 BE가 파일을 중계하지 않도록, FE와 AI가 스토리지에 직접 업로드하고 BE는 비동기 작업을 조정하게 했습니다.`
- `클라이언트가 스토리지에 직접 업로드하면 서버는 무엇이 올라갔는지 알 수 없으므로, 업로드 전 해시를 선언받고 업로드 후 대조해 검증했습니다.`
- `분석 작업을 DB에 기록하는 것과 외부 워커에 보내는 것은 다른 시스템이므로, 커밋이 확정된 뒤에만 디스패치하고 누락은 주기적 재조정으로 회수했습니다.`
- `파일 메타데이터를 공통 테이블로 분리하자는 제안이 팀에서 회의적이었지만, 중복 컬럼과 실제 사례를 근거로 설득해 채택했고 최종 구현에서 열 개 테이블이 이를 참조합니다.`
- `동일 내부망의 두 피어에서 하드웨어 지연을 제외한 RTT를 10회 측정해 평균 약 10ms를 확인했습니다.`
- `실사용 중 Wi-Fi 음 끊김을 확인했고, 지터 버퍼를 20ms에서 40ms로 조정했습니다. 이후 끊김은 사라지는 대신 체감 지연이 조금 증가했습니다.`
- `Active DB를 직접 중단해 읽기는 유지되고 쓰기는 지연되는 결과를 구분해 확인했습니다.`
- `공개 필요 여부에 따라 내부 서비스는 VPN, 공개 서비스는 Tunnel과 Nginx 경로로 나눴습니다.`
- `구조 변경 뒤 기존 공인 포트 차단, VPN 내부 접속, 공개 서비스 접속을 각각 직접 확인했습니다.`

## 9. 통합 금지 문장

프로젝트별 금지 문장은 각 재료 파일에 있다. 아래는 전체에 걸친 것이다.

- `직접 해보는 개발자` 같은 추상적 성향 선언을 첫 주장으로 쓰는 것
- 기능 목록·기술 로고·숙련도 그래프로 근거를 대체하는 것
- 담당 업무를 나열하는 것 (`PL, 인프라, 기술발표, BE, FE`) — 행동으로 서술한다
- 팀 결과를 본인 기여로 읽히게 배치하는 것
- 측정하지 않은 개선을 비율·시간으로 환산하는 것
- 기업 경력자의 증거 규모를 개인·교육 프로젝트에 투영하는 표현
- 회고를 `다음에 해보고 싶다`로만 끝내는 것 — 이미 실행한 개선이 있으면 그것으로 닫는다
- 비공개 저장소의 코드·명세·캡처를 허가 없이 게시하는 것

## 10. 서술 기준 — 프로젝트 상세의 여섯 요소

각 프로젝트 상세는 아래 여섯 요소를 갖춘다. **`판단`과 `결과·검증`이 모두 있어야 한다.** 둘 중 하나라도 없으면 그 항목은 상세로 쓰지 않는다.

1. 맥락 또는 문제
2. 제약 또는 선택지
3. 본인 역할과 행동
4. **선택 이유 또는 판단**
5. **결과 또는 검증 근거**
6. 한계·회고 또는 다음 변화

세 재료 파일의 각 항목이 `상황 / 구현 / 판단 / 검증 / 한계 / 활용` 형식을 쓰는 이유가 이것이다. 그대로 옮기면 여섯 요소가 채워진다.

### 실제 포트폴리오 관찰에서 나온 주의

한국어 포트폴리오 50개를 같은 기준으로 확인한 결과다. **빈도는 효과의 증명이 아니라 자주 관찰된 선택을 뜻한다.**

| 자주 관찰된 것 | 50개 중 | 위험 |
| --- | ---: | --- |
| 첫 문장이 직무 선언만 하고 강점은 뒤로 미룸 | 26 | 첫 화면에서 판단 근거가 안 보임 |
| 프로젝트가 기능·기술 목록으로만 제시됨 | 20 | 판단·증거 항목이 불명확으로 떨어짐 |
| 상세 근거가 사이트 밖(GitHub·PDF)으로 나감 | 18 | 이동 단계가 늘고 근거가 사라질 수 있음 |
| 성향·태도 수식어를 첫 화면에 먼저 배치 | 12 | 목표 직무를 가림 |

| 드물지만 강한 것 | 50개 중 |
| --- | ---: |
| 문제·해결·결과를 문자 라벨로 고정 | 8 |
| 별도 프로젝트 상세 페이지를 둠 | 8 |
| **채택하지 않은 대안을 이유와 함께 남김** | **4** |
| **한계·회고를 문자로 남김** | **3** |

**아래 둘은 이 포트폴리오의 강점이다.** 채택하지 않은 대안(웹소켓·폴링, BE 중계·직접 업로드, 포트포워딩·VPN·Tunnel, WebRTC·AOO)과 한계 서술이 프로젝트마다 있다.

### 같은 장치가 메시지를 흐린 반례

- 별도 상세 페이지를 두었으나 상세에 근거가 없어 이동이 판단을 진전시키지 못한 경우
- 결과 수치가 많으나 **그 수치를 만든 선택이 없어** 재현 가능한 판단으로 읽히지 않은 경우
- 프로젝트 판단·증거는 명확하지만 **첫 주장 문장 자체가 없어** 누가 어떤 직무로 지원하는지 문서가 답하지 못한 경우
- 첫 주장은 명확하나 **프로젝트가 그 주장을 확인해 주지 않은** 경우
- 직무 선언은 백엔드인데 프로젝트를 넓게 묶어 첫 주장과 배치가 어긋난 경우
- 근거 섹션을 가장 뒤에 두고 연락처를 첫 섹션에 둔 경우

## 11. 면접 예상 반문 종합

프로젝트별 반문은 각 재료 파일의 `활용` 항목에 있다. 아래는 프로젝트를 가로지르는 것이다.

| 예상 질문 | 준비 방향 |
| --- | --- |
| 인프라를 하고 싶은가 백엔드를 하고 싶은가 | 팀이 함께 쓸 기준을 만드는 일을 해왔고 그 일이 백엔드와 인프라의 경계에 있었다고 답한다. JWT와 이중화, HealthCheck와 무중단 배포를 사례로 든다 |
| 실제 기능 개발은 해봤나 | 데일밴드 고스트 기능으로 답한다. 비동기 + 외부 스토리지 + 3자 연동 구조를 설명한다. TeenyFinny에서 기능 모듈을 구현하지 않았다는 사실은 숨기지 않는다 |
| AI로 짠 코드 아닌가 | 구조 설계는 본인, 세부 로직은 AI 생성 후 리뷰라고 답한다. 커밋 분포로 뒷받침한다. 그리고 **AI가 만든 결과를 무엇으로 신뢰할지가 이 프로젝트의 문제 정의였다**고 연결한다 |
| 팀 프로젝트에서 본인 몫은 어디까지인가 | 각 재료 파일의 `본인 기여와 팀 결과의 경계`를 그대로 말한다 |
| 왜 자꾸 인프라를 맡았나 | 처음엔 팀원이 꺼려서, 이후엔 재미와 실력 차이 인식, 나중엔 팀 생산성. 그리고 독점이 팀의 학습 기회를 빼앗는다고 느껴 설명회를 열었다고 답한다 |
| 이 포트폴리오에서 가장 아쉬운 점은 | 측정하지 않은 것들을 든다. 부하 절감, 무중단 배포 검증, 가동률. 갖춰둔 도구(k6·InfluxDB)는 있으나 프로젝트에 적용하지 못했다고 말한다 |
