## 1. 재료 목록

### 1.1 모든 것을 숨기지 않고 공개 필요에 따라 경로를 나누기

**상황**
이전 프로젝트에서 운영 도구가 Public 환경에 있었던 점이 아쉬웠는데, 정작 개인 서버를 처음 만들 때도 모든 서비스를 포트포워딩으로 열었다. SSH나 비밀번호 관리자처럼 외부에 노출할 이유가 없는 서비스까지 공개된 상태였다.

**구현**
외부 접근 방식으로 포트포워딩·터널링·VPN을 비교한 뒤 서비스 성격에 따라 경로를 나눴다. SSH·비밀번호 관리자 등 내부용은 **Tailscale VPN으로만** 접근하게 하고, 공개가 필요한 서비스는 포트포워딩을 해제하고 **Cloudflare Tunnel에서 Nginx로** 전달하도록 바꿨다. Cloudflare의 트래픽 모니터링과 캐시 기능도 함께 활용한다. `[실물]` Notion `04. 구축 중 이슈 — 외부 접근 방식 선정`

**판단**
접근 기술 하나를 모든 서비스에 통일하지 않고 **공개 필요 여부와 사용 주체를 기준으로** 경로를 결정했다. 모두 VPN 뒤로 숨기면 팀원이 써야 하는 SonarQube와 공개 서비스의 접근성이 떨어지고, 모두 공개하면 운영 도구의 노출 범위가 커진다.

포트포워딩을 걷어낸 실무적 이유도 있었다. 일부 Well-Known Port는 **통신사 환경에서 포워딩이 제한**되었고, 공유기나 회선이 바뀌면 설정을 다시 잡아야 했다. Cloudflare Tunnel은 이런 환경 의존성을 줄여준다. `[실물]` `[답변]`

**검증**
구조 변경 뒤 세 가지를 각각 직접 확인했다. `[답변]`
1. 공유기 설정과 웹 포트 확인 서비스, 실제 주소 접속으로 **기존 공인 포트가 닫힌 것** 확인
2. Tailscale 연결 후 **내부 서비스 접속 성공**
3. 외부망에서 **`roodev.me` 정상 응답** — `200 OK`와 Cloudflare 헤더 확인 `[실물]`

**한계**
실제 침해나 비인가 접근은 없었다. 따라서 침해 대응 사례가 아니라 **학습 후 위험을 재평가한 예방적 개선**이다. `제로 트러스트 전체 구현`이라고 쓰지 않는다. 비인가 접근이 없었다는 사실도 안전성의 증명이 아니며, 모든 포트의 보안성을 검증한 것도 아니다.

**활용**
**Projects의 대표 항목.** `기준`·`경계` 앵커를 회수하는 자리. 성장 흐름에서 이전 프로젝트의 아쉬움을 받는 지점이자, 다음 팀 프로젝트로 재투입되는 출발점.

### 1.2 Docker Published Port가 방화벽을 우회한다는 것을 확인하고 막기

**상황**
Docker로 여러 서비스를 운영하던 중, 컨테이너의 Published Port가 UFW 같은 호스트 방화벽 정책과 **별개로 외부에 노출될 수 있다**는 점을 확인했다.

**구현**
외부에서 직접 접근할 필요가 없는 컨테이너는 포트를 열지 않고 Docker Network 내부에서 Nginx를 통해서만 접근하도록 구성했다. 관련 서비스는 Docker Compose 단위로 묶고 필요한 컨테이너끼리만 통신하도록 네트워크를 나눴다. `/var/run/docker.sock`을 넘기는 Docker-outside-of-Docker 구성도 필요한 경우에만 사용해 **컨테이너가 호스트 Docker를 제어할 수 있는 범위를 줄였다.** `[실물]` Notion `04. 구축 중 이슈 — Docker 기반 서비스 운영`

**판단**
방화벽 규칙을 믿고 끝내지 않고 **실제 노출 경로를 확인한 뒤 구성으로 막았다.**

**검증**
서비스별 실행 환경과 네트워크를 분리하면서 불필요한 외부 노출을 줄이고, 필요한 환경을 빠르게 구성·재배포할 수 있게 되었다. `[실물]` `[답변]`

**한계**
`모든 컨테이너를 격리했다`고 쓰지 않는다. 외부 접근이 필요한 컨테이너는 여전히 공개 경로에 있다.

**활용**
1.1의 하위 근거. **`도구를 썼다`가 아니라 `도구의 기본 동작이 만드는 빈틈을 확인했다`** 는 점이 차별점이다. 면접에서 Docker 보안 질문이 나오면 이 사례로 답한다.

### 1.3 장애를 메트릭으로 좁히고 자동화로 막기

**상황**
VPN을 통한 내부망 접속이 갑자기 막혔다.

**구현**
시스템 메트릭과 서비스 상태를 먼저 확인해 **서버 노드 자체의 문제가 아님**을 파악했다. 집에서는 내부망 접속이 되지만 VPN 경유만 차단된다는 점에서 Tailscale 문제로 좁혔다. 원인은 **Tailscale node key의 만료**(기본 주기 180일)였다. 만료 주기보다 짧은 간격으로 갱신하는 셸 스크립트를 작성해 재발을 막았다. `[답변]`

**판단**
**만료 기능을 끄지 않고 갱신을 자동화하는 쪽을 택했다.** 만료 기능이 존재하는 데는 이유가 있다고 보았기 때문이다. `[답변]`

**검증**
자동화 이후 같은 장애가 재발하지 않았다. `[답변]`

**한계**
**`인증서가 만료되었다`고 쓰지 않는다. node key 만료다.** 다른 프로젝트의 사설 CA 인증서 이슈와 용어가 섞이면 신뢰도가 떨어진다. 정석은 tagged device 방식임을 알고 있으나 지금도 만료 제거는 택하지 않는다.

**활용**
**진단 경로 자체가 재료다.** `메트릭 확인 → 서버 노드 배제 → 경로 대조 → 원인 특정 → 자동화`. 신입이 장애 대응 서사를 구조적으로 말할 수 있는 흔치 않은 사례.

면접 반문 `key expiry를 끄면 되지 않나요?` → 만료 기능이 있는 이유가 있다고 보아 갱신을 자동화했다고 답하고, tagged device가 정석임을 알고 있다고 덧붙인다.

### 1.4 필요에 따라 모니터링을 계층화하기

**상황**
서비스가 늘어날수록 각 컨테이너에 직접 접속해 로그와 메트릭을 확인하는 방식은 관리하기 어려웠다.

**구현**
처음에는 **Uptime Kuma로 서비스 동작 여부만** 확인했으나 메트릭과 로그까지 보기에는 한계가 있었다. Grafana를 중심으로 **Prometheus와 Loki**를 연동해 메트릭과 로그를 한곳에서 확인하도록 구성했고, **Node Exporter**로 미니 PC의 CPU·메모리·디스크 등 시스템 메트릭도 수집·시각화했다. 추가로 **InfluxDB를 연동해 k6 부하 테스트 결과**도 Grafana에서 확인할 수 있게 했다. `[실물]` Notion `04. 구축 중 이슈 — 모니터링 시스템 구축`, 대시보드 이미지 2장

**판단**
처음부터 큰 스택을 세우지 않고 **Uptime Kuma로 시작해 한계를 만난 뒤 확장했다.** 도구 취향이 아니라 관측 대상의 범위(동작 여부 → 메트릭·로그 → 시스템 자원 → 부하 결과)가 늘어난 결과다.

**검증**
문제 발생 시 서비스를 일일이 확인하지 않고 전체 상태와 로그를 한곳에서 보며 원인을 찾을 수 있게 되었다. **실제로 1.3의 장애 진단에서 이 환경을 사용했다.** `[실물]` `[답변]`

**한계**
가동률 수치를 말하려면 Uptime Kuma 또는 Grafana 캡처가 필요하다. `[미확인]` **`8개월 무사고 운영`은 근거 확보 전까지 쓰지 않는다.**

**활용**
1.3과 짝을 이룬다. 모니터링을 갖췄다는 사실보다 **그것으로 실제 장애를 좁혔다**는 점이 근거다. k6·InfluxDB는 부하 테스트 도구를 갖추고 있다는 근거로 쓸 수 있다.

### 1.5 모니터링의 사각지대를 스스로 특정하기

**상황**
1.3의 장애는 알림으로 감지되지 않았다.

**구현**
멘토의 `모니터링 다음에는 알림을 구현하라`는 조언을 받아 알림을 구성했고, 컨테이너 상태 변화 알림을 실제로 수신했다. `[답변]`

**판단**
장애가 알림에 걸리지 않은 이유를 분석했다. **서버와 컨테이너는 정상이었고 실패한 것은 외부 접근 경로였다.** 내부 메트릭은 감시하지만 밖에서 실제로 접근이 되는지는 감시하지 않고 있었다.

**검증**
컨테이너 상태 변화 알림 수신 확인. `[답변]`

**한계**
알림 컴포넌트가 Alertmanager인지 서버에서 확인되지 않았다. `[미확인]` 확인 전에는 `알림을 붙였습니다`로만 쓰고 **컴포넌트명을 명시하지 않는다.** 외부 접근 프로브는 아직 추가하지 않았다.

**활용**
**한계를 스스로 특정한 사례.** `다음에 해보고 싶다`가 아니라 **`무엇이 왜 감지되지 않았는지`** 를 말한다는 점이 차이다. 회고가 미완 목록으로 끝나지 않는다.

### 1.6 개인 학습 환경을 팀 개발 환경으로 재투입하기

**상황**
개인 서버를 서비스 호스팅 용도로만 쓰지 않고 팀 프로젝트에 활용하고 싶었다.

**구현**
GitLab Runner, GitHub Actions Runner, Jenkins, SonarQube를 직접 호스팅해 팀 프로젝트용 개발 환경을 구축했다. 실제 팀 프로젝트에 적용해 빌드·테스트·정적 분석·배포를 자동화했고, 프로젝트마다 반복되는 환경 구성과 배포 작업을 줄였다. `[실물]` Notion `04. 구축 중 이슈 — 팀 프로젝트 개발 환경 구축`

**판단**
서비스별 공개 범위에 맞춰 배치를 나눴다. **GitLab Runner는 Private에 두고 outbound로 작업을 가져오게 했다.** SonarQube는 팀원이 열람해야 하므로 Public 접점에 두되 권한으로 범위를 나눴다. Grafana는 Tailscale 전용으로 옮겼다. `[답변]` GitLab 공식 문서로 outbound 방식 확인

**검증**
팀원들이 개발 환경 구성 없이 개발에 집중할 수 있었고, 이 서버의 SonarQube를 실제 팀 프로젝트에서 사용했다. `[답변]`

**한계**
**Jenkins는 현재 중지 상태**이며 CI는 GitLab Runner 중심으로 운영한다. `Jenkins를 현재 운영 중이다`라고 쓰지 않는다. 최초 상담의 `Public Runner` 답변은 본인 정정으로 폐기됐다.

**활용**
**성장 흐름의 완결점.** 이전 프로젝트의 아쉬움 → 개인 서버 → 팀 개발 환경 재투입. `개인 서버` 앵커가 취미가 아니라 주장의 일부가 되는 지점이며, **학습을 실제 생산성 개선으로 연결했다**는 서술의 근거다.

### 1.7 공동 소유 프로젝트에 맞는 권한 단위 정하기

**상황**
SonarQube를 Public 접점에 두면서 열람 범위를 정해야 했다.

**구현**
프로젝트별 공용 계정을 만들고 프로젝트 단위 권한으로 열람 범위를 나눴다. Grafana는 Tailscale 전용으로 옮기면서 `admin/1234` 자격증명을 복잡한 ID와 비밀번호로 함께 바꿨다. `[답변]`

**판단**
교육 과정의 공동 소유 프로젝트라는 맥락에 맞춰 개인 계정이 아닌 **프로젝트 단위 공용 계정**을 선택했다.

**검증**
팀 프로젝트에서 실제로 사용되었다. `[답변]`

**한계**
**이를 기업 자산의 개인별 감사 추적 기준으로 평가하지 않는다.** 공용 계정은 누가 무엇을 했는지 추적할 수 없다. `admin/1234`를 바꿨다는 사실은 기본 자격증명 위험을 인지했다는 근거로 쓸 수 있으나, **그것을 방치했던 기간이 있었다는 뜻이기도 하므로 자랑으로 쓰지 않는다.**

**활용**
면접에서 `공용 계정을 쓰면 감사 추적이 안 되지 않나요?`가 나올 수 있다. **한계를 먼저 인정하고 맥락을 설명하는 방식**으로 준비한다.

### 1.8 24시간 운영을 기준으로 하드웨어를 고르기

**상황**
개인 서버를 상시 가동해야 했다.

**구현**
firebat t8 plus(N100 · DDR5 16GB · SSD 512GB)를 선택하고 Ubuntu 24.04.3 LTS로 구성했다. `[실물]` Notion `02. 서버 스펙 소개`, 실물 사진

**판단**
24시간 운영을 고려해 **성능 대비 전력 효율을 우선순위로** 두고 장비를 선택했다. `[실물]`

**검증**

## 3. 금지 문장

- `제로 트러스트를 완전히 구현했다.`
- `모든 운영 도구를 내부망에 격리했다.` — SonarQube는 Public 접점
- `비인가 접근이 없었으므로 보안성이 검증됐다.`
- `8개월 무사고 운영` — 가동률 캡처 확보 전 금지
- `Jenkins를 현재 운영 중이다.` — 중지 상태
- `Public Runner를 사용한다.` — 폐기된 진술, Private + outbound가 맞음
- `인증서가 6개월마다 만료된다.` — Tailscale **node key** 만료(180일)
- `Alertmanager로 알림을 구성했다.` — 컴포넌트 확인 전 금지
- `모든 컨테이너를 격리했다.`
- 침해 대응 사례로 서술하는 것 — 예방적 개선이다
