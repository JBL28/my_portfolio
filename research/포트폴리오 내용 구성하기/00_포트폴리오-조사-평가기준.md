# 한국어 포트폴리오 전달 전략 100개 조사 기준

## 1. 조사 목적

실제 한국어 포트폴리오가 **어떤 페이지에서 어떤 메시지를 먼저 제시하고, 어떤 순서의 근거로 지원자에 대한 판단을 만들도록 구성되었는지** 추적하여 이정복 포트폴리오의 구조와 의도를 설명할 수 있는 근거를 만든다.

이 조사는 예쁜 화면을 모으거나 포트폴리오가 채용 성공을 일으켰다는 인과관계를 증명하기 위한 것이 아니다. 공개된 포트폴리오에서 관찰되는 전달 장치, 구조, 문장과 반례를 비교하는 정성 조사다.

## 2. 고정 원칙

- 실제 공개 URL을 직접 열어 확인한 내용만 기록한다.
- 검색 결과 요약만 본 페이지는 완료 사례에 포함하지 않는다.
- 페이지가 여러 개면 Home, About/Experience, Projects와 공개된 Project Detail을 모두 확인한다.
- 현업 경력, 수상, 합격 후기는 작성자의 배경 정보로만 기록하며 포트폴리오 효과의 인과 근거로 사용하지 않는다.
- 관찰 사실, 평가자 해석, 이정복 포트폴리오 적용 후보를 서로 다른 블록에 기록한다.
- 실제 렌더링을 확인하지 못하면 시각 항목은 반드시 "평가불가"다.
- 총점과 순위를 만들지 않는다.
- 좋은 문장을 복제하지 않고 문장의 역할과 앞뒤 연결 방식만 분석한다.
- 100개 조사가 끝나기 전에는 최종 Home, Projects, Project Detail 구조를 확정하지 않는다.
- 최종 콘텐츠에는 Notion에 기록된 이정복의 사실과 이미지만 사용한다.

## 3. 표본 구성

### 3.1 직군 할당

100개 사례가 한 직군의 관습에 치우치지 않도록 다음 구성을 목표로 한다.

| 직군 | 목표 |
| --- | ---: |
| 백엔드·인프라 | 40 |
| 프론트엔드·풀스택 | 30 |
| 데이터·AI·모바일 | 15 |
| 제품·UX·기술 문서 | 15 |

할당 수는 비교 범위를 위한 목표이며 특정 직군에서 실제 접근 가능한 사례가 부족하면 변경 사유와 날짜를 기록한다.

### 3.2 발견 경로

사례마다 최초 발견 경로를 기록한다.

- 개인 도메인, GitHub Pages, Vercel 등 공개 개인 사이트
- 공개 Notion 포트폴리오
- 채용·합격 회고에서 연결된 포트폴리오
- 개발 커뮤니티, 수상자, 발표자, 교육기관 수료자 페이지에서 연결된 포트폴리오
- 기타 검색 경로

한 발견 경로가 전체 사례의 절반을 넘지 않게 한다. 같은 템플릿과 같은 작성자의 이전 버전은 중복 사례로 세지 않는다.

### 3.3 배경 정보

다음 정보는 표본 설명에만 사용하며 전달 효과 판정에는 사용하지 않는다.

- 현업 경력 확인
- 수상·합격·출시 등 공개 성과
- 포트폴리오가 실제 지원에 사용되었다는 작성자 진술
- 작성 시기와 최근 수정 시기

## 4. 포함·제외 조건

### 4.1 포함

- 한국어가 주요 서술 언어다.
- 개인의 경력, 역량 또는 프로젝트를 채용·협업 목적으로 설명한다.
- 실제 공개 페이지에서 첫 메시지와 프로젝트 근거를 확인할 수 있다.
- 공개된 포트폴리오 하위 페이지의 확인 범위를 기록할 수 있다.

### 4.2 제외

- 템플릿 데모, 제작 강의 실습, 대행사 예시
- 회사나 제품 소개가 주목적이며 개인을 판단할 내용이 없는 사이트
- 로그인 필요, 비공개, 접속 오류, 본문 없음
- 저장소 README만 있고 포트폴리오 페이지가 없는 경우
- 검색 결과 문구만 확인한 경우
- 동일 작성자나 동일 템플릿의 실질적 중복

제외 사례는 URL, 제외 이유, 확인일만 별도 목록에 남긴다.

## 5. 다중 페이지 확인 규칙

페이지가 여러 개인 경우 각 페이지마다 다음을 기록한다.

1. 실제 URL과 페이지 제목
2. 이 페이지가 문자 그대로 답하는 질문
3. 처음 제시하는 주장 또는 정보
4. 페이지 안에서 제시하는 대표 근거
5. 내부 CTA 또는 링크가 넘기는 다음 질문
6. 대표 근거까지 필요한 이동 단계

이동 단계는 다음 기준으로 센다.

- "0단계": 현재 페이지 첫 콘텐츠 블록에서 근거가 보인다.
- "1단계": 같은 페이지의 섹션 이동 또는 한 번의 내부 링크로 도달한다.
- "2단계 이상": 두 번 이상의 내부 이동이 필요하다.
- "도달 불가": 공개된 상세 근거가 없다.

단일 페이지는 주요 섹션을 페이지처럼 나누어 같은 항목을 기록한다.

## 6. 사례 기록의 세 층

### A. 관찰 사실

실제 페이지에서 확인한 문장, 섹션 순서, 링크, 이미지 위치와 이동 단계를 기록한다. 작성자의 의도나 면접관의 반응을 단정하지 않는다.

### B. 평가자 해석

모든 문장은 "추정:"으로 시작한다. 구조가 유도할 가능성이 있는 판단, 메시지의 충돌, 읽기 위험과 반례를 기록한다. 해석은 원문 인용 또는 관찰 항목을 바로 참조해야 한다.

### C. 적용 원리 후보

사례당 최대 한 개만 기록한다. 좋은 점을 억지로 만들지 않으며 후보가 없으면 공란으로 둔다. 100개 조사와 Notion 양방향 대조가 끝나기 전에는 적용 결정이 아니다.

## 7. 여섯 판정 항목의 조작적 정의

각 판정에는 출처별 합계 25단어 이하의 원문 근거 또는 URL·섹션·이동 단계가 반드시 연결되어야 한다. 근거 없이 판정하지 않는다.

"평가불가"는 렌더링 실패, 페이지 소실, 본문 접근 불가처럼 정보가 없을 때만 사용한다. 판단이 애매한 경우에는 "부분적"을 사용하고 이유를 기록한다.

### 7.1 핵심 주장 식별 가능성

첫 콘텐츠 블록은 H1과 바로 인접한 소개 문장 또는 첫 화면에서 가장 먼저 읽히는 텍스트 블록을 뜻한다.

- "명확": 첫 콘텐츠 블록에 목표 직무와 직무에 관련된 구체적인 강점·행동·경험 중 하나가 모두 문자로 명시되어 있다.
- "부분적": 목표 직무 또는 구체적인 강점 중 하나만 있거나 두 정보가 서로 다른 초기 블록에 흩어져 있다.
- "불명확": 이름, 추상적인 성격 표현, 기술 목록만 있고 목표 직무와 구체적인 강점을 식별할 문장이 없다.
- "평가불가": 첫 콘텐츠 블록의 본문을 확인할 수 없다.

### 7.2 핵심 주장과 대표 근거 연결

- "명확": 첫 주장의 핵심 명사·행동어 중 하나가 대표 프로젝트에서 문자 그대로 다시 등장하고, 해당 프로젝트에 본인의 역할 또는 행동과 결과 근거가 함께 있다.
- "부분적": 같은 단어는 등장하지만 역할·행동·결과 중 하나가 없거나, 첫 주장과 대표 프로젝트에 동일한 프로젝트명·도메인명·기술명이 문자 그대로 등장한다.
- "불명확": 첫 주장과 대표 프로젝트 사이에 문자 그대로 공유되는 핵심 단어·프로젝트명·도메인명·기술명이 없거나 프로젝트가 기술·기능 목록으로만 제시된다.
- "평가불가": 첫 주장 또는 대표 프로젝트 본문을 확인할 수 없다.

동의어나 의미상 연결은 A 관찰이 아니라 B 해석에만 "추정:"으로 기록한다.

### 7.3 페이지별 역할과 다음 이동

- "명확": 각 페이지 또는 주요 섹션의 제목·첫 문단이 다루는 주제를 명시하고, 대표 근거나 다음 정보 계층으로 가는 내부 CTA·Anchor가 있다.
- "부분적": 페이지 역할은 제목·첫 문단에서 식별되지만 다음 이동이 없거나, CTA는 있지만 이동한 페이지가 같은 내용을 반복한다.
- "불명확": 페이지별 주제가 구분되지 않고 동일 내용이 반복되거나 프로젝트 근거로 갈 수 있는 내부 이동이 없다.
- "평가불가": 내비게이션이나 하위 페이지를 확인할 수 없다.

### 7.4 프로젝트의 판단·증거 구조

다음 여섯 요소를 문자 그대로 확인한다.

1. 맥락 또는 문제
2. 제약 또는 선택지
3. 본인 역할과 행동
4. 선택 이유 또는 판단
5. 결과 또는 검증 근거
6. 한계·회고 또는 다음 변화

- "명확": 4개 이상이 있고, "선택 이유 또는 판단"과 "결과 또는 검증 근거"가 모두 포함된다.
- "부분적": 2~3개가 있거나 4개 이상이어도 판단과 결과 중 하나가 없다.
- "불명확": 0~1개만 있고 기능·기술 목록이 대부분이다.
- "평가불가": Project Detail 또는 이에 준하는 본문을 확인할 수 없다.

### 7.5 문장 역할과 앞뒤 연결

모든 사례에서 임의로 좋은 문장을 고르지 않고 다음 두 문장만 분석한다.

1. 첫 콘텐츠 블록에서 이름을 제외하고 처음 나오는 완결된 주장 문장. H1 자체가 완결된 문장이면 H1을 사용한다.
2. 대표 프로젝트 상세에서 "판단·선택·접근·결과·회고"라고 문자로 표시된 첫 제목 아래의 첫 완결 문장. 해당 제목이 없으면 Project Detail 본문의 첫 완결 문장을 사용한다. Project Detail이 없으면 다른 좋은 문장으로 대체하지 않고 "없음"으로 기록한다.

두 문장을 각각 "핵심 주장", "전환", "문제", "판단", "행동", "결과", "회고" 중 하나로 분류한다.

- "명확": 두 문장 모두 역할이 문자 내용으로 식별되고, 같은 섹션의 직전·직후 두 블록 안에 문장을 준비하는 맥락 또는 뒷받침하는 근거가 있다.
- "부분적": 한 문장만 조건을 만족하거나, 역할은 식별되지만 앞 맥락이나 뒤 근거 중 하나만 연결되거나 세 블록 이상 떨어져 있다. Project Detail 문장이 "없음"이어도 첫 주장 문장의 연결을 확인할 수 있으면 부분적으로 판정한다.
- "불명확": 두 문장이 모두 추상적인 결론으로 단독 배치되거나, 첫 주장 문장에서 역할과 같은 섹션의 맥락·근거를 찾을 수 없다.
- "평가불가": 연속된 본문 구조를 확인할 수 없다.

직접 인용은 출처별 합계 25단어 이하로 제한하고, 직전·직후 내용은 원문 복제가 아닌 사실 요약으로 기록한다.

### 7.6 시각적 우선순위

데스크톱과 모바일 실제 렌더링을 모두 확인하고 확인 기록을 남긴 경우에만 판정한다.

- "명확": 첫 화면에서 이름·직무·핵심 메시지의 시각 우선순위가 구분되고, 본문·이미지·CTA가 읽기 순서를 가리지 않으며, 프로젝트 상세에서도 제목·근거·TOC의 계층이 유지된다.
- "부분적": 핵심 메시지는 식별되지만 장식, 이미지, 긴 기술 목록 또는 내비게이션이 한 화면 이상에서 읽기 순서를 경쟁한다.
- "불명확": 첫 시각 초점이 지원자 메시지나 프로젝트 근거가 아니고, 데스크톱 또는 모바일에서 정보 순서가 무너진다.
- "평가불가": 실제 렌더링을 한 화면이라도 확인하지 못했다.

## 8. 사례별 최소 기록 양식

| 구분 | 필드 |
| --- | --- |
| 메타 | ID, 이름·직군, 확인일, 발견 경로, 배경 정보 |
| 범위 | 확인한 모든 URL, 전체 공개 페이지 수, 미확인 페이지와 이유 |
| A 관찰 | 첫 주장, 전체 콘텐츠 순서, 페이지별 질문과 CTA, 대표 프로젝트 근거, 이미지 위치 |
| 판정 | 여섯 항목의 판정과 각각의 직접 근거 |
| B 해석 | "추정:"으로 시작하는 구조 의도, 유도 가능 판단, 위험과 반례 |
| C 후보 | 적용 원리 후보 최대 1개 또는 공란 |
| 문장 | 위치, 역할, 앞 맥락, 25단어 이하 인용, 뒤 근거 |
| 완료 | 다중 페이지 확인 완료 여부, 재판정 이력 |

## 9. 판정 드리프트와 조사 운영

### 9.1 파일럿

본 사례 1번을 시작하기 전에 최종 표본에 포함하지 않을 3개 포트폴리오에 여섯 정의를 적용한다. 정의만으로 판정하기 어렵다면 정의를 수정하고 수정 이력을 남긴다.

### 9.2 20개 단위 재판정

20, 40, 60, 80개 완료 시 다음을 수행한다.

- 1번 사례
- 직전 점검 시점의 중간 사례
- 가장 최근 사례

판정이 바뀌면 조사를 멈추고 같은 이유가 적용되는 이전 사례를 즉시 전부 재판정한다.

### 9.3 포화도

20개 단위로 새로 등장한 전달 장치와 반례 수를 기록한다. 100개 조건은 유지하되 뒤 구간에서 새로운 패턴이 거의 나오지 않으면 그 사실도 결과에 기록한다.

### 9.4 빈도 분모

항목별 빈도는 "명확 + 부분적 + 불명확" 사례 수를 분모로 사용한다. "평가불가"는 분모에서 제외하고 제외 수와 사유를 별도로 표시한다.

## 10. 100개 완료 전 금지하는 결론

- 특정 구조가 채용 성공을 만든다는 결론
- 가장 좋은 포트폴리오 또는 점수 순위
- 이정복 포트폴리오의 최종 페이지 순서
- 외부 사례의 문장 복제
- Notion에 없는 수치, 성과, 설명의 추가
- 빈도가 높다는 이유만으로 전략을 적용하는 결정
- 기업 경력자의 증거 규모를 개인·교육 프로젝트에 그대로 투영하는 표현

## 11. 100개 완료 후 종합

다음 순서로만 종합한다.

1. 전달 장치별 평가 가능 사례 수와 관찰 빈도
2. 같은 장치가 메시지를 흐리게 만든 반례
3. 직군·발견 경로별 차이
4. 단일 페이지와 다중 페이지의 정보 계층 차이
5. 첫 주장과 대표 근거의 문자 연결 방식
6. 프로젝트 상세의 판단·증거 요소 조합
7. 새 패턴 출현률과 조사 포화도
8. 이정복 Notion 원문과의 양방향 대조

빈도는 효과의 증명이 아니라 자주 관찰된 선택을 뜻한다.

## 12. Notion 양방향 대조와 설계 추적

### 12.1 조사에서 Notion으로

"조사 패턴 → 반례 → Notion 실제 근거 → 전달할 채용 메시지 → 배치 페이지 → Anchor" 순서로 추적한다.

### 12.2 Notion에서 조사로

"Notion 고유 근거 → 외부 조사에 유사 패턴이 있는지 → 없어도 이정복에게 필요한지 → 필요한 페이지와 순서"를 검토한다.

외부 사례에 없는 전략이라도 이정복의 실제 성장 흐름을 더 정확하게 전달하면 유지할 수 있다.

### 12.3 적용 승인 조건

전달 장치는 다음 조건을 모두 만족할 때만 설계 결정으로 승격한다.

- Notion 원문에 같은 주장을 뒷받침할 실제 문장·기간·이미지·행동이 있다.
- TeenyFinny → 개인 서버 운영 → 데일밴드의 시행착오·판단·개선 흐름을 강화한다.
- 백엔드 개발자의 운영, 안정성, 기술 판단 또는 문서화 역량을 더 명확하게 만든다.
- 기능 설명, 기술 로고, 숙련도 그래프 없이 근거를 전달한다.
- 새 프로젝트가 추가되어도 같은 콘텐츠 모델을 유지할 수 있다.
