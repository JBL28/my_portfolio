# 웹 포트폴리오 본문 작성

## Context

신입 백엔드 개발자의 채용용 웹 포트폴리오에 들어갈 본문을 쓴다. 재료는 `research/포폴재료_*.md` 네 개에 정리를 마쳤고, 슬로건과 프로젝트 배치 순서도 확정됐다.

구조안을 두 번 썼고 두 번 다 폐기했다. 원인은 세 가지다.

1. 개요 없이 바로 완성문을 시도해서 구조와 표현이 뒤엉켰다
2. 재료 파일의 과장 금지 규칙을 문안에 그대로 옮겨 자백문이 됐다
3. 번역투가 남았다

작문의 표준 순서(주제 → 개요 → 초고 → 퇴고)를 지켜 단계를 분리한다. 개요 단계에서는 뼈대만, 초고 단계에서는 표현에 얽매이지 않고 칸을 채우고, 퇴고에서 구조 → 흐름 → 문장 순으로 손본다.

## 확정된 전제

- 슬로건: `팀이 함께 쓸 기준을 만드는 백엔드 개발자`
- 프로젝트 순서: 시간순 (TeenyFinny → 개인 서버 → 데일밴드), 데일밴드가 대표
- 형태: Home 단일 스크롤 + 프로젝트 상세 3개
- 성장은 프로젝트 사이의 연결과 난이도 상승으로 보여준다. 자기비판으로 만들지 않는다

## 산출물

`research/포폴초안.md` 하나. **사이트에 그대로 넣을 본문만 담는다.**

### 군더더기의 정의

군더더기란 개발자 본인이나 작업자에게 설명하는 글, 그리고 AI 에이전트를 위한 글이다. 아래는 한 줄도 넣지 않는다.

- `설계 의도`, `노린 것`, `이 문안이 충족하는 판정` 같은 해설 블록
- 참고한 사례 표, 출처 표기, 적용 근거 설명
- 평가 기준 항목 번호나 판정 용어
- 문서 상단의 HTML 주석, 파일 성격 설명
- 남은 결정 목록, 다음 할 일, 확인 필요 항목
- 재료 파일이나 다른 문서로 가는 링크

파일을 열었을 때 **채용 담당자가 사이트에서 읽을 문장만** 있어야 한다.

## 레퍼런스를 쓰는 방식

자료 조사는 개요 작성 전에 끝낸다(완료). 모방은 베낀 다음 비교하는 과정에서 효과가 난다. 그래서 레퍼런스는 두 지점에서만 쓰고, 초고를 쓰는 동안에는 보지 않는다.

| 시점 | 레퍼런스 용도 |
| --- | --- |
| 개요 | 구조를 가져온다. 항목 구성, 소제목 형태 |
| 초고 | 보지 않는다. 기억으로 재구성해 쓴다 |
| 대조 | 원문과 나란히 놓고 무엇이 달라졌는지 확인한다 |
| 퇴고 | 대조에서 나온 차이를 반영한다 |

수집한 레퍼런스
- 구조: cogi(상세 페이지 구성), 손찬양(검증 범위), 강지(밀도 차등), hyejin(메타 기여 표기)
- 표현: cogi(회고 명사형, 문제·원인·해결·결과), 이희망(판단 한 문장), dohoasen(소제목에 결과)

## 작업 순서

### 1단계 — 개요

항목식 개요를 만들어 승인받는다. 본문 문장은 쓰지 않는다.

먼저 각 자리에서 전할 메시지를 정한다.

- 첫 화면이 답해야 할 것
- 프로젝트 세 개가 각각 맡을 역할
- 프로젝트 사이를 잇는 지점
- 상세에서 보여줄 판단

메시지를 정한 뒤 소제목을 뽑고, 소제목마다 뒷받침할 근거를 재료에서 찾아 한 줄로 붙인다.

소제목 개수는 메시지 수에 따라간다. 데일밴드가 대표이므로 다른 둘보다 많되, 미리 정하지 않는다.

여기서 레퍼런스의 구조를 적용한다. 소제목은 결과나 원칙을 품는다. `기능명 — 원칙` 또는 `A에서 B로` 형태.

### 2단계 — 초고

개요의 칸을 채운다. **레퍼런스를 보지 않는다.** 표현도 다듬지 않는다.

분량 기준
- 판단 한 건 = 2~3문장, 문단 하나
- 회고 = 배운 점 / 아쉬운 점 / 개선 방향, 각 1~2줄 명사형
- 한계 고지 = 프로젝트당 한 줄

### 3단계 — 대조

내 초고와 레퍼런스 원문을 나란히 놓고 차이를 찾는다. 항목별로 무엇이 달라졌는지 적는다.

- 문제 1문장 + 해결 1문장으로 끝나는가
- 판단이 `~라서 ~했습니다` 한 문장인가
- 소제목에 결과나 원칙이 있는가
- 회고가 명사형 한 줄인가
- 부정형 종결(`못 했습니다`, `아닙니다`)이 남았는가
- 분량이 레퍼런스의 몇 배인가

### 4단계 — 퇴고

대조에서 나온 차이를 반영한다. 구조 → 흐름 → 문장 순으로 손본다. AI 문체 패턴을 제거한다.

- 문두 접속사 (`그런데`, `그래서`, `다만`, `여기에 더해`)
- 사역형 (`~하도록 했습니다`, `~하게 했습니다`)
- 형식명사 (`~한 것이다`, `~것이 핵심입니다`)
- 결산 구절 (`결론적으로`, `이를 통해`)
- 굵게 강조 남용
- 이중 피동

## 문안 규칙

| 항목 | 기준 |
| --- | --- |
| 문체 | 니다체. 요체 금지 |
| 블라인드 | 학교명·교육기관명·이력 섹션 제외. 이력서로 보낸다 |
| 톤 | 어필. 한계는 신뢰를 만드는 만큼만 |
| 수치 | 재료 파일에서 확인된 것만. `[미확인]` 항목은 주장하지 않는다 |
| 비공개 저장소 | 기관명 없이 `비공개 저장소입니다. 설계 판단 위주로 정리했습니다` 한 줄 |

## 재료를 고르는 방식

재료를 미리 배정하지 않는다. 배정해두면 전할 메시지가 가진 재료 안으로 좁아진다.

순서는 메시지가 먼저다.

1. 각 자리에서 무슨 말을 할지 정한다
2. 그 말을 뒷받침할 근거를 `research/포폴재료_*.md`에서 찾는다
3. 근거가 없으면 그 메시지를 버리거나 다른 근거를 찾는다

한 재료가 여러 자리에 쓰일 수도, 어떤 재료는 한 번도 안 쓰일 수도 있다. 31개를 다 소진하려 하지 않는다.

재료 파일에서 각 항목의 `활용` 줄에 어디에 쓸지 적어두었으나, 그것도 후보이지 결정이 아니다.

## 검증

1. 개요 단계에서 소제목만 훑어 무슨 판단을 했는지 읽히는지 확인
2. 초고 완성 후 프로젝트당 분량을 센다. 판단 한 건이 3문단을 넘으면 줄인다
3. `못`, `아닙니다`, `않습니다`, `하도록`, `그래서`, `것입니다` 문자열을 검색해 잔존 여부를 센다
4. 소제목만 뽑아 나열했을 때 성장 궤적(문제 난이도 상승)이 보이는지 확인

## 피드백 — AI 활용 메시지 (2026-08-16)

"AI가 개발과 서비스에 들어온 환경에서도, 결과를 검증하고 운영 가능한 시스템으로 만드는 백엔드 개발자"라는 메시지가 들어가는 것이 AX가 가장 큰 관심사인 2026년에 유리할 것으로 판단됩니다.

2026년 AX 흐름을 고려해, 포트폴리오 전체에서 “AI가 개발과 서비스에 들어온 환경에서도, 결과를 검증하고 운영 가능한 시스템으로 만드는 백엔드 개발자”라는 인상이 자연스럽게 드러나도록 조정한다.

단, 기존의 백엔드 정체성을 AI 개발자로 바꾸거나 모든 경험을 억지로 AI와 연결하지 않는다. 백엔드 역량을 중심에 두고, AI를 활용한 개발 생산성 향상·AI 결과물의 검증·AI 기능의 안정적인 운영 경험을 기존 프로젝트 경험 속에서 근거가 있는 부분에만 드러낸다.

특히 다음 경험은 적극적으로 활용한다.

AI Agent를 활용한 구현과 이를 검증하기 위한 Build → Test → SonarQube → Quality Gate
AI를 활용한 기존 API 역분석과 사람의 검수, Mock Server/API Docs를 통한 계약 고정
BE와 AI Worker 사이의 비동기 처리, 실패 복구, 정합성 관리 등 AI 기능을 실제 서비스에서 운영하기 위한 설계

최종적으로 독자가 “백엔드만 잘하는 개발자”가 아니라 “AI를 적극적으로 활용하면서도, AI가 만든 결과를 그대로 신뢰하지 않고 검증·통제하여 실제 서비스 수준으로 만드는 백엔드 개발자”라고 느끼게 한다.

AI, AX, LLM 등의 키워드를 단순히 추가하는 방식은 피하고, 반드시 실제 경험과 행동을 통해 메시지가 전달되도록 수정한다.
