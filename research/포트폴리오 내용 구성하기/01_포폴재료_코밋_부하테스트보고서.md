# Komit API 다중화 성능 비교 보고서

> 동일한 앱 자원 2 CPU / 3 GiB에서 단일 인스턴스와 이중 인스턴스를 비교한 결과, 119 RPS에서는 모든 구성이 요청을 100% 처리했지만 이중 인스턴스의 CPU 사용량과 tail latency가 더 높았다. 한계 부하 탐색에서는 Docker 단일 인스턴스가 214 RPS까지 통과한 반면 K3s 2 Pod는 179 RPS에서 CPU throttling으로 성능 기준을 넘었다.  
> 이번 프로젝트는 비용 제약으로 단일 서버 안에서 총 자원을 고정해 비교했기 때문에 실제 분산 서버의 확장성을 검증한 실험은 아니다. 결과적으로 제한된 자원을 단순히 여러 인스턴스로 나누는 것에는 성능 비용이 있었으며, 다음 프로젝트에서는 여러 서버에 Pod를 분산해 수평 확장과 장애 대응 효과를 검증할 필요가 있다.

## 1. 실험 목적

Komit의 Service API를 여러 인스턴스로 실행했을 때 성능이 어떻게 달라지는지 확인하기 위해 부하 테스트를 진행했다.

대상은 DB 조회 비중이 높은 다음 API 3종이다.

- R1: 개발자 목록 조회
- R2: 개발자 상세 조회
- R3: 개발자 리뷰 조회

확인하려는 질문은 다음과 같다.

> 동일한 총 CPU와 메모리를 사용할 때, 하나의 인스턴스에 자원을 집중하는 것보다 여러 인스턴스로 나누는 것이 더 높은 처리량을 낼 수 있는가?

초기 가설은 `K3s 2 Pod` 구성이 `Docker 단일 인스턴스`보다 높은 처리량을 낼 것이라는 것이었다.

다만 이번 프로젝트에서는 인프라 비용 때문에 여러 서버를 확보하지 못했다. 따라서 실제 여러 서버에 Pod를 분산하는 환경이 아니라, 하나의 서버 안에서 동일한 총 자원을 단일·이중 인스턴스에 각각 할당해 비교했다.

---

## 2. 비교 환경

총 애플리케이션 자원은 모든 환경에서 `2 CPU / 3 GiB`로 동일하게 맞췄다.

| 구분 | 실행 환경 | 인스턴스 | 인스턴스당 자원 | 총 앱 자원 |
|---|---|---:|---|---|
| A | Docker | 1개 | 2 CPU / 3 GiB | 2 CPU / 3 GiB |
| B | K3s | 1 Pod | 2 CPU / 3 GiB | 2 CPU / 3 GiB |
| C | K3s | 2 Pod | 1 CPU / 1536 MiB | 2 CPU / 3 GiB |
| D | Docker | 2개 | 1 CPU / 1536 MiB | 2 CPU / 3 GiB |

A와 C가 핵심 비교 대상이다.

A는 하나의 JVM이 최대 2 CPU를 사용할 수 있지만, C는 두 JVM이 각각 최대 1 CPU만 사용할 수 있다.

B와 D는 차이가 K3s 자체에서 발생하는지, 인스턴스를 둘로 나눈 데서 발생하는지 구분하기 위해 함께 측정했다.

---

## 3. 실험 조건

환경 외의 조건이 결과에 미치는 영향을 줄이기 위해 다음 조건을 고정했다.

| 항목 | 조건 |
|---|---|
| 앱 이미지 | 모든 환경에서 동일한 이미지 사용 |
| 앱 총 자원 | 2 CPU / 3 GiB |
| PostgreSQL | 4 CPU / 2 GiB |
| DB 데이터 | 모든 실행에서 동일 |
| Connection Pool | read/write 각각 총합 20 |
| JVM | G1 GC, Initial RAM 20%, Max RAM 50% |
| Proxy | nginx |
| 요청 비율 | R1/R2/R3 = 50/30/20 |
| Retry | 없음 |
| Timeout | 3초 |
| 부하 방식 | k6 `constant-arrival-rate` |
| 측정 시간 | 환경별 60초 |
| 프로세스 | 실행마다 새 프로세스 시작 |

DB에는 사용자 20,000건, 개발자 10,000건과 프로젝트·방·계약·리뷰 각각 160,000건을 적재했다. 전체 DB 크기는 약 186 MiB이며 시험용 인덱스 12개를 사용했다.

따라서 이번 결과는 읽기 중심의 warm-cache 환경에 대한 결과이며, 쓰기 부하나 대용량 I/O 환경까지 포함하지 않는다.

실험 통과 기준은 다음과 같다.

| 지표 | 기준 |
|---|---:|
| API p95 | 500 ms 이하 |
| API p99 | 1,000 ms 이하 |
| 무효 요청 | 1% 미만 |
| 목표 요청 시작률 | 99% 이상 |

이 기준은 제품 SLO가 아니라 환경 간 비교를 위해 정한 실험 기준이다.

# 4. 1차 실험 — 59 RPS

## 4.1 부하 선정

먼저 K3s 2 Pod 환경에서 부하를 단계적으로 높이며 성능이 저하되기 시작하는 지점을 찾았다.

| 목표 RPS | R1 p95 | 앱 CPU s/req | 통과 여부 |
|---:|---:|---:|---|
| 1 | 71.5 ms | 0.0628 | 통과 |
| 7 | 54.5 ms | 0.0320 | 통과 |
| 15 | 44.0 ms | 0.0190 | 통과 |
| 26 | 41.0 ms | 0.0131 | 통과 |
| 38 | 40.0 ms | 0.0090 | 통과 |
| 55 | 41.0 ms | 0.0085 | 통과 |
| 59 | 40.0 ms | 0.0084 | 통과 |

59 RPS에서도 성능 저하가 시작되는 지점을 찾지 못했다.

CPU 사용량으로 계산한 상한 근사는 약 238 RPS였기 때문에 59 RPS는 그 약 25%에 불과했다. 예비 테스트 시간 제한에 도달해 59 RPS에서 1차 비교를 진행했다.

## 4.2 59 RPS 측정 결과

각 환경을 두 번씩 측정했다.

| 환경 | N | goodput | R1 p95 | R1 p99 | R2 p95 | R3 p95 | 앱 CPU |
|---|---:|---:|---:|---:|---:|---:|---:|
| A Docker 단일 | 2 | 59.00 RPS | 38 ms | 43 ms | 7 ms | 4 ms | 0.35 core |
| B K3s 단일 | 2 | 59.00 RPS | 39 ms | 44 ms | 8 ms | 4 ms | 0.34 core |
| C K3s 2 Pod | 2 | 59.00 RPS | 41 ms | 56 ms | 9 ms | 6 ms | 0.44 core |
| D Docker 2개 | 2 | 59.00 RPS | 40 ms | 50 ms | 8 ms | 5 ms | 0.46 core |

네 환경 모두 목표 59 RPS를 100% 처리했다.

따라서 이 부하에서는 처리량 차이를 확인할 수 없었다.

다만 단일 환경과 이중 환경 사이에서는 차이가 나타났다.

- A와 B는 지연과 CPU 사용량이 거의 동일했다.
- C와 D는 단일 환경보다 앱 CPU를 약 30% 많이 사용했다.
- 이중 환경의 p95 차이는 작았지만 p99를 포함한 tail latency가 더 길었다.

즉 59 RPS에서는 K3s 자체의 뚜렷한 성능 비용은 보이지 않았지만, JVM을 두 개 실행하는 데 따른 추가 CPU 사용량은 확인됐다.

### 1차 실험 결론

59 RPS는 모든 환경에 너무 낮은 부하였다.

따라서 다중화가 최대 처리량에 어떤 영향을 주는지 확인하기 위해 더 높은 부하에서 2차 실험을 진행했다.

# 5. 2차 실험 — 경계 부하 탐색

1차 실험에서 요청당 CPU 사용량이 약 `0.0084 s/req` 수준으로 수렴했다.

이를 기준으로 예상 처리량 약 238 RPS의 50%, 75%, 90%에 해당하는 부하를 후보로 정했다.

| 후보 | 목표 RPS |
|---|---:|
| 50% | 119 |
| 75% | 179 |
| 90% | 214 |

핵심 비교 대상인 A와 C에서 후보 부하를 단계적으로 적용했다.

## 5.1 경계 탐색 결과

| 환경 | 목표 RPS | 결과 | drop | R1 p95 | R1 p99 | 앱 CPU s/req | CPU throttling |
|---|---:|---|---:|---:|---:|---:|---|
| C K3s 2 Pod | 119 | 통과 | 0 | 119 ms | 247 ms | 0.0091 | 10.5s / 5.1s |
| C K3s 2 Pod | 179 | 실패 | 81 | 1,161 ms | 2,101 ms | 0.0083 | 24.0s / 23.4s |
| A Docker 단일 | 119 | 통과 | 0 | 41 ms | 50 ms | 0.0057 | 0.0s |
| A Docker 단일 | 179 | 통과 | 0 | 46 ms | 71 ms | 0.0051 | 0.1s |
| A Docker 단일 | 214 | 통과 | 0 | 44 ms | 61 ms | 0.0049 | 0.0s |

가장 큰 차이는 179 RPS에서 나타났다.

C는 R1 p95가 1,161 ms까지 증가하면서 기준인 500 ms를 크게 초과했다. R2와 R3 역시 p95가 각각 1,085 ms, 1,014 ms까지 증가했다.

같은 시간 동안 두 Pod는 각각 60초 중 약 24초 동안 CPU throttling이 발생했다.

반면 A는 179 RPS뿐 아니라 214 RPS에서도 기준을 통과했으며 CPU throttling도 사실상 발생하지 않았다.

따라서 이번 실험 범위에서 관측된 경계는 다음과 같다.

| 환경 | 관측된 처리 범위 |
|---|---|
| A Docker 단일 | 최소 214 RPS까지 통과 |
| C K3s 2 Pod | 119 RPS 통과, 179 RPS 실패 |

A의 실제 최대 처리량은 214 RPS보다 높을 수 있지만 이번 테스트에서는 더 높은 부하를 시험하지 않았다.

# 6. 공통 부하 119 RPS 비교

A와 C가 모두 통과한 가장 높은 후보인 119 RPS를 공통 비교 부하로 선정했다.

119 RPS에서 A, B, C, D를 다시 비교했다.

## 6.1 환경별 결과

| 환경 | N | goodput | 성공률 | R1 p95 | R1 p99 | R2 p95 | R3 p95 | 앱 CPU |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| A Docker 단일 | 2 | 119.0 RPS | 100% | 44 ms | 61 ms | 10.5 ms | 4.5 ms | 0.61 core |
| B K3s 단일 | 2 | 119.0 RPS | 100% | 45 ms | 58 ms | 10.5 ms | 5 ms | 0.61 core |
| C K3s 2 Pod | 3 | 119.0 RPS | 100% | 50 ms | 73 ms | 14 ms | 7 ms | 0.80 core |
| D Docker 2개 | 2 | 119.0 RPS | 100% | 46 ms | 67 ms | 11 ms | 5.5 ms | 0.75 core |

119 RPS에서는 모든 환경이 다시 요청을 100% 처리했다.

따라서 정상적으로 감당 가능한 부하 안에서는 단일·이중 구성 모두 같은 처리량을 냈다.

반면 자원 사용량은 달랐다.

| 비교 | 단일 | 이중 | 변화 |
|---|---:|---:|---:|
| Docker 앱 CPU | A 0.61 | D 0.75 | 약 +23% |
| K3s 앱 CPU | B 0.61 | C 0.80 | 약 +31% |
| Docker R1 p95 | A 44 ms | D 46 ms | +2 ms |
| K3s R1 p95 | B 45 ms | C 50 ms | +5 ms |

특히 K3s 2 Pod인 C는 A보다 CPU를 약 31% 더 사용했고 p99와 R2/R3 p95에서도 더 긴 tail latency가 나타났다.

표본 수가 적기 때문에 몇 ms 수준의 지연 차이를 통계적으로 확정할 수는 없다. 하지만 이중 구성에서 CPU 사용량이 증가하고 tail latency가 길어지는 방향은 Docker와 K3s 양쪽에서 함께 나타났다.

# 7. 왜 이중 구성이 더 많은 CPU를 사용했나

가장 직접적인 원인은 인스턴스별 CPU 제한이다.

A는 하나의 JVM이 최대 2 CPU를 사용할 수 있다.

```text
A: Docker 단일

JVM
└── 최대 2 CPU
```

반면 C에서는 총 CPU가 같아도 각 JVM이 사용할 수 있는 CPU는 1개로 제한된다.

```text
C: K3s 2 Pod

JVM 1
└── 최대 1 CPU

JVM 2
└── 최대 1 CPU
```

GC, JIT 컴파일, 요청 처리 등으로 특정 JVM에 순간적으로 1 CPU 이상의 연산이 필요해도 다른 Pod의 남는 CPU를 가져와 사용할 수 없다.

실제로 179 RPS의 C에서는 두 Pod가 각각 약 24초 동안 CPU quota에 걸려 throttling됐다.

또한 JVM을 두 개 실행하면 다음 자원도 각각 필요하다.

- JIT Compiler
- GC
- JVM 내부 스레드
- Spring 런타임
- Connection Pool
- Heap과 각종 JVM 메타데이터

실제 요청당 CPU 사용량도 높은 부하에서 다음과 같이 나타났다.

| 구성 | CPU s/req |
|---|---:|
| A Docker 단일 | 약 0.0049~0.0054 |
| C K3s 2 Pod | 약 0.0063~0.0068 |

C가 요청 하나를 처리하는 데 약 25~35% 더 많은 CPU를 사용했다.

# 8. K3s 자체가 느린 것은 아니었다

Docker 단일 A와 K3s 단일 B를 비교하면 결과가 거의 같다.

| 지표 | A Docker 단일 | B K3s 단일 |
|---|---:|---:|
| goodput | 119 RPS | 119 RPS |
| 성공률 | 100% | 100% |
| R1 p95 | 44 ms | 45 ms |
| R1 p99 | 61 ms | 58 ms |
| 앱 CPU | 0.61 core | 0.61 core |

실험 범위에서는 K3s 자체가 애플리케이션 성능을 크게 떨어뜨렸다는 근거가 없다.

반대로 인스턴스를 둘로 나눈 C와 D에서 공통적으로 CPU 사용량이 증가했다.

따라서 이번에 관측된 성능 차이의 핵심은 Docker와 K3s의 차이라기보다 동일한 총 자원을 여러 JVM으로 분할한 것에 있다.

# 9. DB와 부하 발생기는 병목이 아니었다

119 RPS에서 PostgreSQL은 약 1 CPU를 사용했다.

179~214 RPS에서도 약 1.9 CPU 수준이었으며 할당량은 4 CPU였다.

따라서 애플리케이션이 한계에 도달했을 때도 DB에는 자원 여유가 있었다.

k6 역시 119 RPS 본 측정에서 약 0.17~0.18 core만 사용했으며 VU 부족이나 drop이 발생하지 않았다.

즉 179 RPS에서 C의 응답시간이 급격하게 증가한 현상을 DB나 부하 발생기의 한계로 설명하기는 어렵다.

# 10. 콜드 스타트에서 확인한 문제

119 RPS 본 측정 전에 각 환경을 새로 시작해 바로 부하를 넣었을 때는 네 환경 모두 첫 30초 안에 timeout과 drop이 집중됐다.

당시 앱 CPU는 총 2 CPU 한도에 거의 붙어 있었다.

JVM이 시작된 직후에는 JIT 컴파일과 실제 요청 처리가 동시에 CPU를 사용하기 때문이다.

2차 워밍업 이후에는 모든 실행에서 무효 요청과 drop이 사라졌다.

다만 120초 워밍업 후에도 CPU 사용량이 계속 감소하고 있었기 때문에 JVM이 완전히 안정된 상태라고 보기는 어려웠다.

이 결과는 실제 운영에서 새 Pod를 바로 트래픽에 투입하는 방식에 주의가 필요하다는 점도 보여준다.

다만 콜드 스타트 대응은 이번 실험의 주목적이 아니므로 별도 검증 대상으로 남긴다.

# 11. 이번 프로젝트에서 다중화가 갖는 의미

이번 결과만 보면 동일한 자원을 하나의 JVM에 주는 구성이 처리량 면에서는 더 유리했다.

그렇다고 해서 실제 운영에서도 단일 인스턴스를 선택해야 한다는 뜻은 아니다.

이번 프로젝트는 비용 제약으로 하나의 서버만 사용할 수 있었고, 총 자원을 의도적으로 동일하게 맞췄다.

즉 실제로 비교한 구조는 다음과 같다.

```text
단일 구성

Server
└── Instance
    └── 2 CPU / 3 GiB
```

```text
현재 프로젝트의 다중화

Server
├── Instance 1
│   └── 1 CPU / 1536 MiB
│
└── Instance 2
    └── 1 CPU / 1536 MiB

총 자원 = 여전히 2 CPU / 3 GiB
```

인스턴스를 늘렸지만 사용할 수 있는 전체 CPU와 메모리는 늘어나지 않았다.

따라서 이번 실험은 일반적인 의미의 수평 확장 성능 테스트라기보다, 제한된 하나의 서버 안에서 같은 자원을 여러 인스턴스로 나눴을 때의 비용을 확인한 실험에 가깝다.

실제 분산 서버 환경에서는 구조가 달라진다.

```text
Server A
└── Pod 1
    └── 2 CPU / 3 GiB

Server B
└── Pod 2
    └── 2 CPU / 3 GiB

총 자원 = 4 CPU / 6 GiB
```

이 환경에서는 Pod가 하나 늘어날 때 사용할 수 있는 전체 자원도 증가한다.

또한 하나의 서버에 장애가 발생해도 다른 서버의 Pod가 계속 요청을 처리할 수 있다.

이번 프로젝트에서는 비용 문제로 이러한 구성을 직접 시험하지 못했다.

다음 프로젝트에서는 여러 서버를 확보해 Pod를 노드별로 분산하고 다음 항목을 검증할 예정이다.

- Pod 증가에 따른 실제 처리량 증가
- HPA 기반 수평 확장
- 특정 Pod 장애 시 요청 지속 처리
- 노드 하나가 내려갔을 때 서비스 유지 여부
- 여러 노드 사이의 부하 분산
- 노드 간 통신 비용

# 13. 실험의 한계

첫째, 모든 환경을 단일 VM에서 실행했다.

특히 K3s도 단일 노드였기 때문에 여러 물리 서버에 Pod를 분산했을 때의 확장성과 장애 대응은 확인하지 못했다.

둘째, C의 179 RPS 실패는 예비 단계에서 한 번 측정됐다.

이때 JVM이 완전히 warm된 상태가 아니었기 때문에 JIT 컴파일에 사용된 CPU가 결과에 일부 포함됐을 가능성이 있다. CPU throttling 자체는 실제로 측정됐지만, 완전히 warm된 상태에서도 정확히 179 RPS에서 실패하는지는 추가 검증이 필요하다.

셋째, A는 214 RPS에서도 성능 기준을 통과했다.

따라서 A의 최대 처리량은 이번 실험에서 찾지 못했다.

넷째, 반복 횟수가 충분하지 않았다.

119 RPS에서는 A 2회, B 2회, C 3회, D 2회를 측정했다. 지연시간의 작은 차이를 통계적으로 확정하기에는 부족하다.

다섯째, 읽기 전용 warm-cache 워크로드다.

실제 운영 환경의 쓰기 요청, 더 큰 DB, 디스크 I/O, 네트워크 지연까지 포함한 결과로 일반화할 수 없다.

# 14. 결론

이번 실험에서는 동일한 총 자원 `2 CPU / 3 GiB` 안에서 애플리케이션을 여러 인스턴스로 나누는 것만으로 처리량이 증가하지 않았다.

정상적으로 처리 가능한 119 RPS에서는 단일·이중 구성이 모두 요청을 100% 처리했지만, 이중 구성은 JVM을 두 개 실행하는 비용 때문에 CPU 사용량과 tail latency가 증가했다.

높은 부하에서는 차이가 더 크게 나타났다.

K3s 2 Pod는 각 Pod의 1 CPU quota에 걸려 179 RPS에서 CPU throttling과 1초 이상의 p95 지연이 발생한 반면, 하나의 JVM이 2 CPU를 사용할 수 있는 Docker 단일 구성은 214 RPS까지 성능 기준을 통과했다.

반면 Docker 단일과 K3s 단일의 성능은 거의 같았다. 따라서 이번 결과는 K3s 자체의 성능 문제라기보다 제한된 총 자원을 여러 JVM으로 분할하면서 발생한 CPU quota와 JVM 중복 비용의 영향으로 해석할 수 있다.

이번 프로젝트에서 다중화를 적용한 목적도 동일 자원에서 처리량을 높이는 데만 있지는 않다. 여러 인스턴스를 독립적으로 운영할 수 있는 구조를 구성함으로써 이후 장애 격리와 수평 확장으로 이어질 기반을 마련했다.

다만 현재는 비용 제약으로 모든 인스턴스를 하나의 서버에서 실행했기 때문에 실제 서버 장애를 견디는 고가용성이나, 서버를 추가하면서 전체 자원까지 늘리는 수평 확장 효과를 검증했다고 볼 수는 없다.

따라서 이번 실험의 결론은 다음과 같다.

> **제한된 하나의 서버 안에서 같은 자원을 여러 인스턴스로 나누면 일정한 성능 비용이 발생하며, 다중화 자체가 처리량을 증가시키지는 않았다. 반면 여러 인스턴스를 운영할 수 있는 구조적 기반은 확보했다. 다음 프로젝트에서는 비용 제약을 해소하고 여러 서버에 Pod를 실제로 분산해, 수평 확장에 따른 처리량 증가와 노드 장애 대응까지 검증할 예정이다.**
