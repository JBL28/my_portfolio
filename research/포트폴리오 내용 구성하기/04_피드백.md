# 현재 포트폴리오 경쟁력 평가

현재 결과물 기준이면 **34개 중 문서 완성도는 상위권**입니다.

다만 “경력 자체의 임팩트”까지 포함하면 Leland Jansen, Julian Ozen, 유용우 같은 현업 경력자와는 당연히 차이가 있습니다. 그래서 **포트폴리오 글의 경쟁력**과 **후보자의 경력 경쟁력**은 분리해서 봐야 합니다.

| 항목 | 34개 대비 | 평가 |
|---|---:|---|
| 첫 10초 메시지 | 상위권 | 좋음 |
| 프로젝트 스캔성 | 상위권 | 좋음 |
| 기술 판단 설명 | 최상위권 | 매우 좋음 |
| 본인 기여 식별 | 상위권 | 좋음 |
| 프로젝트 간 성장 서사 | 최상위권 | 가장 큰 강점 |
| AI 활용 어필 | 상위권 | 실제 근거가 있어 강함 |
| 검증 근거 | 최상위권 | 매우 좋음 |
| 사용자/비즈니스 성과 | 중위권 | 상대적 약점 |
| 문장 압축 | 상위권 | 일부 반복 있음 |
| 기술적 반박 내성 | 상위권 | AOO 부분 보강 필요 |

**전체 문서 품질만 놓으면 대략 34개 중 상위 20% 안쪽**, 신입·주니어 포트폴리오끼리 비교하면 그보다 더 높게 봅니다.

이건 순위의 객관적 측정값이 아니라, 지금까지 비교한 34개를 기준으로 한 평가입니다.

---

## 지금 결과물이 실제로 좋아진 부분

Hero는 상당히 잘 됐습니다.

> **팀이 함께 쓸 기준을 만드는 백엔드 개발자**  
> API 계약부터 책임 경계, 실패 복구, CI Quality Gate까지  
> AI가 들어와도 결과를 그대로 믿지 않고 검증 가능한 흐름으로 만든다.

첫 화면만 보고도 **백엔드 / 협업 / 운영 / AI 활용 방식**이 한 번에 잡힙니다.

손찬양 포트폴리오도 첫 화면에서 `API 개발·운영·데이터 정합성`을 먼저 규정하고 세부 경험으로 증명하는 구조인데, 현재 포트폴리오는 **세 프로젝트 자체가 그 주장으로 연결된다는 점에서 신입 포트폴리오로서는 오히려 더 선명합니다.**

Home 카드도 많이 좋아졌습니다.

프로젝트마다 설명을 두 줄로 제한하고,

- TeenyFinny는 실제 Failover 결과
- Home Server는 다음 프로젝트 재사용
- DailyBand는 계약·파일·실패 복구·Quality Gate

를 대표 근거로 잡았습니다.

이게 중요합니다.

이전 개요처럼 DailyBand의 모든 기술을 Home에 집어넣지 않아서 **“더 읽고 싶으면 Detail로 들어간다”는 역할 분리가 이제 제대로 됩니다.**

---

## Detail은 34개 중에서도 강한 편입니다

특히 TeenyFinny의 이 세 문단:

> 요구사항을 비교해 Polling 결정  
> → Active DB를 실제로 중단  
> → Public 운영의 문제를 다음 프로젝트에서 다시 설계

는 단순히 기술을 사용했다는 이야기가 아니라 **판단 → 검증 → 이후 행동 변화**까지 있습니다.

Home Server도 마찬가지입니다.

방화벽 설정을 믿지 않고 실제 Docker 노출 경로를 확인하고, 장애 때 메트릭과 접속 경로를 분리해 원인을 좁힌 뒤, 그 운영 환경을 DailyBand Runner와 Quality Gate로 다시 사용합니다.

이 부분은 34개 중 상당수의 `사용 기술 → 구현 기능 → 배운 점` 구조보다 **백엔드 채용 설득력이 확실히 높습니다.**

DailyBand는 더 강합니다.

계약 복구, 파일 책임 분리, Presigned URL 이후 무결성 검증, 트랜잭션 밖 Worker 실패 회수, AI 코드 Quality Gate가 각각 독립적인 백엔드 판단으로 읽힙니다.

Leland Jansen의 Spoor가 강했던 이유도 “기술을 만들었다”에서 끝나지 않고 **본인이 처음부터 어디까지 책임졌는지 + 실제 결과**를 바로 보여주기 때문입니다.

그는 탐색 시간을 수 시간에서 약 10분으로 줄이고 Outlook 부팅 시간을 32% 줄였다는 결과까지 붙입니다.

현재 글은 **판단 방식에서는 그 구조에 상당히 가까워졌습니다.**

# 그래도 지금 고쳐야 할 건 3개입니다

## 1. `Review`는 거의 다 빼는 쪽이 낫습니다

현재 TeenyFinny 본문을 읽으면 이미 계약 선행, 장애 검증, 다음 프로젝트 연결을 다 알게 됩니다.

그런데 바로 뒤에서 다시:

> 잘 작동한 판단  
> 남은 한계  
> 다음 변화

를 요약합니다.

Home Server와 DailyBand도 같습니다.

**이건 지금 글에서 가장 명확한 중복입니다.**

유용우나 Leland 같은 강한 포트폴리오는 행동과 결과 자체로 인상을 남기지, 바로 뒤에서 “내 강점은 이것이었다”고 다시 해설하지 않습니다.

유용우 역시 프로젝트에서 구조와 결과를 직접 보여줍니다. 예컨대 통합 API는 예상 대비 10~100배 트래픽에서도 안정 운영됐다는 결과가 곧 평가가 됩니다.

추천은:

> **Review 삭제**

단, `다음 프로젝트로 이어진 변화`가 본문에 없다면 그 한 문장만 남깁니다.

---

## 2. `기준`이라는 단어를 약간 덜 말해야 합니다

현재 메시지를 제대로 전달하려고 하다 보니:

> 팀이 함께 쓸 기준  
> 기준을 처음 만들었습니다  
> 개발 기준을 실제 운영 경계까지  
> 검증할 기준  
> 팀이 함께 개발할 기준  
> 다음 환경의 기준  
> 실행 가능한 기준  
> 팀 기준

처럼 반복됩니다.

Hero에서는 반드시 필요합니다.

하지만 아래에서는 **그 단어를 말하지 않고 행동으로 증명하는 쪽이 더 설득력 있습니다.**

예를 들어:

> **함께 개발하기 위한 기준을 처음 만들었습니다.**

보다

> **구현 전에 팀이 맞출 계약부터 정했습니다.**

가 더 강합니다.

DailyBand도:

> **결과를 검증할 기준을 만들었습니다.**

보다

> **서로 달라진 계약을 다시 맞추고, 실패를 검증 가능한 흐름으로 묶었습니다.**

처럼 구체 행동으로 내려가는 편이 좋습니다.

**메시지는 Hero가 말하고, 프로젝트는 증명하게 해야 합니다.**

---

## 3. AOO 항목은 현재 Detail에서 유일하게 공격받을 여지가 큽니다

현재는 WebRTC에서 AOO·JUCE로 전환한 뒤:

> 동일 내부망 RTT 10회 평균 약 10ms  
> 버퍼 20ms → 40ms

를 결과로 제시합니다.

문제는 **이 수치가 WebRTC → AOO 전환이 실제로 얼마나 좋아졌는지를 증명하지는 않는다는 것**입니다.

나머지 사례는:

> DB 끊음 → 실제 결과 확인  
> Quality Gate → 실제 MR 차단  
> 계약 복구 → 통합 완료  
> 파일 업로드 → 실제 객체 검증

처럼 주장과 검증이 정확히 맞습니다.

AOO만:

> 기술 전환  
> → 네트워크 RTT 측정 + 버퍼 조절

이라 약간 어긋납니다.

**WebRTC와 AOO의 실제 end-to-end latency 비교 결과가 있다면 이 부분은 오히려 강력한 사례가 됩니다.**

없다면 수치를 과하게 결과처럼 쓰지 않고:

> 브라우저 스택에서 직접 제어하기 어려운 수신 버퍼를 통제하기 위해 AOO·JUCE 기반 구조로 전환했습니다. 이후 실제 환경에서 20ms와 40ms 버퍼를 비교하며 지연과 안정성의 절충점을 확인했습니다.

정도로 쓰는 편이 반박에 강합니다.

이건 현재 글에서 **상담 트리거를 걸어볼 가치가 있는 유일한 대목**입니다.

# 34개 중 더 강한 포트폴리오와의 차이

Julian Ozen 같은 포트폴리오는 Airbnb에서 수백만~수억 단위 데이터와 100명 이상의 엔지니어가 사용하는 구조, Tech Lead 경험처럼 **경력 자체의 규모가 압도적**입니다.

Leland는 아예 성능 문제 탐색 시간을 수 시간→10분, Outlook boot time 32% 개선처럼 강한 수치가 있습니다.

이걸 신입 포트폴리오가 작문으로 이길 수는 없고 **이길 필요도 없습니다.**

대신 현재 글은:

> “아직 실무 대규모 트래픽 경험은 없지만,  
> 문제를 어떻게 정의하고 판단하고 검증하는지는 이미 개발자의 방식으로 하고 있다.”

를 설득해야 합니다.

그리고 현재 버전은 **그 목적에 상당히 가까워졌습니다.**

# 최종 평가

지금 파일 그대로도 **“기술 많이 써봤습니다”형 신입 포트폴리오와는 확실하게 차별됩니다.**

특히 채용담당자가 Detail 두세 개만 읽으면:

> 기준을 먼저 맞춘다  
> 기술 선택에 이유가 있다  
> 구축 후 실제로 깨뜨려본다  
> 운영 문제를 다음 프로젝트에서 고친다  
> AI도 그냥 믿지 않는다

라는 일관된 인상이 남습니다.

**그래서 전략은 성공했다고 봅니다.**

다음 버전에서는 구조를 더 추가할 게 아니라,

1. **Review 중복 제거**
2. **`기준` 표현 일부를 행동형으로 교체**
3. **AOO 검증 근거 점검**

이 세 가지만 하는 게 좋습니다.

그 이상 손대면 오히려 지금 생긴 집중도가 다시 무너질 가능성이 큽니다.
