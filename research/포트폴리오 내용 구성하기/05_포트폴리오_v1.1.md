# Project Detail — TeenyFinny

부모와 자녀가 함께 사용하는 청소년 용돈·투자 관리 서비스입니다. 처음 PL을 맡아 **API 계약을 정리하고 백엔드 공통 구조와 인프라를 만드는 역할**을 맡았습니다.

2025.10 ~ 2025.12 · 5인  
PL · Backend · Infrastructure  
Spring Boot · MySQL · AWS · Nginx · Jenkins · SonarQube  
**Result. 최종 프로젝트 우수팀**

## 구현보다 먼저 팀이 맞출 계약을 정했습니다

FE와 BE가 병행 개발해야 했기에 구현 후 형식을 맞추는 대신 API 명세를 먼저 정했습니다. 명세에 맞춰 `BaseEntity`와 `BaseException`을 작성하고, FE는 Postman Mock Server에 맞춰 개발한 뒤 실제 서버와 연동했습니다.

## 기술보다 요구사항을 먼저 비교했습니다

실시간 주식 시세에 WebSocket과 Polling 중 의견이 갈렸습니다. 두 방식을 조사한 뒤 **초저지연·양방향 통신이 필요한가**를 요구사항과 대조했고, 청소년의 소액 투자 경험에는 필요하지 않다고 판단해 Polling을 제안했습니다. 팀은 이 판단에 합의해 Polling을 채택했습니다.

## 이중화는 직접 끊어보고 확인했습니다

MySQL 이중화와 ProxySQL·Orchestrator 기반 Failover를 구성한 뒤 Active DB를 직접 중단했습니다. Failover 동안 **읽기는 유지됐고, 쓰기는 수 초 지연된 뒤 재개**됐습니다. 구성 완료를 무중단으로 표현하지 않고 읽기와 쓰기가 실제 장애에서 어떻게 달라지는지 구분해 확인했습니다.

## 운영의 아쉬움을 다음 환경에서 다시 설계했습니다

Grafana·Loki·Prometheus로 여러 서버를 관측하고 Jenkins·SonarQube로 개발 흐름을 자동화했지만, 운영 도구까지 Public 환경에 둔 점이 남았습니다. 이 문제를 다음 프로젝트로 넘기지 않고 개인 서버를 구축해 **서비스 공개 필요 여부에 따라 접근 경계를 다시 설계**했습니다.

# Project Detail — Home Server

TeenyFinny에서 남은 Public 운영 문제를 다시 다루기 위해 미니 PC에 Linux 서버를 구축했습니다. **접근 경계부터 장애 진단, 자동화까지 직접 운영하고 그 환경을 다시 팀 프로젝트에 사용했습니다.**

2026.01 ~ 현재 · 개인 프로젝트  
Infrastructure · DevOps  
Ubuntu · Docker · Nginx · Tailscale · Cloudflare Tunnel · Grafana

## 공개 필요 여부에 따라 접근 경로를 나눴습니다

처음에는 SSH와 비밀번호 관리자까지 포트포워딩으로 열어 두었습니다. 이후 **내부 서비스는 Tailscale, 공개 서비스는 Cloudflare Tunnel → Nginx**로 분리하고 기존 포트포워딩을 제거했습니다. 변경 뒤 공인 포트 차단, VPN 내부 접속, 외부 공개 서비스 응답을 각각 확인했습니다.

## 방화벽 설정보다 실제 노출 경로를 확인했습니다

Docker Published Port가 호스트 방화벽 정책과 별개로 노출될 수 있음을 확인했습니다. 외부 접근이 필요 없는 컨테이너는 Published Port를 없애고 Docker Network 내부에서만 통신한 뒤 Nginx를 거치게 했습니다. 설정값이 아니라 **실제로 외부에 열리는 경로**를 확인하며 경계를 다시 잡았습니다.

## 메트릭과 접속 경로를 대조해 장애를 좁혔습니다

VPN 경유 접속만 막혔을 때 메트릭과 서비스 상태로 서버 문제를 먼저 배제하고, 내부망과 VPN 경로의 차이에서 Tailscale node key 만료를 특정했습니다. 만료 기능을 끄는 대신 갱신을 자동화했고 이후 같은 장애는 재발하지 않았습니다. 이 과정에서 내부 상태가 정상이어도 **외부 접근 경로는 별도의 관측 대상**이라는 사각지대도 확인했습니다.

## 개인 서버를 팀의 품질 검증 환경으로 연결했습니다

GitLab Runner와 SonarQube를 직접 호스팅해 팀 프로젝트에 사용했습니다. Runner는 Private 환경에서 outbound로 작업을 가져오게 하고, 팀원이 열람해야 하는 SonarQube는 접근 권한을 둔 Public 접점으로 분리했습니다. 이 환경은 DailyBand의 **Build → Test → SonarQube → Quality Gate** 흐름으로 이어졌습니다.

# Project Detail — DailyBand

초보자가 온라인으로 합주하고 AI 피드백을 받을 수 있는 서비스입니다. **Spring 백엔드와 Storage·AI Worker의 연결 구조, CI/CD를 맡아 컴포넌트 사이의 계약과 실패 흐름을 정리했습니다.**

2026.07 ~ 2026.08 · 5주 · 팀 프로젝트  
Backend · Infrastructure · CI/CD  
Spring Boot · PostgreSQL · Redis · MinIO · FastAPI · Electron · C/C++ · GitLab CI/CD · SonarQube · AOO · JUCE  
**Result. 최종 발표에서 전체 기능 실시간 시연**

> 비공개 저장소입니다. 공개 가능한 범위에서 설계 판단과 검증 결과를 정리했습니다.

## 서로 달라진 계약을 실행 가능한 형태로 복구했습니다

공통 계약 없이 개발이 진행되면서 BE·Signaling·FE·AI의 엔드포인트와 데이터 형식이 달라졌습니다. AI Agent로 기존 BE를 역분석해 초안을 만들되 그대로 채택하지 않고 **다른 Agent의 검토 → 팀의 실제 구현 대조 → FastAPI Mock Server와 API Docs 확인**을 거쳤습니다. 복구에 1주가 들었지만 통합을 완료했고 이후 같은 유형의 계약 불일치는 재발하지 않았습니다.

## 저장 책임과 도메인 책임을 나눠 변경 범위를 줄였습니다

MP3·MIDI·MusicXML·JSON마다 스토리지 메타데이터가 반복될 수 있어 객체 키·크기·해시 같은 정보는 `files`에, 음악 정보는 각 도메인에 두는 구조를 제안했습니다. 팀의 회의적인 의견에는 실제 사례와 중복 컬럼을 근거로 설명했고, 최종 구현에서 `files`는 **10개 테이블에서 13개 외래키**로 참조됩니다.

## 백엔드를 우회해도 파일은 검증했습니다

원본 1개가 결과 MP3 5개로 늘어나는 흐름에서 BE가 모든 파일을 중계하지 않도록 FE와 AI가 Presigned URL로 MinIO에 직접 업로드하게 했습니다. BE는 URL 발급·완료 신호·Job 상태만 조정합니다. 직접 업로드로 생긴 신뢰 공백은 **업로드 전 SHA-256·크기·Content-Type 선언 → 업로드 후 실제 객체 대조**로 보완했습니다.

## 트랜잭션 밖의 AI 실패를 별도 상태로 회수했습니다

DB에 Job을 기록하는 것과 외부 AI Worker에 작업을 보내는 것은 서로 다른 시스템입니다. DB가 rollback됐는데 Worker만 실행되는 상태를 피하려고 **Job commit → AFTER_COMMIT 비동기 dispatch** 순서로 분리했습니다. 커밋 뒤 dispatch 실패는 rollback할 수 없으므로 15초 주기의 Reconciler가 PENDING Job을 다시 보내거나 timeout 처리하게 했습니다.

## AI가 만든 코드도 같은 검증 흐름을 통과시켰습니다

AI Agent로 여러 언어의 코드를 빠르게 작성하되 생성 결과를 신뢰의 근거로 삼지 않았습니다. `Build → Test → SonarQube → Quality Gate → Deploy` 파이프라인과 테스트를 두고 **Quality Gate를 MR 병합 조건**으로 연결했습니다. 실제 Quality Gate 미달 MR이 차단됐고, 도구의 판정 역시 입력 경로와 수정 비용을 확인한 뒤 적용했습니다.

## 수신 버퍼를 직접 제어하기 위해 네이티브 구조로 전환했습니다

합주 레이턴시를 **I/O · Network · Receive Buffer**로 나눠 보니 사용자 장비와 ISP 경로는 팀이 직접 줄이기 어려웠습니다. 브라우저 스택에서는 수신 버퍼를 직접 통제하기 어려워 AOO·JUCE 기반 네이티브 구조로 전환했습니다. 이후 실제 Wi-Fi 환경에서 버퍼를 20ms와 40ms로 바꿔 비교했고, 20ms에서 발생하던 음 끊김을 40ms에서 줄이는 대신 지연이 늘어나는 **안정성과 레이턴시의 절충**을 확인했습니다.
