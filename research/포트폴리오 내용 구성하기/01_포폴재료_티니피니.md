## 1. 재료 목록

### 1.1 계정계와 채널계를 분리해 금융권 구조를 모사하기

**상황**
금융 서비스를 처음 다루면서 실제 은행 시스템이 어떻게 구성되는지 감을 잡아야 했다. 실제 코어뱅킹 시스템을 사용할 수 없는 교육 환경이었다.

**구현**
채널 서버와 코어 서버를 별도 애플리케이션으로 분리하고 HTTP REST로 연결했다. 코어 서버는 실제 은행 계정계를 대신하는 Mock으로 두고 계좌·이체 등 핵심 금융 데이터를 담당하게 했다. 채널 서버는 사용자 서비스와 비즈니스 로직을 맡았다. `[실물]` 저장소 2개로 분리, Notion `02. DB설계`에 구조 기록

**판단**
현업 개발자와 강사의 조언을 바탕으로 결정했다. 하나의 애플리케이션으로 만들 수도 있었지만, 실제 금융권 구조를 경험하는 것이 교육 목적에 맞다고 보았다. 실제 코어뱅킹은 C/C++ 기반이라고 전해 들었고 팀은 Spring으로 구현했다. `[답변]`

**검증**
두 서버가 REST로 연동되어 동작했다. `[실물]`

**한계**
분리 아이디어는 멘토·강사 조언에서 나왔으므로 **본인의 독자적 설계로 표현하지 않는다.** 실제 코어뱅킹이 C/C++ 기반이라는 것은 전해 들은 내용이므로 포트폴리오 본문에 사실로 단정하지 않는다. 은행 앱 점검 시간에 이루어지는 배치 기반 대규모 거래 처리도 개념만 학습했고 구현은 팀원이 했으며 세부를 설명할 수 없으므로 재료로 쓰지 않는다.

**활용**
Projects 요약의 첫 줄. 면접에서 `왜 두 서버로 나눴나요?`가 나오면 조언 출처를 밝히고 학습 의도를 답한다. **금융권 지원 시 도메인 이해도를 보여주는 카드.**

### 1.2 계약을 먼저 정하고 구현하기

**상황**
처음 PL을 맡았고, 5인이 같은 저장소에서 작업하는데 예외 처리와 응답 형식의 기준이 없었다. 프론트엔드와 백엔드가 병행 작업해야 했다.

**구현**
API 명세를 먼저 설계하고, 그 규격에 맞는 응답이 나오도록 `BaseEntity`와 `BaseException`을 직접 작성했다. 프론트엔드는 Postman Mock Server를 기준으로 병행 작업했다. 이슈·PR 템플릿을 정의하고 Notion 기술 문서를 관리했다. `[답변]` `[실물]` Notion에 템플릿 정의와 PL 역할 조사 기록

**판단**
기능을 먼저 구현하며 형식을 맞춰갈 수도 있었지만 병행 작업이 전제였으므로 **계약을 선행해야 통합 비용이 줄어든다**고 보았다. PL 역할을 맡은 뒤 가장 먼저 PL의 역할을 조사했고, 문서와 산출물 관리·기술 이슈 관리가 주요 역할이라는 점을 확인한 뒤 이에 맞춰 행동했다. `[답변]` `[실물]`

**검증**
프론트엔드가 Mock Server 기준으로 작업한 뒤 실제 서버와 연결하는 데 큰 소요가 필요하지 않았다. `[답변]`

**한계**
`통합 소요가 적었다`는 본인 체감이며 측정값이 아니다. **절감 시간이나 비율을 만들지 않는다.**

**활용**
**핵심 재료.** 이 방식을 이미 성공시켰다는 사실이 있어야, 다음 프로젝트에서 같은 원칙을 지키지 못해 1주를 쓴 경험이 `처음 몰랐다가 배웠다`가 아니라 **`효과를 알던 원칙도 불확실성이 큰 환경에서는 지키기 어려웠다`** 는 이야기가 된다. 성장 서사의 출발점.

### 1.3 팀이 따를 공통 구조 세팅

**상황**
프로젝트 초기 구조를 잡아야 했다.

**구현**
JWT 기반 인증·인가를 설정하고 DB 연결, `BaseEntity`, `BaseException` 등 협업의 기준이 될 공통 구조를 세팅했다. `[답변]` `[실물]` `auth` 모듈과 Spring Security + JWT 의존성 확인

**판단**
인증은 정석대로 JWT로 구현했다. **이후 서버를 이중화하면서 이 선택의 이점을 체감했다.** 세션 방식이었다면 서버를 늘릴 때 세션 공유를 함께 해결해야 했다. `[답변]`

**검증**
공통 클래스가 API 명세 규격에 맞는 응답을 만들어냈고, 이 규격 위에서 Mock Server 기반 병행 작업이 가능했다. `[답변]`

**한계**
초기 세팅은 튜토리얼 수행으로도 읽힐 수 있다. **반드시 그 안에서 어떤 선택을 했는지(JWT stateless 선택 → 이중화 이점)와 함께 써야 한다.** 기능 모듈(`account` `transfer` `goal` `investment` 등)은 팀원 담당이므로 본인 구현으로 쓰지 않는다.

**활용**
**`백엔드 결정이 인프라 결과로 돌아온 경험`** 이라는 형태로 쓴다. `인프라를 아는 백엔드` 포지셔닝을 직접 뒷받침하는 재료.

### 1.4 이중화가 어디까지 버티는지 장애를 주입해 확인하기

**상황**
민감정보를 보호하면서 서비스가 멈추지 않게 하려면 무엇이 필요한지 판단해야 했다. 이중화 구성을 발표 자료에 그리는 것만으로는 Active DB 중단 시 서비스가 어떻게 보이는지 설명할 수 없었다.

**구현**
데이터베이스마다 MySQL 노드를 두 개 두고 ProxySQL로 읽기를 로드밸런싱했으며, Orchestrator로 Failover 플로우를 구성했다. AWS ALB와 Nginx로 로드밸런싱을 구성했다. `[실물]` `TeenyFinny_DB_cluster` 저장소, Notion `03. 담당 기능 개발`

**판단**
Active–Standby Failover는 분산 DB나 완전한 재해 복구가 아니다. 읽기와 쓰기가 같은 방식으로 동작한다고 가정할 수 없어 **구분해서 확인해야 한다**고 보았다. 민감정보가 저장되는 DB는 온프레미스에, 확장이 필요한 백엔드 서버는 클라우드에 두는 하이브리드 구성도 같은 맥락의 판단이다. `[답변]`

**검증**
**Active 데이터베이스를 실제로 중단시켜 확인했다.** Failover가 완료되는 동안 읽기 작업은 계속 동작했고, 쓰기 작업은 **수 초 지연된 뒤 재개되었으며 실패로 이어지지 않았다.** `[답변]`

**한계**
- **무중단이 아니라 커넥션 타임아웃 안에서 흡수된 지연이다.** Failover가 길어지면 쓰기는 실패할 수 있다
- 중단된 노드가 복구되어 복제를 재구성하는 동안 요청이 들어오면 정합성 문제가 발생할 수 있다
- `Nginx Retry로 쓰기가 성공했다`는 설정 확인 전까지 쓰지 않는다. 프록시 계층 재시도는 금융 도메인에서 이중 처리 위험이 있다 `[미확인]`

**활용**
**세 프로젝트를 통틀어 가장 강한 검증 사례.** 구성으로 끝내지 않고 끊어봤다는 점, 결과를 읽기·쓰기로 나눠 말했다는 점이 핵심이다.

면접 반문 `쓰기가 왜 실패가 아니라 지연이었나요?` → 커넥션 획득 타임아웃이 Failover 시간보다 길어 대기 후 성공한 것으로 본다고 답하되, **설정 확인 전에는 관찰 사실만 말한다.**
면접 반문 `Nginx가 POST를 재시도했다면 중복 쓰기 위험은 없었나요?` → 프록시 계층 재시도가 금융 도메인에서 이중 처리 위험이 있음을 인지하고 있다고 답한다.

### 1.5 온프레미스와 클라우드를 연결하며 인증서 신뢰 관계 구성하기

**상황**
민감정보 DB는 온프레미스에, 백엔드 서버는 클라우드에 두기로 했고 두 환경을 연결할 방법이 필요했다.

**구현**
온프레미스와 클라우드 사이를 Cloudflare Tunnel로 연결했다. Spring이 데이터베이스 인증서를 신뢰하지 않아 SSL 연결이 거부되는 문제가 발생하자, **사설 CA를 구성해 데이터베이스용 인증서를 직접 발급하고 Spring TrustStore에 사설 CA 인증서를 등록**해 신뢰 관계를 구성했다. `[답변]` `[실물]` Notion `개발 중 이슈 — 고가용성 환경 구축`

**판단**
민감정보 격리와 확장성이라는 상충하는 요구를 환경 분리로 풀고, 그 대가로 생긴 연결·신뢰 문제를 해결했다. 서버와 DB를 다중화하는 것뿐 아니라 **분산된 환경에서 발생하는 네트워크 보안과 인증서 신뢰 관계까지 함께 고려해야** 안정적인 인프라를 구성할 수 있다는 것을 이 과정에서 확인했다. `[답변]` `[실물]`

**검증**
Spring 서버와 온프레미스 데이터베이스 간 SSL 연결을 정상화했다. `[답변]`

**한계**
**`인증서가 만료되었다`고 쓰지 않는다.** 신뢰 관계 미구성이 원인이다.

**활용**
면접 반문 `MySQL은 TCP인데 Cloudflare Tunnel로 어떻게 연결했나요?` → 클라이언트 측 TCP 매핑 구성을 확인해 답하고, **엣지 경유로 RTT가 추가되는 트레이드오프도 함께 말한다.** `[미확인]` 구성 확인 필요

### 1.6 기술 갈등을 요구사항 대조로 중재하기

**상황**
청소년 대상 실시간 주식 시세 조회 기능에서 웹소켓과 폴링 중 팀원 의견이 갈렸다. 한 명은 실시간성을 위해 웹소켓을, 다른 한 명은 연결 유지 비용을 이유로 폴링을 주장했다.

**구현**
두 기술의 특징과 장단점을 조사해 문서로 정리하고 팀에 공유했다. 웹소켓은 실시간성·양방향 통신에 강점이 있으나 연결을 지속 유지해야 하고, 폴링은 주기적 조회로 구현이 단순하다는 점을 정리했다. `[실물]` Notion `개발 중 이슈 — 팀원 간의 기술 갈등`, 공유 문서 `Teenyfinny의 분산환경 세팅`

**판단**
기술의 장단점만 비교하지 않고 **프로젝트 요구사항과 대조했다.** 서비스 목적은 청소년의 소액 투자 경험이었고, 초저지연 실시간성이나 양방향 통신이 필요한 기능이 없었으므로 폴링을 선택했다. `[답변]` `[실물]`

**검증**
팀이 폴링을 채택했다. 이후 새로운 기술 도입 시 개요와 특징을 먼저 조사·문서화해 공유하는 습관이 생겼다. `[실물]` Notion 회고

**한계**
`갈등을 해결했다`를 리더십 성과로 부풀리지 않는다. **조사·공유·요구사항 대조라는 행동으로만 쓴다.**

**활용**
**채택하지 않은 대안을 이유와 함께 기록한 사례.** 기술은 장단점만 비교하는 것이 아니라 프로젝트의 목적과 요구사항을 함께 고려해 선택해야 한다는 결론이 명시적으로 남아 있다.

### 1.7 테스트를 형식이 아니라 게이트로 운영하기

**상황**
5인이 병행 작업하는 상황에서 코드 품질 기준이 필요했다.

**구현**
Unit Test를 작성하고 **테스트 커버리지 컷을 80%로** 걸었다. Jacoco 보고서를 SonarQube에 연결했다. `[답변]` `[실물]` `build.gradle`의 SonarQube·Jacoco, `src/test` 디렉터리 존재

**판단**
테스트를 작성 여부로만 두지 않고 **통과 기준을 수치로 걸어 실제 개발 흐름에서 작동하게** 했다. `[답변]`

**검증**
`[미확인]` 게이트가 실제로 무엇을 막았는지에 대한 근거가 아직 없다.

**한계**
커버리지 80%가 **전체 코드 기준인지 신규 코드 기준인지 확인되지 않았다.** 확인 전에는 `커버리지 80%를 유지했다`고 단정하지 않는다.

**활용**
면접 반문 `커버리지 80%를 채우려고 형식적인 테스트를 쓰지 않았나요?` → **의미 있는 테스트 사례 한 건을 준비해 제시한다.** 공개 저장소의 `src/test`에서 확보할 수 있으므로 가장 값싼 보강이다.

### 1.8 의사결정을 설명하는 기술 발표

**상황**
교육 과정 최종 발표에서 팀의 기술 선택을 외부 심사위원을 포함한 청중에게 설명해야 했다.

**구현**
직접 그린 인프라 구조도와 PPT 애니메이션으로 웹소켓·폴링 의사결정, 무중단 배포, DB 이중화를 교육생·강사·멘토·외부 심사위원에게 설명했다. `[답변]` `[실물]` 발표 PDF가 Notion에 첨부되어 있음

**판단**
발표에서도 **구현 범위를 분산이 아닌 이중화로 구분하고, 읽기 성공만 강조하지 않고 쓰기 지연을 함께 제시했다.** `[답변]`

**검증**
은행 IT 개발 관련 외부 심사위원이 **재해 복구를 직접 고민해 본 흔적이 느껴진다**는 취지의 긍정적 피드백을 남겼다. `[기억]`

**한계**
- 피드백은 기억에 따른 요약이며 **공식 평가표나 축어 인용이 아니다**
- 우수팀 선정의 공식 사유는 확인되지 않았으므로 **발표가 수상을 만들었다고 쓰지 않는다**
- 애니메이션 제작 주체와 청중 이해 효과는 본인 체감이며 객관 검증되지 않았다

**활용**
`설명에서 검증으로` 흐름의 한 축. 핵심은 발표를 잘했다는 자기평가가 아니라 **선택과 결과를 다른 사람이 검토할 수 있는 구조로 바꿨다는 행동**이다.

### 1.9 무중단 배포를 위한 상태 점검 구성

**상황**
서버를 이중화하면서 응답 없는 서버로 트래픽이 가지 않게 해야 했다.

**구현**
Spring Actuator 기반 HealthCheck와 Readiness를 설정해 Nginx가 주기적으로 확인하고, 응답 없는 서버로는 트래픽을 전달하지 않도록 구성했다. `[답변]` `[실물]` Actuator 의존성 확인

**판단**
무중단 배포와 재해 복구 양쪽에 같은 상태 점검을 활용했다. `[답변]`

**검증**
`[미확인]` 무중단 배포를 실제로 수행해 확인한 근거는 확보되지 않았다.

**한계**
`무중단 배포를 구현했다`까지만 쓰고 **무중단이 검증되었다고 확대하지 않는다.**

**활용**
1.3의 JWT stateless 선택과 함께 **`백엔드와 인프라의 경계에 있는 작업`** 사례로 쓴다.

### 1.10 DevOps·모니터링 환경 구축과 남은 아쉬움

**상황**
온프레미스와 클라우드에 여러 서버를 운영하게 되면서, 장애 확인과 로그·상태 점검을 위해 서버마다 SSH로 접속해야 했다. 서버가 늘수록 원인 파악에 시간이 걸렸다.

**구현**
Grafana에 Loki와 Prometheus를 연동해 여러 서버의 로그와 메트릭을 한 곳에서 확인하는 통합 모니터링 환경을 구축했다. Jenkins와 SonarQube를 도입해 빌드와 정적 분석을 자동화했다. `[실물]` Notion `개발 중 이슈 — DevOps와 모니터링 환경 구축`, `Jenkinsfile` 존재

**판단**
운영 효율 문제를 도구 도입으로 풀었다. `[답변]`

**검증**
`[답변]` 운영 효율이 높아졌다는 본인 서술. 정량 근거는 없다.

**한계**
**DevOps와 모니터링 시스템을 퍼블릭 환경에서 운영한 점이 아쉬움으로 남았다.** 로그인 기능이 있더라도 운영 도구는 내부망 접근이 적절하다고 판단했으나 프로젝트가 끝난 뒤였다.

**활용**
**성장 흐름의 연결 고리.** 이 아쉬움이 개인 서버 구축의 직접적인 출발점이 된다.

## 3. 금지 문장

- `인프라 발표 덕분에 우수팀으로 선정됐다.`
- `완전한 재해 복구·분산 DB·DB 무중단 전환을 구현했다.`
- `Nginx Retry로 쓰기가 성공했다.` — 설정 확인 전 금지
- `커버리지 80%를 유지했다.` — 전체/신규 기준 확인 전 금지
- `인증서가 만료되어 SSL이 끊겼다.` — 신뢰 관계 미구성이 원인
- `계정계·채널계 분리를 독자적으로 설계했다.` — 멘토·강사 조언
- `실제 코어뱅킹은 C/C++로 되어 있다.` — 전해 들은 내용, 본문 단정 금지
- `배치로 대규모 거래를 처리했다.` — 팀원 구현, 설명 불가
- `통합 시간을 N% 줄였다.` — 측정값 없음
- `무중단 배포를 검증했다.` — 구성까지만 확인
- 기본 CRUD 기능 목록 나열
