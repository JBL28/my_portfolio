## 2. Section 종류별 처리 (H2 / Overview / Home Profile)

- 벡터 인덱스 노출 여부: `compute_section_embeddings()`(L376-387)이 `s["searchable"]`로 필터링하고, Overview는 `create_section(tx, overview, embedding=None)`(L715)로 호출돼 `SET s.embedding = null`이 실행된다 — Neo4j에서 프로퍼티에 `null`을 SET하는 것은 해당 프로퍼티를 제거하는 것과 같으므로, Overview 노드에는 `embedding` 프로퍼티 자체가 생성되지 않는다. `schema.cypher`의 벡터 인덱스는 프로퍼티가 없는 노드를 인덱싱하지 않으므로 Overview는 벡터 검색에 이중으로(searchable 플래그 + 프로퍼티 부재) 노출되지 않는다.

세 종류 모두 3.2/3.3 규칙대로 정확히 구분 처리된다.

## 3. Overview 조합 vs `ProjectOverview.tsx`

**확인함.** 두 코드를 나란히 대조했다.

`ProjectOverview.tsx`(L16-56) 렌더 순서: `<h1>{project.name}</h1>` → `summary` → `dl`(기간/팀 구성/담당/기술 스택/결과) → `repositoryNotice`(있을 때만, `project.repositoryNotice ? ... : null`).

`build_overview_body()`(`load_graph.py` L208-224) 조합 순서: `summary` → 빈 줄 → `기간: {period}` → `팀 구성: {teamSize}` → `담당: {roles join}` → `기술 스택: {technologies join}` → `결과: {result}` → (있을 때만) 빈 줄 + `repositoryNotice`.

- 필드 순서와 필드 목록이 정확히 일치한다. `project.name`은 body에 반복되지 않고 `build_overview_section()`의 `title`(L231)로만 표현되는데, 이는 TSX의 `<h1>`이 `body`가 아니라 별도 요소로 분리돼 있는 것과 개념적으로 대응한다(설계 3.2 "Overview Section의 title은 프로젝트 이름을 그대로 쓴다"와 일치).
- `repositoryNotice` 처리: `.get("repositoryNotice")`로 필드 **존재 여부**만 확인하고, `repositoryVisibility` 값으로부터 새 문구를 만들지 않는다(L220-222). TSX도 `project.repositoryNotice ?` 조건으로 동일하게 존재 여부만 확인(L50-54).
- `repositoryVisibility: "unknown"`인 Home Server(`data/projects/home-server.json`)는 `repositoryNotice` 필드 자체가 없음을 직접 확인했다 — `build_overview_body()`는 이 경우 `repository_notice = None`이 되어 아무 문구도 추가하지 않는다. 원문에 없는 문구를 만들어내지 않는다는 요구사항을 만족한다.
- `technologies` 사용처: `build_overview_body()`는 `project["technologies"]`(표시용 원본, 정규화 이전 값)를 그대로 join한다(L215) — `create_project_uses_technology()`가 관계 생성 시에만 별도로 `normalize_technology()`를 호출하며(L550), Overview body 생성에는 정규화된 이름이 재사용되지 않는다. 설계 3.2의 "정규화된 이름은 관계 생성에만 쓰고 Overview.body 생성에는 다시 사용하지 않는다" 요구사항과 정확히 일치.

## 6. ID 처리 / 멱등성

**확인함.**

- Project/Section/Case: `data/`에 이미 있는 UUID를 `create_project`/`create_section`/`create_case`가 그대로 사용(별도 생성 로직 없음, `project["id"]`/`section["id"]`/`case["id"]` 직접 참조).
- Portfolio/Competency/Technology: `data/`에 id가 없으므로 `stable_id(*parts) = str(uuid.uuid5(_ID_NAMESPACE, ":".join(parts)))`(L101-102)로 파생. `uuid5`는 (namespace, name) 쌍이 같으면 항상 같은 UUID를 반환하는 결정론적 함수이고, `_ID_NAMESPACE`(L98)는 스크립트에 고정된 상수이며 `parts`(예: `"portfolio"`, `("competency", name)`, `("technology", canonical)`, `("overview", slug)`)도 매 실행마다 동일한 문자열이 재사용되므로, 재적재해도 항상 같은 id가 나온다 — 멱등성 요구(4장 7번)를 만족한다.
- 재적재 방식: `wipe_graph()`(`MATCH (n) DETACH DELETE n`, L415-417) 뒤 전체를 다시 생성 — 02_구현계획.md 0장이 확정한 "전체 삭제 후 재생성"과 일치. 삭제된 Case/Section/관계가 좀비로 남을 수 없는 구조(매번 완전히 비우고 다시 채움).
- 트랜잭션: `wipe_graph`부터 `create_influenced_relationships`까지 전부 `_rebuild_graph()`(L682-754) 하나의 함수 안에서 이뤄지고, `main()`이 이를 `session.execute_write(_rebuild_graph, ...)`(L821-831)로 단일 트랜잭션으로 호출한다. 스키마 적용(`apply_schema`, L395-404)은 Neo4j 제약상 별도 auto-commit으로 분리돼 있는데, 이는 신규 노드/관계 생성과 무관한 DDL이라 트랜잭션 원자성 요구와 충돌하지 않는다. 구현자의 "도중 실패 시 롤백" 주장은 코드 구조로 확인된다(단, 실제 Neo4j 서버에 대해 실행해 커밋/롤백을 관찰하지는 못했다 — 8절 참고).

## 7. 임베딩 처리

**확인함.**

- 대상 필터링: `compute_section_embeddings()`(L376-387)이 `searchable_sections = [s for s in all_sections if s["searchable"]]`로 `searchable=true` Section만 추출.
- `OPENAI_API_KEY` 부재 시 처리: `require_env("OPENAI_API_KEY")`(`main()` L767)가 값이 없으면 `require_env()`(L114-123) 내부에서 즉시 `RuntimeError`를 던진다. "조용히 건너뛰지 않는다"는 주장은 코드로 확인된다.
- 벡터 차원: `EMBEDDING_DIMENSIONS = 1536`(L74)이 `fetch_embeddings()`(L359-373)에서 응답 임베딩 길이 검증에 쓰이고(L367-371), `schema.cypher`의 `vector.dimensions: 1536`(L47)과 일치한다.
- 배치/정렬: `fetch_embeddings()`가 100개 단위로 배치 호출하고 `sorted(response.data, key=lambda d: d.index)`로 각 배치 내부 순서를 재보정한 뒤 `embeddings` 리스트에 순서대로 append — `zip(searchable_sections, embeddings)`(L385-387)로 짝지을 때 순서가 어긋나지 않음을 로직으로 확인했다(배치별 index는 해당 배치 입력 내 0-based 상대 인덱스이므로, 배치 간 순서는 루프 자체가 보장하고 배치 내 순서는 정렬로 보장 — 이중으로 안전).
- 개수 검증: `main()`이 `len(embedding_by_section_id) != searchable_count`이면 `RuntimeError`(L798-802)를 던져, 일부 Section만 임베딩되고 넘어가는 상황을 차단한다.

## 10. Cypher 문법

**확인함(문서 대조 기준), 실행 검증은 불가.**

- 제약조건: `CREATE CONSTRAINT <name> IF NOT EXISTS FOR (n:Label) REQUIRE n.id IS UNIQUE;` — Neo4j 5.x의 신규 구문(`FOR ... REQUIRE ... IS UNIQUE`, 구버전 `ON ... ASSERT` 아님)이 6개 라벨 전부에 올바르게 적용됨을 확인.
- 벡터 인덱스: `CREATE VECTOR INDEX <name> IF NOT EXISTS FOR (s:Section) ON (s.embedding) OPTIONS {indexConfig: {`vector.dimensions`: 1536, `vector.similarity_function`: 'cosine'}};` — Neo4j 5.13+에서 GA된 벡터 인덱스 구문과 일치한다.
- `apply_schema()`의 파싱: `text.split(";")` 뒤 `//`로 시작하는 줄을 필터링하는 방식은 현재 파일(주석이 항상 독립된 줄에만 있고, 문자열 리터럴 안에 `;`가 없음)에서는 안전하게 동작함을 확인했다. 다만 이 파싱 방식 자체는 견고하지 않다 — 향후 이 파일에 `;`를 포함한 문자열 리터럴이나 코드와 같은 줄에 붙는 inline 주석이 추가되면 깨질 수 있다(12절 "사소한 문제" 참고).

## 11. Python 문법/구조

**확인함(육안 대조), 실제 인터프리터 실행은 불가.**

- import 순환 없음: 단일 스크립트 파일이 `neo4j`/`openai`/`dotenv`(외부 패키지)만 참조하고 내부 모듈 간 상호 import가 없다.
- 경로 계산 검증: `SCRIPT_DIR`(`apps/ai-server/scripts`) → `AI_SERVER_DIR`(`apps/ai-server`) → `REPO_ROOT = AI_SERVER_DIR.parent.parent`(저장소 루트)로, 실제 디렉터리 구조(`apps/ai-server/scripts/load_graph.py`, `data/`가 저장소 루트 바로 아래)와 대조해 정확함을 확인했다.
- 오탈자·명백한 논리 오류 없음: 함수별로 인자 전달·딕셔너리 키 접근·옵셔널 필드 처리(`case.get(...)`)를 전부 추적했으며, 발견된 문제 없음.
- `ManagedTransaction`을 타입힌트로 쓰는 모든 `create_*` 함수가 `_rebuild_graph()` 안에서만 호출되고, `_rebuild_graph`는 `session.execute_write(_rebuild_graph, ...)`로 호출된다 — `neo4j` 드라이버의 `Session.execute_write(transaction_function, *args, **kwargs)` 시그니처(첫 인자로 `tx` 자동 주입)와 일치하는 사용법이다. 다만 `neo4j` 패키지 최상위에서 `ManagedTransaction`이 실제로 import 가능한지는 실행 환경 없이 100% 확정할 수 없다(13절 참고).

## 13. 실행 필요(검증 불가) 항목 (3건)

이 환경에는 Docker/Python 런타임/Neo4j 인스턴스/OpenAI API 키가 전혀 없어 아래는 정적으로 "설계 문서·SDK 문서 지식과 대조해 그럴듯하다"까지만 확인했고, 실제 실행으로 재현하지 못했다. 구현자도 동일하게 실행 검증을 하지 못했다고 명시했으며, 나 역시 독립적으로 실행할 수 없었다.

1. **`from neo4j import Driver, GraphDatabase, ManagedTransaction, Session`가 `neo4j>=5.24,<6` 버전에서 실제로 이 이름들을 최상위에서 export하는지, `Session.execute_write(fn, **kwargs)`의 시그니처가 코드가 가정한 그대로인지** — 패키지를 설치할 수 없어 확인 불가. 사용자의 홈서버 환경에서 `pip install "neo4j>=5.24,<6"` 후 `python -c "from neo4j import Driver, GraphDatabase, ManagedTransaction, Session"`으로 1차 확인 필요.
2. **`schema.cypher`의 `CREATE VECTOR INDEX ... OPTIONS {indexConfig: {...}}` 구문이 사용자의 실제 Neo4j 서버 마이너 버전에서 에러 없이 적용되는지** — 벡터 인덱스는 Neo4j 5.13+에서 GA됐다는 것은 문서 지식 수준에서만 확인했다. 실제 서버 버전이 그보다 낮으면 이 DDL 자체가 실패한다. `Neo4j Browser`에서 직접 `db/schema.cypher`를 실행해 확인 필요.
3. **OpenAI `client.embeddings.create(model="text-embedding-3-small", ...)` 응답이 `response.data[i].embedding`(1536차원)/`response.data[i].index` 형태로 오는지, `openai>=1.50,<2` SDK와 실제로 호환되는지** — API 키가 없어 호출 자체를 못 했다. 실제 호출 1회로 확인 필요.

이 세 가지 외에는 트랜잭션 커밋/롤백의 실제 동작(6절에서 코드 구조로는 확인했으나 실제 실패를 주입해 롤백을 관찰하지는 못함)도 실행 검증 대상으로 남아 있다.
