# 00. 데이터 원본 작성 검증보고서

> Phase 00(`data/` 디렉토리 JSON 작성) 산출물을, 00_기획.md·01_설계.md·00_GraphRAG 스키마 설계.md와 `research/포트폴리오 내용 구성하기/07_포트폴리오_v1.3.md` 원문에 직접 대조해 검증한 결과다. `00_구현보고서.md`의 주장을 그대로 신뢰하지 않고, 파일을 직접 읽고 스크립트로 원문 substring 매칭·참조 무결성·UUID 형식·Competency/Technology 목록을 재검증했다.

## 검증 방법

- 8개 JSON 파일 전부 `node`로 직접 파싱(문법 유효성 확인).
- 전체 31개 id를 UUID v4 정규식으로 재검사, 중복 여부 재검사(구현자 보고와 별개로 독립 재실행).
- `Case.sectionIds`, `Case.influencedByCaseIds`, `Project.buildsOnEvidenceSectionIds`, `Project.buildsOnProjectSlug`가 가리키는 대상이 실제로 존재하는지 스크립트로 전수 대조.
- `Case.competencies`가 7개 고정 목록 안에 있는지 전수 검사.
- `Project.technologies` / `Case.usedTechnologies` / `Case.consideredTechnologies`에 등장하는 전체 기술명 집합과 `technology-aliases.json`의 canonical 목록을 상호 diff.
- 모든 Section `body`, `profile.body`, 각 Project `summary`를 `07_포트폴리오_v1.3.md` 원문에서 정확히 substring으로 찾을 수 있는지 스크립트로 전수 대조(육안 대조에 의존하지 않음).
- Case의 `problem`/`judgment`/`action`/`result`/`learning`을 해당 `sectionIds`가 가리키는 Section `body`와 대조(문자 단위 substring 검사 + 불일치 건 수동 판독).

## 치명적 (1건)

### 1. `data/projects/home-server.json` `repositoryVisibility: "private"` — 원문에 근거 없는 추론

- **파일/필드**: `data/projects/home-server.json` line 12, `"repositoryVisibility": "private"`
- **원문 대조**: 07_포트폴리오_v1.3.md 어디에도 Home Server 저장소가 비공개라는 명시적 문장이 없다.
  - Home 카드(line 35-49): `[Detail] [Architecture]` — GitHub 버튼이 없을 뿐, "비공개 저장소" 같은 안내 문구가 없다.
  - Project Detail — Home Server(line 104-128): 저장소 공개 여부에 대한 언급 자체가 없다.
  - 대조군인 DailyBand는 `[Detail] [Architecture] [Demo]`(버튼 없음) **+** "> 비공개 저장소입니다. 공개 가능한 범위에서 설계 판단과 검증 결과를 정리했습니다."라는 **명시적 문장**이 함께 있어 `private`를 확정할 근거가 원문에 실제로 존재한다. Home Server는 이 명시적 문장이 없다.
- **왜 문제인가**: `00_기획.md` 공통 주의사항 1번 "더미 데이터, 문서에 없는 설명 ... 을 임의 추가하지 않습니다"와 요구사항 "모든 데이터는 실제 포트폴리오 원문을 기준으로 생성하며, 원문에 없는 사실을 추론하여 추가하지 않는다"를 정면으로 위반한다. `repositoryVisibility`는 AI가 "이 프로젝트 저장소는 공개인가요?" 류의 질문에 사실로 답변하는 근거 필드가 되므로, 확인되지 않은 값을 확정적 사실처럼 적재하면 안 된다.
- **구현자 스스로도 인지한 지점**: `00_구현보고서.md` 5.1이 "이것은 확정적 원문 근거가 아니라 유비 추론이며, 검증 담당자가 재확인해야 할 지점"이라고 명시적으로 자백했다. 재확인 결과, 이 추론은 근거가 부족하다고 판단한다 — GitHub 버튼의 부재는 "저장소가 없다" / "비공개다" / "카드 레이아웃상 생략했다" 등 여러 해석이 가능한 약한 신호이며, DailyBand처럼 명시적 안내 문장이 짝을 이루지 않는 한 확정할 수 없다.
- **참고**: TeenyFinny의 `repositoryVisibility: "public"`은 같은 방식(버튼 유무)의 추론이지만, "GitHub 버튼이 실제로 원문(Home 카드+Detail 카드)에 존재한다"는 것 자체는 원문에 있는 사실이고, 포트폴리오가 작동하지 않는 링크를 걸어둘 이유가 없다는 점에서 Home Server의 "버튼이 없다"는 부재 신호보다 훨씬 강한 근거다. TeenyFinny 건은 confirmed-OK로 분류했다(아래 참고).
- **권고**: Home Server의 `repositoryVisibility`를 `private`로 확정하지 말고, 원문에 없는 값임을 반영할 수 있는 처리(예: `unknown`/`null` 또는 사용자에게 실제 공개 여부를 확인받아 명시적 근거 문장을 원문에 추가) 중 하나를 다음 단계에서 결정해야 한다.

### 2. `data/projects/home-server.json` `teamSize: "1인"` — Detail 개요 블록 원문과 다른 값, 소스 불일치

- **파일/필드**: `data/projects/home-server.json` line 7, `"teamSize": "1인"`
- **원문 대조**:
  - Project Detail — Home Server 개요 블록(line 108): `2026.01 \~ 현재 · 개인 프로젝트` — "1인"이라는 표현이 **없다**. "개인 프로젝트"라고만 되어 있다.
  - "1인"이라는 문구는 **Home 카드**(line 38)에만 있다: `2026.01 \~ 현재 · 1인 · Infrastructure / DevOps`.
- **왜 문제인가**: `01_설계.md` 3.2는 Overview Section(및 그 소스가 되는 Project 메타데이터)을 "각 Project Detail 페이지 **상단의 개요 블록**"으로부터만 조합 생성한다고 명시했다. `00_구현보고서.md` 5.2는 바로 이 원칙에 따라 `roles` 필드를 Home 카드가 아닌 Detail 블록에서만 가져왔다고 명시적으로 판단·기록했는데, 같은 원칙이 `teamSize`에는 적용되지 않았다 — Detail 블록 원문("개인 프로젝트")이 아니라 Home 카드 원문("1인")에서 값을 가져왔고, 이 판단은 구현보고서 어디에도 기록되어 있지 않다(roles처럼 의도적으로 검토된 흔적이 없다).
  - 이로 인해 적재 시 자동 생성되는 Overview Section의 body에 "1인"이라는, Detail 페이지 원문에는 없는 표현이 들어가게 된다. "1인" ≈ "개인 프로젝트"로 의미가 같기는 하지만, 3.2가 "표시용 원본 필드"를 "화면에 그대로 보이는 원문 텍스트로 채움"이라고 요구한 기준에서 보면 소스 리전이 어긋난다.
- **권고**: Detail 개요 블록 원문 그대로 "개인 프로젝트"를 쓰거나, "1인"을 쓰기로 한다면 그 판단 근거(Home 카드 원문 인용)를 구현보고서에 명시해 다른 필드와 동일한 검토 수준을 갖추도록 한다.

### 3. Case `usedTechnologies` 중 일부가 Section 원문에 기술명이 직접 등장하지 않는데도 Project 기술 스택에서 소거법으로 채워짐

`00_구현보고서.md` 5.5는 Home Server Case3에서 "메트릭"이라는 표현만으로 Grafana를 넣지 않았다고 명시하며 "본인이 직접 썼다고 원문에서 확인되는 기술만"이라는 기준을 스스로 세웠다. 그런데 같은 기준이 아래 두 곳에는 적용되지 않았다.

- **DailyBand Case "공통 files 테이블로 파일 메타데이터 책임 통합"** (`data/rag/cases/dailyband.json`, id `e13719a0-288a-45e8-9aa5-99043f9ff896`) `usedTechnologies: ["PostgreSQL", "MinIO"]`
  - 이 Case가 가리키는 Section(`0138280f-7687-44a5-916d-dd64a46a69d1`, "반복되던 파일 메타데이터 책임을 한 곳으로 모았습니다")의 원문 어디에도 "PostgreSQL"/"Postgres"라는 단어가 없다. "`files` 테이블", "스키마", "10개 테이블이 `files`를 참조"라는 일반적인 RDB 용어만 등장한다. Project `technologies`에 PostgreSQL이 유일한 RDB라는 이유로(소거법) 채워 넣은 것으로 보인다.

Project 스택에 후보가 하나뿐이라는 소거법 추론이 완전히 근거 없는 것은 아니지만("메트릭"보다는 "테이블"/"MR"이 후보를 좁히는 데 더 유리한 것은 사실), 엄밀히는 기술명이 원문에 직접 등장하지 않으므로 같은 잣대로 재검토가 필요하다.
- **권고**: Home Server Case3과 동일한 기준을 적용해 두 항목을 제거하거나, 반대로 "Project 스택 소거법"을 공식적으로 허용 기준에 추가하고 Home Server Case3에도 소급 적용할지 결정한다. 현재 상태로는 기준이 Case마다 다르게 적용된 것으로 보인다.

## 사소 (3건)

### 4. `data/profile.json`에 `order` 필드 누락

- Section 스키마(00_GraphRAG 스키마 설계.md / 01_설계.md 3장)는 Section에 `order`를 요구하지만, `data/profile.json`(Home Profile Section)에는 `order` 키가 없다. Profile Section이 1개뿐이라 실질적 영향은 없지만, 스키마 필드 완전성 관점에서는 누락이다.

### 5. Case 필드에서 원문의 backtick(`` ` ``)·bold(`**`) 서식이 일부 생략됨

- 예: DailyBand Section `0138280f-...`의 `body`는 "공통 `` `files` `` 테이블"처럼 backtick을 유지하는데, 같은 내용을 옮긴 Case(`e13719a0-...`)의 `problem`/`result` 필드는 "공통 files 테이블"처럼 backtick 없이 적혀 있다(`**10개 테이블이 `files`를 참조**` → "10개 테이블이 files를 참조"). 사실 관계 오류는 아니고, Case 필드가 "검색·요약을 돕는 구조화 메타데이터"(01_설계.md 4장 2번)로 문자 그대로의 인용이 아니어도 되지만, Section body와 서식이 다르다는 점은 일관성 측면에서 참고할 만하다.

### 6. `technology-aliases.json`의 `GitLab` alias가 `GitLab CI/CD`로만 매핑됨

- `{ "canonical": "GitLab CI/CD", ..., "aliases": ["GitLab CI", "GitLab"] }` — "GitLab"이라는 단독 표기는 플랫폼 전체를 가리킬 수도 있는데, 같은 테이블에 별도 canonical로 `GitLab Runner`가 이미 존재한다. 사용자가 채팅에서 "GitLab"이라고만 입력하면 항상 `GitLab CI/CD`로만 정규화되어 `GitLab Runner` 관련 근거를 놓칠 가능성이 있다. 다만 이 테이블은 포트폴리오 사실 데이터가 아니라 검색 정규화용 유틸리티 테이블이므로(구현보고서 5.9에서 자체적으로 이 구분을 밝힘) 심각도는 낮게 판단한다.

- **TeenyFinny 0-Case 판단**: "운영의 아쉬움을 다음 환경에서 다시 설계했습니다" Section을 0-Case로 판단한 근거(앞부분은 이미 다룬 활동의 요약, 뒷부분은 TeenyFinny 자체가 아니라 다음 프로젝트로의 전환 서술)는 원문과 대조했을 때 타당하며, 01_설계.md 3.1이 정확히 이 상황을 예견하고 있었음("전자가 실제로 0개의 Case로 판단될 수도 있다").
- **CONSIDERED**: TeenyFinny(WebSocket)·DailyBand(WebRTC) 두 건 모두 명시적 비교 문맥이 원문에 있고, 01_설계.md 2장이 두 사례를 CONSIDERED 예시로 직접 인용하고 있어 근거가 확실함. (TeenyFinny 건은 "대신"/"vs" 문구가 문자 그대로 등장하진 않지만, 설계 문서가 이 사례를 CONSIDERED로 미리 승인한 것으로 간주함.)
- **DailyBand repositoryVisibility/repositoryNotice**: "private"이 원문의 명시적 문장("비공개 저장소입니다. 공개 가능한 범위에서 설계 판단과 검증 결과를 정리했습니다.")에 정확히 근거하며, `repositoryNotice` 필드도 원문과 토씨 하나 틀리지 않고 일치함.
- **TeenyFinny repositoryVisibility**: "public"은 Home 카드/Detail 카드에 실제로 존재하는 `[GitHub]` 버튼을 근거로 하며, 이는 원문에 실재하는 UI 요소를 근거로 한 판단이라 Home Server 건(부재 신호만으로 추론)보다 근거가 강함. 다만 엄밀히는 이것도 명시적 문장이 아닌 UI 신호 기반 추론이라는 점은 참고 사항으로 남긴다.
- **Case-USES vs Project-USES 구분(대부분)**: TeenyFinny 3건, Home Server 4건, DailyBand의 나머지 4건은 usedTechnologies 항목이 해당 Section 원문에 기술명으로 명시적으로 등장함을 확인함(위 "중요 3번" 2건 제외).
- **스키마 필드 완전성**: Project(id/name/slug/summary/period/teamSize/roles/result/repositoryVisibility/technologies/order/buildsOnProjectSlug/buildsOnEvidenceSectionIds)와 Section(id/title/body/anchor/order/searchable, profile 예외 제외), Case(id/title/summary/order/sectionIds + 원문에서 확인되는 범위 내의 problem/judgment/action/result/learning/competencies/usedTechnologies/consideredTechnologies/influencedByCaseIds)가 대체로 충족됨. problem/judgment/result/learning 등이 일부 Case에서 비어 있는 것은 01_설계.md 4장 2번이 "원문에서 확인할 수 없는 필드는 임의로 채우지 않는다"고 명시적으로 허용한 것이라 결함이 아님.
- **DailyBand의 `repositoryNotice` 추가 필드**: 00_GraphRAG 스키마의 옛 목록에는 없지만 01_설계.md 3.2/4장 3번이 "저장소 공개 여부 안내"를 Overview 소스 필드로 명시하고 있어 정당한 확장임.
- **Section에 `path` 필드가 없는 것(profile 제외)**: 01_설계.md 3.2가 H2 Section의 `path`는 프로젝트 slug로부터 기계적으로 도출 가능(`/projects/{slug}`)하다고 명시하므로, 데이터 파일에 중복 저장하지 않은 것은 설계 의도와 부합하며 문제가 아님.

## 종합 판정: **보완 필요**

Section 원문 일치, 참조 무결성, Competency/Technology 목록 준수, BUILDS_ON/INFLUENCED 근거, Case 분리 판단(TeenyFinny 0-Case 포함)은 스크립트 기반 전수 검증을 통과했고 매우 꼼꼼하게 작업되어 있다. 다만:

- **치명적 1건**(Home Server `repositoryVisibility: "private"`)은 프로젝트의 최우선 원칙("원문에 없는 사실을 추론하여 추가하지 않는다")을 정면으로 위반하는 확정적 사실 주장이며, 구현자 스스로도 근거 부족을 인지하고 재확인을 요청한 사안이므로 Neo4j 적재 전에 반드시 해소해야 한다.
- **중요 2건**(Home Server teamSize 소스 불일치, DailyBand 일부 Case의 usedTechnologies 소거법 추론)은 데이터 신뢰도에 직접 영향을 주지만 국소적이라 수정 범위가 작다.
- **사소 3건**은 스키마 완전성·서식 일관성 수준의 이슈로 데이터 정확성 자체에는 영향이 적다.

전체 재작업이 필요한 수준은 아니며, 위 6건(치명적 1 + 중요 2 + 사소 3)을 개별적으로 수정한 뒤 재검증하면 Phase 00을 종료할 수 있다고 판단한다.
