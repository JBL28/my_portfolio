# 02. Neo4j 스키마·적재 파이프라인 구현보고서

> Phase 02: `data/`(Phase 00 산출물)를 유일한 입력으로 삼아 Neo4j 그래프를 전체 재생성하는 스키마 DDL과 적재 스크립트를 `apps/ai-server/`에 구현한 결과를 기록한다. FastAPI 앱(Gate/Extract/Retrieve/Generate)과 Retrieve 스코어링 로직은 Phase 03 범위이므로 이번 Phase에는 포함하지 않았다.

**이 환경에서는 Docker·Python 런타임·Neo4j 인스턴스·OpenAI API 키가 전부 없어 스크립트를 실제로 실행할 수 없었다.** 아래 내용은 전부 정적 코드 리뷰(구문·타입·데이터 참조 관계를 눈으로 재확인)로 검증한 결과이며, "실행해서 성공했다"는 주장은 어디에도 포함하지 않았다. 실제 실행·연결 검증은 사용자의 홈서버 환경에서 이뤄져야 한다(01_설계.md 0장).

## 1. 만든 파일 목록

```
apps/ai-server/
  db/
    schema.cypher            # 제약조건(id UNIQUE) + Section.embedding 벡터 인덱스 DDL
  scripts/
    load_graph.py            # data/ → Neo4j 전체 재적재 스크립트
  pyproject.toml              # 의존성: neo4j, openai, python-dotenv
  .gitignore                  # __pycache__/.venv/.env 제외 (비밀 값 커밋 방지)
```

FastAPI 앱 코드(`app/main.py` 등), Retrieve 스코어링 로직은 만들지 않았다(Phase 03 범위, 과업 지시 그대로 준수).

## 2. `db/schema.cypher` — 제약조건 + 벡터 인덱스

- 노드 라벨 6개(`Portfolio`/`Project`/`Section`/`Case`/`Competency`/`Technology`) 전부에 `id` UNIQUE 제약을 건다. Neo4j 5.x 신규 구문(`CREATE CONSTRAINT ... FOR (n:Label) REQUIRE n.id IS UNIQUE`)을 사용했다 — 구버전의 `ASSERT` 구문이 아니다.
- `Section.embedding`에 벡터 인덱스를 생성한다: `vector.dimensions: 1536`, `vector.similarity_function: 'cosine'` — 02_구현계획.md 0장이 확정한 `text-embedding-3-small`(1536차원)과 01_설계.md 3.3의 cosine 유사도 요구사항을 그대로 반영했다.
- 모든 statement에 `IF NOT EXISTS`를 붙여 멱등하게 만들었다 — `load_graph.py`가 재적재할 때마다 이 파일을 다시 실행해도 안전하다(4장 7번 "멱등" 요구사항의 일부).

## 3. `scripts/load_graph.py` — 적재 로직 요약

### 3.1 실행 순서 (Neo4j를 건드리기 전에 검증을 전부 끝낸다)

1. 환경변수 확인(`NEO4J_URI`/`NEO4J_USER`/`NEO4J_PASSWORD`/`OPENAI_API_KEY`) — 하나라도 없으면 `require_env()`가 즉시 `RuntimeError`로 실패한다. 특히 `OPENAI_API_KEY`가 없을 때 조용히 건너뛰지 않고 실패하게 만든 것은 3.3의 "임베딩 없는 Section이 그래프에 올라가면 안 된다"는 취지를 그대로 코드로 옮긴 것이다.
2. `data/`(profile, projects/*, rag/cases/*, rag/technology-aliases)를 전부 읽고 `validate_and_assemble()`에서 참조 무결성을 검증한다 — 이 단계까지는 Neo4j에 연결조차 하지 않으므로, 검증 실패 시 기존 그래프는 손상되지 않는다.
3. OpenAI 임베딩을 생성한다(`compute_section_embeddings`) — 이 역시 Neo4j 연결 이전에 수행해, 임베딩 API 호출이 실패해도 그래프를 비운 채로 남기지 않는다.
4. Neo4j에 연결해 `schema.cypher`를 적용한다(제약조건/벡터 인덱스, 개별 auto-commit — Neo4j는 스키마 변경을 데이터 쓰기와 같은 트랜잭션에 섞을 수 없다는 제약이 있어 아래 5)와 분리했다).
5. `MATCH (n) DETACH DELETE n` 전체 삭제부터 마지막 관계 생성까지를 **하나의 명시적 쓰기 트랜잭션**(`session.execute_write(_rebuild_graph, ...)`)으로 묶었다. 애초 초안은 개별 `session.run()`(각각 auto-commit)을 순서대로 호출하는 구조였는데, 그러면 삭제 이후 생성 도중 예외가 나는 순간 그래프가 "비어 있는 채로 반쯤 재생성된" 상태로 남을 위험이 있어 리뷰 중에 트랜잭션 함수로 리팩터링했다. 이제는 중간에 실패하면 전체가 롤백되어 이전 그래프가 그대로 보존된다.

### 3.2 노드·관계 생성 로직 (01_설계.md 4장 6번 체크리스트 전부 커버)

| 노드/관계 | 만드는 함수 | 비고 |
|---|---|---|
| `Portfolio` | `create_portfolio` | 싱글턴. id는 `stable_id("portfolio")`(아래 3.4) |
| `Project` | `create_project` | `data/projects/{slug}.json`의 id/name/slug/summary/period/teamSize/roles/result/repositoryVisibility/order를 그대로 저장. `technologies`/`repositoryNotice`/`buildsOnProjectSlug`는 "00_GraphRAG 스키마 설계.md"의 Project 노드 프로퍼티 목록에 없으므로 노드 프로퍼티로 중복 저장하지 않고 관계로만 표현했다 |
| `Section` (H2) | `create_section` (project["sections"] 순회) | `path`는 `data/`에 없어 `f"/projects/{slug}"`로 스크립트가 조합 |
| `Section` (Overview, 자동 생성) | `build_overview_section` + `create_section` | 3.3 참고, body 조합은 4장에서 설명 |
| `Section` (Home Profile) | `create_section(profile, ...)` | `data/profile.json`을 그대로 사용 — 이미 id/title/body/path/anchor/order/searchable을 전부 갖고 있음 |
| `Case` | `create_case` | problem/judgment/action/result/learning은 있는 필드만 `SET c += $props`로 반영(없는 필드를 null로 덮어쓰지 않음) |
| `Competency` (7개 고정) | `create_competencies` | 아래 3.5 참고 |
| `Technology` (정규화) | `create_technologies` | `Project.technologies` + `Case.usedTechnologies` + `Case.consideredTechnologies`에 등장하는 모든 원문을 `technology-aliases.json`으로 정규화한 canonical 이름의 합집합만 생성 |
| `HAS_PROJECT` | `create_project` 내부 | `(Portfolio)-[:HAS_PROJECT]->(Project)` |
| `HAS_SECTION` | `create_profile_relationships`(Portfolio→Profile Section), `create_project_has_section`(Project→Overview/H2 Section) | |
| `HAS_CASE` | `create_case_relationships` | `(Project)-[:HAS_CASE]->(Case)` |
| `DESCRIBED_IN` | `create_case_relationships` | `case["sectionIds"]` 전부 순회 (최소 1개 — validate 단계에서 이미 보장) |
| `DEMONSTRATES` | `create_case_relationships` | `case["competencies"]` 순회 |
| `USES` (Case) | `create_case_relationships` | `case["usedTechnologies"]` |
| `USES` (Project) | `create_project_uses_technology` (프로젝트 순회 루프 내부) | `project["technologies"]` |
| `CONSIDERED` | `create_case_relationships` | `case["consideredTechnologies"]` |
| `BUILDS_ON` | `create_builds_on` | 모든 `Project` 노드가 생성된 뒤 별도 루프에서 처리(자기참조 그래프이므로 순서 문제 방지). `evidenceSectionIds` 관계 프로퍼티에 `project["buildsOnEvidenceSectionIds"]`를 그대로 채운다(3번 요구사항) |
| `INFLUENCED` | `create_influenced_relationships` | 모든 프로젝트의 `Case` 노드가 전부 생성된 뒤 마지막에 한 번에 처리 — DailyBand의 Case가 Home Server의 Case를 참조하는 것처럼 **프로젝트 경계를 넘는 참조**가 실제 데이터에 있기 때문에(`data/rag/cases/dailyband.json`의 `influencedByCaseIds: ["7417f494-...900-9c02-6bc36fe2dab1"]`가 `data/rag/cases/home-server.json`의 Case를 가리킴), 프로젝트별 루프 안에서 처리하면 순서에 따라 대상 Case가 아직 없을 수 있어 전체를 모은 뒤 마지막 단계로 분리했다 |

`validate_and_assemble()`은 위 표의 생성 로직이 실제로 성립하도록 미리 다음을 전부 검사한다: Section id 전역 유일성, `buildsOnProjectSlug`가 실재하는 프로젝트인지, `buildsOnEvidenceSectionIds`가 실재하는 Section인지, `buildsOnProjectSlug`가 없는데 evidence만 있는 모순이 없는지, Case의 `sectionIds`가 비어있지 않고 전부 실재하는지, `competencies`가 7개 고정 목록 밖의 값을 쓰지 않는지, `usedTechnologies`/`consideredTechnologies`/`Project.technologies`가 전부 `technology-aliases.json`으로 정규화 가능한지, `influencedByCaseIds`가 실재하는(다른 프로젝트 포함) Case id를 가리키는지. 실제 `data/` 3개 프로젝트·13개 Case·28개 기술 alias 항목을 손으로 대조해, 이 검증을 전부 통과하는 것을 확인했다(4장 참고).

### 3.3 Overview Section body 조합 방식 (3.2, 4장 3번)

`build_overview_body()`가 `apps/web/components/domains/project/ProjectOverview.tsx`와 **같은 필드·순서**로 조합한다:

1. `project.summary`
2. 빈 줄
3. `기간: {period}`
4. `팀 구성: {teamSize}`
5. `담당: {roles를 ", "로 join}`
6. `기술 스택: {technologies를 ", "로 join}`
7. `결과: {result}`
8. `repositoryNotice`가 있을 때만(`.get()`으로 존재 여부만 확인 — `repositoryVisibility` 값 자체로 문구를 새로 만들지 않음, ProjectOverview.tsx와 동일한 원칙) 빈 줄을 사이에 두고 그 문장 그대로 추가

`project.name`은 Overview Section의 `title`로 이미 표현되므로(3.2 — "Overview Section의 title은 프로젝트 이름을 그대로 쓴다") body 안에서 다시 반복하지 않았다. Overview Section의 `id`는 `stable_id("overview", slug)`로 프로젝트 slug로부터 결정론적으로 파생해, 재적재할 때마다 같은 프로젝트면 같은 id가 나오게 했다. `searchable=False`, `path=f"/projects/{slug}"`, `anchor="overview"`로 고정했다(3.2 그대로).

### 3.4 ID 안정성 — Portfolio/Competency/Technology

`Project`/`Section`/`Case`는 `data/`에 이미 UUID가 박혀 있어(02_구현계획.0장 "ID 생성 방식: UUID v4") 그 값을 그대로 쓴다. 반면 `Portfolio`(싱글턴이라 파일 자체가 없음)·`Competency`(스크립트 상수가 원본)·`Technology`(alias 파일에 canonical 이름만 있고 id 필드가 없음)는 `data/`에 id가 없으므로, 이름 문자열로부터 `uuid.uuid5(NAMESPACE, name)`로 결정론적 UUID를 파생시켰다(`stable_id()` 헬퍼, 고정 namespace UUID를 스크립트 상수로 둠). 재적재할 때마다 같은 이름이면 같은 id가 나와 3.2의 "ID 안정성" 취지를 벗어나지 않으면서도, 별도 id 필드를 `data/`에 새로 추가할 필요가 없었다.

### 3.5 Competency 7개 고정 목록을 둔 위치

`apps/ai-server/scripts/load_graph.py` 상단의 `COMPETENCIES: list[str] = [...]` 상수(협업/기술적 판단/문제 해결/운영/DevOps/AI 활용/학습 및 성장)가 유일한 원본이다. "00_GraphRAG 스키마 설계.md" 맨 아래 "## Competency" 목록을 그대로 옮겼고, 02_구현계획.md가 "Competency는 `data/`에 별도 파일을 두지 않는다"고 확정한 것과 일치한다. `validate_and_assemble()`이 모든 Case의 `competencies` 필드를 이 상수와 대조해, 정의되지 않은 값이 있으면 즉시 실패시킨다.

### 3.6 임베딩 (3.3)

- `searchable=true`인 Section만(H2 Section 대부분 + Home Profile Section) `compute_section_embeddings()`가 OpenAI `text-embedding-3-small`로 임베딩을 생성한다. Overview Section은 `searchable=False`로 만들어지므로 이 함수의 필터(`[s for s in all_sections if s["searchable"]]`)에서 자동으로 제외된다 — 3.2/3.3이 요구하는 "Overview는 임베딩 대상에서 제외"를 별도 예외 처리 없이 `searchable` 플래그 하나로 구현했다.
- OpenAI 응답의 각 임베딩 차원이 1536이 아니면 즉시 `RuntimeError`로 실패한다(`schema.cypher`의 벡터 인덱스 차원과 어긋나는 데이터가 조용히 들어가는 것을 방지).
- `fetch_embeddings()`는 100개 단위로 배치 호출하며, 응답의 `index` 필드로 한 번 더 정렬해 입력 순서와 어긋나지 않게 방어적으로 처리했다.

### 3.7 재적재 방식

02_구현계획.md 0장이 확정한 "전체 삭제 후 재생성"을 그대로 구현했다(`MATCH (n) DETACH DELETE n`, 3.1 참고). diff 기반 upsert는 만들지 않았다.

## 4. `data/` 전수 대조 결과 (정적 리뷰)

실제 파일을 읽고 스크립트 로직이 다음을 빠짐없이 처리하는지 하나씩 손으로 대조했다.

- **`data/profile.json`**: 필드 7개(id/title/body/path/anchor/order/searchable) 전부 `create_section()`이 그대로 소비. `searchable=true`라 임베딩 대상에 포함됨을 확인.
- **`data/projects/{teenyfinny,home-server,dailyband}.json`** 3개 파일: 각 파일의 `sections` 배열(4/4/6개, 총 14개 H2 Section)이 프로젝트별 루프에서 전부 순회됨을 확인. `buildsOnProjectSlug`(`null`/`"teenyfinny"`/`"home-server"`)와 `buildsOnEvidenceSectionIds`가 각각 `create_builds_on()`에서 대상 Project·evidence property로 정확히 이어짐을 확인 — 특히 TeenyFinny는 `buildsOnProjectSlug: null`이고 `buildsOnEvidenceSectionIds: []`라 `create_builds_on()`이 `target_slug is None`으로 조기 반환해 관계를 만들지 않는 것도 확인.
- **`data/rag/cases/{teenyfinny,home-server,dailyband}.json`** 3개 파일(teenyfinny 3개 + home-server 4개 + dailyband 6개 = 총 13개 Case)의 모든 필드(id/title/summary/order/sectionIds/problem?/judgment?/action?/result?/learning?/competencies/usedTechnologies?/consideredTechnologies?/influencedByCaseIds?)가 `create_case`/`create_case_relationships`에서 옵셔널 필드 존재 여부까지 포함해 처리됨을 확인. 특히 `dailyband.json`의 `0f20bbd4-...` Case가 갖는 `influencedByCaseIds: ["7417f494-...dab1"]`이 **다른 프로젝트 파일**(`home-server.json`)의 Case id라는 것, 그리고 `create_influenced_relationships()`가 모든 Case 노드 생성 이후 별도 최종 루프로 처리되어 이 참조가 순서 문제 없이 해결됨을 코드 흐름으로 재확인했다.
- **`data/rag/technology-aliases.json`**: 28개 canonical 항목의 alias 전부(`build_technology_lookup`)를 소문자 정규화해 사전에 넣는지 확인. 3개 Project의 `technologies`(합쳐서 중복 포함 23개, canonical 기준 20개), 그리고 모든 Case의 `usedTechnologies`/`consideredTechnologies`에 등장하는 원문 전부가 이 표에서 조회 가능함을 항목 단위로 대조했다 — 조회 실패 시 `normalize_technology()`가 예외를 던지므로, 만약 별칭 테이블에 없는 새 기술명이 `data/`에 들어오면 스크립트가 자동으로 실패한다(정규화 원칙을 코드가 강제).

## 5. 실행 검증을 하지 못한 부분과 이유 (명시)

**아래는 전부 실제로 실행해 확인하지 못했다.** 이 세션에는 Docker, 동작하는 Python 런타임(Windows Store alias만 있고 pip도 없음), Neo4j 인스턴스, OpenAI API 키가 전혀 없기 때문이다(작업 지시에 명시된 환경 제약). 검증 방법은 처음부터 끝까지 **정적 코드 리뷰**(구문을 눈으로 재확인, Cypher 문법을 Neo4j 5.x 문서와 대조, `data/` 파일을 직접 열어 스크립트 로직과 필드 단위로 대조)로 대체했다.

- `python apps/ai-server/scripts/load_graph.py`를 실제로 실행해본 적이 없다. `import json/os/sys/uuid`, `from neo4j import ...`, `from openai import ...` 등 임포트가 실제 설치된 패키지 버전과 100% 호환되는지, 특히 `neo4j` 드라이버의 `ManagedTransaction`/`Session.execute_write` API가 pyproject.toml에 명시한 버전 범위(`neo4j>=5.24,<6`)에서 정확히 이 시그니처로 존재하는지는 문서 기억에 기반한 것이며 실제 `pip install` 후 `python -c "import neo4j"` 등으로 확인하지 못했다.
- Neo4j 인스턴스가 없어 `schema.cypher`의 `CREATE CONSTRAINT`/`CREATE VECTOR INDEX` 구문이 실제 Neo4j 5.x 서버에서 에러 없이 적용되는지 확인하지 못했다. Neo4j 공식 문서 기준으로 구문을 작성했지만, 서버 버전에 따른 사소한 차이(예: `vector.dimensions`/`vector.similarity_function` 키 표기, 특정 5.x 마이너 버전에서의 지원 여부)까지는 실행 없이 100% 보장할 수 없다.
- OpenAI API 키가 없어 `client.embeddings.create(model="text-embedding-3-small", ...)` 호출이 실제로 1536차원 벡터를 반환하는지, 응답 스키마(`response.data[i].embedding`/`response.data[i].index`)가 openai 파이썬 SDK 최신 버전에서 정확히 이 형태인지 실행으로 확인하지 못했다.
- `python -m ast`로 문법 오류만이라도 기계적으로 확인하려 시도했으나, 이 환경의 `python`/`python3`는 실제로는 Windows Store 진입점(alias)이라 실행되지 않았다(`EXIT:49`로 즉시 종료 — 실제 인터프리터가 아님을 재확인). 따라서 문법 검증도 전부 손으로 한 줄씩 재확인하는 방식에 의존했다 — f-string 내 따옴표 중첩, 인접 문자열 리터럴 결합, `from __future__ import annotations`로 인한 `list[float] | None` 같은 PEP 604 문법의 3.11 호환성, 들여쓰기 일관성 등을 반복해서 확인했지만 실제 인터프리터의 검증을 대체할 수는 없다.
- 트랜잭션 리팩터링(3.1의 `_rebuild_graph` + `session.execute_write`) 이후의 최종 코드 경로를 실제 Neo4j에 대해 실행해 커밋/롤백 동작을 확인하지 못했다 — 로직상 올바르다고 판단했지만 이 역시 실행 검증은 아니다.
