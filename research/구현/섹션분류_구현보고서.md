# 프로젝트 상세 섹션 분류 구현보고서

> 이번 작업의 목표는 기능 추가 자체가 아니라 **유지보수**다. 프로젝트가 늘거나 분류명이 바뀌어도 같은 정책을 여러 화면에서 수정하지 않도록 구성했다. 상세 기준은 `01_설계.md` 5.7에 두고, `03_섹션분류_구현계획.md`에는 작업 순서만 남겼다.

## 1. 변경 범위

| 파일 | 역할 |
|---|---|
| `apps/web/lib/project-section-categories.ts` | 공통 표시 순서와 라벨의 단일 설정. 분류 타입도 이 목록에서 파생 |
| `apps/web/lib/project-section-groups.ts` | 분류 검증, 원본을 변경하지 않는 정렬·그룹화, 빈 그룹 제거 |
| `apps/web/types/portfolio.ts` | Section에 필수 category 타입 추가 |
| `data/projects/*.json` | 기존 24개 Section에 category만 추가 |
| `apps/web/components/domains/project/ProjectSectionGroup.tsx` | 분류 제목과 글 묶음의 위계 렌더링 |
| `apps/web/components/domains/project/ProjectDetailSection.tsx` | H3 제목과 그룹 내부 간격 적용 |
| `apps/web/app/projects/[slug]/page.tsx` | 기존 갤러리 아래에 그룹 목록 연결 |
| `research/프로젝트 기획_설계/01_설계.md` | 5.7에 유지보수 목표, 분류 기준과 배치 기록 |
| `research/프로젝트 기획_설계/03_섹션분류_구현계획.md` | 설계를 참조하는 작업 순서로 정리 |

## 2. 유지보수 판단

- 순서와 화면 이름을 프로젝트 JSON에 복사하지 않았다. 개별 글의 소속은 category로 지정하고 공통 표시 정책은 한 설정에서 관리한다.
- 분류 타입을 별도 문자열 목록으로 다시 작성하지 않고 공통 설정에서 파생했다. 설정과 타입이 서로 달라질 변경 지점을 줄였다.
- 그룹화와 화면 렌더링을 분리했다. 그룹화 함수는 원본 Section 배열을 정렬하거나 수정하지 않는다.
- JSON은 TypeScript 타입 검사의 대상이 아니므로 category가 누락되거나 잘못되면 해당 Section id를 포함한 오류를 낸다. 빌드에서 글이 조용히 사라지는 것을 방지한다.
- 기존 Section 컴포넌트의 본문·강조·증거·링크 처리와 서버 코드 강조를 재사용했다. 그룹 컴포넌트에는 분류 위계만 두었다.
- 기존 named export, Readonly props, 경로 별칭, 프로젝트 도메인 계층, Tailwind와 Server Component 컨벤션을 따랐다. 새 라이브러리나 클라이언트 상태는 추가하지 않았다.

## 3. 원문과 연결 보존

수정 전 데이터를 별도로 읽어 둔 뒤, 수정 후 JSON에서 category만 제거한 전체 객체를 깊은 비교로 대조했다. 네 프로젝트 모두 동일했다. 제목·본문·볼드·id·anchor·order·증거·링크·프로젝트 메타데이터는 변경하지 않았다.

화면의 H2는 분류 제목, H3는 기존 Section 제목이다. 제목 단계가 바뀌어도 기존 Section의 DOM id를 유지하므로 문단 링크와 citation 목적지는 동일하다. category는 표시용 값으로, AI 서버·Neo4j 적재·임베딩·파생 Case는 수정하지 않았다.

## 4. 실행 결과

ESLint, TypeScript noEmit 검사, Next.js production build가 모두 종료 코드 0으로 통과했다. 빌드에서 네 상세 페이지는 모두 SSG로 생성됐으며 `/api/chat`은 기존 동적 경로로 남았다.

그룹화 함수와 실제 브라우저 검증 결과는 `섹션분류_검증보고서.md`에 기록했다. 커밋·외부 배포·그래프 재적재는 수행하지 않았다.
