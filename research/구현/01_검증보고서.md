# 01. Next.js 정적 페이지 검증보고서

> 검증자는 구현자(01_구현보고서.md)의 보고를 신뢰하지 않고, `apps/web` 코드와 `data/` 원본, 그리고 직접 재실행한 빌드 산출물(`apps/web/.next/server/app/*.html`)을 대조해 아래 항목을 확인했다. 사용 환경: Node v24.19.0 / npm 11.x, Windows. Docker·Python 실행환경 없음(설계상 Phase 01은 Neo4j·FastAPI 없이 완결 가능하므로 검증 범위에 영향 없음).

## 0. 재실행 결과

- `apps/web`에서 `rm -rf .next && npm run build` 재실행 → 성공. `/`(○ Static), `/projects/{teenyfinny,home-server,dailyband}`(● SSG, `generateStaticParams`) 3개 모두 생성됨. 구현자 보고와 동일한 결과.
- `npm run lint` 재실행 → 오류/경고 없음(구현자 보고와 동일).
- `.next/server/app/index.html`, `.next/server/app/projects/{slug}.html`를 직접 grep으로 열어 `NEXT_HTTP_ERROR_FALLBACK` 문자열이 없음을 확인 — 구현자가 보고한 "params Promise 미처리로 인한 404" 버그가 재발하지 않음을 독립적으로 재확인했다(로그만 보지 않고 산출물 직접 대조).

## 1. 발견된 문제

### 1-1. [중요] Project Detail 페이지의 `<meta name="description">`에 마크다운 원문(`**...**`)이 그대로 노출됨

- 파일: `apps/web/app/projects/[slug]/page.tsx` (`generateMetadata`, `description: project.summary`)
- 근거: 재빌드한 산출물에서 3개 프로젝트 전부 확인됨.
  - `dailyband.html`: `<meta name="description" content="...서비스입니다. **고스트 기능의 FE·BE·AI·MinIO 연결 API와 파일·Job 구조, API 계약 복구, CI/CD를 맡아 컴포넌트 사이의 계약과 실패 흐름을 정리했습니다.**">`
  - `home-server.html`: `content="...구축했습니다. **접근 경계부터 장애 진단, 자동화까지 직접 운영하고 그 환경을 다시 팀 프로젝트에 사용했습니다.**">`
  - `teenyfinny.html`: `content="...관리 서비스입니다. 처음 PL을 맡아 **API 계약과 공통 백엔드 구조, 인프라와 개발 흐름을 정리하는 역할**을 맡았습니다.">`
- 원인: 페이지 본문(`ProjectOverview`, `ProjectCard`)은 `project.summary`를 `RichText`/`parseInlineRichText`로 파싱해 `**`를 `<strong>`으로 변환하지만, `generateMetadata`는 같은 `project.summary` 원문을 파싱 없이 그대로 `description`에 대입한다. 실제 화면(`<h1>`, `<p>` 등 방문자가 보는 태그)에는 이 문제가 없음을 별도 grep으로 확인했다 — 오직 `<meta>` 태그로만 새는 문제다.
- 영향: 00_기획.md FE 요구사항 "SSG를 활용하여 검색엔진에 최적화된 사이트를 구성해야 합니다"와 직접 관련된다. 검색엔진 결과 스니펫이나 SNS 링크 미리보기(OG description은 별도 미설정이라 이 description이 폴백으로 쓰일 가능성이 있음)에 별표가 그대로 노출되면 SEO/공유 품질이 떨어진다. 기능 자체가 깨지는 것은 아니라 "치명적"은 아니지만, 3개 프로젝트 페이지 전부에서 재현되는 실제 결함이라 "중요"로 분류한다.

### 1-2. [사소] `ProjectOverview`의 필드 순서가 설계 문서와 다름(기술 스택 ↔ 결과 순서 뒤바뀜)

- 파일: `apps/web/components/domains/project/ProjectOverview.tsx` (29–45행)
- 설계 근거: 01_설계.md 3.2 "프로젝트 소개 문장 + 기간·팀·담당·기술 스택·결과 + 저장소 공개 여부 안내"(193행), 4장 3번 "프로젝트 소개 문장, 기간, 팀 구성, 담당, `technologies`..., 결과, 저장소 공개 여부 안내"(234행), 2장 Extract 스키마 주석 "기간/팀 구성/담당 역할/기술 스택/결과"(72행) — 세 곳 모두 **기술 스택이 결과보다 먼저** 나열된다.
- 실제 구현 순서(DOM 순서, `<dl>` 내부): `기간` → `팀 구성` → `담당` → `결과` → `기술 스택`(→ 이후 `repositoryNotice`). 즉 결과와 기술 스택의 순서가 설계 문서와 뒤바뀌어 있다.
- 영향: 2열 그리드 레이아웃이라 시각적으로 크게 어색하지는 않고(기술 스택이 배지 목록이라 마지막에 전체 폭으로 두는 것 자체는 UI적으로 납득 가능한 선택), 데이터 값 자체는 원문 그대로이며 왜곡·누락은 없다. 다만 설계 문서가 세 군데에서 일관되게 명시한 순서와 다르므로 "사소" 문제로 기록한다.

## 2. 확인함 (문제 없음)

- **실제 렌더링 내용**: `.next/server/app/index.html`에 `id="profile"` 섹션, 헤드라인("팀이 함께 쓸 기준을 만드는 백엔드 개발자"), 프로젝트 카드 3개(TeenyFinny/Home Server/DailyBand)가 실제 텍스트로 존재함을 확인. 3개 Detail 페이지 모두 `NEXT_HTTP_ERROR_FALLBACK` 없이 실제 Section 본문(H2 제목 + body)이 렌더링됨을 확인.
- **데이터 무결성**: `lib/portfolio-data.ts`의 `getAllProjects()`/`getProjectBySlug()`가 동일한 `data/projects/{slug}.json`을 읽는 하나의 코드 경로를 공유함을 코드로 확인했고, 빌드 산출물에서도 DailyBand의 "SonarQube", "고스트 기능 연결 API" 같은 값이 Home 카드(index.html)와 Detail 개요(dailyband.html) 양쪽에 동일하게 나타남을 grep으로 재확인했다. `data/`의 원문 텍스트(예: `**강조**`, `` `files` `` 표기 포함)를 요약·가공하지 않고 `RichText` 파서로 태그만 씌워 그대로 렌더링함을 확인(본문 `<p>`/`<h1>`/`<li>` 등에서 별표 잔존 없음 — 1-1의 `<meta>` 이슈와는 별개).
- **Home Server `repositoryVisibility: "unknown"` 처리**: `data/projects/home-server.json`에는 `repositoryNotice` 필드가 없다. `ProjectOverview.tsx`는 `repositoryNotice` 필드의 **존재 여부**로만 분기하며(`{project.repositoryNotice ? ... : null}`) `repositoryVisibility` 값 자체를 문구로 노출하지 않는다. 빌드 산출물(`home-server.html`)에서 "공개"/"비공개" 관련 텍스트를 검색한 결과 매치는 전부 원문 Section 본문의 네트워크 설명("공개 서비스는 Cloudflare Tunnel..." 등)이며 저장소 공개 여부에 대한 임의 문구는 없음을 확인. TeenyFinny(`repositoryVisibility: "public"`, `repositoryNotice` 없음)도 동일하게 저장소 관련 문구가 렌더링되지 않음을 확인. DailyBand만 `repositoryNotice` 원문("비공개 저장소입니다...")이 그대로 노출됨을 확인. 원문에 없는 문구를 만들어내지 않는다는 원칙을 지켰다.
- **anchor 렌더링 규칙(01_설계.md 3.2)**: 3개 Detail 페이지 전부에서 `<section id="overview">`와 `<section id="{H2 slug}">`가 `data/projects/{slug}.json`의 `sections[].anchor` 값과 정확히 일치함을 grep으로 확인(예: `id="서로-달라진-계약을-실행-가능한-형태로-복구했습니다"`). Home의 Profile Section도 `<section id="profile">`로 렌더링됨을 확인. DB에는 `#` 없는 slug만 저장하고 렌더링 시 `id`로만 부여한다는 규칙과 일치.
- **컴포넌트 계층**: `apps/web/components/`가 `ui/`(Badge, Card, Container, ThemeToggle), `layouts/`(Header, Footer, PageLayout), `domains/project/`(ProjectCard, ProjectOverview, ProjectDetailSection)로만 구성되어 있음을 파일 목록으로 확인. `components/domains/chat`는 존재하지 않음(디렉터리 자체가 없음) — 이 Phase 범위 밖 요소를 만들지 않았다.
- **Server/Client 컴포넌트 경계**: 저장소 전체에서 `"use client"`가 있는 파일은 `components/ui/ThemeToggle.tsx` 단 하나뿐임을 grep으로 확인. Home/Detail 페이지, `ProjectCard`/`ProjectOverview`/`ProjectDetailSection`/`Header`/`Footer`/`PageLayout`/`Card`/`Badge`/`Container`는 전부 지시자 없는 Server Component. 다크모드 토글이라는 실제 상호작용에만 Client Component를 썼다는 설계 5.2 원칙과 일치.
- **범위 이탈 여부**: `apps/web/package.json`의 `dependencies`는 `next`, `next-themes`, `react`, `react-dom`뿐이고 `devDependencies`도 Tailwind/ESLint/TypeScript 표준 도구뿐이다. `axios`, `framer-motion`(`motion`), `shadcn`류 컴포넌트 라이브러리, 인증/CMS 관련 패키지 없음. 저장소 전체에서 `chat`/`api` 이름의 파일을 검색한 결과 `apps/web` 안에는 없음(=`/api/chat` 라우트, 채팅 위젯 모두 미구현, 구현자 보고와 일치하며 Phase 01 범위와도 일치).
- **비주얼 톤(5.5)**: 컴파일된 CSS에서 실제 `gradient` 배경 규칙은 없음(매치된 유일한 문자열은 Tailwind의 `transition` 기본값에 포함된 `--tw-gradient-from` 변수 목록으로, 실제 그라디언트 사용이 아님). 색상은 `zinc` 계열 무채색 팔레트만 사용되고 카드/뱃지 모두 얇은 보더 + 낮은 채도로 구성되어 "화려한 장식 없는 컴팩트 톤" 원칙과 일치.
- **다크모드/반응형(5.6)**: `app/layout.tsx`에서 `next-themes`의 `ThemeProvider(attribute="class", defaultTheme="system", enableSystem)`가 실제로 적용되어 있고, `app/globals.css`의 `@custom-variant dark (&:where(.dark, .dark *));`로 class 전략 재정의가 되어 있음을 확인. 컴파일된 CSS에서 `.dark\:border-zinc-700:where(.dark,.dark *){...}` 같은 규칙이 실제로 생성됨을 확인해 다크모드가 겉모습만이 아니라 실제로 동작하는 구조임을 검증했다. `sm:`/`lg:` 반응형 브레이크포인트가 그리드(`grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`)와 타이포(`text-2xl sm:text-3xl`) 등 여러 곳에서 실제로 쓰이고 있음을 확인.
- **데이터 파일 스캐폴딩**: `apps/web`에 `create-next-app` 기본 산출물(`README.md`/`next.config.ts`/`tsconfig.json`/`eslint.config.mjs`/`postcss.config.mjs`/`AGENTS.md`/`CLAUDE.md`)이 수정 없이 그대로 남아 있음을 확인 — 불필요한 설정 변경 없음.

## 3. 종합 판정

**보완 필요 (Minor revision required)** — 치명적 결함은 없다(빌드·라우팅·데이터 무결성·컴포넌트 경계·범위 준수는 모두 재검증 통과). 다만 아래 1건을 수정한 뒤 다음 Phase로 넘어가는 것을 권장한다:

- [중요] 1-1: `generateMetadata`의 `description`에 마크다운 원문이 그대로 노출되는 문제를 고친다(예: `parseInlineRichText`가 아니라 별표/백틱을 제거한 순수 텍스트만 추출하는 별도 유틸을 `lib/rich-text.tsx`에 추가해 `description`에 사용).
- [사소] 1-2: `ProjectOverview`의 `기술 스택`/`결과` 순서를 설계 문서(3.2/4장 3번) 순서에 맞게 조정할지 여부는 사용자 판단에 맡긴다(현재도 데이터 왜곡은 없고 UI적으로도 문제는 없어 보이므로, 굳이 안 고쳐도 치명적이지 않음).

문제 개수: 중요 1건, 사소 1건, 치명적 0건.
