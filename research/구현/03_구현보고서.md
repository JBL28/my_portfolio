# 03. FastAPI AI 서버 구현보고서

> Phase 03: `apps/ai-server/app/` 아래 FastAPI Graph RAG AI 서버를 완성한 결과를 기록한다. 이 Phase는 세션 도중 다른 작업자가 파이프라인(Gate1/Gate2/Extract/Retrieve/Generate)·스키마·Neo4j 클라이언트 코드를 만들다가 세션 한도로 중단됐고, 이번 세션이 그 나머지(`api/chat.py`, `app/main.py`, 이 보고서)를 이어서 마무리했다. 아래는 **이전 작업자가 만든 것 + 이번 세션이 만든 것을 합친 Phase 03 전체**를 기준으로 작성한다.

**이 환경에는 Docker·동작하는 Python 런타임(`python`/`python3`는 Windows Store alias 진입점뿐이라 실행 불가)·Neo4j 인스턴스·OpenAI API 키가 전혀 없다.** 아래 내용은 전부 정적 코드 리뷰(구문을 눈으로 재확인, 기존 pipeline 함수들의 실제 시그니처와 새 코드의 호출부를 한 줄씩 대조)로 검증한 결과이며, "실행해서 성공했다"는 주장은 포함하지 않는다. 실제 실행·연결 검증은 사용자의 홈서버 환경에서 이뤄져야 한다(00_구현보고서·02_구현보고서와 동일한 제약).

기존 pipeline/schemas/graph 코드는 한 줄도 리팩터링하지 않았다 — 과업 지시("기존 코드를 임의로 고치지 마라")를 그대로 따랐다. 문제로 보이는 지점은 고치지 않고 7장에 관찰로만 남겼다.

## 2. `app/api/chat.py` — POST /chat 오케스트레이션

01_설계.md 2장 순서를 그대로 코드로 옮겼다: `run_gate_portfolio` → (false면 조기 종료) → `run_gate_site` → (true면 조기 종료) → `run_extract` → `retrieve` → `run_generate`. 각 pipeline 함수 호출부는 실제 시그니처와 인자 순서를 하나씩 대조했다:

| 호출 | 실제 시그니처(기존 코드) | 일치 여부 |
|---|---|---|
| `run_gate_portfolio(client, latest_message, history)` | `(client: OpenAI, latest_message: str, history: list[ChatMessage]) -> Gate1Result` | 일치 |
| `run_gate_site(client, latest_message, history)` | `(client: OpenAI, latest_message: str, history: list[ChatMessage]) -> Gate2Result` | 일치 |
| `run_extract(client, latest_message, history)` | `(client: OpenAI, latest_message: str, history: list[ChatMessage]) -> ExtractResult` | 일치 |
| `retrieve(client, extract_result)` | `(openai_client: OpenAI, extract: ExtractResult) -> list[Candidate]` — 인자 순서가 `(openai_client, extract)` | 일치 (순서 확인함) |
| `run_generate(client, latest_message, extract_result, candidates)` | `(client: OpenAI, latest_message: str, extract: ExtractResult, candidates: list[Candidate]) -> GenerateResult` | 일치 |

엔드포인트 함수는 `async def`가 아니라 일반 `def`로 선언했다 — 내부에서 호출하는 OpenAI SDK·Neo4j driver 호출이 전부 동기(블로킹) 코드이기 때문에, FastAPI가 이런 경로 함수는 자동으로 스레드풀에서 실행해 이벤트 루프를 막지 않는다. `async def`로 선언했다면 이 블로킹 호출들이 이벤트 루프를 직접 점유해 동시 요청 처리를 막았을 것이다.

### 2.1 Gate 1 조기 종료 문구

00_기획.md 요구사항: `"포트폴리오와 관련된 내용이 아니라면 정해진 안내 문구를 답변합니다. (예시: 지원자에 대한 질문을 해주세요. 를 예의바르게)"`. 이 예시의 취지(정중하게 거절 + 포트폴리오 질문 유도)를 그대로 옮겨 고정 문자열로 만들었다:

> "죄송하지만 저는 이 포트폴리오 지원자의 프로젝트 경험과 역량에 관한 질문에만 답변드릴 수 있어요. 지원자에 대해 궁금하신 점을 질문해 주시면 도와드리겠습니다."

정확한 워딩은 01_설계.md/00_기획.md 어디에도 고정돼 있지 않으므로(예시일 뿐), 이 문구는 임의로 다듬어도 되는 자유도가 있다 — 필요하면 나중에 FE(Phase 04) 쪽 요구에 맞춰 바꿔도 설계를 벗어나지 않는다.

### 2.2 Gate 2 조기 종료 문구

00_기획.md: `"포트폴리오 그 자체에 대한 내용이라면 깃허브 링크를 안내합니다."` 실제 저장소 공개 URL은 01_설계.md 어디에도 확정돼 있지 않다는 과업 지시에 따라, `settings.github_repo_url`(이전 세션이 이미 `config.py`에 `GITHUB_REPO_URL` 환경변수로 준비해둠, 없으면 `None`)을 그대로 소비했다:

- 값이 있으면: `"...아래 GitHub 저장소에서 확인하실 수 있습니다: {url}"`
- 값이 없으면(`None`): `"...다만 지금은 저장소 링크를 안내해드리기 어렵습니다."` (링크 없이 안내만)

URL을 새로 지어내지 않았다.

### 2.3 대화 이력을 N=3턴으로 자르는 방식

`ChatRequest.messages`의 마지막 항목을 이번 질문(`latest_message = request.messages[-1].content`)으로, 그 앞부분(`request.messages[:-1]`)을 이력으로 삼는다. 02_구현계획.md 0장이 확정한 N=3(사용자 3개+어시스턴트 3개, 최대 메시지 6개)을 `_truncate_history()`에서 그대로 구현했다:

```python
def _truncate_history(history: list[ChatMessage]) -> list[ChatMessage]:
    max_messages = settings.context_window_turns * 2  # context_window_turns=3 (config.py)
    return history[-max_messages:] if max_messages > 0 else []
```

`history`는 이미 시간순(오래된 것 먼저)으로 온다고 전제하고 뒤에서부터 최대 6개만 남긴다 — `settings.context_window_turns`는 이미 이전 세션이 `config.py`에 `3`으로 고정해뒀으므로(02_구현계획.md 0장 "이미 확정된 설계 값이므로 배포 시점에 바꿀 이유가 없어 환경변수로 노출하지 않음"), 새 환경변수를 추가하지 않고 그 값을 그대로 참조했다.

이렇게 잘린 `history`를 Gate1/Gate2/Extract 세 곳 모두에 동일하게 넘긴다. 한 가지 파급 효과를 기록해둔다: `extract.py`의 `_collect_previous_citations(history)`는 인자로 받은 `history`에서만 이전 citations를 모으므로, 6개 메시지보다 더 이전 턴에서 나온 citations는 `refers_to_previous_citations`의 후보가 되지 않는다 — 이는 "최근 N턴만 본다"는 설계 결정의 당연한 귀결이며 버그가 아니다.

### 2.4 조기 종료 시 응답 형태

`schemas/chat.py`의 `ChatResponse` 클래스 주석이 이미 "Gate 1/2에서 조기 종료된 경우에도 같은 모양을 유지해 FE가 응답 형태를 분기하지 않아도 되게 한다 — isEvidenceSufficient=False, citations=[]로 채운다"고 명시해뒀으므로, 두 조기 종료 분기 모두 `ChatResponse(answer=..., isEvidenceSufficient=False, citations=[])` 형태로 반환한다.

### 2.5 OpenAI 클라이언트 재사용

`graph/client.py`의 `get_driver()`/`close_driver()`(모듈 전역 `_driver` 싱글턴)와 동일한 패턴으로, `api/chat.py`에도 모듈 전역 `_openai_client`를 두고 `_get_openai_client()`가 최초 호출 시 한 번만 `OpenAI(api_key=settings.openai_api_key)`를 생성해 재사용하게 했다. 요청마다 새 클라이언트를 만들지 않는다. (기존 `get_driver()`와 마찬가지로 락 없는 단순 None 체크라 이론상 콜드스타트 시점에 동시 요청이 들어오면 클라이언트 객체가 중복 생성될 수 있지만, 그래도 각 객체는 정상 동작하므로 실질적 문제는 없다 — 기존 코드와 동일한 수준의 단순성을 유지했다.)

## 3. `app/main.py` — FastAPI 진입점

`app/__init__.py`(이전 세션이 이미 패키지 개요 docstring에 "main.py — FastAPI 앱 진입점"이라고 이 파일의 존재를 예고해뒀다)의 설명대로 만들었다:

- `lifespan` 컨텍스트 매니저(FastAPI 최신 권장 방식, `on_event` 사용 안 함)를 정의해 앱 종료 시 `graph/client.py`의 `close_driver()`를 호출한다.
- `api/chat.py`의 `router`를 `app.include_router(chat_router)`로 등록한다(prefix 없음 — `router.post("/chat")`이 이미 최종 경로이므로 `POST /chat`이 그대로 노출된다).
- **CORS 미들웨어는 추가하지 않았다.** 01_설계.md 1장 핵심 원칙: "브라우저는 오직 Next.js(같은 origin)와만 통신한다"·"AI 서버 주소는 Next.js 서버 프로세스만 알고 있으며 클라이언트로 절대 전달되지 않는다" — 이 서버는 Next.js BFF에서만(같은 서버 프로세스 간 통신, 배포 경로에 따라 내부망 또는 Cloudflare Tunnel 경유) 호출되고 브라우저가 직접 호출하지 않으므로 CORS 설정 자체가 불필요하다고 판단했다. 인증 미들웨어(공유 시크릿 헤더 등)도 1장에서 "외부 배포 시에만 필요, 내부망 배포면 선택 사항"이라고 조건부로 남겨둔 사항이라 이 Phase에서 임의로 확정하지 않았다.

## 5. 기존(이전 세션) 코드에서 관찰됐지만 고치지 않은 사항

과업 지시("문제가 있다고 판단되면 고치지 말고 보고서에 남겨라 — 그건 검증 단계에서 다룬다")에 따라 코드는 그대로 두고 아래에만 기록한다.

- **`GenerateResult`의 `model_validator`가 예외를 던질 수 있는 경로**: `structured_outputs.py`의 `_check_citation_constraint`는 `is_evidence_sufficient=True`인데 `citations`가 비어 있으면 `ValueError`를 던진다. OpenAI Structured Outputs의 JSON Schema는 "타입/필수 필드" 같은 구조적 제약만 강제할 수 있고 "A가 true면 B가 비어있으면 안 된다" 같은 필드 간 조건부 제약은 강제할 수 없다 — 따라서 모델이 프롬프트 지시를 완벽히 따르지 못해 `is_evidence_sufficient=true`+`citations=[]` 조합을 반환하면, `client.beta.chat.completions.parse()` 내부에서 이 validator가 예외를 던지고 `generate.py`가 이를 잡지 않는다(`result = completion.choices[0].message.parsed`가 `None`이 아니라 애초에 예외로 끊길 수 있음). 결과적으로 `api/chat.py`의 `chat()` 함수까지 예외가 전파되고, `main.py`에 별도 예외 핸들러를 두지 않았으므로 FastAPI 기본 동작으로 500 에러가 반환된다. 드문 경계 케이스라고 판단해 고치지 않았지만, 실제 트래픽에서 관측되면 Gate/Generate 프롬프트 강화 또는 `try/except`로 `is_evidence_sufficient=False`로 강제 완화하는 방어 로직이 필요할 수 있다.
- **파이프라인 도중 예외에 대한 전용 에러 응답이 없다**: Neo4j 연결 실패, OpenAI API 오류(rate limit 등), 위 항목의 validator 예외 모두 FastAPI의 기본 500 응답으로만 처리된다. 01_설계.md 8장(관측성)이 Phase 05 범위로 명시돼 있어 이번 Phase에서 별도 에러 핸들링 계층을 추가하지 않았다 — 이 판단이 맞는지는 Phase 05에서 재검토가 필요하다.
- 그 외 pipeline/schemas/graph 코드 자체(Cypher 쿼리, 스코어링 가중치, 프롬프트 문구 등)는 01_설계.md 2~4장과 대조했을 때 구조적으로 설계를 벗어나는 지점을 찾지 못했다.

## 6. 실행 검증을 하지 못한 부분과 이유 (명시)

**아래는 전부 실제로 실행해 확인하지 못했다.** 00/02 구현보고서와 동일한 환경 제약(Docker·동작하는 Python 런타임·Neo4j 인스턴스·OpenAI API 키 전부 없음) 때문이다.

- `uvicorn app.main:app`으로 서버가 실제로 기동되는지, `app.include_router(chat_router)` 이후 `POST /chat` 라우트가 FastAPI 라우팅 테이블에 정확히 등록되는지 실행으로 확인하지 못했다.
- `POST /chat`에 실제 JSON 바디를 보내 Gate1→Gate2→Extract→Retrieve→Generate 전체 경로가 끝까지 도는지, 각 pipeline 함수가 실제 OpenAI/Neo4j 응답에 대해 기대한 예외 없이 동작하는지 확인하지 못했다 — 특히 5장에서 지적한 `GenerateResult` validator 예외 경로는 실제 LLM 응답으로만 재현 가능하다.
- Gate 1/Gate 2 조기 종료 분기, `GITHUB_REPO_URL` 유/무 두 경우 모두 실제 HTTP 응답으로 검증하지 못했다.
- `lifespan`의 `close_driver()`가 실제 앱 종료(SIGTERM 등) 시점에 호출되는지, Neo4j driver가 정상적으로 정리되는지 확인하지 못했다.
- `fastapi`/`uvicorn[standard]` 버전 범위가 기존 `neo4j`/`openai` 패키지와 의존성 충돌 없이 설치되는지 `pip install`로 확인하지 못했다.
- Python 문법은 전부 손으로 한 줄씩 재검토했다(들여쓰기, f-string, `from __future__ import annotations`, `X | None` 표기 등) — 실제 인터프리터의 파싱을 대체하지는 못한다.

**다음 실행 시 사용자가 직접 확인해야 할 것**: `pip install -e apps/ai-server`(또는 개별 설치) → `NEO4J_URI`/`NEO4J_USER`/`NEO4J_PASSWORD`/`OPENAI_API_KEY` 환경변수 설정(선택: `GITHUB_REPO_URL`) → `python scripts/load_graph.py`로 그래프 적재(Phase 02 선행) → `uvicorn app.main:app --reload`(작업 디렉토리: `apps/ai-server`)로 서버 기동 → `curl -X POST localhost:8000/chat -H "Content-Type: application/json" -d '{"chatSessionId":"test","messages":[{"role":"user","content":"..."}]}'` 등으로 5개 시나리오(포트폴리오 무관 질문/사이트 자체 질문/정상 질문/후속 질문/근거 부족 질문)를 직접 확인.
