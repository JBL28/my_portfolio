# 00. 데이터 원본 작성 구현보고서

> Phase 00: `data/` 디렉토리의 JSON 파일 작성 결과와, 그 과정에서 내린 판단·근거를 기록한다. 이 문서는 이후 검증 담당자가 `research/포트폴리오 내용 구성하기/07_포트폴리오_v1.3.md` 원문과 대조 검증할 자료다.

## 1. 만든 파일 목록

- `data/profile.json`
- `data/projects/teenyfinny.json`
- `data/projects/home-server.json`
- `data/projects/dailyband.json`
- `data/rag/cases/teenyfinny.json`
- `data/rag/cases/home-server.json`
- `data/rag/cases/dailyband.json`
- `data/rag/technology-aliases.json`

모든 파일은 `node -e`로 파싱해 문법 유효성을 확인했고, 아래 항목도 스크립트로 교차 검증했다:
- 모든 id가 UUID v4 정규식(`^[0-9a-f]{8}-...4[0-9a-f]{3}-[89ab][0-9a-f]{3}-...$`)을 만족한다.
- 전체 31개 id에 중복이 없다.
- `buildsOnEvidenceSectionIds`, Case의 `sectionIds`, `influencedByCaseIds`가 가리키는 id가 전부 실제로 존재한다.
- 모든 Case가 `sectionIds`를 최소 1개 갖는다(13개 Case 전부 확인).
- 모든 Case의 `competencies`가 7개 고정 목록 안에 있다.
- `technologies`/`usedTechnologies`/`consideredTechnologies`에 등장하는 기술 28종이 `technology-aliases.json`의 canonical 목록 28종과 정확히 일치한다(누락 없음).

## 2. 프로젝트별 Case 개수와 0-Case 판단

### TeenyFinny — 4개 Section 중 3개에 Case 생성 (S4는 0-Case)

1. "처음 맡은 PL에서 팀이 일할 방식을 먼저 정했습니다" → Case 1개 (PL 역할 조사 → 문서/템플릿/Mock Server 흐름 수립)

   이유: 01_설계.md 3.1이 명시적으로 "전자가 실제로 0개의 Case로 판단될 수도 있다"고 힌트를 준 Section이다. 본문("Grafana·Loki·Prometheus로 여러 서버를 관측하고 Jenkins·SonarQube로 개발 흐름을 자동화했지만, 운영 도구까지 Public 환경에 둔 점이 남았습니다. 프로젝트가 끝난 뒤 개인 서버를 구축해 서비스 공개 필요 여부에 따라 접근 경계를 다시 설계했습니다.")를 보면, 앞부분은 이전 세 Section에서 이미 다룬 활동의 요약(관측/자동화 도구 나열)이고, 뒷부분("프로젝트가 끝난 뒤 개인 서버를 구축해 ... 다시 설계했습니다")은 TeenyFinny 자체의 문제·판단·행동 흐름이 아니라 **다음 프로젝트(Home Server)에서 일어난 일**을 가리킨다. TeenyFinny 안에서 완결되는 구체적 경험(문제→판단/행동)이 아니라 배경 요약 + 다음 프로젝트로의 전환부이므로 Case를 만들지 않았다.
   - 부수 판단: 이 Section 본문에 등장하는 Grafana·Loki·Prometheus는 TeenyFinny의 `technologies` 필드(화면 표시 그대로 Spring Boot·MySQL·AWS·Nginx·Jenkins·SonarQube)에는 없다. `technologies`는 "화면에 보이는 그대로의 표기"만 담아야 하므로(01_설계.md 3.2/4장 3번) 이 Section 본문에만 등장하는 도구를 임의로 Project 기술 스택에 추가하지 않았다. 0-Case이므로 Case-USES로도 연결되지 않는다 — 결과적으로 Grafana/Loki/Prometheus는 TeenyFinny 데이터에서 Section.body 텍스트 안에만 남고 그래프 관계는 생성되지 않는다.

## 3. INFLUENCED / BUILDS_ON 연결과 원문 근거

01_설계.md 3.1은 두 개의 **후보 Section 쌍**을 제시했다. 각각 실제로 어떻게 처리했는지 아래에 기록한다.

### 3.1 BUILDS_ON (Project 레벨, 항상 확정된 관계)

- `(Home Server)-[:BUILDS_ON]->(TeenyFinny)`
  - `home-server.json`의 `buildsOnProjectSlug: "teenyfinny"`, `buildsOnEvidenceSectionIds: ["aa221ace-dccc-4b02-b3af-edce10843774"]` (TeenyFinny의 "운영의 아쉬움을 다음 환경에서 다시 설계했습니다" Section id)
  - 원문 근거: Home Server Detail 첫 문단 "TeenyFinny에서 남은 Public 운영 문제를 다시 다루기 위해 미니 PC에 Linux 서버를 구축했습니다."
- `(DailyBand)-[:BUILDS_ON]->(Home Server)`
  - `dailyband.json`의 `buildsOnProjectSlug: "home-server"`, `buildsOnEvidenceSectionIds: ["a3ca4969-bd79-4363-87fd-e855478d3c6d"]` (Home Server의 "개인 서버를 팀의 품질 검증 환경으로 연결했습니다" Section id)
  - 원문 근거: Home Server 본문 "이 환경은 DailyBand의 Build → Test → SonarQube → Quality Gate 흐름으로 이어졌습니다." 및 Home 페이지 DailyBand Result "개인 운영 환경이 DailyBand의 CI/CD·Quality Gate로 연결"

이 두 관계는 01_설계.md 3.1에서 이미 방향과 근거까지 확정된 내용을 그대로 반영한 것으로, 별도 해석이 필요하지 않았다.

### 3.2 INFLUENCED (Case 레벨)

01_설계.md 3.1이 제시한 두 후보 Section 쌍을 각각 다음과 같이 처리했다.

**후보 1** — TeenyFinny "운영의 아쉬움을 다음 환경에서 다시 설계했습니다" ↔ Home Server "공개 필요 여부에 따라 접근 경로를 나눴습니다"

→ **Case-level INFLUENCED를 만들지 않았다.** TeenyFinny 쪽 Section이 위 2장에서 서술한 대로 0-Case로 판단됐기 때문에, INFLUENCED의 출발점이 될 이전 Case 자체가 존재하지 않는다. 이는 01_설계.md 3.1이 정확히 예견한 상황("전자가 실제로 0개의 Case로 판단될 수도 있다")이다. 두 프로젝트 사이의 실제 연결은 Case 레벨이 아니라 Project 레벨의 BUILDS_ON(위 3.1 참고)으로만 표현된다.

**후보 2** — Home Server "개인 서버를 팀의 품질 검증 환경으로 연결했습니다" ↔ DailyBand "AI가 만든 코드도 같은 검증 흐름을 통과시켰습니다"

→ **Case-level INFLUENCED를 생성했다.** `dailyband.json`의 cases 파일에서 Case "AI가 만든 코드도 Quality Gate로 검증"(id `0f20bbd4-1a03-449a-9a42-9bbef4f1fdac`)의 `influencedByCaseIds`에 Home Server의 Case "개인 서버를 팀 품질 검증 환경으로 연결"(id `7417f494-1d99-43cc-9c02-6bc36fe2dab1`)의 id를 넣었다.
  - 원문 근거: Home Server 쪽 Case 본문(= Section 본문)에 "이 환경은 DailyBand의 Build → Test → SonarQube → Quality Gate 흐름으로 이어졌습니다."라는 문장이 명시적으로 있다. DailyBand 쪽 Section 자체는 이 인과관계를 다시 언급하지 않지만, Home Server 쪽 원문이 "이 환경이 DailyBand의 이 흐름으로 이어졌다"고 인과를 직접 서술하고 있고, 01_설계.md 3.1이 이 두 Section을 정확히 이 쌍으로 지목했으므로 임의 추론이 아니라 원문 근거가 있는 연결로 판단했다.
  - **애매했던 지점**: INFLUENCED 방향은 3.1에서 "(이전 Case)-[:INFLUENCED]->(이후 Case)"로 확정되어 있다. Home Server의 Case가 시간상 이전이고 DailyBand의 Case가 이후이므로, `influencedByCaseIds`는 이후 Case인 DailyBand 쪽 파일에 이전 Case id를 적재하는 방식으로 구현했다(적재 스크립트가 `previousCaseId ∈ currentCase.influencedByCaseIds`이면 `(previousCase)-[:INFLUENCED]->(currentCase)`를 생성하는 4장 규칙과 일치).

두 후보 외에 원문에서 "이전 경험이 이후 판단에 영향을 줬다"고 명시적으로 확인되는 다른 서술은 찾지 못해, 추가 INFLUENCED 관계는 만들지 않았다.

## 5. 스스로 판단이 필요했던 애매한 지점 전부

### 5.1 `repositoryVisibility` — Home Server를 "private"로 판단

Home 페이지의 프로젝트 카드 버튼 목록을 근거로 삼았다:
- TeenyFinny: `[Detail] [GitHub] [Architecture]` → GitHub 링크 존재 → `public`
- Home Server: `[Detail] [Architecture]` → GitHub 링크 없음
- DailyBand: `[Detail] [Architecture] [Demo]` → GitHub 링크 없음, 그리고 "비공개 저장소입니다..." 명시적 안내 문구 존재 → `private` (확실)

DailyBand는 "GitHub 링크 없음 + 명시적 비공개 안내"라는 두 신호가 모두 확인되므로 확실히 private다. Home Server는 "GitHub 링크 없음"이라는 신호만 있고 명시적 비공개 안내 문구는 원문에 없다. 두 신호가 DailyBand에서 일치하는 패턴을 근거로 Home Server도 `private`로 판단했지만, **이것은 확정적 원문 근거가 아니라 유비 추론이며, 검증 담당자가 재확인해야 할 지점**이다. `repositoryNotice`는 DailyBand에만 추가했다(원문에 실제 인용할 문장이 있는 경우는 DailyBand뿐이므로) — Home Server는 private로 판단했지만 인용할 원문 문장이 없어 `repositoryNotice` 필드 자체를 두지 않았다.

### 5.2 `roles` 필드의 소스 — "본인 담당" 목록을 사용, Home 카드의 역할 카테고리 라인은 사용하지 않음

Home 페이지 프로젝트 카드에는 두 종류의 역할 정보가 따로 있다: (1) "PL / Backend / Infrastructure" 같은 카테고리 라인, (2) "본인 담당 · API 명세·공통 구조 · DB·배포 인프라 · DevOps·기술 문서" 같은 상세 목록. 그런데 Project Detail 페이지의 개요 블록(Overview Section의 소스가 되어야 하는 영역)에는 (2)만 있고 (1)은 없다. 01_설계.md 3.2가 "Overview Section은 Detail 페이지 상단 개요 블록으로부터 조합 생성"한다고 명시했으므로, Detail 페이지에 실제로 있는 (2) "본인 담당" 목록을 `roles` 필드로 사용했다. (1) 카테고리 라인은 Home 카드에만 있고 Detail 개요 블록에는 없으므로 Project 메타데이터에 반영하지 않았다. `roles` 배열은 "본인 담당" 뒤에 " · "(공백-가운데점-공백)으로 구분된 항목을 그대로 분리했다.

### 5.3 `period`/`teamSize` 재분할 — DailyBand

DailyBand Detail 개요 블록의 원문은 "2026.07 ~ 2026.08 · 5주 · 6→5인 팀 프로젝트"로 기간·소요·인원이 한 줄에 섞여 있다. `period`/`teamSize`가 별도 필드이므로 `period: "2026.07 ~ 2026.08 · 5주"`, `teamSize: "6→5인"`으로 나눴다. 원문에 있는 정보를 재배치했을 뿐 새로 추가하거나 수치를 바꾸지 않았다.

### 5.4 Case의 `usedTechnologies`에 Project `technologies` 목록 밖의 도구를 포함

design 문서(01_설계.md 4장 2번)는 "Case-USES와 Project-USES의 의미를 다르게 유지"한다고 명시한다. 이에 따라 Section 본문에 개인 행동으로 명시된 도구는 Project의 표시용 `technologies` 목록에 없더라도 Case의 `usedTechnologies`에 넣었다:
- TeenyFinny Case 1: `Notion`, `Postman` — "Notion 기술 문서를 관리했으며, ... Postman Mock Server를 기준으로" 원문에 본인 행동으로 명시.
- TeenyFinny Case 3: `ProxySQL`, `Orchestrator` — "ProxySQL·Orchestrator 기반 Failover를 구성" 원문에 명시.
- Home Server Case 4: `GitLab Runner` — "GitLab Runner와 SonarQube를 직접 호스팅" 원문에 명시. (Home Server의 Project `technologies`에는 GitLab Runner/SonarQube가 없음 — Overview 카드 표기 기준으로는 Ubuntu·Docker·Nginx·Tailscale·Cloudflare Tunnel·Grafana만 명시되어 있기 때문. 두 필드가 서로 다른 의미라 불일치가 아니라 정상이다.)

이 판단에 따라 `technology-aliases.json`에는 Project 표시용 기술 스택에는 없지만 Case에서만 등장하는 기술(Notion, Postman, ProxySQL, Orchestrator, GitLab Runner, Polling, WebSocket, WebRTC)도 모두 canonical 항목으로 등록했다.

### 5.5 Home Server Case 3의 "메트릭" — Grafana를 usedTechnologies에 넣지 않음

"메트릭과 서비스 상태로 서버 문제를 먼저 배제"라는 문장만으로 어떤 도구(Grafana 등)를 썼는지 원문에 도구명이 명시되어 있지 않다. Project `technologies`에 Grafana가 있다고 해서 이 Case에 자동으로 귀속시키면 "본인이 직접 썼다고 원문에서 확인되는 기술만"이라는 기준을 넘어서는 추론이 되므로, 이 Case의 `usedTechnologies`에는 원문에 도구명이 직접 등장하는 `Tailscale`만 넣고 Grafana는 넣지 않았다.

### 5.6 Competency 배정의 근거 — 00_GraphRAG 스키마 설계.md / 01_설계.md 3.4의 7개 예시와 대조

### 5.8 원문의 markdown 강조(`**...**`)·인라인 코드(`` ` ``)와 이스케이프 처리

원문(07_포트폴리오_v1.3.md)에는 `**굵게**` 강조, `` `files` `` 같은 인라인 코드 표기, 그리고 `\[`, `\---` 같은 markdown 이스케이프가 섞여 있다. 이스케이프(`\[`, `\---`)는 버튼 라벨·구분선 등 UI 요소에만 나타나고 실제 본문 문장(H2 Section body)이나 `roles` 항목에는 등장하지 않아 이 문제를 마주치지 않았다. `**강조**`와 `` `인라인 코드` ``(예: DailyBand Section "반복되던 파일 메타데이터 책임을 한 곳으로 모았습니다"의 `` `files` ``, DailyBand `roles`의 `` `files`·Job ``, Section "트랜잭션 밖의 AI 실패를 별도 상태로 회수했습니다"의 `AFTER_COMMIT`은 원문이 `AFTER\_COMMIT`으로 이스케이프한 것을 실제 콘텐츠인 `AFTER_COMMIT`으로 복원)는 필자가 의도적으로 표시한 서식(원문의 일부)으로 보고 Section/Case body와 `roles`에 그대로 유지했다 — 화면 렌더링 시에도 markdown으로 처리된다고 가정한 판단이며, FE 구현 단계에서 실제로 markdown 렌더러를 거치지 않는다면 이 판단을 재검토해야 한다.

### 5.9 `technology-aliases.json`의 alias 항목

alias 목록에는 원문에 실제로 등장하지 않는 일반적인 표기 변형(예: `PostgreSQL`의 alias로 `Postgres`)도 일부 추가했다. 이는 "포트폴리오 콘텐츠를 임의로 추가하지 않는다"는 원칙과는 별개로, 이 테이블 자체가 런타임에 사용자가 채팅에서 입력하는 임의의 기술명 표기를 canonical 이름으로 정규화하기 위한 유틸리티 테이블이기 때문이다(01_설계.md 4장 4번, 2장 [Retrieve] 1번 — Extract가 추출한 자유 텍스트 `technologies`를 정규화). 포트폴리오 사실 정보가 아니라 기술 매칭 보조 데이터이므로 널리 알려진 표준 표기 변형만 최소한으로 추가했다. 필요하면 검증 단계에서 제거해도 데이터 무결성에 영향이 없다(다른 파일이 이 alias 항목들을 참조하지 않는다 — canonical 이름만 참조됨).
