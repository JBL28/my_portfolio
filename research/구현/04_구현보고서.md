# 04. FE 채팅 위젯 연결 구현보고서

> Phase 04: `apps/web/`에 채팅 UI를 붙이고 Next.js BFF(`/api/chat`)로 FastAPI(`apps/ai-server`)에 프록시하는 작업. 범위는 01_설계.md 5.2~5.4로 정확히 한정했고, 00_기획.md("플로팅 버튼/플로팅 모달"), 02_구현계획.md 0장(N=3턴)·1장 5번을 함께 참고했다.

**이 환경에는 Docker·Python 실행환경이 없어 FastAPI 서버를 실제로 띄울 수 없다.** 따라서 `/api/chat` BFF가 실제 FastAPI 응답을 받는 end-to-end 왕복 테스트는 하지 못했다. 대신 `npm install`/`npm run build`/`npm run lint`는 전부 실제로 실행해 통과를 확인했고, axios 요청/응답 타입은 `apps/ai-server/app/schemas/chat.py`·`structured_outputs.py`와 필드 단위로 대조했다.

## 3. FastAPI 스키마와 타입 대조

`apps/web/lib/api/chat.ts`의 타입을 `apps/ai-server/app/schemas/chat.py`·`structured_outputs.py`와 필드 단위로 대조했다.

| Python (chat.py / structured_outputs.py) | TypeScript (lib/api/chat.ts) | 일치 여부 |
|---|---|---|
| `ChatMessageCitation { sectionId: str; caseId: str \| None }` | `ChatMessageCitation { sectionId: string; caseId: string \| null }` | 일치 |
| `ChatMessage { role: Literal["user","assistant"]; content: str; citations: list[ChatMessageCitation] \| None }` | `ChatMessage { role: "user" \| "assistant"; content: string; citations?: ChatMessageCitation[] \| null }` | 일치 |
| `ChatRequest { chatSessionId: str; messages: list[ChatMessage] }` | `ChatRequest { chatSessionId: string; messages: ChatMessage[] }` | 일치. `requestId`는 8.1/5.4 명시대로 바디에 포함하지 않음 |
| `Citation { sectionId: str; caseId: str\|None; projectSlug: str\|None; path: str; anchor: str; quotedTitle: str }` | `Citation { sectionId: string; caseId: string\|null; projectSlug: string\|null; path: string; anchor: string; quotedTitle: string }` | 일치 |
| `ChatResponse { answer: str; isEvidenceSufficient: bool; citations: list[Citation] }` | `ChatResponse { answer: string; isEvidenceSufficient: boolean; citations: Citation[] }` | 일치 |

`ChatMessage.citations`가 전체 `Citation`(path/anchor/quotedTitle 포함)이 아니라 축소형 `ChatMessageCitation`(sectionId/caseId만)이라는 점이 chat.py의 핵심 계약이라, FE도 이 두 타입을 별도로 정의해 섞이지 않게 했다(4장 참고).

## 4. `chatSessionId` / `citations` 재전송 로직

- **`chatSessionId` 재생성**: `ChatModal.tsx`에서 `useState(() => crypto.randomUUID())`로 컴포넌트 마운트 시 1회 생성한다. `FloatingChatButton`이 모달을 `{isOpen ? <ChatModal .../> : null}`로 조건부 마운트/언마운트하므로, 모달을 닫았다가 다시 열 때마다 `ChatModal`이 새로 mount되어 `chatSessionId`도 자동으로 새 값이 된다(8.2 "모달을 새로 열 때마다 새로운 chatSessionId를 생성한다"). 별도의 "재오픈 감지" 로직을 두지 않고 React의 mount/unmount 자체를 그 트리거로 삼았다.
- **대화 이력·로딩 상태**: `ChatModal.tsx` 로컬 `useState`(`turns`, `isLoading`, `error`)로만 관리한다. Context·전역 상태관리 라이브러리를 쓰지 않았고, 모달이 unmount되면(닫힘) 이 상태도 함께 사라진다 — "모달을 닫으면 대화가 사라진다" 정책과 구현이 자연스럽게 일치한다.
- **화면 표시용 상태와 전송용 페이로드를 분리**: `MessageList.tsx`가 정의하는 `ConversationTurn`은 assistant 턴에 대해 렌더링(citation 링크)에 필요한 전체 `Citation[]`을 들고 있다. 반면 요청 바디에는 chat.py의 `ChatMessage.citations`가 요구하는 축소형만 넣어야 하므로, `ChatModal.tsx`의 `handleSend()`에서 매 요청마다 `turns`를 `messages: ChatMessage[]`로 변환하면서 assistant 턴의 citations를 `{ sectionId, caseId }`만 남기고 나머지(path/anchor/quotedTitle)는 제거한다:

  ```ts
  citations: turn.citations.map(({ sectionId, caseId }) => ({ sectionId, caseId }))
  ```

  이렇게 하면 링크 렌더링에 필요한 정보를 화면 상태에 유지하면서도, 서버로 나가는 페이로드는 chat.py 스키마와 정확히 같은 모양을 유지한다.
- **재전송 범위**: 매 요청마다 `turns`(해당 모달 세션 동안 누적된 전체 이력)를 그대로 `messages`에 실어 보낸다. "최근 N턴"(02_구현계획.md 0장 확정값 N=3)으로 자르는 로직은 FE에 두지 않았다 — 01_설계.md 어디에도 FE가 이력을 자르라는 명시가 없고, 2장 원문("서버는 세션을 저장하지 않는 stateless 구조") 기준으로 서버(Extract 단계)가 얼마나 과거까지 볼지 결정하는 것이 더 일관적이라고 판단했다. 실제로 03_구현보고서 기록을 보면 이 절단은 이미 FastAPI `api/chat.py`의 `_truncate_history()`에 구현돼 있어, FE가 중복으로 자르지 않아도 된다.
- **citation 링크 라우팅**: `CitationLink.tsx`가 `citation.projectSlug`가 있으면 `/projects/{slug}#{anchor}`, 없으면 `/#profile`로 Next.js `Link`(같은 탭)를 렌더링한다(3.2 규칙 그대로).
- **안내 문구**: `ChatModal.tsx` 헤더 바로 아래 고정 배너로 "이 대화는 저장되지 않습니다. 새로고침하거나 창을 닫으면 대화 내용이 사라집니다."를 항상 표시한다(대화 도중에도 계속 보이도록 해서 "조용히 사라지는" 상황을 피했다).

## 5. 그 외 구현 메모

- `next/dynamic(..., { ssr: false })`는 Client Component 안에서만 허용되는데(`FloatingChatButton`이 `"use client"`), `FloatingChatButton` 자체가 Client Component이므로 이 옵션을 그대로 썼다 — Server Component에서 이 옵션을 쓰면 Next.js 16 문서(`node_modules/next/dist/docs/01-app/02-guides/lazy-loading.md`) 기준 빌드 에러가 난다는 점을 미리 확인하고 피했다.
- Framer Motion(패키지명 `motion`)은 `motion/react`에서 `motion.div`(배경 opacity, 모달 scale/opacity, 각각 `duration: 0.2`)와 `AnimatePresence`(닫힐 때 exit 애니메이션 재생 후 실제 unmount)를 사용했다. 5.5 "무채색·컴팩트" 톤을 유지하기 위해 색상은 기존 코드와 동일한 zinc 팔레트만 썼고, 그라디언트·큰 장식 요소는 추가하지 않았다.
- Esc 키로 모달을 닫는 것과 배경 클릭으로 닫는 것은 설계 문서에 명시된 요구는 아니지만, `role="dialog" aria-modal="true"`로 만든 모달의 최소 접근성 관례로 판단해 추가했다 — 새로운 기능이 아니라 이미 있는 "닫기" 동작의 추가 트리거일 뿐이다.

## 6. 실행 검증을 하지 못한 부분 (명시)

- **`/api/chat` BFF ↔ FastAPI 실제 왕복**: Python 실행환경이 없어 `apps/ai-server`를 기동할 수 없으므로, `route.ts`가 실제 `AI_SERVER_URL`로 요청을 보내고 FastAPI가 응답하는 흐름 전체를 실행으로 확인하지 못했다. 대신 스키마 필드를 3장 표처럼 한 줄씩 대조했고, `route.ts`는 요청/응답 바디를 그대로 통과시키는 얇은 프록시라 별도 변환 로직이 없어 타입 불일치가 생길 지점 자체가 거의 없다고 판단했다.
- **브라우저에서의 실제 채팅 시나리오**(버튼 클릭 → 모달 오픈 애니메이션 → 메시지 전송 → 응답 렌더링 → citation 클릭 → 페이지 이동)는 `next dev` 서버를 띄워 눈으로 보는 수동 확인을 하지 않았다. `npm run build`가 타입 체크까지 통과했고 각 컴포넌트의 props/타입이 서로 맞물리는 것은 TypeScript 컴파일로 검증됐지만, 런타임 렌더링 결과(레이아웃 깨짐, 다크모드 대비 등)는 사용자가 직접 확인해야 한다.
- **`AI_SERVER_URL` 환경변수 미설정 시 동작**: `route.ts`가 500을 반환하는 분기를 코드로는 작성했지만, 실제로 `.env`를 비운 채 요청을 보내 그 응답을 받는 것까지는 확인하지 못했다.

**다음 실행 시 사용자가 직접 확인해야 할 것**: `apps/web/.env.local`(또는 배포 환경)에 `AI_SERVER_URL`을 설정(예: 홈서버 내부 배포라면 `http://localhost:8000` 또는 내부망 주소) → `apps/ai-server`를 Python 환경에서 기동(03_구현보고서의 실행 안내 참고) → `npm run dev`로 `apps/web` 기동 → 브라우저에서 플로팅 버튼 클릭 → 질문 전송 → 답변·citation 링크·모달 닫기(대화 소멸) 시나리오를 직접 확인.
