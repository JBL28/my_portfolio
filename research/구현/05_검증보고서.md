### 2.1 retrieve.graph의 matched_case_ids/matched_project_slugs — 근사치 (사소)

`retrieve.py` L384-390에서 `matched_case_ids`/`matched_project_slugs`는 `_step1_graph_matching`이 반환한
`seed_case_ids`/`seed_project_slugs`만 담는다. `_step2_considered`/`_step3_growth`/`_step5_followup_and_similar`가
추가로 매칭하는 case/project id는 `_Hit` 자료구조에 애초에 case_id/project_slug 필드가 없어 기록되지 않는다.
구현자가 구현보고서 2.1절에서 이 근사를 스스로 명시했고, 코드 주석(retrieve.py L39-41)에도 "관측 전용이며 매칭
로직 자체에는 쓰이지 않는다"고 밝혔다. `matched_section_ids`는 모든 hit을 정확히 반영해 완전하다.

8.2 표 문구("매칭된 Case/Section/Project id")를 문자 그대로 보면 완전성이 부족하지만, `_Hit`/각 step 함수의
반환 타입을 확장하려면 Phase 03에서 확정된 함수 시그니처를 바꿔야 해서 "기존 파이프라인 로직·시그니처는 건드리지
말 것"이라는 이번 검증 지시와 충돌한다. 실제 파이프라인 매칭 로직에는 영향이 없고(관측 attribute만 불완전),
근사임이 코드에 정직하게 문서화돼 있으므로 **사소**로 분류한다.

### 2.2 retrieve.graph/vector/rank 3-span 경계와 5)→4) 재배치 검증 — 확인함, 결과에 영향 없음

`retrieve.py` 모듈 docstring과 실제 코드(L353-427)를 대조했다:

- `retrieve.graph` = 0)(`_step0_overview`) + 1)(`_step1_graph_matching`) + 2)(`_step2_considered`) +
  3)(`_step3_growth`) + 5)(`_step5_followup_and_similar`) — 전부 Cypher 기반, LLM 호출 없음. 설계 원문 2장의
  0~3)/5) 경계와 정확히 일치한다.
- `retrieve.vector` = 4)(`_step4_vector`, 임베딩 + 벡터 검색)만 포함.
- `retrieve.rank` = 6)(`_merge`) + 7)(`_select_top_k`) 포함.

**재배치가 결과에 영향을 주는지 직접 코드 흐름으로 검증했다**:

- `_step5_followup_and_similar(extract)`(L207-231)는 인자로 `extract`(ExtractResult)만 받는다 — `_step4_vector`가
  만드는 `vector_hits`나 그 결과에 전혀 의존하지 않는다. 즉 4)와 5) 사이에 데이터 의존성이 없다는 구현자 주장은
  코드로 확인된다.
- 최종 합집합을 만드는 `_merge(hits)`(L239-273)는 `hits: list[_Hit]`를 순서와 무관하게 처리한다: (1) 후보 집합은
  `section_id`를 key로 하는 `dict`로 구성되므로 리스트 순서가 결과 키 집합에 영향을 주지 않는다, (2) `sources`는
  `set`에 `.add()`로 누적되므로 교환법칙이 성립한다, (3) `mandatory`는 `or` 누적(교환법칙 성립), (4) `vector_score`는
  `max()` 누적(교환법칙 성립), (5) `followup_case_id`는 마지막에 만난 값으로 덮어쓰지만, followup 경로는 5)에서만
  발생하고 다른 어떤 step도 `followup_case_id`를 설정하지 않으므로 실행 순서가 바뀌어도 이 필드에 대입되는 값
  자체는 동일하다.
- 즉 hits 리스트에 0,1,2,3,5,4 순서로 쌓이든 0,1,2,3,4,5 순서로 쌓이든 `_merge()`의 최종 산출물(`candidates` dict)은
  완전히 동일하다. 이후 `_select_top_k`/`_score`도 이 dict만 입력으로 받으므로 영향이 없다.

**결론: 구현자의 "재배치가 최종 candidates 집합에 영향을 주지 않는다"는 주장은 코드 추적으로 사실임이 확인됐다.**
Phase 03에서 확정된 검색 결과(합집합·스코어링) 로직을 부당하게 바꾼 것이 아니다 — 각 step 함수의 내부 로직·시그니처는
`_step0_overview`부터 `_select_top_k`까지 Phase 03 검증보고서가 기술한 것과 동일한 알고리즘임을 대조 확인했다(2)
그래프 매칭에서 project_hints 정규화 보강 로직 위치, 3) seed 유무 분기, 5) followup/similar_case 분기 등 모두 일치).

## 2. security.input / security.output (8.3)

### 규칙 기반 여부 — 확인함

`apps/ai-server/app/security/input_scan.py`, `output_scan.py` 전체를 읽었다. 두 파일 모두 `re`(정규식)와 길이
비교만 사용하며, `openai`/`OpenAI` import나 API 호출이 전혀 없다. 8.3 "보안 판별을 위해 별도 LLM 분류 호출을
추가하면... 규칙 기반으로 시작한다"는 제약을 지켰다.

### 차단 로직 부재 — 확인함 (가장 중요한 항목)

- `input_scan.py` L86: `InputScanResult.blocked: bool = False`(dataclass 기본값). `scan_input()`(L89-109)의
  마지막 return문(L107-109)도 `blocked=False`를 **하드코딩**해 반환한다 — 함수 내부 어디에도 이 값을 다르게
  설정하는 분기가 없다.
- `output_scan.py`의 `OutputScanResult`에는 `blocked` 필드 자체가 아예 없다(원래 8.3도 output scan에는 차단
  개념을 요구하지 않는다).
- `chat.py` L137-143(security.input), L226-236(security.output) 모두 스캔 결과를 `span.set_attribute(...)`로
  기록만 하고, `risk_score`/`blocked`/`system_prompt_exposed`/`internal_info_exposed` 값을 근거로 `if` 분기,
  `raise`, 조기 `return` 등으로 이어지는 코드가 전혀 없다 — 저장소 전체에서 `input_scan_result`/`output_scan_result`
  변수가 attribute 기록 이외의 목적으로 재사용되지 않음을 확인했다.

**차단/조기 반환 경로는 발견되지 않았다. 8.3 위반 없음을 확인함.**

### security.output 규칙의 실효성 — 부분 결함 발견 (중요)

5개 규칙 중 4개(`system_prompt_leak`, `neo4j_schema_or_cypher`, `internal_endpoint`, `credentials_or_keys`)는
실제 의미 있는 키워드/패턴(`Neo4j`, `Cypher`, `DEMONSTRATES` 등 실제 관계명, `FastAPI`, `localhost:포트`,
`OPENAI_API_KEY`, `sk-` 토큰 패턴 등)을 탐지 대상으로 삼고 있어 더미 규칙이 아니다.

**다만 `system_prompt_verbatim` 규칙(`output_scan.py` L30-33)에 실제 버그가 있다.**

- 근거: `output_scan.py` L32의 정규식은 `re.compile(r"근거 후보 목록만을 근거로 답한다")`다. 이 문자열이
  `generate.py` L27의 실제 system prompt 문구를 그대로 재현했다고 구현보고서(3.2절)와 코드 주석이 설명한다.
- 그러나 `generate.py` L27의 실제 문구는 `아래 제공되는 "근거 후보" 목록만을 근거로 답한다.`이다 —
  `"근거 후보"`가 **따옴표로 감싸져 있어** `후보` 바로 뒤에 `"` 문자가 있고, 그 다음에 공백과 `목록만을`이 이어진다.
  반면 정규식 리터럴은 `후보` 바로 뒤에 공백이 오는 문자열(`후보 목록만을`, 따옴표 없음)을 찾는다.
- Node.js로 직접 재현 검증했다(Python 없이도 가능한 순수 문자열/정규식 검증):
  ```
  const line = fs.readFileSync('apps/ai-server/app/pipeline/generate.py', 'utf8');
  /근거 후보 목록만을 근거로 답한다/.test(line)  // → false
  ```
  즉 이 정규식은 **system prompt 원문 자체에도 매치되지 않는다.** LLM이 시스템 프롬프트를 따옴표까지 포함해
  글자 그대로 노출해도(이 규칙이 탐지하려는 정확한 시나리오), `"` 문자 하나 때문에 매치가 실패해 탐지되지 않는다.
- 영향 범위: 8.3 자체가 "이 규칙 기반 스캔은 보안 경계가 아니라 관측을 위한 휴리스틱 신호다"라고 명시하므로
  실제 보안 사고로 이어지지는 않지만, 이 규칙 하나는 설계 의도("프롬프트 원문 유출을 직접 탐지")를 전혀 달성하지
  못하는 죽은 코드나 다름없다. 나머지 4개 규칙은 정상 작동하므로 **치명적**이 아니라 **중요**로 분류한다.
- 권고 수정(적용은 하지 않음, 검증만): 정규식에서 따옴표를 선택적으로 허용(`근거\s*후보"?\s*목록만을`)하거나,
  system prompt에서 따옴표를 뺀 부분 문자열(예: `목록만을 근거로 답한다`처럼 따옴표를 포함하지 않는 구간)을
  패턴으로 삼으면 해결된다.

## 3. requestId (8.1/8.4)

### BFF가 매 요청 새 UUID v4를 생성하고 클라이언트 값을 신뢰하지 않는가 — 확인함

`apps/web/app/api/chat/route.ts` L38: `const requestId = crypto.randomUUID();`. 이 파일의 `POST` 핸들러
(L19-59) 전체를 읽었다 — 들어오는 `request`(Next.js `Request` 객체)의 `headers`를 **어디에서도 읽지 않는다**.
`request.headers.get(...)` 같은 호출이 코드에 전혀 없으므로, 클라이언트가 `X-Request-ID`를 보냈든 안 보냈든
그 값은 애초에 참조되지 않는다 — "조건부로만 신뢰하는 미묘한 버그"(예: `request.headers.get("x-request-id") ??
crypto.randomUUID()` 같은 폴백 패턴)는 존재하지 않는다. 매 요청 무조건 새 UUID를 만들어 FastAPI로 보낸다(L46).

### FastAPI가 헤더를 그대로 기록하고 새로 만들지 않는가 — 확인함

`apps/ai-server/app/api/chat.py` L124: `request_id = http_request.headers.get("x-request-id", "")`. FastAPI/

## 수정 반영

문제 #1(중요, `system_prompt_verbatim` 규칙이 실제 system prompt 문구와 매치되지 않는 죽은 규칙 문제)만 수정했다.
문제 #2(사소)와 나머지 4개 규칙, `input_scan.py`, 그 외 파일은 건드리지 않았다.

### 수정 내용

기존에는 `output_scan.py`가 `generate.py`의 system prompt 문구를 별도 정규식 리터럴로 다시 베껴 적고 있었고,
그 과정에서 `generate.py:27`의 실제 문구(`아래 제공되는 "근거 후보" 목록만을 근거로 답한다.`)에 있는 따옴표를
누락해 매치가 실패했다. 단순히 정규식만 고치면 두 파일이 각자 문자열을 유지하게 돼 system prompt 문구가 나중에
다시 바뀔 때 같은 방식으로 재발할 수 있다고 판단해, 최소한의 리팩터링으로 문자열을 한 곳에서만 관리하도록 했다.

1. **`apps/ai-server/app/pipeline/generate.py`**: `_SYSTEM_PROMPT` 정의 바로 위에 탐지 전용 상수
   `SYSTEM_PROMPT_VERBATIM_MARKER = "목록만을 근거로 답한다"`를 추가했다. `_SYSTEM_PROMPT` 문자열 중 따옴표 등
   특수문자를 포함하지 않는, 실제로 존재하는 부분 문자열을 그대로 골랐다(`_SYSTEM_PROMPT` 원문 자체는 수정하지
   않았다).
2. **`apps/ai-server/app/security/output_scan.py`**: `from app.pipeline.generate import
   SYSTEM_PROMPT_VERBATIM_MARKER`를 추가하고, `system_prompt_verbatim` 규칙의 정규식을
   `re.compile(r"근거 후보 목록만을 근거로 답한다")`(따옴표 불일치로 매치 실패하던 리터럴)에서
   `re.compile(re.escape(SYSTEM_PROMPT_VERBATIM_MARKER))`로 교체했다. 이제 두 파일이 같은 문자열을 공유하므로
   `_SYSTEM_PROMPT` 문구가 바뀌어도 이 규칙만 따로 어긋나는 일이 재발하지 않는다.
3. 순환 import 위험 확인: `chat.py`가 `generate.py`와 `output_scan.py`를 각각 독립적으로 import하고 있었고,
   `generate.py`는 `output_scan.py`(또는 `app.security` 패키지 전체)를 import하지 않는다 — `output_scan.py`
   → `generate.py` 단방향 의존만 생기므로 순환 import가 발생하지 않음을 소스를 대조해 확인했다.

### 검증

Python 인터프리터가 없는 환경이라 Node.js로 두 파일을 텍스트로 읽어 문자 단위까지 재확인했다:

- `SYSTEM_PROMPT_VERBATIM_MARKER`의 실제 값이 `"목록만을 근거로 답한다"`임을 확인.
- `generate.py`의 `_SYSTEM_PROMPT` triple-quoted 문자열 전체에 이 마커가 부분 문자열로 포함됨을
  `String.prototype.includes()`로 확인(`true`).
- `output_scan.py`가 `from app.pipeline.generate import SYSTEM_PROMPT_VERBATIM_MARKER`를 포함하고,
  `re.compile(re.escape(SYSTEM_PROMPT_VERBATIM_MARKER))`를 사용함을 문자열 검색으로 확인.
- 마커 문자열을 JS 정규식으로 이스케이프해 `_SYSTEM_PROMPT` 전체 문자열에 대해 `RegExp.prototype.test()`를
  실행한 결과 `true` — 새 규칙이 실제 system prompt 원문과 매치됨을 확인.
- 기존 버그가 있던 리터럴(`r"근거 후보 목록만을 근거로 답한다"`)이 `output_scan.py`에 더 이상 존재하지 않음을
  확인(`false`).

이 정적 검증으로 문제 #1이 해소됐음을 확인했다. 다만 Python 런타임 자체에서 `re.escape()`의 실제 동작이나
FastAPI 앱이 실제로 기동해 이 import가 문제 없이 로드되는지는 이 환경에서 여전히 실행 검증이 불가능하다 —
보고서 5장이 이미 명시한 "실행 필요(검증 불가)" 한계와 동일하다.
