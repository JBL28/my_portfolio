# 03. FastAPI AI 서버 검증보고서

> 검증 대상: `apps/ai-server/app/`(Phase 03, Gate1→Gate2→Extract→Retrieve→Generate 전체 파이프라인).
> 검증자는 구현자(`research/구현/03_구현보고서.md`)와 별개의 독립 검증 담당자다. 구현자의 보고 내용은 신뢰하지 않고,
> `01_설계.md` 2장/3장/5.4, `00_기획.md`, `02_구현계획.md` 0장, `data/` 실 데이터를 기준으로 코드를 처음부터 다시 대조했다.

## 검증 방법 및 한계

**이 환경에는 Docker, 동작하는 Python 인터프리터(`python`/`python3`는 Windows Store alias뿐), Neo4j 인스턴스, OpenAI API 키가 없다.** `which python`/`python --version` 실행으로 직접 재확인했다 — 인터프리터가 없다는 구현자의 주장은 사실이었다. 따라서 이번 검증은 전부 **정적 코드 리뷰**로만 수행했다: 설계 문서 원문과 코드를 줄 단위로 대조하고, 함수 시그니처·호출부·Cypher 쿼리·Pydantic 스키마를 눈으로 재확인했다. 실제 실행 결과가 필요한 항목은 "실행 필요(검증 불가)"로 별도 표시했다.

## 7. 발견된 문제 (심각도순)

### 치명적 — 1건

**#1. `project_hints`가 Project.slug로 정규화되지 않아 Retrieve 0/2/3 단계의 프로젝트 범위 좁히기가 사실상 항상 실패한다.**

- 근거 파일/라인:
  - `apps/ai-server/app/pipeline/extract.py:26` — Extract 시스템 프롬프트: `"project_hints는 질문에서 명시적으로 언급된 프로젝트명만 담는다(TeenyFinny, Home Server, DailyBand 등)."` → LLM이 채워 넣는 값은 **화면 표시용 프로젝트 이름**(`data/projects/{slug}.json`의 `name` 필드, 예: `"Home Server"`, `"TeenyFinny"`)이다.
  - `data/projects/home-server.json:3-4`: `"name": "Home Server", "slug": "home-server"` / `data/projects/teenyfinny.json:3-4`: `"name": "TeenyFinny", "slug": "teenyfinny"` — name과 slug가 대소문자·공백/하이픈에서 서로 다르다.
  - `apps/ai-server/app/pipeline/retrieve.py:313` — `project_hints = list(dict.fromkeys(extract.project_hints))`로 Extract가 뽑은 원문 그대로(정규화 없이) 들고 간다. 기술명(`technologies`)에는 `normalize_technologies()`(`retrieve.py:322`, `graph/technology_aliases.py`)로 alias→canonical 정규화를 거치지만, **project_hints에는 대응하는 정규화 함수가 전혀 존재하지 않는다**(리포지토리 전체에서 project-hints/slug 정규화 로직 검색 결과 없음).
  - 이 값은 그대로 아래 세 곳에서 Cypher `WHERE ... proj.slug IN $slugs`(대소문자 구분, 정확 일치)에 바인딩된다:
    - `apps/ai-server/app/graph/client.py:97-106`(`overview_sections`) — 2장 [Retrieve] 0)
    - `apps/ai-server/app/graph/client.py:179-190`(`cases_with_any_considered`) — 2장 [Retrieve] 2)
    - `apps/ai-server/app/graph/client.py:230-258`(`growth_influenced_all`, `growth_builds_on_all`) — 2장 [Retrieve] 3)
  - Neo4j Cypher의 문자열 `IN` 비교는 대소문자를 구분하는 정확 일치다. `"Home Server" != "home-server"`(공백 vs 하이픈, 대소문자)이므로 **절대 일치하지 않는다**. `"TeenyFinny" != "teenyfinny"`, `"DailyBand" != "dailyband"`도 대소문자가 다르므로 LLM이 정확히 소문자로 뽑아주지 않는 한 일치하지 않는다(Extract 프롬프트의 예시 자체가 대문자 포함 표기라 대문자로 추출될 가능성이 높다).

- 실패 시나리오: 설계 문서 2장이 든 예시 그대로 "TeenyFinny와 DailyBand에서 협업 방식이 어떻게 달라졌나요?"를 물으면 `project_hints=["TeenyFinny", "DailyBand"]`로 추출된다(Extract 프롬프트가 정확히 이 표기를 예시로 제공). `wants_project_overview=true`("TeenyFinny는 몇 명이서 했나요?" 류 질문)일 때 `overview_sections(["TeenyFinny"])`를 호출하면 `WHERE $slugs = [] OR proj.slug IN $slugs`가 `false`가 되어 **아무 Overview도 반환되지 않는다** — "project_hints가 있으면 해당 Project(들)의 Overview만" 포함해야 한다는 2장 요구사항이 완전히 깨지고, "빈 배열이면 전체"로도 폴백되지 않아 결과가 0건이 된다. 대안 비교(2번)·성장 관계(3번, seed 없을 때)에서도 동일하게 project_hints로 범위를 좁히려는 시도가 전부 빈 결과로 귀결된다.
  - 참고로 1번(그래프 매칭)에서 project_hints가 애초에 비어 있었을 때의 보강 경로(`retrieve.py:329-330`)는 Neo4j `proj.slug`에서 직접 얻은 실제 slug 값을 쓰므로 이 결함의 영향을 받지 않는다 — 결함은 **Extract가 채운 project_hints를 그대로 쓰는 경로에만** 있다.

- 판단: 이 결함은 문법 오류가 아니라 설계 의도와 다른 결과(0건 반환)를 조용히 만들어내므로 발견하기 어렵고, 2장이 명시한 대표 예시 시나리오 자체를 깨뜨린다. 근본 원인은 구현 결함이면서 동시에 01_설계.md에도 "project_hints(자유 텍스트 프로젝트명)를 Project.slug와 어떻게 매칭할지"에 대한 규정이 없다는 설계 공백이 겹쳐 있다 — 4장의 `technology-aliases.json`처럼 프로젝트명 alias 테이블을 두거나, Cypher 쪽에서 `toLower(proj.name) = toLower($hint) OR toLower(proj.slug) = toLower($hint)` 식으로 name 기반 매칭을 추가하는 보완이 필요하다. **치명적으로 분류한다** — Retrieve의 핵심 시나리오(특정 프로젝트를 콕 집어 묻는 질문) 다수가 이 경로를 타므로 영향 범위가 넓다.

### 중요 — 1건

- `normalize_project_hints()`(36-49행)가 입력을 `strip().lower()`해 이 테이블에서 조회하고, 매칭되면 slug를 담고 안 되면(자유 입력) 조용히 버리는 것을 확인했다 — `normalize_technologies()`(`technology_aliases.py:37-53`)와 실패 처리 방침이 동일함도 두 파일을 나란히 대조해 확인했다.
- `retrieve.py:313-319`를 직접 읽었다: `project_hints = list(dict.fromkeys(extract.project_hints))` 직후 `project_hints = normalize_project_hints(project_hints)`가 실행되고, 이 변수가 이후 0)(`_step0_overview`, 323-324행), 2)(`_step2_considered`, 339-340행), 3)(`_step3_growth`, 343-344행)에 그대로 전달됨을 호출부까지 추적해 확인했다. `_step0_overview`/`_step2_considered`/`_step3_growth`는 이 값을 각각 `graph.overview_sections`/`graph.cases_with_any_considered`/`graph.growth_influenced_all`·`growth_builds_on_all`에 넘기고, 이 함수들(`graph/client.py`)의 Cypher는 여전히 `WHERE $slugs = [] OR proj.slug IN $slugs` 형태의 정확 일치 비교다 — 이제 정규화된 slug가 들어가므로 실제로 일치한다.
- 1)의 보강 로직(`retrieve.py:334-336`, `if not project_hints and seed_project_slugs: project_hints = list(seed_project_slugs)`)은 정규화(319행) **이후**, `_step1_graph_matching` 호출(326-332행) **이후**에 실행된다. 즉 순서는 정규화 → 1) 그래프 매칭 → (project_hints가 그래도 비어 있으면) 보강 → 2)/3) 순이며, 보강은 정규화가 이미 값을 채워둔 경우 건너뛴다. 두 로직이 같은 변수를 다른 시점에 조건부로 채우는 구조라 충돌하지 않는다 — 수정 반영 섹션의 서술과 실제 코드가 일치한다.
- 원 보고서가 지적한 실패 시나리오("TeenyFinny와 DailyBand에서...", "Home Server는 몇 명이서 했나요?")를 직접 손으로 재현해봤다: `extract.project_hints=["TeenyFinny","DailyBand"]` → `normalize_project_hints` → `["teenyfinny","dailyband"]`(둘 다 조회 테이블의 slug-키 경로로 매칭), `["Home Server"]` → `["home-server"]`(name-키 경로로 매칭). 실제 Neo4j `proj.slug` 값과 정확히 일치한다 — 원 결함이 지적한 구체적 실패 사례가 코드 추적상 해소됨을 확인했다.
- `graph/client.py`는 원 검증 시점과 비교해 쿼리·함수 시그니처 어디도 변경되지 않았음을 전체 파일(317줄)을 다시 읽어 확인했다 — 정규화는 오직 `retrieve.py`/`project_hints.py`(신규)에서만 이뤄지고 Cypher 쪽은 손대지 않은 것도 설계 의도(정규화는 애플리케이션 레이어 책임)와 일치한다.
- 범위 이탈 없음: 새 데이터 파일을 만들지 않고 기존 `data/projects/*.json`만 재사용했고, `technology_aliases.py`는 전혀 수정되지 않았다(비교용으로 다시 읽어 대조 완료, 내용 원본 그대로).

### #2(중요) — 파이프라인 예외 처리: **해결 확인**

- `apps/ai-server/app/api/chat.py` 전체를 다시 읽었다. `try:`는 96행이 아니라 실질적으로 109행(`try:`)에서 시작해 Gate1 호출(111행)부터 `return ChatResponse(...)`(137-141행, Generate 정상 완료 시)까지를 포함하고, `except (RuntimeError, ValueError):`(142행)로 끝난다. Gate1 false 조기 종료(112-117행)와 Gate2 true 조기 종료(120-126행)는 `try` 블록 **안에서의 `return`**이다 — Python 의미상 `return`은 예외가 아니라 정상 제어 흐름으로 함수를 즉시 빠져나가므로 `except` 절을 절대 거치지 않는다. 즉 "Gate1이 `is_portfolio_related=false`를 반환하는 것"(정상 반환값)과 "Gate1 호출 자체가 RuntimeError를 던지는 것"(예외)은 코드 구조상 명확히 분리되어 있다 — 전자는 `if not gate1_result.is_portfolio_related:` 조건문 분기, 후자만 `except`가 잡는다.
- 예외 발생 지점을 4개 파이프라인 파일에서 직접 재확인했다: `gate_portfolio.py:37-40`, `gate_site.py:45-48`, `extract.py:80-82`, `generate.py:107-109` 모두 `completion.choices[0].message.parsed is None`일 때 `RuntimeError`를 던지는 동일 패턴이며, 이 네 함수 호출(`run_gate_portfolio`/`run_gate_site`/`run_extract`/`run_generate`)이 모두 `chat.py`의 `try` 블록 안(111/120/129/135행)에서 이뤄짐을 확인했다. `GenerateResult._check_citation_constraint`(`structured_outputs.py:167-176`)가 던지는 `ValueError`는 `generate.py`의 `client.beta.chat.completions.parse()` 호출(구조화 출력 파싱 시점) 안에서 발생하므로 역시 `run_generate` 호출(135행) 지점에서 `try` 블록에 걸린다.
- 예외 시 반환값(147-151행) `ChatResponse(answer=_PIPELINE_ERROR_MESSAGE, isEvidenceSufficient=False, citations=[])`을 `schemas/chat.py`의 `ChatResponse` 정의(48-56행: `answer: str`, `isEvidenceSufficient: bool`, `citations: list[Citation] = Field(default_factory=list)`)와 대조했다 — 필드명 3개 모두 camelCase 표기(`isEvidenceSufficient`)와 타입이 정확히 일치한다. Gate1/Gate2 조기 종료 응답(114-117행, 122-126행)과 완전히 같은 모양이라 FE가 세 가지 종료 경로를 구분할 필요가 없다는 설계 의도(`schemas/chat.py:48-52` 주석)도 그대로 유지된다.
- `except` 타입 범위도 확인했다: `RuntimeError`/`ValueError` 두 타입만 잡으므로, 이 두 예외와 무관한 다른 버그(예: `retrieve.py`/`graph/client.py`에서 날 수 있는 `neo4j` 드라이버 예외, `KeyError`, `AttributeError` 등)는 여전히 잡히지 않고 그대로 전파된다 — 이는 문제 #2가 지적한 범위(Structured Output 파싱 실패·citation 제약 위반) **만** 정확히 해소하고, 그 외 잠재적 버그를 부주의하게 숨기지 않는다는 뜻이라 오히려 바람직한 스코프다.
- `HTTPException(status_code=400, ...)`(98-99행, `messages` 빈 경우)은 `try` 블록 **이전**에 위치해 이 예외 처리와 무관함을 확인했다 — 정상적으로 FastAPI가 처리해 400을 반환한다(회귀 없음).
- 범위 이탈 없음: `main.py`를 다시 읽어 `@app.exception_handler`가 여전히 등록되지 않았음(전역 핸들러를 추가하지 않고 로컬 `try/except`만 추가)을 확인했고, CORS 미도입 주석도 그대로다. `gate_portfolio.py`/`gate_site.py`/`extract.py`/`generate.py` 4개 파일 모두 원 검증 시점과 동일한 내용(RuntimeError를 던지는 지점 자체는 수정하지 않고 그대로 둠)임을 재확인했다 — "잡는 쪽"만 고쳤고 "던지는 쪽"은 손대지 않았다는 수정 반영 섹션의 서술과 일치한다.

### #3(사소) — 주석 정정: **해결 확인**

- `structured_outputs.py`를 다시 읽었다. `Competency` enum docstring(26-27행)과 `ExtractResult.competencies`의 `description`(79-82행) 모두 "strict JSON Schema가 enum을 강제하므로 스키마 단에서 원천 차단되고 후처리 필터링 로직이 아니다"는 취지로 정정돼 있음을 확인했다.
- 저장소 전체에서 `apps/ai-server` 아래 "후처리"라는 단어가 등장하는 3곳을 모두 확인했다: `structured_outputs.py:27`, `:81`(둘 다 "후처리 없음"으로 정확히 서술), `extract.py:84`(`refers_to_previous_citations`의 **실제로 존재하는** 후처리 필터링 — `run_extract`가 `allowed` 집합으로 `result.refers_to_previous_citations`를 걸러내는 코드, 88-97행). 즉 "후처리가 없는 경우"와 "후처리가 실제로 있는 경우"를 코드 동작과 주석이 정확히 구분해서 설명하고 있다 — 원 결함이 지적한 대조(competencies는 후처리 없음 vs refers_to_previous_citations는 후처리 있음)가 이제 코드 주석에도 정확히 반영됐다.
