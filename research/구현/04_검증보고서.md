## 2. 타입 계약 일치 (`lib/api/chat.ts` ↔ `chat.py`/`structured_outputs.py`)

**확인함.** 필드 단위로 한 줄씩 대조했다.

| Python | TypeScript | 결과 |
|---|---|---|
| `ChatMessageCitation.sectionId: str` (필수) | `sectionId: string` (필수) | 일치 |
| `ChatMessageCitation.caseId: str \| None = None` (선택, nullable) | `caseId: string \| null` (필수 키, nullable) | 일치. FE는 항상 명시적으로 `caseId` 키를 채워 보내므로(`{sectionId, caseId}` 구조분해) 값 자체는 항상 호환됨 |
| `ChatMessage.role: Literal["user","assistant"]` | `role: "user" \| "assistant"` | 일치 |
| `ChatMessage.citations: list[...] \| None = None` (선택) | `citations?: ChatMessageCitation[] \| null` (선택) | 일치 |
| `ChatRequest{chatSessionId, messages}`, `requestId` 없음 | 동일, `requestId` 없음 | 일치 (5.4/8.1 명시대로 요청 바디에서 제외) |
| `Citation.sectionId/path/anchor/quotedTitle: str` (전부 필수) | 전부 `string` (필수) | 일치 |
| `Citation.caseId: str \| None` (필수 키, nullable) | `caseId: string \| null` (필수 키, nullable) | 일치 |
| `Citation.projectSlug: str \| None` (필수 키, nullable) | `projectSlug: string \| null` (필수 키, nullable) | 일치 |
| `ChatResponse{answer: str, isEvidenceSufficient: bool, citations: list[Citation]}` | `{answer: string, isEvidenceSufficient: boolean, citations: Citation[]}` | 일치 |

**축소형 vs 전체형 구분도 실제로 지켜졌다.** `MessageList.tsx`의 `ConversationTurn`(화면 표시용, assistant 턴에 전체 `Citation[]` — path/anchor/quotedTitle 포함)과 `lib/api/chat.ts`의 `ChatMessage.citations`(전송용, `ChatMessageCitation[]` — sectionId/caseId만)가 별도 타입으로 분리돼 있고, `ChatModal.tsx`의 `handleSend()`가 매 요청마다

```ts
citations: turn.citations.map(({ sectionId, caseId }) => ({ sectionId, caseId }))
```

로 전체형→축소형 변환을 실제로 수행한다. 두 타입을 뒤섞어 그대로 전송하는 코드 경로는 없다.

## 5. 상태 관리 (5.3)

**확인함.**

- `chatSessionId`: `ChatModal.tsx`에서 `useState(() => crypto.randomUUID())`로 컴포넌트 마운트 시 1회 생성. `FloatingChatButton.tsx`가 `{isOpen ? <ChatModal .../> : null}`(및 `AnimatePresence`)로 조건부 마운트하므로 모달을 닫았다가 다시 열 때마다 새 인스턴스·새 `chatSessionId`가 생성된다.
- 대화 이력·로딩 상태(`turns`, `isLoading`, `error`)는 `ChatModal.tsx` 로컬 `useState`로만 관리한다. 레포 전체에서 `createContext`/전역 상태관리 라이브러리(zustand, redux 등) 사용처를 찾을 수 없었다 — Context/전역 상태를 쓰지 않는다는 주장과 일치.
- 모달 unmount 시 상태 소멸: React가 컴포넌트 트리에서 제거되면 로컬 `useState`는 자동으로 사라지므로, "닫으면 대화가 사라진다"는 정책과 실제 구현이 구조적으로 일치한다. `AnimatePresence`의 exit 애니메이션이 끝난 뒤 실제 unmount가 일어나는 것은 Framer Motion의 표준 동작이며 재오픈 시 새 인스턴스가 생성되는 것과 모순되지 않는다.

## 7. citation 링크 이동 규칙 (3.2) — 부분 지적 (사소)

**기능적으로는 확인함, 다만 구현 방식이 설계 문구와 다르다(사소한 문제 1).**

`CitationLink.tsx`:
```ts
const href = citation.projectSlug
  ? `/projects/${citation.projectSlug}#${citation.anchor}`
  : "/#profile";
```

5.3 원문은 "`citation.path + '#' + citation.anchor`로 이동한다 — Home Profile Section이면 `/#profile`로, 프로젝트 Section이면 `/projects/{slug}#{anchor}`로"라고 되어 있다. 즉 설계는 백엔드가 이미 채워 보내는 `citation.path` 필드를 그대로 조합해 쓰라는 것이고, 두 사례(`/#profile`, `/projects/{slug}#{anchor}`)는 `path`가 각각 `"/"`, `"/projects/{slug}"`일 때 이 공식이 만들어내는 결과를 설명한 것뿐이다(`apps/ai-server/db`·`load_graph.py`에서 Section.path가 실제로 이 두 값 중 하나로만 채워지는 것도 확인했다).

`CitationLink.tsx`는 `citation.path`를 아예 쓰지 않고 `projectSlug` 유무로 분기해 경로를 직접 재조합한다. 현재 데이터 모델(Project.slug가 유일한 원본이고 path가 항상 `/projects/{slug}` 패턴으로만 생성됨, 2절 GraphRAG 스키마·03 검증보고서에서 이미 확인된 사실)에서는 두 방식이 항상 같은 결과를 내므로 **지금 당장 링크가 잘못되는 사례는 없다.** 다만:
- `Citation` 타입에 정의된 `path` 필드가 FE 어디에서도 실제로 읽히지 않는 죽은 필드가 된다.
- 설계 문서가 명시한 "백엔드가 준 path를 그대로 신뢰한다"는 원칙과 어긋나, 향후 path 생성 규칙이 바뀌면(예: 프로젝트 경로에 버전이 붙는 등) `CitationLink`만 조용히 어긋난 링크를 만들게 되는 결합도가 생긴다.

기능 결함이 아니라 설계 문구 대비 구현 방식의 불일치이므로 **사소한 문제**로 분류했다.

## 10. Server/Client 컴포넌트 경계 (5.2)

**확인함.** `"use client"`가 있는 파일은 정확히 5개: `FloatingChatButton.tsx`, `ChatModal.tsx`, `ChatInput.tsx`, `MessageList.tsx`, `ThemeToggle.tsx`(Phase 01) — 5.2가 명시적으로 나열한 Client Component 목록과 정확히 일치한다. `CitationLink.tsx`는 훅이나 브라우저 API를 쓰지 않는 순수 렌더 함수라 `"use client"`가 없는데, `MessageList`(Client Component)가 이를 직접 import·렌더링하므로 실질적으로 클라이언트 번들에 포함된다 — Next.js 규칙상 오류는 아니지만(클라이언트 경계 안에서 서버 전용 API를 안 쓰는 한 문제 없음), `CitationLink`를 굳이 Client Component 트리 밖에 둘 이유가 없어 지시자 유무가 실질적 차이를 만들지는 않는다. 정적 콘텐츠 컴포넌트(`ProjectCard`, `ProjectDetailSection`, `ProjectOverview` 등, Phase 01)에는 `"use client"`가 여전히 없음을 확인했다.

## 12. 사소한 문제 (2건)

1. **`CitationLink.tsx`가 `citation.path`를 쓰지 않고 `projectSlug`로 경로를 재구성한다** (7절 참고) — 현재 데이터 모델에서는 결과가 항상 같아 기능 결함은 아니지만, 설계 문서가 명시한 "path를 그대로 조합" 방식과 다르고 `path` 필드가 죽은 코드가 된다.
2. **`MessageList.tsx`가 turn 렌더링 key로 배열 index를 사용한다**(`key={index}`) — 현재는 `turns`가 항상 끝에만 추가되고 재정렬·삭제가 없어 실제 렌더링 버그로 이어지지는 않지만, React 권장 패턴은 아니다.

## 수정 반영

12절의 사소한 문제 1건(citation 링크가 `citation.path`를 쓰지 않고 `projectSlug`로 경로를 재구성하는 점)을 수정했다. 사소한 문제 2번(index를 key로 쓰는 것)은 이번 수정 범위가 아니므로 손대지 않았다.

**`apps/web/components/domains/chat/CitationLink.tsx` 변경 내용**

```diff
- const href = citation.projectSlug
-   ? `/projects/${citation.projectSlug}#${citation.anchor}`
-   : "/#profile";
+ const href = `${citation.path}#${citation.anchor}`;
```

5.3 원문 "`citation.path + '#' + citation.anchor`로 이동한다" 문구를 그대로 코드로 옮겼다. `projectSlug` 유무로 분기하던 로직을 제거했으므로 `path` 필드가 더 이상 죽은 값이 아니다. 주석도 "백엔드가 채워 보내는 `citation.path`를 그대로 신뢰"한다는 점을 명시하도록 갱신했다.

**FastAPI 쪽 `path` 채움 로직 확인 (수정 없이 확인만 함)**

지시대로 `apps/ai-server`는 고치지 않고, `citation.path`가 두 경우(`/`, `/projects/{slug}`) 모두 실제로 올바르게 채워지는지만 코드로 추적했다:

1. **데이터 원본**: `data/profile.json`에 `"path": "/"`가 이미 박혀 있다(Home Profile Section). `scripts/load_graph.py`는 프로젝트의 Overview Section(233행)과 H2 Section(264행, 720행) 각각에 `"path": f"/projects/{slug}"`를 부여한 뒤, `create_section`(474행)에서 `s.path = $path`로 Neo4j `Section` 노드에 그대로 저장한다. 즉 Section.path는 이 두 값(`"/"` 또는 `"/projects/{slug}"`) 중 하나로만 채워지며, 03 검증보고서가 이미 확인한 사실과 일치한다.
2. **Retrieve 단계**: `app/graph/client.py`의 `fetch_sections_with_cases()`가 Cypher로 `s.path AS path`를 그대로 조회하고, `app/pipeline/retrieve.py`(230행)가 이 값을 `Candidate.path`에 그대로 담는다 — 코드가 path를 가공·재조합하지 않는다.
3. **Generate 단계**: `app/pipeline/generate.py`의 `_format_candidate()`(57행)가 `path: {candidate.path}`를 프롬프트 컨텍스트에 그대로 포함시키고, system prompt(37~39행)가 "sectionId/path/anchor/projectSlug 값은 그 후보에 주어진 값을 그대로 사용하고 새로 지어내지 않는다"고 명시적으로 지시한다. `GenerateResult.citations`(LLM structured output)는 이 지시를 따라 후보의 path를 그대로 복사하는 것을 전제로 한다.
4. **응답 단계**: `app/api/chat.py`(140행)는 `generate_result.citations`를 가공 없이 그대로 `ChatResponse.citations`에 담아 반환한다.

**결론**: FastAPI 쪽은 `path`를 두 경우 모두 올바르게 채워 보낸다 — 문제는 없었다. 다만 한 가지 짚어둘 점은, 3번 단계의 "그대로 사용" 보장이 코드 레벨의 강제(예: 서버가 후보 목록에서 path를 재조회해 LLM 응답을 덮어쓰는 방식)가 아니라 system prompt 지시에 대한 LLM의 순응에 의존한다는 것이다. 즉 이론적으로는 LLM이 프롬프트 지시를 어기고 path를 다른 값으로 채워 반환할 가능성이 구조적으로 남아 있다. 다만 이는 Phase 03에서 이미 검증·통과된 Generate 파이프라인의 기존 설계이고, 이번 지시 범위(FE의 `projectSlug` 재구성 문제)와는 별개의 사안이라 고치지 않았고 새로운 문제로 등록하지도 않았다 — 참고용으로만 기록해 둔다.
