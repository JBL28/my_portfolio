# 01. Next.js 정적 페이지 구현보고서

> Phase 01: Neo4j·FastAPI 없이 `data/`만으로 완결되는 Next.js 정적 포트폴리오(App Router, TypeScript, Tailwind CSS)를 `apps/web/`에 구현한 결과와, 그 과정에서 내린 판단·근거를 기록한다. 채팅 위젯(`components/domains/chat`, `/api/chat`)은 이 Phase 범위가 아니므로 만들지 않았다.

## 3. Overview body 조합에 실제로 사용한 템플릿

01_설계.md 3.2는 "Overview Section은 Detail 페이지 상단 개요 블록(소개 문장 + 기간·팀·담당·기술 스택·결과 + 저장소 공개 여부 안내) 전체"라고 정의하고, `data/`에는 이 body 원문이 별도로 없다고 명시한다. `components/domains/project/ProjectOverview.tsx`가 `<section id="overview">`로 아래 순서·구조로 조합해 렌더링한다(Project 메타데이터 필드 → 화면 요소 매핑):

1. `project.name` → `<h1>` (페이지 전체에서 유일한 h1)
2. `project.summary` → 소개 문단(`RichText`로 `**강조**` 파싱)
3. `<dl>` 메타 목록 — `period`(기간) / `teamSize`(팀 구성) / `roles`(담당, 목록) / `result`(결과) / `technologies`(기술 스택, `Badge` 목록)를 2열 그리드로 배치
4. `project.repositoryNotice`가 **존재할 때만** 그 문장을 그대로 출력 (필드가 없으면 이 블록 자체를 렌더링하지 않음)

이 조합은 "사실의 원본은 Project 메타데이터 한 곳에만 둔다"는 01_설계.md 3.2 원칙을 그대로 따른 것이며, Home 카드(`ProjectCard.tsx`)도 **같은** `data/projects/{slug}.json` 값을 그대로 읽어 렌더링하므로 두 화면이 서로 다른 값을 보여줄 여지가 없다(4장에서 실측 확인).

## 4. 판단이 필요했던 지점

### 4.1 `repositoryVisibility: "unknown"` (Home Server) — 어떤 문구도 만들지 않음

Home Server는 `repositoryVisibility: "unknown"`이고 `repositoryNotice` 필드 자체가 없다. "공개 저장소입니다"류의 문장을 추론해서 채워 넣지 않았다 — `ProjectOverview`는 `repositoryNotice` 필드의 **존재 여부**로만 렌더링을 분기하지(`{project.repositoryNotice ? ... : null}`), `repositoryVisibility` 값 자체를 텍스트로 노출하지 않는다. 같은 규칙을 TeenyFinny(`public`, `repositoryNotice` 없음)에도 동일하게 적용해, "공개 저장소입니다" 같은 문구도 만들지 않았다 — data에 실제로 있는 문장(DailyBand의 `repositoryNotice`)만 그대로 보여주고, 나머지 두 프로젝트는 저장소 공개 여부에 대해 완전히 침묵한다. 이는 00_기획.md의 "포트폴리오에 없는 설명을 임의 추가하지 않는다" 원칙을 그대로 지키기 위함이다.

### 4.2 경량 마크다운 파서를 직접 구현(외부 라이브러리 미도입)

`data/`의 body/roles 필드에는 `**강조**`(굵게)와 `` `코드` ``(인라인 코드, 예: DailyBand의 `` `files` ``, `` `files`·Job ``) 두 가지 표기가 실제로 섞여 있다(`data/projects/dailyband.json` 확인). `research/구현/00_구현보고서.md` 5.8에도 "이 서식은 필자가 의도적으로 표시한 것이며 FE가 markdown으로 처리한다고 가정했다"고 명시돼 있어, 텍스트를 그대로 방치(별표/백틱이 화면에 그대로 노출)하면 안 된다고 판단했다. `remark`/`react-markdown` 같은 라이브러리를 새로 추가하는 대신, 이 두 규칙만 처리하는 최소 파서(`lib/rich-text.tsx`)를 직접 작성했다 — 02_구현계획.md가 스타일링 도구만 Tailwind로 확정했을 뿐 마크다운 렌더러 도입 여부는 정한 바 없고, shadcn/ui 같은 컴포넌트 라이브러리 도입 금지 원칙과 같은 취지로 불필요한 의존성 추가를 피했다. 이 파서는 문단(`\n\n`)·`**강조**`·`` `코드` `` 세 규칙만 처리하며 그 외 마크다운 문법(리스트, 링크 등)은 원문에 등장하지 않아 구현하지 않았다.

### 4.3 Next.js 16 App Router의 `params`는 Promise — 처음에 동기 타입으로 잘못 작성해 3개 페이지가 전부 404로 렌더링되던 버그를 빌드 후 직접 발견/수정

처음에 `app/projects/[slug]/page.tsx`를 `{ params: { slug: string } }`(동기 객체)로 타입을 작성했다. `npm run build`는 타입 오류 없이 통과하고 라우트 표에도 3개 페이지가 `●`(SSG)로 표시되어 겉으로는 문제가 없어 보였지만, **실제 생성된 HTML을 열어보니 3개 페이지 전부 `NEXT_HTTP_ERROR_FALLBACK;404`(=`notFound()`가 실행된 결과)였다** — Next.js 15+/16에서 `params`가 `Promise<{slug:string}>`로 바뀌었는데 이를 await하지 않아 `params.slug`가 `undefined`가 되고, `getProjectBySlug(undefined)`가 `null`을 반환해 매 요청이 `notFound()`로 빠졌기 때문이다. `.next/types/routes.d.ts`의 `PageProps` 정의(`params: Promise<ParamMap[...]>`)로 원인을 확인한 뒤 `generateMetadata`/`ProjectDetailPage`를 `async function`으로 바꾸고 `const { slug } = await params`로 수정해 해결했다. 수정 후 재빌드해 세 HTML 파일 모두 `NEXT_HTTP_ERROR_FALLBACK` 문자열이 없고 실제 프로젝트 콘텐츠(섹션 제목/본문/roles/technologies)가 들어있음을 grep으로 재확인했다.

이 버그는 "`next build`가 에러 없이 통과했다"는 사실만으로는 전혀 드러나지 않았고, **생성된 HTML 산출물을 직접 열어봐야만** 발견할 수 있었다 — 이번 검증에서 로그만 보지 않고 산출물을 열어본 이유이자, 앞으로 유사한 회귀를 잡으려면 빌드 성공 여부뿐 아니라 산출물 내용 검증이 필요하다는 근거이기도 하다.

### 4.4 Home profile body를 "첫 문단(h1) + 나머지(본문)"으로 분리

`data/profile.json`의 `title`은 `"프로필"`이라는 Section 메타데이터용 라벨일 뿐(01_설계.md 3.2 — "H2 헤딩이 없는 것은 Overview와 동일한 이유"), 실제로 화면에 노출할 지원자 소개 헤드라인이 아니다. 반면 `body`의 첫 문단("팀이 함께 쓸 기준을 만드는 백엔드 개발자")은 그 자체로 헤드라인처럼 읽히도록 원문이 이미 구성돼 있다. 페이지에 시맨틱상 유일한 `<h1>`이 필요하다고 판단해, `body`를 `\n\n` 기준으로 분리한 뒤 첫 문단만 `<h1>`, 나머지는 본문 `<RichText>`로 렌더링했다 — 텍스트 내용 자체는 한 글자도 바꾸지 않고 태그만 나눈 것이며, `title`(`"프로필"`)을 화면에 그대로 노출하지 않기로 한 판단이다. 이름/직군 라벨은 `data/profile.json`에 필드 자체가 없어(00_구현보고서 5.7에서 "이름/직군 표기는 body에서 의도적으로 제외했다"고 이미 기록됨) 페이지 어디에도 지어내지 않았다.

### 4.5 Tailwind v4의 dark 변형을 class 전략으로 재정의

Tailwind CSS v4는 기본적으로 `prefers-color-scheme` 미디어 쿼리 기반 dark 변형을 쓰는데, `next-themes`는 `<html>`에 `class="dark"`를 토글하는 방식이라 그대로면 수동 토글이 동작하지 않는다. `app/globals.css`에 `@custom-variant dark (&:where(.dark, .dark *));`를 추가해 class 기반으로 재정의했다. 컴파일된 CSS에서 `.dark ...` 규칙이 실제로 생성됨을 확인했다(2장 참고).

### 4.6 `Container`를 className 오버라이드 대신 `size` prop으로 설계

`tailwind-merge` 같은 클래스 충돌 해결 라이브러리를 추가하지 않기로 했으므로(불필요한 의존성 최소화), `max-w-3xl`이 기본인 `Container`에 페이지마다 다른 className(`max-w-5xl`)을 그냥 이어붙이면 두 유틸리티 클래스의 CSS 우선순위가 클래스 속성상의 순서가 아니라 Tailwind가 생성한 스타일시트 내 규칙 순서로 결정되어 어느 쪽이 이길지 보장할 수 없다. 대신 `size: "narrow" | "wide"` prop으로 명시적 분기를 두어 이 충돌 가능성 자체를 없앴다. Home/Header/Footer는 `size="wide"`, Project Detail 본문은 `size="narrow"`(가독성을 위한 좁은 본문 폭)를 사용한다.

### 4.7 반응형/다크모드 외 애니메이션·상호작용 요소를 추가하지 않음

00_기획.md·01_설계.md 5.2는 이 Phase에서 상호작용이 필요한 요소를 다크모드 토글 정도로 한정한다. Framer Motion, 플로팅 채팅 버튼/모달, `/api/chat`, axios, 로그인/CMS는 만들지 않았고, `components/domains/chat`도 생성하지 않았다(둘 다 Phase 04 범위). Project Detail에 목차(TOC)나 섹션 간 이동 네비게이션도 추가하지 않았다 — 00_기획.md·01_설계.md 어디에도 이 Phase에서 요구한 내용이 아니므로 임의로 추가하지 않았다(공통 주의사항 "기획된 내용 이상의 요소를 추가할 때는 반드시 사용자의 허가를 받는다").

## 5. 확인한 것 — Home 카드와 Detail 페이지 데이터 일치

`lib/portfolio-data.ts`의 `getAllProjects()`(Home 카드용)와 `getProjectBySlug()`(Detail용)는 동일한 `data/projects/{slug}.json` 파일을 읽는 같은 코드 경로를 공유한다 — 두 화면이 별도로 값을 베껴 적을 여지 자체가 구조적으로 없다. 실제 빌드 산출물에서도 DailyBand의 담당 목록("고스트 기능 연결 API" 등)과 기술 스택("SonarQube" 등)이 Home 카드와 Detail 개요 블록 양쪽에 동일하게 나타남을 grep으로 재확인했다.
