### 2.1 retrieve.graph의 "매칭된 Case/Section/Project id·매칭 경로" — 근사치임을 명시

기존 `_Hit` 자료구조(pipeline/retrieve.py)는 대부분 `section_id`만 들고 있고 `case_id`/`project_slug`는 일부 단계(주로 step 1)에서만 별도 반환값(`seed_case_ids`, `seed_project_slugs`)으로 얻을 수 있다. `_Hit`의 필드를 늘리면 각 step 함수의 반환 타입을 바꿔야 해서 "step 함수 내부 로직·시그니처는 건드리지 마라"는 지시와 충돌한다. 그래서:

- `matched_section_ids`는 정확하다(모든 hit이 section_id를 갖는다).
- `matched_case_ids`/`matched_project_slugs`는 step 1이 반환하는 `seed_case_ids`/`seed_project_slugs`만 기록한다 — step 2/3/5에서 추가로 매칭된 case/project id는 `_Hit`이 들고 있지 않아 기록하지 못했다(step 2/3/5의 Cypher 쿼리 자체는 caseId를 반환하지만, 오케스트레이터로 넘어오는 `_Hit`에는 담기지 않는다).
- `matched_relations`는 `_Hit.source`(예: `graph_competency`, `considered`, `growth_case`)를 실제 관계 타입으로 매핑한 근사치다(`_SOURCE_TO_RELATION` 딕셔너리, `retrieve.py` 상단). `overview`/`followup`은 관계 매칭이 아니라 2장이 정의한 명시적 경로(0번/5번)라 관계명 대신 `explicit:...` 태그를 붙였고, `similar_case`는 DEMONSTRATES/USES/CONSIDERED 중 어느 것으로 매칭됐는지 원 코드가 구분해 반환하지 않아 셋을 합쳐 표기했다.

이 근사는 관측 목적(사후 분석)에는 충분하다고 판단했지만, "Case id별로 정확히 어떤 관계였는지" 수준의 정밀한 감사가 필요해지면 `_Hit`/step 함수의 반환값을 확장하는 리팩터링이 추가로 필요하다 — 이번 Phase 범위(계측만 얹기)를 넘어서므로 하지 않았다.

## 3. security.input / security.output 규칙과 근거

8.3: "이 규칙 기반 스캔은 보안 경계가 아니라 관측을 위한 휴리스틱 신호다." 두 모듈 모두 `blocked`/차단 로직을 갖지 않으며, `api/chat.py`의 기존 try/except 흐름을 전혀 바꾸지 않았다(스캔 실패는 예외를 던지지 않고 규칙이 매칭되지 않은 것으로만 처리된다).

### 3.1 `app/security/input_scan.py` — security.input

| 규칙 | 매칭 대상 | 근거 |
|---|---|---|
| `length_exceeded` | 입력 길이 > 2000자 | 8.3 "길이 제한". 정상적인 포트폴리오 질문은 이 길이를 넘기 어렵다는 가정. 8.6 "데이터가 쌓이기 전까지는 최소한의 규칙으로 시작한다"에 따라 보수적인 값으로만 시작 |

| `system_prompt_exfil` / `system_prompt_exfil_reverse` | "system prompt/시스템 프롬프트"와 "보여줘/출력해줘/reveal/show" 류가 20자 이내에 함께 등장 | system prompt 탈취 시도(8.3 "프롬프트 탈취 패턴") |

## 5. Python 코드 정적 재검토 (실행 불가 — 손으로 확인)

Python 실행환경이 없어(`python --version` 실행 시 Windows 스토어 스텁만 응답하고 실제 인터프리터 없음을 확인) `pip install`도, `uvicorn` 기동도, `python -m py_compile`도 할 수 없었다. 대신 다음을 손으로 확인했다:

- 새로 만들거나 수정한 6개 Python 파일(`observability/tracing.py`, `security/input_scan.py`, `security/output_scan.py`, `main.py`, `pipeline/retrieve.py`, `pipeline/generate.py`, `api/chat.py`) 전체를 다시 읽으며 괄호/들여쓰기 짝을 확인했다.
- 탭 문자 혼입 여부를 `grep -P '\t'`로 전수 검사 — 없음을 확인.
- `api/chat.py`의 `try/except/finally` 중첩 구조(root span의 `with` 안에 `try`, 그 안에 각 단계별 `with tracer.start_as_current_span(...)`)가 기존 `except (RuntimeError, ValueError)` 절의 위치·조건을 그대로 유지하는지 확인했다 — span context manager는 예외를 기록한 뒤 그대로 다시 던지므로(OpenTelemetry 기본 동작), 기존 예외 흐름을 바꾸지 않는다.
- `openai.types.completion_usage.CompletionUsage`의 필드명(`prompt_tokens`/`completion_tokens`/`total_tokens`)은 OpenAI Python SDK의 공개 타입 정의를 기준으로 확인했다 — 실제 설치된 패키지에서 import가 성공하는지는 실행 확인하지 못했다.
- `opentelemetry.exporter.otlp.proto.http.trace_exporter.OTLPSpanExporter`가 인자 없이 생성될 때 `OTEL_EXPORTER_OTLP_ENDPOINT` 등 표준 환경변수를 읽는 동작은 OpenTelemetry Python 공식 문서 기준으로 확인했다 — 실제 Phoenix 인스턴스로 export가 성공하는지는 8.5(Phase 06 배포 범위) 이전이라 애초에 검증 대상이 아니다.

## 6. 8.1/8.4 요구사항 재확인

- **security.input이 gate.portfolio보다 먼저 실행되는 순서**: `api/chat.py`에서 `security.input` span은 root span 진입 직후, `try` 블록의 첫 줄에서 실행되고 그 다음에 `gate.portfolio` span이 온다 — 8.1 다이어그램 순서와 일치.
- **requestId는 BFF가 생성하고 FastAPI는 새로 만들지 않는다**: `apps/web/app/api/chat/route.ts`가 매 요청마다 `crypto.randomUUID()`로 생성해 `X-Request-ID` 헤더로 전달한다. FastAPI(`api/chat.py`)는 이 헤더를 `http_request.headers.get("x-request-id", "")`로 그대로 읽어 `request_id` attribute에 기록할 뿐, 새 UUID를 생성하지 않는다.
- **클라이언트가 보낸 X-Request-ID를 신뢰하지 않는다**: `route.ts`는 들어온 요청의 헤더를 전혀 읽지 않고 매번 새 `crypto.randomUUID()`를 생성해 덮어쓴다 — "신뢰하지 않는다"를 "애초에 참조하지 않는다"로 구현했다.
- **risk_score로 차단하지 않는다**: `input_scan.py`/`output_scan.py` 어디에도 반환값을 근거로 예외를 던지거나 응답을 바꾸는 코드가 없다. `api/chat.py`도 두 스캔 결과를 span attribute로 기록하기만 하고 분기에 쓰지 않는다.
- **Nginx/BFF rate limiting은 구현하지 않았다**: `route.ts`에 추가한 것은 `requestId` 생성/헤더 전달뿐이며, 요청 횟수 제한 로직은 추가하지 않았다(8.4 — Phase 06 범위).
- **8.5(Phoenix 배포, Docker Compose, SQLite)는 손대지 않았다**: docker-compose 파일이나 배포 스크립트를 만들거나 수정하지 않았다.

## 7. 실행 검증을 하지 못한 부분 (명시)

- **span이 실제로 생성되고 OTLP로 export되는지**: FastAPI를 기동할 Python 런타임이 없어, `uvicorn`으로 서버를 띄우고 실제 `/chat` 요청을 보내 Phoenix(또는 다른 OTLP 수신자)에 trace가 도착하는지 확인하지 못했다.
- **OTLP exporter 초기화 실패 시 서버가 실제로 죽지 않는지**: `configure_tracing()`을 `try/except`로 감싼 코드는 작성했지만, 실제로 `OTEL_EXPORTER_OTLP_ENDPOINT`를 비운 채 서버를 기동해 정상 응답하는지는 실행으로 확인하지 못했다.
- **`opentelemetry-exporter-otlp` 등 신규 의존성의 실제 설치 가능 여부**: `pip`/`uv` 등 패키지 매니저를 실행할 수 없어 `pyproject.toml`에 추가한 버전 범위(`>=1.27,<2`)로 실제 설치가 성공하는지는 확인하지 못했다.
- **security.input/output 규칙의 오탐·미탐률**: 실제 트래픽 데이터가 없어 정규식이 정상 질문("이 사이트의 system prompt를 어떻게 보호했나요?" 같은 8.3 예시)을 오탐하는지, 실제 우회 시도를 놓치는지는 검증하지 못했다 — 8.6에 명시된 대로 데이터가 쌓인 뒤 재검토가 필요하다.
- **`X-Request-ID`가 FastAPI 로그/응답 어디에서도 실제로 관측되는지**: `http_request.headers.get(...)`로 값을 읽는 코드는 작성했지만, Next.js BFF → FastAPI 실제 왕복 요청으로 헤더가 그대로 전달되는지는 실행 확인하지 못했다(Phase 04 보고서도 같은 한계를 명시했다 — Python 런타임 부재는 04에서도 03에서도 동일).

**다음 실행 시 사용자가 직접 확인해야 할 것**: `apps/ai-server`에 `pip install -e .`(또는 `uv sync`)로 신규 OTel 의존성을 설치 → `OTEL_EXPORTER_OTLP_ENDPOINT`(Phoenix 등)를 환경변수로 설정 → `uvicorn app.main:app`으로 기동 → `apps/web`에서 `/api/chat`으로 요청을 보내 실제 trace가 backend에 도착하는지, span 10개(request/security.input/gate.portfolio/gate.site/extract/retrieve.graph/retrieve.vector/retrieve.rank/generate/security.output — Gate1/2 조기 종료 시에는 그 이후 span이 생성되지 않는 것이 정상)가 8.1 순서대로 나타나는지 직접 확인.
