# 포트폴리오 프로젝트 기획

## 개요
* 이 프로젝트는, 채용 담당자가 빠르게 내용을 파악할 수 있도록 그래프 RAG를 적용하는 포트폴리오입니다.
* 사용자 페르소나 : 짧은 시간 안에 지원자의 역량과 프로젝트 경험을 파악하려는 채용 담당자 및 면접관
* 문제상황 : 프로젝트별 상세 내용과 경험이 많아질수록 사용자가 원하는 정보를 직접 찾아야 하며, 지원자의 역량과 이를 뒷받침하는 구체적인 사례 사이의 연결을 한눈에 파악하기 어렵다.
* 가치 : 사용자가 지원자에 대해 궁금한 내용을 자연어로 질문하면, 관련 프로젝트와 사례를 찾아 포트폴리오 원문을 근거로 답변하고 해당 문단으로 직접 이동할 수 있도록 한다. AI는 포트폴리오를 대신 설명하는 주체가 아니라, 사용자가 포트폴리오의 근거를 더 빠르게 찾도록 돕는 탐색 수단으로 사용한다.

## 공통 주의사항
* 더미 데이터, 문서에 없는 설명, 포트폴리오에 없는 기능/성과/수치를 임의 추가하지 않습니다.
* "이 버튼을 누르면 프로젝트로 이동합니다"와 유사한 쓸데없는 기능 설명을 포함하지 않습니다.
* 기획된 내용 이상의 요소를 추가할 때는 반드시 사용자의 허가를 받습니다.

## 요구사항
* 구현해야하는 기능은 다음과 같습니다.
    * Graph RAG
        * 사용자의 프롬프트가 포트폴리오와 관련된 내용인지 structured outputs를 활용해 판별합니다.
            * 포트폴리오와 관련된 내용이 아니라면 정해진 안내 문구를 답변합니다. (예시: 지원자에 대한 질문을 해주세요. 를 예의바르게)
            * 포트폴리오와 관련된 내용이라면 다음 단계로 넘어갑니다.
        * 사용자의 질문이 포트폴리오 그 자체와 관련된 내용인지 structured outputs를 활용해 판별합니다. (지원자의 경험이 아니라 현재 포트폴리오 웹사이트의 구현 방식이나 소스코드 자체를 묻는 경우)
            * 포트폴리오 그 자체에 대한 내용이라면 깃허브 링크를 안내합니다.
            * 아니라면 다음 단계로 넘어갑니다.
        * 사용자의 질문에서 검색에 필요한 의도 및 핵심 개념(역량, 기술, 프로젝트 등)을 추출합니다.
            * 추출한 의도 및 핵심 개념을 바탕으로 Graph RAG를 수행합니다.
        * Graph RAG의 과정에서 검색 결과는 다음을 포함해야 합니다. 
            * 포트폴리오 웹사이트의 해당 부분으로 이동할 수 있는 주소와 앵커
            * 관련된 본문의 내용
        * 관련된 본문의 내용과 함께, 포트폴리오의 해당 부분으로 이동 가능한 링크를 제공합니다.
        * 대화 맥락을 사용하여 연속된 질문에 답변할 수 있어야 합니다. (예시 : 이 사용자는 협업을 어떻게 하나요? -> 그 근거가 뭔가요?)
        * 원문에 없는 사실 추론 금지, 근거가 부족하면 부족하다고 답하기, 반드시 Section 링크 제공 같은 제약이 필요합니다.
    * FE
        * Next.js를 사용하여 AI 서버의 주소를 클라이언트가 알지 못하도록 합니다.
            * axios를 활용한 API 관리가 필요합니다.
                * axios 객체와 API 목록을 중앙화하여 관리합니다. 유지보수를 위함입니다.
        * 일반모드와 다크모드를 지원해야 합니다.
        * 데스크탑, 태블릿, 모바일 등 다양한 환경에서 접근 가능하도록 설계해야합니다.
        * Next.js를 활용하는 만큼, SSG를 활용하여 검색엔진에 최적화된 사이트를 구성해야 합니다.
            * 프로젝트 내용이나 자기소개 등 바뀌지 않을 내용을 SSG로 구현합니다.
            * 이 때, 정적인 포트폴리오 페이지와 동적인 API 라우팅이 공존하는 구조가 되어야합니다.
        * Next.js의 라우팅 원칙을 준수합니다.
        * Next.js의 클라이언트/서버 컴포넌트 원칙을 준수합니다.
        * 컴포넌트는 유지보수 가능하도록 관리합니다.
            * components - domains - buttons/layouts 등등 계층화하여 관리합니다.
        * Framer Motion(현재 이름 Motion)를 활용해 애니메이션을 적용합니다.
            * 글의 가독성을 해치지 않도록 적당한 수준으로 적용되어야 합니다.
        * RAG 기능을 플로팅 버튼/플로팅 모달로 구현합니다.
            * AI가 그려져있는 플로팅 버튼을 클릭할 시 플로팅 모달이 펼쳐집니다.
            * 플로팅 모달에는 입력창과 채팅 화면이 나타납니다.
        * 메인 화면에서 지원자를 설명하며, 프로젝트 디테일마다 별도의 페이지를 갖습니다.
    * Graph DB
        * Neo4j를 사용합니다.
            * 스키마의 경우 "00_GraphRAG 스키마 설계" 문서를 참고합니다.
        * 데이터는 다음 기준으로 추가합니다.
        * 모든 데이터는 실제 포트폴리오 원문을 기준으로 생성하며, 원문에 없는 사실을 추론하여 추가하지 않습니다.
            * Section은 포트폴리오의 실제 문단을 기준으로 생성합니다.
                * body는 원문의 내용을 그대로 유지합니다.
                * 실제 웹페이지의 path와 anchor를 함께 저장하여 검색 결과에서 원문으로 이동할 수 있도록 합니다.
                * 검색에 사용할 Section에만 embedding을 생성합니다.
            * Case는 하나의 문제, 판단 또는 행동 흐름으로 설명할 수 있는 구체적인 경험을 기준으로 생성합니다.
                * 단순히 기술을 사용했다는 사실만으로 Case를 생성하지 않습니다.
                * problem, judgment, action, result, learning은 원문에서 확인 가능한 내용만 기록합니다.
                * 원문에서 확인할 수 없는 필드는 임의로 채우지 않습니다.
                * 모든 Case는 최소 하나 이상의 Section과 DESCRIBED_IN 관계를 가져야 합니다.
            * Competency는 "00_GraphRAG 스키마 설계"에서 정의한 역량만 사용하며 임의로 새로운 역량을 생성하지 않습니다.
                * Case에서 실제 행동이나 판단으로 확인할 수 있는 역량만 DEMONSTRATES 관계로 연결합니다.
            * Technology는 동일한 기술이 중복된 노드로 생성되지 않도록 이름을 정규화합니다.
                * 실제 프로젝트에서 사용한 기술만 USES 관계로 연결합니다.
                * 검토하거나 대안으로 비교했지만 실제 사용하지 않은 기술은 CONSIDERED 관계로 연결합니다.
            * Project 간 BUILDS_ON 관계와 Case 간 INFLUENCED 관계는 이전 경험이 이후 프로젝트나 판단에 영향을 주었다는 내용이 원문에서 확인되는 경우에만 생성합니다.
            * AI를 활용해 데이터를 추출하더라도 위 기준을 만족하지 않는 노드나 관계를 임의로 생성하지 않습니다.
