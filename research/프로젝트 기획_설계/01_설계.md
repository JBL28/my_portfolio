# 프로젝트 설계

> 이 문서는 "00_기획.md"의 요구사항을 실제로 구현 가능한 시스템 구조로 옮긴 설계 문서입니다.
> 작업 순서(일정, 단계 분할)는 다루지 않습니다. 작업 계획은 이 설계가 검증된 뒤 "02_구현계획.md"에서 다룹니다.

## 0. 확정된 전제

| 항목 | 결정 |
|---|---|
| AI 서버 스택 | Python (FastAPI) |
| LLM / Structured Output | OpenAI API · 저비용 모델 우선 (구체 모델명은 미정) |
| AI 서버 · Neo4j 배포 위치 | 직접 운영 홈서버 (Home Server 프로젝트 인프라 재사용) |
| FE | Next.js (App Router) |

## 1. 전체 시스템 아키텍처

```
[ Browser ]
    │  HTTPS (같은 origin)
    ▼
[ Next.js ]  ── 정적 페이지: SSG (Home, /projects/[slug])
    │            동적 라우트: /api/chat (Route Handler, BFF)
    │
    │  서버 사이드에서만 호출 (AI_SERVER_URL은 서버 환경변수, 클라이언트 번들에 노출 안 됨)
    │  배포 위치에 따라 아래 두 경로 중 하나로 FastAPI에 도달한다 (7장, 아직 미확정)
    │   A) 홈서버 밖(예: Vercel) 배포 → HTTPS → Cloudflare Tunnel → Nginx → FastAPI (인터넷 경유)
    │   B) 홈서버 안에 함께 배포        → 내부 네트워크 → FastAPI 직접 호출         (인터넷 비경유)
    ▼
[ FastAPI AI 서버 ]  (홈서버, Docker)
    │                 │
    ▼                 ▼
[ Neo4j ]        [ OpenAI API ]
(그래프 + 벡터 인덱스)  (판별 / 추출 / 답변 생성)
```

**핵심 원칙**: 브라우저는 오직 Next.js(같은 origin)와만 통신한다. AI 서버 주소는 Next.js 서버 프로세스만 알고 있으며, 클라이언트로 절대 전달되지 않는다. 이것이 기획서 "Next.js를 사용하여 AI 서버의 주소를 클라이언트가 알지 못하도록" 요구사항의 구현 방식이다.

Next.js ↔ FastAPI 사이의 통신 경로는 Next.js 배포 위치에 따라 달라지며, 아직 확정되지 않았다(7장). 외부에 배포해 인터넷을 경유하는 경우 Cloudflare Tunnel 진입점에서 공유 시크릿 헤더(예: `X-Internal-Token`)로 Next.js 서버발 요청만 허용하고 그 외 요청은 Nginx/FastAPI 단에서 거부한다. 홈서버에 함께 배포해 내부 네트워크로 통신하는 경우, 이미 외부에 노출되지 않는 구간이므로 이 인증 계층은 선택 사항이 된다. 어느 쪽이든 브라우저는 FastAPI 주소를 알 수 없다는 핵심 원칙은 동일하게 유지된다.

임베딩(벡터 생성)에 쓰이는 모델·제공자는 위 다이어그램의 "OpenAI API" 확정 범위에 포함되지 않는다 — 판별/추출/답변 생성에 OpenAI API를 쓴다는 것만 확정됐고, 임베딩은 별도로 결정할 사항이다(3.3, 7장 참고).

## 2. Graph RAG 파이프라인 설계

기획서의 요구 흐름(관련성 판별 → 자기참조 판별 → 의도/개념 추출 → 그래프 검색 → 근거 기반 답변)을 아래와 같이 단계화한다. 이 중 LLM을 호출하는 Gate 1/2, Extract, Generate 단계는 OpenAI Structured Outputs로 스키마를 강제한다 — Retrieve는 Neo4j 검색/스코어링을 수행하는 코드 단계이며 LLM 호출 대상이 아니다.

```
사용자 입력 + 최근 대화 이력(N턴)
        │
        ▼
[Gate 1] 포트폴리오 관련 질문인가?
   schema: { is_portfolio_related: bool, reason: string }
   └ false → 고정 안내 문구 반환 후 종료
        │ true
        ▼
[Gate 2] 포트폴리오 "웹사이트 자체"(구현/소스코드)에 대한 질문인가?
   schema: { is_about_site_itself: bool, reason: string }
   └ true → GitHub 링크 안내 문구 반환 후 종료
        │ false
        ▼
[Extract] 의도 및 핵심 개념 추출 (대화 맥락 포함)
   schema: {
     search_intent: string,          // 정규화된 검색 의도
     competencies: Array<"협업"|"기술적 판단"|"문제 해결"|"운영"|"DevOps"|"AI 활용"|"학습 및 성장">,
                                      // 3.4에서 정의한 7개로 제한된 enum — 이 목록 밖 값은 후처리에서 버린다
     technologies: string[],         // 자유 텍스트 추출. Retrieve에서 alias→canonical 정규화 후 Technology와 매칭(4장 참고)
     project_hints: string[],        // 언급된 프로젝트 0개/1개/여러 개 모두 가능
                                      // (예: "TeenyFinny와 DailyBand에서 협업 방식이 어떻게 달라졌나요?")
     wants_project_overview: bool,   // 기간/팀 구성/담당 역할/기술 스택/결과 등 프로젝트 메타데이터를 묻는 질문인지
     wants_alternatives_considered: bool,  // "여러 대안 중 하나를 선택한 사례가 있나요?" 같이 CONSIDERED 관계가 필요한 질문인지
     wants_growth_connection: bool,        // "이전 경험이 다음 프로젝트에 어떻게 반영/영향을 줬나요?" 같이
                                            // BUILDS_ON/INFLUENCED 관계가 필요한 질문인지
     wants_similar_cases: bool,      // "비슷한 경험이 다른 프로젝트에도 있나요?" 같이, 직전 답변의 근거 Case와
                                      // 유사한 Case를 다른 프로젝트에서 확장 검색해야 하는 후속 질문인지
     is_followup: bool,              // "그 근거가 뭔가요?" 같은 후속 질문 여부
     refers_to_previous_citations: { sectionId: string, caseId: string | null }[]
     // is_followup=true일 때, 클라이언트가 함께 보낸 이전 턴 citations 중 이 질문이 가리키는 것
   }
        │
        ▼
[Retrieve] Graph RAG 검색 — 3장에서 확정한 관계(DEMONSTRATES/USES/CONSIDERED/BUILDS_ON/INFLUENCED)를 모두 사용한다
   0) project_hints는 기본 검색 seed·우선 범위로 사용한다(빈 배열이면 특정 프로젝트로 좁히지 않음). 단, 3)의 성장 관계
      탐색은 `BUILDS_ON`/`INFLUENCED`를 따라 이 범위 밖의 연결된 Project·Case로 확장될 수 있다 — 예를 들어
      `project_hints=[DailyBand]`여도 "이전 경험이 어떻게 반영됐나요?"라는 질문에는 Home Server까지 확장해야 한다.
      Overview는 벡터 검색으로는 검색하지 않고 명시적 경로로만 후보에 포함한다(3.2/3.3 참고) — 이 0번 경로와, 1번의
      `Project-USES-Technology` 매칭 결과 두 가지다.
        - `wants_project_overview=true`이면 이 0번 경로에서 Overview를 포함한다:
          project_hints가 있으면 해당 Project(들)의 Overview만, 비어 있으면(예: "어떤 프로젝트들을 했나요?",
          "팀 프로젝트는 몇 개예요?") 전체 Project의 Overview를 후보로 포함한다.
        - `wants_project_overview=false`이면 **이 0번 경로에서는** project_hints가 있어도 Overview를 추가하지 않는다
          (관련 없는 Overview가 Top-K 자리를 차지하지 않도록). 다만 1번에서 `Project-USES-Technology`로 그 Project가
          직접 매칭되면 이 값과 무관하게 Overview가 후보에 추가될 수 있다 — 그 경로는 별개의 명시적 근거이기 때문이다.
   1) 그래프 매칭 (역량/기술): competencies로 (Case)-[:DEMONSTRATES]->(Competency)를 탐색한다.
      technologies는 먼저 alias→canonical 정규화(4장)를 거친 뒤 (Case)-[:USES]->(Technology)와 (Project)-[:USES]->(Technology)를
      모두 탐색한다 — 특정 Case가 아니라 프로젝트 전체가 그 기술을 썼다는 사실도 근거가 될 수 있기 때문이다.
      → 매칭된 Case는 (Case)-[:DESCRIBED_IN]->(Section)으로 따라가 근거 Section을 확보한다.
      (Project)-[:USES]->(Technology)로 매칭된 Project는 그 Project의 **Overview Section을 곧바로 후보에 추가**한다
      (`wants_project_overview` 값과 무관하게 이 경로로 추가된다 — 그 기술을 썼다는 근거 자체가 Overview에 있으므로
      관련 없는 노이즈가 아니다). project_hints가 비어 있었다면 이 매칭 결과로 project_hints를 보강해 3)의 성장
      관계 탐색에도 반영한다.
   2) 대안 비교 매칭: `wants_alternatives_considered=true`면
        - technologies가 있으면: 정규화된 technologies로 (Case)-[:CONSIDERED]->(Technology)를 탐색해, 검토했지만
          채택하지 않은 기술에 대한 Case까지 후보에 포함한다 (예: TeenyFinny의 WebSocket vs Polling, DailyBand의
          WebRTC 대신 AOO·JUCE).
        - technologies가 없으면(예: "여러 대안 중 하나를 선택한 사례가 있나요?" — 기술명이 특정되지 않은 질문):
          `CONSIDERED` 관계를 가진 Case 전체를 후보로 삼는다. project_hints가 있으면 해당 Project로 범위를 좁힌다.
   3) 성장/연결 매칭: `wants_growth_connection=true`면
        - 1)에서 매칭된 Case/Project가 있으면(seed 있음): 이를 기준으로 (Case)-[:INFLUENCED]->(Case),
          (Project)-[:BUILDS_ON]->(Project)를 양방향 1-hop 확장해 관련 Case/Project를 후보에 추가한다.
        - seed가 없으면(예: "이전 프로젝트의 경험이 다음 프로젝트에 어떻게 반영됐나요?" — competency/technology/project
          가 특정되지 않은 질문): 원문 근거로 생성된 `INFLUENCED`/`BUILDS_ON` 관계 자체를 순회해 연결된 Case/Project
          쌍을 후보로 삼는다. project_hints가 있으면 그 Project가 관여된 관계로 좁힌다.
        - `INFLUENCED`로 찾은 Case 쌍은 각 Case의 `sectionIds`(4장 2번)로 이미 근거 Section을 갖고 있다. `BUILDS_ON`으로
          찾은 Project 쌍은 Project 노드 자체가 아니라, 매칭된 `BUILDS_ON` 관계의 `evidenceSectionIds` property(4장 3번 —
          재적재 시 `data/`의 `buildsOnEvidenceSectionIds`로부터 채워짐)가 가리키는 Section을 근거로 후보에 추가한다.
          이 property는 Neo4j 안에 있으므로 FastAPI가 `data/` 파일을 따로 열지 않고도 조회할 수 있다 — Project 노드는
          Generate가 받을 수 있는 근거(Section.body)가 아니므로, 이 변환 없이는 BUILDS_ON 매칭 결과가 답변까지
          이어지지 않는다.
   4) 벡터 매칭: search_intent 임베딩 vs Section.embedding (Neo4j vector index) 유사도 검색
      → Case가 없는 Section(배경 설명 등)도 이 경로로는 후보가 될 수 있다. Overview는 임베딩이 없으므로
        이 경로로는 후보가 되지 않는다(3.3 참고) — 0)의 명시적 경로로만 검색된다.
   5) is_followup=true면 refers_to_previous_citations(클라이언트가 되돌려준 이전 턴의 citations)를 후보 집합에 포함한다.
      추가로 `wants_similar_cases=true`이고 refers_to_previous_citations에 caseId가 있으면("비슷한 경험이 다른
      프로젝트에도 있나요?" 같은 질문), 그 Case의 (Case)-[:DEMONSTRATES]->(Competency)와
      (Case)-[:USES]/[:CONSIDERED]->(Technology)를 역으로 따라가 같은 Competency/Technology를 가지면서 **다른
      Project**에 속한 Case를 후보로 추가한다 — Vector 검색이 우연히 찾아줄 수도 있지만, 이 질문 유형은 Graph RAG가
      명시적으로 지원하기로 한 유형이므로 Vector에만 맡기지 않는다.
   6) 0~5의 결과를 합집합으로 구성한다. Case가 있는 Section은 Case 필드(검색을 돕는 구조화 메타데이터 — 최종 근거는
      Section.body, [Generate] 참고)까지 스코어링 근거로 함께 사용하고, Case가 없는 Section은 body만 사용한다.
   7) 스코어링 후 Top-K(예: 3~5개) 선정. 단 아래 두 종류는 스코어링으로 탈락시키지 않고 **항상 포함**한다(mandatory candidate):
        - is_followup=true일 때 5)의 refers_to_previous_citations 대상
        - wants_project_overview=true일 때 0)의 Overview 후보
      나머지 후보(그래프/대안/연결/유사사례/벡터 매칭 결과)만 스코어링으로 Top-K 나머지 자리를 채운다.
        │
        ▼
[Generate] 근거 기반 답변 생성
   입력: 선택된 Section.body(최종 근거 원문) + 연결된 Case 필드(problem/judgment/action/result/learning —
        검색·요약을 돕는 구조화 메타데이터이며 원문 자체는 아님) + path, anchor, project 정보
   system prompt 제약:
     - 제공된 Section.body 범위 밖의 사실을 추론하지 않는다. Case 필드는 참고 정보일 뿐, 최종 근거는 Section.body로 검증한다
     - `Project-USES`/Project Overview는 그 프로젝트에서 기술이 사용됐다는 근거일 뿐 지원자 개인의 직접 구현·사용을
       의미하지 않는다. 개인 기여를 주장하려면 Case 또는 Section 원문에서 본인의 행동이 명시적으로 확인되어야 한다
       (4장 2번의 Case-USES/Project-USES 구분 참고)
     - 근거가 부족하면 "부족하다"고 답하고 citations는 비워둔다 (근거 없는 Section을 억지로 채우지 않는다)
     - 답변은 관련 경험을 짧게 요약해 탐색을 돕는 수준으로 제한한다. AI가 포트폴리오를 대신 설명하지 않으며,
       상세 내용 확인은 Section 링크로 유도한다 (00_기획.md의 "탐색 수단" 원칙)
   schema: {
     answer: string,
     is_evidence_sufficient: bool,
     citations: [{ sectionId, caseId: string | null, projectSlug: string | null, path, anchor, quotedTitle }]
     // quotedTitle: caseId가 있으면 그 Case.title(4장 2번), caseId가 없으면(Case 없는 Section·Overview·Home
     // Profile Section) Section.title을 사용한다. 어느 쪽이든 Section.body 자체가 아니라 인용 링크에 표시할
     // 짧은 제목이다.
     // projectSlug는 nullable — Home Profile Section(3.2)은 특정 프로젝트에 속하지 않으므로 null
     // is_evidence_sufficient=true일 때만 citations 최소 1개 이상.
     // false면 citations=[] 허용 (근거 충분 여부와 인용 강제가 충돌하지 않도록 분리)
   }
        │
        ▼
FE 렌더링: 답변 텍스트 + 근거 링크(클릭 시 citation의 path/anchor로 이동 — 프로젝트 Section이면 `/projects/{slug}#{anchor}`,
Home Profile Section(projectSlug=null)이면 `/#profile`)
        │
        ▼
클라이언트가 (질문, 답변, 사용된 citations 전체: sectionId + caseId)를 대화 이력에 누적 → 다음 요청에 함께 전송
```

**대화 맥락 처리 방식**: 서버는 세션을 저장하지 않는 stateless 구조로 설계한다. 클라이언트(브라우저 메모리/모달 상태)가 최근 대화 이력을 들고 있다가 매 요청마다 함께 보낸다. 이때 각 assistant 턴에는 실제 사용된 citations(sectionId + caseId)를 함께 저장해, 다음 요청의 Extract 단계가 후속 질문("그 근거가 뭔가요?")에서 정확히 어떤 근거를 가리키는지 판별할 수 있게 한다(Extract 스키마의 `refers_to_previous_citations`는 이 값을 그대로 참조한다 — 클라이언트가 갖고 있지 않은 별도의 Case ID 체계를 요구하지 않는다). 로그인이 없는 익명 방문자 대상 챗 위젯이므로 서버 세션 저장소를 두는 것은 불필요한 복잡도로 판단한다. 다만 새로고침이나 모달을 닫으면 대화 이력이 사라지므로, FE에서 이 사실을 사용자에게 안내해야 한다(5.3 참고).

## 3. Neo4j 스키마 확정

"00_GraphRAG 스키마 설계.md"의 "스키마 수정본"(Case 중심 구조)을 채택한다. 실제 포트폴리오 원문(TeenyFinny / Home Server / DailyBand, 총 3개 Project, 프로젝트별 Overview 1개 + 서술형 H2 Section 4~6개)과 대조해 다음을 확정한다.

### 3.1 관계 방향 확정 (원문 근거 기반)

- `BUILDS_ON`은 **시간상 이후 프로젝트 → 이전 프로젝트** 방향으로 정의한다 (`(이후 프로젝트)-[:BUILDS_ON]->(이전 프로젝트)`).
  - `(Home Server)-[:BUILDS_ON]->(TeenyFinny)` — 원문: "TeenyFinny에서 남은 Public 운영 문제를 다시 다루기 위해 미니 PC에 Linux 서버를 구축"
  - `(DailyBand)-[:BUILDS_ON]->(Home Server)` — 원문: "개인 운영 환경이 DailyBand의 CI/CD·Quality Gate로 연결"
  - `BUILDS_ON` 관계는 `evidenceSectionIds` property(이 관계를 뒷받침하는 Section id 목록)를 갖는다. FastAPI가 Retrieve에서 `BUILDS_ON`을 찾았을 때 근거 Section을 Neo4j 안에서 바로 조회할 수 있도록 하기 위함이다(4장 3번, 2장 [Retrieve] 3) 참고) — `data/`의 `buildsOnEvidenceSectionIds`가 원본이고, 이 property는 재적재 때마다 그로부터 채워지는 복제본이다.
- `INFLUENCED`는 `BUILDS_ON`과 **반대 방향**이다: `(이전 Case)-[:INFLUENCED]->(이후 Case)`. "이전 경험이 이후 판단에 영향을 줬다"고 자연스럽게 읽히도록 화살표의 출발점을 원인(이전 경험), 도착점을 결과(이후 판단)로 둔다. `BUILDS_ON`은 "인프라/프로젝트가 이전 것 위에 구축됐다"는 의미이므로 이후→이전이 맞지만, `INFLUENCED`를 같은 방향으로 맞출 이유는 없다 — 두 관계는 의미가 다르므로 방향도 독립적으로 정한다.
  - 이 문서(설계 단계)에서는 **방향만** 확정한다. 실제로 어떤 Case와 Case를 연결할지는 3.2/4장에서 Case 분리가 끝난 뒤에 결정할 사항이며, 이 시점에는 아직 어느 Section에서 몇 개의 Case가 나올지 정해지지 않았다. 아래는 원문에서 영향 관계가 드러나는 **Section 수준의 후보**일 뿐, 확정된 Case 연결이 아니다:
    - TeenyFinny의 "운영의 아쉬움을 다음 환경에서 다시 설계했습니다" Section ↔ Home Server의 "공개 필요 여부에 따라 접근 경로를 나눴습니다" Section — 원문상 전자가 후자의 배경이 됨 (전자가 실제로 0개의 Case로 판단될 수도 있다)
    - Home Server의 "개인 서버를 팀의 품질 검증 환경으로 연결했습니다" Section ↔ DailyBand의 "AI가 만든 코드도 같은 검증 흐름을 통과시켰습니다" Section — 원문상 전자가 후자의 배경이 됨
  - 각 Section에서 실제 Case가 분리되고 나면, "이전 Case를 실제로 언급/전제하는 문장이 원문에 있는가"를 기준으로만 `INFLUENCED`를 연결하고, 임의 추론으로 연결하지 않는다(기획서 공통 주의사항).

### 3.2 Section ↔ 실제 페이지 매핑, 그리고 Case와의 관계

- 각 Project Detail 페이지의 H2 블록이 하나의 **Section**이 된다. `path`는 `/projects/{slug}`, `anchor`는 `#` 없는 slug 문자열로 저장한다 (예: `처음-맡은-pl에서-팀이-일할-방식을-먼저-정했습니다`). `title`은 그 H2 헤딩 문구 그대로다(예: "처음 맡은 PL에서 팀이 일할 방식을 먼저 정했습니다") — anchor가 이 title로부터 기계적으로 파생된 slug라, 같은 원본을 두 번 관리하지 않는다. Section은 인용(citation)과 임베딩의 기본 단위다.
- H2 Section과 별개로, 각 Project Detail 페이지 **상단의 개요 블록**(프로젝트 소개 문장 + 기간·팀·담당·기술 스택·결과 + 저장소 공개 여부 안내 등, 실제 화면에 표시되는 pre-H2 영역 전체)을 `anchor: "overview"`인 Section으로 등록한다. 다만 이 Section의 `body`를 사람이 따로 작성하지는 않는다 — `data/projects/{slug}`의 **표시용 원본 필드**(화면에 그대로 보이는 원문 텍스트로 채움. 4장 3번 참고)로부터 적재 시점에 조합해 자동 생성한다. `(Project)-[:USES]->(Technology)` 관계를 만들 때 이 필드를 alias→canonical 정규화(4장 4번 참고)하지만, **정규화된 이름은 관계 생성에만 쓰고 Overview.body 생성에는 다시 사용하지 않는다** — canonical 이름이 화면 원문과 달라질 수 있기 때문이다(예: 원문 "Postgres" vs canonical "PostgreSQL"). 표시용 원본과 관계용 정규화 이름은 같은 `technologies` 필드에서 나오되 정규화는 적재 시점에만 일어나므로, `data/`에 두 벌로 저장해 서로 어긋날 여지 자체가 없다(4장 3번 참고). 기간·팀 구성·담당·기술 스택·결과라는 같은 사실을 Project 메타데이터와 Section 본문 두 곳에 각각 적으면 하나를 고쳐도 다른 하나가 낡은 채로 남을 수 있으므로, 사실의 원본은 `data/projects/{slug}`의 Project 메타데이터 한 곳에만 둔다. 이 Section이 없으면 "DailyBand는 몇 명이서 했나요?" 같은 질문에 답할 근거 Section 자체가 존재하지 않는다. (Home 페이지의 프로젝트 카드는 여전히 Graph에 넣지 않는다 — 그건 검색에도 인용에도 쓰이지 않는 별개의 요약 UI이고, 이 Overview Section은 Detail 페이지에서 실제로 인용 가능해야 하는 근거다.)
  - Overview Section의 `title`은 H2 헤딩이 없으므로 프로젝트 이름을 그대로 쓴다(예: "DailyBand").
  - **Overview는 `searchable=false`로 두어 임베딩을 생성하지 않는다**(3.3 참고). Overview는 벡터 검색 대상에서 완전히 제외되고, [Retrieve]의 `wants_project_overview` 경로(0번)와 Project 단위 그래프 매칭 경로(1번, `Project-USES-Technology`)처럼 명시적인 경로로만 후보에 포함된다 — 벡터 검색으로 우연히 걸려 관련 없는 질문의 Top-K 자리를 차지하는 상황을 원천적으로 막기 위함이다.
- Home의 **지원자 소개 원문**(`data/profile`, 예: "팀이 함께 쓸 기준을 만드는 백엔드 개발자...")도 `(Portfolio)-[:HAS_SECTION]->(Section)`으로 등록한다. `path="/"`, `anchor="profile"`, `title="프로필"`(H2 헤딩이 없는 것은 Overview와 동일한 이유), `searchable=true`(실제 임베딩 대상). "이 지원자는 어떤 개발자인가요?", "가치관은?" 같은 질문에 프로젝트 Case를 거쳐 AI가 종합하지 않고도 직접적인 근거 원문이 있어야 하기 때문이다 — 원문에 없는 추론을 최소화한다는 원칙과도 맞는다. Home의 **프로젝트 카드**는 여전히 Graph에 넣지 않는다(위 Overview 항목과 동일한 이유) — 이 Profile Section은 카드가 아니라 지원자 소개 문단만을 가리킨다.
- **anchor 렌더링 규칙**: DB/데이터에는 `#`을 포함하지 않는 slug만 저장한다. 렌더링 시 `<section id={section.anchor}>`로 DOM에 id를 부여하고, 인용 링크는 클라이언트에서 `${path}#${anchor}` 형태로 조합한다.
- **ID 안정성**: `Project`/`Section`/`Case`의 id는 제목·본문 텍스트와 독립적인 안정적 식별자로 관리하며, 표시 텍스트를 수정해도 id는 바뀌지 않는다. `sectionIds`, `influencedByCaseIds`, `buildsOnEvidenceSectionIds`, `citations`의 `sectionId`/`caseId`(2장 참고)처럼 id를 참조하는 곳이 이미 많아, id가 텍스트에서 파생되면 텍스트 수정만으로 참조가 연쇄적으로 깨질 수 있다. 생성 방식(UUID vs 수동 slug 등)은 02에서 정한다.
- **Case는 Section과 별개 개념이며, 원래 스키마 그대로 `(Case)-[:DESCRIBED_IN]->(Section)`을 유지한다.** 하나의 Section 안에 Case가 0개, 1개, 또는 여러 개 존재할 수 있으며, "H2 하나 = Case 하나"를 스키마 제약으로 고정하지 않는다.
  - 실제 원문을 보면 대부분의 Section이 문제·판단·행동 중 하나 이상의 흐름을 담은 응집된 서술로 쓰여 있어(00_기획.md 기준 "문제, 판단 또는 행동 흐름으로 설명할 수 있는 구체적인 경험" — 세 요소가 모두 있어야 하는 것은 아니다) 결과적으로 1 Section : 1 Case인 경우가 많아 보이지만, 이는 현재 원문이 그렇게 쓰여 있다는 관찰일 뿐이다. 몇 개의 Case가 있는지는 스키마 설계 시점이 아니라, 4장의 데이터 적재 파이프라인에서 사람이 각 Section의 원문을 검토하며 개별적으로 판단한다.
  - Case가 없는 Section(예: 배경 설명, 결과 요약만 담긴 문단)도 존재할 수 있다. 이 경우 그래프 매칭(Competency/Technology 경유)으로는 검색되지 않고, 벡터 검색으로만 후보가 되며, 근거로 쓰일 때는 Case 필드 없이 Section 본문만 제공한다(2장 [Retrieve] 참고).

### 3.3 임베딩

- 대상: `searchable=true`인 Section의 `body`. Overview Section은 `searchable=false`로 두어 임베딩 대상에서 제외한다(3.2 참고) — `wants_project_overview` 또는 Project 단위 그래프 매칭 같은 명시적 경로로만 검색되므로 벡터 검색에 노출될 필요가 없다. Home Profile Section은 `searchable=true`라 임베딩 대상에 포함된다.
- 모델/제공자: 미정이다. 벡터 검색을 하려면 Section.body에 대한 임베딩이 필요하다는 것만 확정됐을 뿐, OpenAI를 포함해 어떤 모델·API로 임베딩을 생성할지는 정해지지 않았다. "OpenAI API 사용 확정"은 판별(Gate 1/2)·의도 추출(Extract)·답변 생성(Generate) 단계에 한정되며, 임베딩까지 자동으로 포함되는 것은 아니다 — 구현 단계에서 별도로 결정 필요(7장 미결 사항 참고).
- 저장/검색: Neo4j 5.x 벡터 인덱스(`CREATE VECTOR INDEX`)를 사용해 별도 벡터 DB 없이 그래프와 함께 관리한다. 그래프 순회(Cypher)와 벡터 유사도 검색을 같은 데이터베이스 내에서 수행할 수 있어 Graph RAG 파이프라인의 [Retrieve] 단계 구현이 단순해진다.

### 3.4 Competency 목록 재검증

기존 문서의 Competency 목록(협업 / 기술적 판단 / 문제 해결 / 운영 / DevOps / AI 활용 / 학습 및 성장)은 실제 원문의 서술(예: PL로서 팀 기준 수립, WebSocket/Polling 판단, Failover 검증, 접근 경계 재설계, Reconciler를 통한 실패 복구, Quality Gate를 통한 AI 결과 검증, 처음 다루는 C/C++ 영역 학습)과 대조했을 때 모두 실제 사례로 뒷받침된다. 임의 추가 없이 그대로 유지한다.

## 4. Neo4j 데이터 적재 파이프라인 (설계 범위)

> 실제 스크립트 작성/실행 순서는 02_구현계획.md에서 다룬다. 여기서는 파이프라인의 구조만 정의한다.

**원칙**: Neo4j 전체를 `data/`로부터 언제든 다시 만들 수 있는 **재생성 가능한 projection**으로 취급한다. Neo4j를 스크립트 밖에서 직접 편집하지 않는다 — 무언가를 고치고 싶으면 항상 `data/`를 고친 뒤 재적재 스크립트를 실행한다. 이 원칙이 있어야 3장에서 확정한 관계(DEMONSTRATES/USES/CONSIDERED/BUILDS_ON/INFLUENCED)를 포함한 그래프 전체가 실제로 만들어지고, 원본이 바뀌었을 때 무엇을 다시 반영해야 하는지도 기계적으로 정해진다.

1. `data/profile`(Home 소개), `data/projects/{slug}`(Section 원문 + Project 메타데이터), `data/rag/cases/{slug}`(Case + 관계 원본)를 Neo4j 적재의 유일한 입력으로 삼는다(별도 Markdown 파싱 없음).
2. Section 단위로 사람이 원문을 검토해, 문제·판단·행동 중 하나 이상의 흐름으로 설명 가능한 구체적 경험(00_기획.md 기준 — 세 요소가 모두 있어야 하는 것은 아니다)이 몇 개 있는지 판단하고(0개/1개/여러 개), 있는 만큼 Case를 분리해 `data/rag/cases/{slug}`에 다음을 원문 범위 내에서만 채운다:
   - `sectionIds: string[]` — 이 Case가 실제로 서술된 Section id (최소 1개. 한 Case가 여러 Section에 걸쳐 서술되는 경우도 배열로 표현) → `DESCRIBED_IN`. 00_기획.md의 "모든 Case는 최소 하나 이상의 Section과 DESCRIBED_IN 관계를 가져야 한다"는 제약을 이 필드가 직접 보장한다.
   - `title: string` — Case를 식별하는 짧은 제목(사람이 지음). Section.title과 달리 원문 H2 제목이 아니라 이 Case 하나의 흐름을 가리키는 제목이다 — 한 Section에 Case가 여러 개면 각기 다른 title을 갖는다. citations의 `quotedTitle`(2장 참고)이 caseId가 있을 때 이 값을 사용한다.
   - `summary: string` — Case 흐름을 한 문장으로 요약. Section.body(최종 근거 원문)를 대체하지 않으며, Generate가 근거로 삼는 것은 여전히 Section.body다(2장 [Generate] 참고) — summary는 검색 결과 미리보기·관측성 로그 등 사람이 훑어볼 때 쓰는 보조 정보다.
   - `order: number` — 같은 Section 안에 여러 Case가 있을 때의 노출 순서.
   - `problem` / `judgment` / `action` / `result` / `learning`
   - `competencies: string[]` — 3.4에서 정의한 7개 Competency 중에서만 선택(새 Competency 임의 생성 금지) → `DEMONSTRATES`
   - `usedTechnologies: string[]` — 이 Case에서 지원자 본인의 행동·판단·구현으로 원문에서 확인되는 기술만 담는다(→ `USES`). 팀·프로젝트 차원에서 사용됐지만 이 Case의 서술에서 본인의 직접 기여로 확인되지 않는 기술은 여기 넣지 않고 Project 전체 스택(3번의 `technologies`)으로만 표현한다 — `Case-USES`와 `Project-USES`의 의미를 다르게 유지해야 개인 기여와 팀 결과 사이의 구분이 Graph에서도 무너지지 않는다.
   - `consideredTechnologies: string[]` — 검토했지만 채택하지 않은 기술. 원문에서 "대신", "vs", "고려했지만" 같은 비교가 명시적으로 확인될 때만 채운다 → `CONSIDERED`
   - `influencedByCaseIds: string[]` — 이 Case가 실제로 언급/전제하는 이전 Case (원문 근거가 있을 때만, 3.1 참고). 적재 시 `previousCaseId ∈ currentCase.influencedByCaseIds`이면 `(previousCase)-[:INFLUENCED]->(currentCase)`로 생성한다 — 3.1에서 확정한 "이전 Case → 이후 Case" 방향과 정확히 일치시키기 위해 방향을 여기서 다시 명시한다.

   Case와 관계 원본은 Section 원문으로부터 사람이 파생시키는 데이터이므로, 적재를 실행할 때마다 AI가 다시 추출하게 두지 않고 검증된 결과를 코드 저장소에 고정한다 — 같은 원문인데 적재할 때마다 다른 Case·관계가 나오는 것을 막기 위함이다.
3. `data/projects/{slug}`의 Project 메타데이터는 화면 표시와 그래프 매칭 양쪽에 쓰이는 **표시용 원본 필드**를 하나만 둔다 — 프로젝트 소개 문장, 기간, 팀 구성, 담당, `technologies: string[]`(화면에 보이는 그대로의 기술 스택 표기, 예: `["Postgres", "Redis", "MinIO"]`), 결과, 저장소 공개 여부 안내 등. 이 필드들만으로 Overview Section의 `body`를 조합해 생성한다(3.2 참고). `(Project)-[:USES]->(Technology)` 관계는 이 **같은** `technologies` 필드를 적재 시점에 alias→canonical 정규화(4번 참고)해서 만든다 — 정규화된 이름은 그래프 노드/관계에만 쓰이고 `data/`에 별도로 저장하지 않는다. 표시용 원본과 관계용 정규화 이름을 서로 다른 필드 두 벌로 관리하지 않는 이유는, 두 벌을 두면 한쪽만 고쳤을 때 화면과 그래프가 서로 다른 기술 스택을 보여주는 drift가 다시 생기기 때문이다. (Case별 `usedTechnologies`는 이 프로젝트 전체 스택과 의미가 다른 별개 필드다 — 2번 참고.)

   Project 간 성장 관계는 두 필드로 표현한다: `buildsOnProjectSlug: string | null`(→ `BUILDS_ON`, 원문에서 확인되는 경우만, 3.1 참고)와 `buildsOnEvidenceSectionIds: string[]`(이 `BUILDS_ON` 관계를 실제로 뒷받침하는 Section id — 보통 두 프로젝트 중 한쪽의 기존 H2 Section이다. 예: Home Server의 "개인 서버를 팀의 품질 검증 환경으로 연결했습니다" Section이 `(DailyBand)-[:BUILDS_ON]->(HomeServer)`의 근거다). **재적재 스크립트는 `buildsOnEvidenceSectionIds`를 `BUILDS_ON` 관계 자체의 property(예: `evidenceSectionIds`)로 저장한다** — FastAPI는 Neo4j에서 `BUILDS_ON`을 매칭하는 시점에 이 property를 곧바로 읽을 수 있고, 런타임에 `data/` 파일을 별도로 열 필요가 없다. `data/`의 `buildsOnEvidenceSectionIds`는 이 property의 원본(사람이 수정하는 곳)이고, Neo4j의 property는 재적재 때마다 그로부터 다시 채워지는 복제본이다(4장 8번 동기화 규칙에 포함).
4. **기술명 정규화**: 서로 다른 표기(예: "Postgres", "PostgreSQL", "postgres")가 같은 `Technology` 노드로 합쳐지도록, 적재 스크립트가 alias→canonical 매핑 테이블(`data/rag/technology-aliases`, 세부 포맷은 02에서 정함)을 거쳐 `Technology` 노드를 생성·매칭한다. [Retrieve]의 `technologies` 매칭도 이 테이블을 동일하게 거친다(2장 참고).
5. AI를 활용해 초안 추출(Case 분리, 관계 원본 채움)을 보조하더라도, 기획서 제약(정의된 Competency만 사용, 실제 사용/검토를 USES/CONSIDERED로 구분, 관계는 원문 근거가 있을 때만 생성, Case 개수를 임의로 1개로 맞추지 않음)을 검증하는 사람의 리뷰 단계를 거친 뒤에만 파일에 반영한다.
6. 재적재 스크립트는 이 파일들로부터 다음 노드·관계를 전부 (재)생성한다: `Portfolio`, `Project`, `Section`(H2 Section, 자동 생성되는 Overview Section, Home Profile Section 포함), `Case`, `Competency`(사전 정의 7개 고정), `Technology`(정규화됨) 및 `HAS_PROJECT`, `HAS_SECTION`(Portfolio→Profile Section, Project→Section), `HAS_CASE`, `DESCRIBED_IN`, `DEMONSTRATES`, `USES`(Case·Project 모두), `CONSIDERED`, `BUILDS_ON`(`evidenceSectionIds` property 포함, 3번 참고), `INFLUENCED`.
7. 재적재는 **멱등**하게 만든다 — 스크립트를 다시 실행하면 `data/`에서 삭제된 Case·Section·관계는 Neo4j에서도 함께 제거되어 좀비 데이터가 남지 않는다(전체 삭제 후 재생성 또는 diff 기반 upsert — 구체 방식은 02에서 정한다).
8. 동기화 규칙 (원칙: `data/` 변경 → Neo4j 재적재는 항상 함께 이루어진다):
   - `data/projects/{slug}`의 H2 Section `body`가 수정되면 → Neo4j의 해당 Section을 갱신하고 **embedding을 재생성**한다(3.3). 그로부터 파생된 `data/rag/cases/`의 관련 Case와 관계(DEMONSTRATES/USES/CONSIDERED/INFLUENCED)는 재검토 대상으로 표시해 사람이 다시 확인한다.
   - `data/projects/{slug}`의 Project 메타데이터(`period`/`teamSize`/`roles`/`result`/`technologies`)가 수정되면 → 그로부터 자동 생성되는 Overview Section의 `body`를 다시 생성해 재적재한다. Overview는 임베딩이 없으므로(3.2/3.3) 이 경우 재임베딩은 필요 없다. `buildsOnEvidenceSectionIds`가 바뀌면 `BUILDS_ON` 관계의 `evidenceSectionIds` property도 함께 재적재한다(3번 참고).
   - `data/rag/cases/`의 Case나 관계 원본이 직접 수정되면 → 해당 Case의 노드와 관계만 다시 적재한다(Section 재적재는 불필요).
   - `data/profile`의 소개 원문이 수정되면 → Neo4j의 Home Profile Section을 갱신하고 **embedding을 재생성**한다(3.3) — `searchable=true`인 일반 H2 Section과 동일하게 취급한다.

## 5. FE 아키텍처 (Next.js)

### 5.1 라우팅

| 경로 | 렌더링 방식 | 설명 |
|---|---|---|
| `/` | SSG | Home — 지원자 소개 + 프로젝트 카드 목록 |
| `/projects/[slug]` | SSG (`generateStaticParams`) | 프로젝트 상세 (TeenyFinny / home-server / dailyband) |
| `/api/chat` | Route Handler (Dynamic) | BFF — FastAPI AI 서버로 프록시 |

정적 콘텐츠의 원본은 Markdown이 아니라 역할별로 분리된 구조화 데이터 파일로 관리한다(세부 포맷은 구현 계획에서 확정):

```
data/
  profile                  # Home의 지원자 소개, 연락처 등 — 어떤 프로젝트에도 속하지 않는 정보
  projects/
    {slug}                  # 프로젝트별 메타데이터(period/teamSize/roles/result/technologies 등) + Section 배열
  rag/
    cases/{slug}            # Section에서 파생된 Case + 관계 원본 (4장 참고)
    technology-aliases      # 기술명 alias → canonical 매핑 (4장 참고)
```

(파일 확장자·직렬화 형식은 아직 정하지 않았다 — 7장 참고. 표시된 이름은 논리적 파일 단위일 뿐이다.)

Home 페이지의 소개 영역은 `data/profile`을, 프로젝트 카드는 `data/projects/{slug}`의 메타데이터를 그대로 가져와 렌더링하며 별도로 이중 관리하지 않는다. 빌드 타임에 이 데이터를 읽어 SSG 페이지를 생성하며 런타임에 DB를 조회하지 않는다.

FE와 Neo4j가 쓰는 **Section 원문**(body/path/anchor)은 `data/projects/`(H2 Section)와 `data/profile`(Home Profile Section, 3.2 참고)을 공통 원본으로 정의한다. 다만 Neo4j는 이 원본을 실시간으로 참조하는 것이 아니라 **적재된 복제본**이다 — `data/`를 수정해도 재적재 스크립트를 실행하기 전까지는 Neo4j가 예전 내용 그대로 남아 있다(4장). **Case**와 그 관계 원본(competencies/usedTechnologies/consideredTechnologies/influencedByCaseIds)은 한 단계 더 파생된 데이터로, 사람이 Section 원문을 검토해 별도 파일(`data/rag/cases/`)에 만든다. 따라서 Section 원문을 수정하면 ① Neo4j의 해당 Section을 재적재하고(embedding 재생성 포함) ② 그로부터 파생된 Case와 관계를 재검토해야 한다 — 이 단계를 거치지 않으면 FE(최신 원문)와 Neo4j(과거 Section·Case·관계)가 어긋난 채로 남는다(4장 8번 동기화 규칙 참고).

Neo4j는 오직 AI 서버의 RAG 조회용으로만 쓰이고, 페이지 렌더링 경로와는 분리된다 — 정적 페이지와 동적 API 라우팅이 공존하되 서로 다른 저장소(파일 vs 그래프 DB)를 갖는 구조다.

### 5.2 컴포넌트 계층 및 Server/Client 경계

```
components/
  ui/            # 버튼, 카드 등 범용 프리미티브
  layouts/       # Header, Footer, PageLayout
  domains/
    project/     # ProjectCard, ProjectDetailSection 등 프로젝트 도메인 전용
    chat/        # FloatingChatButton, ChatModal, ChatInput, MessageList, CitationLink 등
```

00_기획.md의 "Next.js의 클라이언트/서버 컴포넌트 원칙을 준수" 요구에 따라 기본값과 경계를 명시한다:

- **Server Component (기본)**: Home, Project Detail, `ProjectCard`, `ProjectDetailSection` 등 정적 콘텐츠를 렌더링하는 컴포넌트는 별도 지시자 없이 Server Component로 유지한다 — 상호작용이 없는 한 클라이언트로 내려보낼 이유가 없다.
- **Client Component (`"use client"`)**: 브라우저 상태·이벤트·애니메이션이 필요한 컴포넌트만 명시적으로 분리한다 — `ThemeToggle`(다크모드 토글), `FloatingChatButton`, `ChatModal`, `ChatInput`, `MessageList`(스크롤/렌더 상태), Framer Motion을 사용하는 인터랙션 경계.
- Server/Client 경계를 나누는 것만으로 초기 번들에서 채팅 코드가 자동으로 빠지지는 않는다 — `FloatingChatButton`이 `ChatModal`을 정적으로 import하면 모달 코드도 초기 클라이언트 번들에 포함될 수 있다. 플로팅 버튼을 클릭하기 전까지 `ChatModal` 로직을 미로딩하려면 `next/dynamic`으로 `ChatModal`을 동적 import한다.

### 5.3 채팅(RAG) UI

- `FloatingChatButton`(전역 고정, AI를 나타내는 아이콘 사용 — 00_기획.md 요구사항) 클릭 → `ChatModal` 오픈 (Framer Motion으로 scale/opacity 트랜지션, 과하지 않게 200ms 내외).
- `ChatModal`에는 `ChatInput`(입력창)과 `MessageList`(채팅 화면)가 함께 나타난다 — 00_기획.md의 "플로팅 모달에는 입력창과 채팅 화면이 나타납니다" 요구사항.
- `ChatModal` 내부 상태(대화 이력, 로딩 상태)는 `ChatModal` 컴포넌트 로컬의 `useState`로 관리한다. "모달을 닫으면 대화 이력이 사라진다"는 정책(아래 항목)과 구현이 어긋나지 않도록, 모달 unmount 이후에도 값이 남는 상위 Context/전역 상태관리 라이브러리는 쓰지 않는다 — 페이지 간 공유가 필요 없는 위젯 상태이기도 하다.
- 답변의 `citations`는 클릭 가능한 링크로 렌더링하며, 같은 탭 내 라우팅(Next.js `Link`)으로 `citation.path + '#' + citation.anchor`로 이동한다 — Home Profile Section(`projectSlug=null`)이면 `/#profile`로, 프로젝트 Section이면 `/projects/{slug}#{anchor}`로 이동한다(3.2 참고).
- 대화 이력은 서버에 저장되지 않고 클라이언트 메모리에만 있으므로(2장 참고), 모달을 닫거나 페이지를 새로고침하면 대화가 사라진다. 이를 사용자에게 안내해야 한다 — 예: 모달 최초 진입 시 안내 문구, 또는 모달을 닫을 때 확인 문구. 아무 안내 없이 대화가 조용히 사라지게 두지 않는다.

### 5.4 API 계층 (axios 중앙화)

```
lib/api/
  client.ts   # axios 인스턴스 (baseURL: '/api', 공통 인터셉터)
  chat.ts     # postChatMessage(request: ChatRequest): Promise<ChatResponse>
```

```
type ChatRequest = {
  chatSessionId: string;   // ChatModal이 열릴 때 생성(8.2 참고), 매 요청에 포함
  messages: ChatMessage[]; // 클라이언트가 들고 있는 대화 이력(사용된 citations 포함, 2장 참고)
}
```

`requestId`는 BFF(Next.js 서버)가 요청을 받은 시점에 생성하므로(8.1 참고) 클라이언트 요청 바디에는 포함하지 않는다. 모든 API 호출은 이 계층을 통해서만 이루어지며, 컴포넌트가 axios를 직접 호출하지 않는다.

### 5.5 비주얼 톤 (필수 원칙)

백엔드 개발자가 만든 듯한 **무채색·컴팩트** 톤을 유지한다. 화려한 그라디언트, 큰 장식 요소, 넓은 컬러 팔레트를 지양한다. 5.3의 Framer Motion(Motion) 사용도 이 톤을 해치지 않는 범위(전환/피드백 목적의 절제된 애니메이션)로 제한하며, 기술 요구(Motion 도입)와 별개로 이 시각적 원칙이 우선한다. 구현 단계에서 색상/타이포 가이드를 확정할 때 이 원칙을 기준으로 삼는다.

### 5.6 다크모드 / 반응형

- 다크모드: `next-themes` 등으로 시스템 설정 감지 + 수동 토글, CSS 변수 기반 테마 전환. 5.5의 무채색 톤은 라이트/다크 양쪽에서 동일하게 유지한다.
- 반응형: 데스크탑/태블릿/모바일 breakpoint 대응 (Tailwind 등 유틸리티 기반 가정, 최종 스타일링 도구는 구현 계획에서 확정).

## 6. 기획서 제약 조건 ↔ 설계 대응표

| 기획서 요구 | 설계 반영 |
|---|---|
| 포트폴리오 무관 질문 차단 | Gate 1 structured output |
| 사이트 자체 질문 분리 | Gate 2 structured output |
| 의도/개념 추출 | Extract 단계 structured output |
| 검색 결과에 이동 링크 + 본문 포함 | citations 스키마에 path/anchor 필수 필드 |
| 대화 맥락으로 후속 질문 처리 | is_followup + refers_to_previous_citations(클라이언트가 보관한 이전 turn citations) + 클라이언트 이력 재전송 |
| 원문 밖 추론 금지 | Generate 단계 system prompt |

## 7. 확인이 필요한 미결 사항

- **Next.js 배포처**: 아직 결정되지 않았다. 1장에서 외부 배포(Cloudflare Tunnel 경유)와 홈서버 내부 배포(내부망 직접 호출) 두 경로를 모두 조건부로 문서화해뒀지만, 실제로는 둘 중 하나로 확정해야 하며 그에 따라 인증 계층(공유 시크릿 헤더) 필요 여부가 달라진다. 구현 계획 수립 전에 결정이 필요하다.
- **스타일링 도구**: Tailwind CSS를 가정했으나 기획서에 명시되지 않았다. 확정 필요.
- **임베딩 모델/제공자**: 완전히 미정이다. OpenAI API 사용 확정은 판별/추출/답변 생성에 한정되며, 벡터 검색용 임베딩에 어떤 모델·제공자를 쓸지는 별도로 결정해야 한다(3.3 참고).
- **Cypher 검색 쿼리의 스코어링 가중치**(그래프 매칭 vs 벡터 유사도 비중)는 실제 데이터로 튜닝이 필요한 영역으로, 설계 문서에서는 구조만 정의하고 구현 단계에서 확정한다.
- **`data/profile`, `data/projects/`(Section 원문), `data/rag/cases/`(파생 Case), `data/rag/technology-aliases`(기술명 정규화 테이블)의 구체적 파일 포맷**은 미정이다. 특히 파일 확장자/직렬화 형식(TS 모듈 vs JSON 등)은 이 문서에서 의도적으로 정하지 않았다 — 이 데이터를 Next.js(TypeScript)뿐 아니라 Neo4j 적재 스크립트(FastAPI, Python)도 읽어야 하므로, TS 모듈로 작성한다면 Python 쪽에서 어떻게 소비할지(빌드 시 JSON으로 export, 또는 JSON/YAML을 원본으로 삼고 FE에서 타입만 얹는 방식 등)를 함께 정해야 한다. 파일 분리 단위, Overview Section 자동 생성 로직의 구현 위치도 구현 계획에서 정한다. (Section-Case 참조 방식은 `sectionIds`/`influencedByCaseIds`로 이미 확정했다 — 4장 참고.)
- **대화 맥락으로 사용할 "최근 N턴"의 N 값**은 아직 정하지 않았다(2장 참고) — 너무 작으면 후속 질문 맥락을 놓치고, 너무 크면 Extract 프롬프트가 길어져 비용·지연시간이 늘어난다. 구현 단계에서 정한다.
- **재적재 스크립트의 동기화 방식**(4장 7번 — 전체 삭제 후 재생성 vs diff 기반 upsert)은 이 설계에서 "멱등해야 한다"는 요구만 확정했고 구체 구현은 02에서 정한다.

## 8. 관측성 / AISecOps (00_기획.md 이후 추가 — 사용자 요청으로 도입)

00_기획.md에는 없던 계층이지만, 시스템 개선(어느 단계에서 응답 품질이 떨어지는지 파악)과 부정사용 모니터링(prompt injection·jailbreak 시도 등)을 위해 사용자 요청으로 추가한다. 2장의 파이프라인이 이미 Gate 1 → Gate 2 → Extract → Retrieve → Generate로 명확히 나뉘어 있어 각 단계를 독립된 span으로 계측하기 좋은 구조다.

### 8.1 아키텍처

```
Browser
    │
    ▼
Next.js BFF  ── requestId 생성 (X-Request-ID), 이후 모든 구간에 전달
    │
    ▼
(1장의 두 배포 경로 중 하나로 FastAPI에 도달 — 외부 배포 경로라면 Nginx가 여기서 rate limit을
 판단하고 requestId와 함께 로그를 남긴다. 여기서 차단된 요청은 FastAPI에 도달하지 않는다.)
    ▼
[ FastAPI ]  ── 요청 1개당 Trace 1개 시작, requestId를 trace attribute로 기록
    │
    ├─ security.input   span  (8.3 참고, 규칙 기반)
    ├─ gate.portfolio    span  (Gate 1)
    ├─ gate.site         span  (Gate 2)
    ├─ extract           span
    ├─ retrieve.graph    span
    ├─ retrieve.vector   span
    ├─ retrieve.rank     span  (8.2 참고 — 최종 스코어링/Top-K 선정 결과)
    ├─ generate          span
    └─ security.output  span  (8.3 참고, 규칙 기반)
    │
    ▼ OTLP export
[ Observability Backend ]  (candidate: Phoenix — 확정 아님, 8.6 참고)
```

FastAPI가 이미 모든 파이프라인 단계를 거치는 유일한 지점이므로(1장), 계측 코드도 FastAPI 안에만 추가하면 된다 — Next.js나 Neo4j 쪽 구조 변경은 필요 없다. 다만 requestId 발급은 BFF(Next.js)에서 이루어져야, Nginx 단계에서 차단된 요청까지 나중에 조회할 수 있다(8.4 참고). 외부에서 들어온 요청에 이미 `X-Request-ID`가 실려 있어도 이를 신뢰하지 않고 BFF가 항상 새 값을 생성해 덮어쓴다 — 그렇지 않으면 임의의 값을 보내 서로 다른 요청의 로그를 같은 요청처럼 보이게 만들 수 있다.

### 8.2 Trace/Span에 기록할 것

| Span | 기록 항목 |
|---|---|
| request (root) | traceId, requestId(BFF에서 생성해 전달받음, 8.4 참고), chatSessionId(클라이언트가 대화 이력과 함께 생성해 매 요청에 포함), 총 처리 시간 |
| security.input | risk_score, 차단 여부(초기엔 항상 false), 트리거된 규칙 |
| gate.portfolio | is_portfolio_related, reason |
| gate.site | is_about_site_itself, reason |
| extract | search_intent, competencies, technologies, project_hints, wants_project_overview, wants_alternatives_considered, wants_growth_connection, wants_similar_cases, is_followup |
| retrieve.graph | 매칭된 Case/Section/Project id, 매칭 경로(DEMONSTRATES/USES/CONSIDERED/BUILDS_ON/INFLUENCED 중 어떤 관계로 매칭됐는지) |
| retrieve.vector | 후보 Section id, 유사도 점수 |
| retrieve.rank | 최종 후보 목록 — sectionId별 sources(graph/considered/growth/similar/vector/mandatory 중 어떤 경로로 후보가 됐는지), finalScore, rank, Top-K 선정(selected) 여부. "왜 이 Section이 최종 근거로 선택됐는가"를 사후 분석하기 위함(2장 [Retrieve] 7) 참고) |
| generate | 사용 모델, 토큰 사용량, is_evidence_sufficient, citations 개수 |
| security.output | 시스템 프롬프트·내부 정보 노출 검사 결과 |

`chatSessionId`는 서버 세션이 아니라(2장에서 stateless로 확정) 클라이언트가 생성해 대화 이력과 함께 들고 있는 상관관계 식별자일 뿐이다 — 이 값만으로 사용자를 식별하지 않으며, trace를 같은 대화로 묶는 용도로만 쓴다. `ChatModal`을 새로 열 때마다 새로운 `chatSessionId`를 생성한다 — 5.3의 "모달을 닫으면 대화가 사라진다" 정책과 맞물려, 재오픈 시점부터는 별개의 대화로 취급한다.

사용자 입력/답변 원문을 이 표의 어느 필드에 그대로 저장할지(예: request span에 raw 입력, generate span에 answer 전문)는 아직 결정하지 않았다 — 저장 여부·마스킹·보존 기간을 포함해 8.6에서 미결로 남긴다. `gate.portfolio`/`gate.site`의 `reason`, `extract`의 `search_intent`도 LLM이 사용자 입력을 바탕으로 생성하는 자유 텍스트라 같은 문제가 적용된다 — raw 입력을 저장하지 않기로 하더라도 이런 파생 필드에 사용자가 입력한 이름 등이 다시 나타날 수 있다(8.6 참고).

### 8.3 Input/Output 보안 스캔은 규칙 기반으로 시작한다 — LLM 호출을 추가하지 않는다

2장 기준 사용자 턴 하나에 OpenAI 호출이 이미 최대 4번(Gate 1, Gate 2, Extract, Generate) 들어간다. 보안 판별을 위해 별도 LLM 분류 호출을 추가하면 턴마다 지연시간과 비용이 늘어난다. 따라서:

- **Input scan**: `security.input` span은 8.1 순서상 Gate 1/2보다 먼저 실행되므로, 이 시점에는 규칙 기반(길이 제한, 알려진 jailbreak·프롬프트 탈취 패턴의 키워드·정규식 매칭 등) `risk_score`만 계산해 기록한다 — 아직 실행되지 않은 Gate의 `reason`을 미리 참조할 수는 없다. Gate 1/2의 `reason`은 각자의 span(`gate.portfolio`, `gate.site`)에 그 시점에 별도로 기록되며, 두 신호를 함께 보고 싶다면 같은 trace 안에서 사후에 대조한다(8.2).
- **Output scan**: 시스템 프롬프트나 내부 인프라 정보(FastAPI 엔드포인트, Neo4j 스키마 세부사항 등)가 답변에 그대로 노출됐는지 규칙 기반으로 점검해 기록한다.
- **관측과 차단을 분리한다**: 초기에는 risk_score를 기록만 하고 기존 파이프라인은 그대로 실행한다. 데이터가 쌓인 뒤에만 low(기록)/medium(경고)/high(차단) 임계값을 정한다 — "이 사이트의 system prompt를 어떻게 보호했나요?" 같은 정상 질문을 오탐으로 막는 상황을 피하기 위함이다.
- 구체적 탐지 규칙 집합이나 별도 라이브러리 도입 여부는 미정이며 8.6에 남긴다.
- **이 규칙 기반 스캔은 보안 경계가 아니라 관측을 위한 휴리스틱 신호다.** 정규식·키워드 기반 탐지는 우회하기 쉽고 오탐도 발생한다. 실제 보안은 AI 서버 주소 비공개(공격면 축소), 요청 인증(접근 통제), RAG 근거를 원문 범위로 제한하는 구조적 제약(응답 무결성·환각 억제)과 같은 구조적 통제에 의존하며(1장, 2장, 6장), 이 규칙 기반 스캔은 그 통제를 보완하는 모니터링 수단일 뿐이다 — "정규식 몇 개로 판별했으니 안전하다"는 결론으로 이어지지 않는다.

### 8.4 부정사용 탐지는 탐지 위치를 분리한다

- **요청 폭주·반복 호출 같은 전통적 abuse**: Nginx/BFF 계층의 rate limiting으로 처리한다. 이 요청은 FastAPI에 도달하지 않으므로 **AISecOps trace 자체가 생기지 않는다** — Nginx/BFF 쪽 로그에 8.1의 `requestId`를 함께 남겨 나중에 조회할 수 있게 한다.
- **Prompt injection·jailbreak·system prompt 탈취 시도 같은 AI 특화 abuse**: 요청이 FastAPI까지 도달한 뒤 8.3의 보안 스캔에서 탐지하고 trace에 기록한다.

두 신호는 같은 trace로 묶이지 않는다 — Nginx 단계에서 차단된 요청은 애초에 Trace가 없기 때문이다. 대신 `requestId`를 상관관계 키로 사용해, 필요할 때 "Nginx에서 막힌 요청"과 "FastAPI까지 도달해 Trace로 남은 요청"을 같은 식별자로 연결해 조회한다. 탐지 로직 자체는 계층을 분리해서 구현한다 — 하나의 컴포넌트가 두 종류의 abuse를 모두 판단하게 만들지 않는다.

### 8.5 배포

Phoenix를 선택할 경우, 0장에서 이미 확정한 "직접 운영 홈서버" 인프라 위에 Docker 컨테이너 하나로 추가하고 저장소는 SQLite로 시작한다(공식 문서 기준 single-user/local 배포에 적합) — 트래픽이 늘어 필요해지면 PostgreSQL로 전환한다. 관측성 백엔드는 OTLP 수집을 지원하는 제품을 우선 선택한다 — 직접 지원하지 않는 도구를 고를 경우 OpenTelemetry Collector를 중간 수집 계층으로 둘 수 있다. 어떤 조합이든 FastAPI는 OTLP로 trace를 export하기만 하면 되고 Next.js·Neo4j 쪽 구조 변경은 필요 없다.

### 8.6 확인이 필요한 미결 사항

- **관측성 도구**: Phoenix를 제안했지만 비교 검토를 거쳐 확정한 것은 아니다 — 셀프호스팅 가능 여부, Docker 배포 용이성, OpenTelemetry 기반이라는 점을 근거로 들었을 뿐이다.
- **규칙 기반 스캔의 구체적 규칙 집합**(정규식 목록, 길이 임계값 등)은 미정이며, 데이터가 쌓이기 전까지는 최소한의 규칙으로 시작한다.
- **risk_score의 low/medium/high 임계값과 차단 정책 전환 시점**은 실제 트래픽 데이터를 모은 뒤 결정한다.
- **사용자 입력에서 파생된 자유 텍스트 저장 정책**: 질문·답변 원문뿐 아니라 `gate.portfolio`/`gate.site`의 `reason`, `extract`의 `search_intent`처럼 LLM이 사용자 입력을 바탕으로 생성하는 자유 텍스트 attribute 전체에도 PII·민감정보가 다시 나타날 수 있다 — "원문은 저장하지 않는다"고 정해도 이런 파생 필드에 사용자가 입력한 이름 등이 그대로 남을 수 있다는 뜻이다. 방문자가 익명이라는 것과 이런 텍스트에 PII가 없다는 것은 별개 문제이므로, "익명 위젯이라 가능성이 낮다"는 근거로 판단하지 않는다. 다음이 모두 미결이다: 질문·답변 원문과 reason·search_intent 등 파생 자유 텍스트를 trace에 그대로 저장할지, 저장한다면 마스킹할지, 보존 기간, 접근 권한. 확정된 것은 접근 범위가 홈서버 내부 도구로 한정되어 외부에는 노출되지 않는다는 것뿐이다(1장의 배포 경계 재사용).
- **requestId 발급/전달 방식**: 8.1/8.4에서 방향만 정했다. Next.js에서 어떤 형식으로 생성하는지, Nginx 설정에서 이 값을 어떻게 로그에 남기는지는 구현 단계에서 정한다.
