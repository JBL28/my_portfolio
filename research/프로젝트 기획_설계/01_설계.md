# 프로젝트 설계

> 이 문서는 "00_기획.md"의 요구사항을 실제로 구현 가능한 시스템 구조로 옮긴 설계 문서입니다.
> 작업 순서(일정, 단계 분할)는 다루지 않습니다. 작업 계획은 이 설계가 검증된 뒤 "02_구현계획.md"에서 다룹니다.

## 0. 확정된 전제

| 항목 | 결정 |
|---|---|
| AI 서버 스택 | Python (FastAPI) |
| LLM / Structured Output | OpenAI API |
| AI 서버 · Neo4j 배포 위치 | 직접 운영 홈서버 (Home Server 프로젝트 인프라 재사용) |
| FE | Next.js (App Router) |

## 1. 전체 시스템 아키텍처

```
[ Browser ]
    │  HTTPS (같은 origin)
    ▼
[ Next.js ]  ── 정적 페이지: SSG (Home, /projects/[slug])
    │            동적 라우트: /api/chat (Route Handler, BFF)
    │
    │  서버 사이드에서만 호출 (AI_SERVER_URL은 서버 환경변수, 클라이언트 번들에 노출 안 됨)
    ▼
[ Cloudflare Tunnel → Nginx ]  (Home Server 기존 운영 경계 재사용)
    │
    ▼
[ FastAPI AI 서버 ]  (홈서버, Docker)
    │                 │
    ▼                 ▼
[ Neo4j ]        [ OpenAI API ]
(그래프 + 벡터 인덱스)  (판별 / 추출 / 답변 생성 / 임베딩)
```

**핵심 원칙**: 브라우저는 오직 Next.js(같은 origin)와만 통신한다. AI 서버 주소는 Next.js 서버 프로세스만 알고 있으며, 클라이언트로 절대 전달되지 않는다. 이것이 기획서 "Next.js를 사용하여 AI 서버의 주소를 클라이언트가 알지 못하도록" 요구사항의 구현 방식이다.

Next.js ↔ FastAPI 사이는 인터넷을 경유하는 구간이므로, Cloudflare Tunnel 진입점에서 공유 시크릿 헤더(예: `X-Internal-Token`)로 Next.js 서버발 요청만 허용하고, 그 외 요청은 Nginx/FastAPI 단에서 거부한다.

## 2. Graph RAG 파이프라인 설계

기획서의 요구 흐름(관련성 판별 → 자기참조 판별 → 의도/개념 추출 → 그래프 검색 → 근거 기반 답변)을 아래와 같이 단계화한다. 각 단계는 OpenAI Structured Outputs로 스키마를 강제한다.

```
사용자 입력 + 최근 대화 이력(N턴)
        │
        ▼
[Gate 1] 포트폴리오 관련 질문인가?
   schema: { is_portfolio_related: bool, reason: string }
   └ false → 고정 안내 문구 반환 후 종료
        │ true
        ▼
[Gate 2] 포트폴리오 "웹사이트 자체"(구현/소스코드)에 대한 질문인가?
   schema: { is_about_site_itself: bool, reason: string }
   └ true → GitHub 링크 안내 문구 반환 후 종료
        │ false
        ▼
[Extract] 의도 및 핵심 개념 추출 (대화 맥락 포함)
   schema: {
     search_intent: string,          // 정규화된 검색 의도
     competencies: string[],         // Competency 노드명과 매칭
     technologies: string[],         // Technology 노드명과 매칭
     project_hint: string | null,    // 특정 프로젝트 언급 시
     is_followup: bool,              // "그 근거가 뭔가요?" 같은 후속 질문 여부
     refers_to_previous_case_ids: string[]  // is_followup=true일 때 직전 답변의 근거 Case id
   }
        │
        ▼
[Retrieve] Graph RAG 검색
   1) 그래프 매칭: Competency/Technology/Project 이름으로 Case 탐색
      (Case)-[:DEMONSTRATES]->(Competency), (Case)-[:USES]->(Technology)
   2) 벡터 매칭: search_intent 임베딩 vs Section.embedding (Neo4j vector index) 유사도 검색
   3) is_followup=true면 refers_to_previous_case_ids를 후보 집합에 우선 포함
   4) 그래프 매칭 결과와 벡터 매칭 결과를 합집합으로 구성, 각 Case는 연결된 Section(DESCRIBED_IN)까지 함께 로드
   5) 스코어링 후 Top-K(예: 3~5개) 선정
        │
        ▼
[Generate] 근거 기반 답변 생성
   입력: 선택된 Case/Section의 원문(body, path, anchor, project 정보)
   system prompt 제약:
     - 제공된 원문 범위 밖의 사실을 추론하지 않는다
     - 근거가 부족하면 "부족하다"고 답한다
     - 모든 주장은 최소 1개 이상의 Section 근거를 포함해야 한다
   schema: {
     answer: string,
     is_evidence_sufficient: bool,
     citations: [{ sectionId, projectSlug, path, anchor, quotedTitle }]  // 최소 1개 강제
   }
        │
        ▼
FE 렌더링: 답변 텍스트 + 근거 링크(클릭 시 해당 프로젝트 상세 페이지의 anchor로 이동)
        │
        ▼
클라이언트가 (질문, 답변, 사용된 citations의 sectionId)를 대화 이력에 누적 → 다음 요청에 함께 전송
```

**대화 맥락 처리 방식**: 서버는 세션을 저장하지 않는 stateless 구조로 설계한다. 클라이언트(브라우저 메모리/모달 상태)가 최근 대화 이력을 들고 있다가 매 요청마다 함께 보낸다. 로그인이 없는 익명 방문자 대상 챗 위젯이므로 서버 세션 저장소를 두는 것은 불필요한 복잡도다. 새로고침 시 대화가 초기화되는 것은 허용 가능한 트레이드오프로 본다.

## 3. Neo4j 스키마 확정

"00_GraphRAG 스키마 설계.md"의 "스키마 수정본"(Case 중심 구조)을 채택한다. 실제 포트폴리오 원문(TeenyFinny / Home Server / DailyBand, 총 3개 Project, 각 4~6개 섹션)과 대조해 다음을 확정한다.

### 3.1 관계 방향 확정 (원문 근거 기반)

- `BUILDS_ON`은 **시간상 이후 프로젝트 → 이전 프로젝트** 방향으로 정의한다 (`(이후 프로젝트)-[:BUILDS_ON]->(이전 프로젝트)`).
  - `(Home Server)-[:BUILDS_ON]->(TeenyFinny)` — 원문: "TeenyFinny에서 남은 Public 운영 문제를 다시 다루기 위해 미니 PC에 Linux 서버를 구축"
  - `(DailyBand)-[:BUILDS_ON]->(Home Server)` — 원문: "개인 운영 환경이 DailyBand의 CI/CD·Quality Gate로 연결"
- `INFLUENCED`도 동일하게 **이후 Case → 이전 Case** 방향.
  - TeenyFinny의 "운영의 아쉬움을 다음 환경에서 다시 설계했습니다" Case ← Home Server의 "공개 필요 여부에 따라 접근 경로를 나눴습니다" Case가 `INFLUENCED` (해당 이전 Case를 참조)
  - Home Server의 "개인 서버를 팀의 품질 검증 환경으로 연결했습니다" Case ← DailyBand의 "AI가 만든 코드도 같은 검증 흐름을 통과시켰습니다" Case가 `INFLUENCED`

  → 데이터 적재 시에는 각 Case별로 "이전 Case를 실제로 언급/전제하는 문장이 원문에 있는가"를 기준으로만 연결하고, 임의 추론으로 연결하지 않는다(기획서 공통 주의사항).

### 3.2 Section ↔ 실제 페이지 매핑

- 각 Project Detail 페이지의 H2 제목이 하나의 Section이자 대응하는 Case의 서술 단위가 된다.
- `path`는 `/projects/{slug}`, `anchor`는 해당 H2의 slug (예: `#처음-맡은-pl에서-팀이-일할-방식을-먼저-정했습니다`).
- Home 페이지의 프로젝트 요약 카드도 Section으로 등록하되(`path=/`, `anchor=#{project-slug}`), `searchable=false`로 두어 임베딩 검색 후보에서 제외한다(기획서: "검색에 사용할 Section에만 embedding 생성"). 상세 서술이 있는 Detail 페이지 Section만 `searchable=true`로 임베딩을 생성한다.

### 3.3 임베딩

- 대상: `searchable=true`인 Section의 `body`.
- 모델: OpenAI `text-embedding-3-small` (비용 대비 성능, 포트폴리오 규모의 데이터량에 적합).
- 저장/검색: Neo4j 5.x 벡터 인덱스(`CREATE VECTOR INDEX`)를 사용해 별도 벡터 DB 없이 그래프와 함께 관리한다. 그래프 순회(Cypher)와 벡터 유사도 검색을 같은 데이터베이스 내에서 수행할 수 있어 Graph RAG 파이프라인의 [Retrieve] 단계 구현이 단순해진다.

### 3.4 Competency 목록 재검증

기존 문서의 Competency 목록(협업 / 기술적 판단 / 문제 해결 / 운영 / DevOps / AI 활용 / 학습 및 성장)은 실제 원문의 서술(예: PL로서 팀 기준 수립, WebSocket/Polling 판단, Failover 검증, 접근 경계 재설계, Reconciler를 통한 실패 복구, Quality Gate를 통한 AI 결과 검증, 처음 다루는 C/C++ 영역 학습)과 대조했을 때 모두 실제 사례로 뒷받침된다. 임의 추가 없이 그대로 유지한다.

## 4. Neo4j 데이터 적재 파이프라인 (설계 범위)

> 실제 스크립트 작성/실행 순서는 02_구현계획.md에서 다룬다. 여기서는 파이프라인의 구조만 정의한다.

1. 포트폴리오 원문(Markdown)에서 Project/Section 구조를 파싱한다.
2. Section 단위로 사람이 Case 후보(problem/judgment/action/result/learning)를 원문 범위 내에서만 채워 초안을 만든다.
3. AI를 활용해 초안 추출을 보조하더라도, 기획서 제약(임의 필드 채움 금지, 원문 미확인 필드는 비움)을 검증하는 사람의 리뷰 단계를 거친다.
4. 검증된 데이터만 Neo4j에 적재하고, `searchable=true`인 Section에 한해 임베딩을 생성/저장한다.

## 5. FE 아키텍처 (Next.js)

### 5.1 라우팅

| 경로 | 렌더링 방식 | 설명 |
|---|---|---|
| `/` | SSG | Home — 지원자 소개 + 프로젝트 카드 목록 |
| `/projects/[slug]` | SSG (`generateStaticParams`) | 프로젝트 상세 (TeenyFinny / home-server / dailyband) |
| `/api/chat` | Route Handler (Dynamic) | BFF — FastAPI AI 서버로 프록시 |

정적 콘텐츠(프로젝트 본문, 소개)는 빌드 타임에 소스(Markdown/구조화 데이터 파일)에서 생성되며 런타임에 DB를 조회하지 않는다. Neo4j는 오직 AI 서버의 RAG 조회용으로만 쓰이고, 페이지 렌더링 경로와는 분리된다 — 정적 페이지와 동적 API 라우팅이 공존하되 서로 다른 데이터 소스를 갖는 구조다.

### 5.2 컴포넌트 계층

```
components/
  ui/            # 버튼, 카드 등 범용 프리미티브
  layouts/       # Header, Footer, PageLayout
  domains/
    project/     # ProjectCard, ProjectDetailSection 등 프로젝트 도메인 전용
    chat/        # FloatingChatButton, ChatModal, MessageList, CitationLink 등
```

### 5.3 채팅(RAG) UI

- `FloatingChatButton`(전역 고정) 클릭 → `ChatModal` 오픈 (Framer Motion으로 scale/opacity 트랜지션, 과하지 않게 200ms 내외).
- `ChatModal` 내부 상태(대화 이력, 로딩 상태)는 React Context 또는 `useState` 기반 로컬 상태로 충분하다 — 페이지 간 공유가 필요 없는 위젯 상태이므로 전역 상태관리 라이브러리는 도입하지 않는다.
- 답변의 `citations`는 클릭 가능한 링크로 렌더링하며, 같은 탭 내 라우팅(Next.js `Link`)으로 해당 프로젝트 상세 페이지의 anchor로 이동한다.

### 5.4 API 계층 (axios 중앙화)

```
lib/api/
  client.ts   # axios 인스턴스 (baseURL: '/api', 공통 인터셉터)
  chat.ts     # postChatMessage(messages: ChatMessage[]): Promise<ChatResponse>
```

모든 API 호출은 이 계층을 통해서만 이루어지며, 컴포넌트가 axios를 직접 호출하지 않는다.

### 5.5 다크모드 / 반응형

- 다크모드: `next-themes` 등으로 시스템 설정 감지 + 수동 토글, CSS 변수 기반 테마 전환.
- 반응형: 데스크탑/태블릿/모바일 breakpoint 대응 (Tailwind 등 유틸리티 기반 가정, 최종 스타일링 도구는 구현 계획에서 확정).

## 6. 기획서 제약 조건 ↔ 설계 대응표

| 기획서 요구 | 설계 반영 |
|---|---|
| 포트폴리오 무관 질문 차단 | Gate 1 structured output |
| 사이트 자체 질문 분리 | Gate 2 structured output |
| 의도/개념 추출 | Extract 단계 structured output |
| 검색 결과에 이동 링크 + 본문 포함 | citations 스키마에 path/anchor 필수 필드 |
| 대화 맥락으로 후속 질문 처리 | is_followup + refers_to_previous_case_ids + 클라이언트 이력 재전송 |
| 원문 밖 추론 금지 | Generate 단계 system prompt + citations 최소 1개 강제 |
| 근거 부족 시 부족하다고 답변 | is_evidence_sufficient 필드 |
| AI 서버 주소 비공개 | Next.js BFF 구조, 서버 전용 env var |
| 더미 데이터 금지 | 데이터 적재 파이프라인에 사람 검증 단계 명시 |

## 7. 확인이 필요한 미결 사항

- **Next.js 배포처**: 아직 결정되지 않았다. 이 설계는 배포 위치에 종속되지 않게 작성했다 (SSG 산출물은 어디서든 서빙 가능, `/api/chat`은 서버 런타임이 있는 환경이면 동작). 다만 Vercel에 올릴 경우 Vercel 서버가 홈서버 FastAPI를 호출하는 구간(외부 인터넷 경유)이 생기므로, 이 경우 공유 시크릿 헤더 인증이 특히 중요해진다. 홈서버에 Next.js까지 함께 올리면 내부망 통신으로 처리할 수 있다. 구현 계획 수립 전에 결정이 필요하다.
- **스타일링 도구**: Tailwind CSS를 가정했으나 기획서에 명시되지 않았다. 확정 필요.
- **Cypher 검색 쿼리의 스코어링 가중치**(그래프 매칭 vs 벡터 유사도 비중)는 실제 데이터로 튜닝이 필요한 영역으로, 설계 문서에서는 구조만 정의하고 구현 단계에서 확정한다.
